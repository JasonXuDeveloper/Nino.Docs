Data outlives code. A save file, a cached asset or a message from an older client is read by a newer build of your types, and sometimes the other way round. Nino gives every type one of three formats, the values of the `NinoFormat` enum, chosen with `[NinoType(format: ...)]`:

| | `NinoFormat.Positional` (default) | `format: NinoFormat.VersionTolerant` | `format: NinoFormat.Keyed` |
| --- | :---: | :---: | :---: |
| Append members to a type without subclasses | ✗ | ✓ | ✓ |
| Append members to a base class | ✗ | ✗ | ✓ |
| Insert, remove or reorder members | ✗ | ✗ | ✓ |
| Rename members | ✓ | ✓ | ✓ with `[NinoFormerName]` |
| New code reads old data | ✗ | ✓ | ✓ |
| Old code reads new data | ✗ | ✓ | ✓ |
| Overhead | none | 4 bytes per object | 8 bytes per member, plus 4 per object |
| Speed | fastest | close to positional: one length per object | slower: a key and length per member, and a key check per member when reading |

The format itself is part of the data: changing a type's `format` makes previously written data unreadable. Choose before you store anything.

In every format, **changing a member's type** is not tolerated. **Renaming a member** is free in positional and version-tolerant types, which write no names. In keyed types the key is the hash of the name, so mark a renamed member with its old name ([Renaming Keyed Members](#renaming-keyed-members)); without it, the rename reads as "one member removed, another added". Rename *types* with [`[NinoFormerName]`](/en/docs/v4/defining-types#former-name) on the type.

## Positional

A bare `[NinoType]` writes the members one after another with no names, lengths or keys. It is the fastest and smallest format, and the right one for data that is written and read by the same build: network messages between matching client and server versions, caches you can rebuild, snapshots in memory.

<Callout type="warn">

Any change to the member list (adding, removing, reordering, changing an index) makes old data unreadable: reading it throws or, worse, produces wrong values.

</Callout>

An unmanaged `[NinoType]` struct is copied as raw memory, so its bytes also depend on its field order and its `StructLayout`: reordering fields or changing the layout breaks existing data. A `NinoFormat.VersionTolerant` or `NinoFormat.Keyed` struct is written member by member instead.

## Version Tolerance

Version 1.1 of a game adds a music volume to its settings file. Players still have files written by 1.0:

```csharp
[NinoType(format: NinoFormat.VersionTolerant)] // [!code highlight]
public class Settings
{
    public float SfxVolume = 1f;
    public bool Subtitles;
    public float MusicVolume = 0.8f; // [!code ++]
}
```

An object's members (those of its `[NinoType]` base classes first) are written after a single 4-byte length, however deep the hierarchy is:

- **Old data, new code:** members missing from the data keep the value they already have: the existing instance's value when you deserialize into it, otherwise whatever the constructor set, field initializers included. A 1.0 file loaded by 1.1 gets `MusicVolume = 0.8f`, not `0`. Types re-created through a constructor (positional records, get-only members) get `default` for a missing constructor argument, not the parameter's default value.
- **New data, old code:** bytes the old code does not know are skipped.
- Members can be appended to the **most derived type**, which is the end of the object's data. This works at any nesting depth: each tolerant object carries its own length, inside collections, dictionaries and polymorphic members too.

<Callout type="warn">

Not tolerated: appending members to a base class that has `[NinoType]` subclasses (see [below](#appending-to-a-base-class)), inserting, removing or reordering members, appending members to a `[NinoType]` interface, and adding or removing a `[NinoType]` class in the hierarchy. With `[NinoType(false)]`, give a new member an index greater than every existing one.

</Callout>

<Callout type="info">

Defining the symbol `WEAK_VERSION_TOLERANCE` in a project makes every `NinoFormat.Positional` type declared in that project `NinoFormat.VersionTolerant`; types from referenced assemblies keep their own format. Prefer the per-type option.

</Callout>

### Appending to a Base Class [#appending-to-a-base-class]

In a version-tolerant hierarchy, append members only to the classes that have no subclasses. If a base class needs a new member, make the hierarchy [`NinoFormat.Keyed`](#keyed-members) instead. Here is why.

All levels of the hierarchy share the object's single length, and their members are written root first. A member appended to a base class therefore lands **before** the members of its subclasses and shifts them:

```csharp
// Version 2 appends Armor to the base class
[NinoType(format: NinoFormat.VersionTolerant)]
public class Unit
{
    public int Hp;
    public int Armor; // [!code ++]
}

public sealed class Archer : Unit
{
    public int Arrows;
}

// after its header, version 1 writes an Archer as  length | Hp | Arrows
// and version 2 writes it as                        length | Hp | Armor | Arrows
```

- **Version 2 reads version 1 data:** `Armor` gets the bytes of `Arrows`, and the data ends before `Arrows`, which keeps its value like any missing member (`0` in a new `Archer`).
- **Version 1 reads version 2 data:** `Arrows` gets the bytes of `Armor`, and the real `Arrows` is skipped as an unknown trailing member.

Here the two members have the same type, so the values are merely wrong. When the types differ, the bytes are misread as another type, and the result is wrong values or an `InvalidOperationException`. Nothing reports the mistake at compile time, because the generator only ever sees one version of your code.

Instances of `Unit` itself are not affected (`Armor` is their last member); the data of every subclass is. So append members only to the classes at the bottom of a hierarchy, such as sealed message classes. Put a member that every subclass needs into each subclass, or make the hierarchy [`NinoFormat.Keyed`](#keyed-members), where members can be added to any class.

## Keyed Members

```csharp
[NinoType(format: NinoFormat.Keyed)] // [!code highlight]
public class EnemyConfig
{
    public string Name;
    public int Health;    // reorder, remove or insert members freely
    public float Speed;
}
```

Each member is written with a **key** (the 32-bit FNV-1a hash of its name, computed by the generator) and its length. This is much like MessagePack's `[Key("name")]`, except that no strings are written:

- Unknown keys in the data are skipped; members missing from the data keep their value, following the same rule as [version tolerance](#version-tolerance) (field initializers apply).
- Reading first assumes the declaration order, so data written by the same schema is read with one 8-byte compare per unmanaged member; at the first mismatch it falls back to dispatching each key.
- If two member names in a type (inherited ones included) hash to the same key, that is a compile-time error (NINO014), so a collision cannot corrupt data.
- Keyed structs are never written as raw memory. Polymorphism works as usual: the type id comes before the body.

This is the format for data kept for a long time and edited by many releases: configuration, documents, settings files, game or level data.

### Renaming Keyed Members

Put `[NinoFormerName("OldName")]` on the renamed field or property, once per earlier name. Reading accepts the current name and every former name; writing always uses the current name.

```csharp
[NinoType(format: NinoFormat.Keyed)]
public class PlayerSave
{
    [NinoFormerName("Hp")]                   // [!code highlight]
    [NinoFormerName("Health")]               // [!code highlight]
    public int HitPoints;                    // reads data written as Hp, Health or HitPoints
    public string Name;
}
```

- A former name that collides with another member of the type is a compile-time error.
- In positional and version-tolerant types the attribute has no effect, since they write no names; the analyzer warns about it there (NINO024).
- Old code still knows only the old name, so data written after the rename loses this member when old code reads it.

## Choosing

<Accordions type="single">
<Accordion title="Messages between a client and a server">

Positional, when both sides always run the same build. If clients and servers are upgraded at different times (rolling upgrades, old app versions in the wild), use `NinoFormat.VersionTolerant` and only ever **append** fields to the message classes themselves (not to their shared base class), or `NinoFormat.Keyed` if you also need to retire fields or add them to the base. See [Network Layer](/en/docs/v4/advanced/networking).

</Accordion>
<Accordion title="Save games and user files">

`NinoFormat.VersionTolerant` if you only add fields over time, to classes without subclasses; `NinoFormat.Keyed` if you want the freedom to remove and reorder them. Add [`trackReferences`](/en/docs/v4/reference-tracking) when the saved graph shares objects or has cycles. See [Persistence and Storage](/en/docs/v4/advanced/persistence).

</Accordion>
<Accordion title="Configuration authored in the Unity editor">

`NinoFormat.Keyed`: designers add, remove and reorder fields all the time, and the cost (8 bytes per member) rarely matters for configuration.

</Accordion>
<Accordion title="Caches and in-memory snapshots">

Positional. If the schema changes, throw the cache away and rebuild it.

</Accordion>
</Accordions>

<Callout type="idea">

The options can be mixed: a keyed save file can hold positional raw structs (such as `Vector3` or your own `[NinoType]` structs) inside it. Each type has its own format.

</Callout>
