Data outlives code. A saved document, a cached asset or a message from an older client is read by a newer build of your types, and sometimes the other way round. Decide each type's format before its data leaves the process: the default, positional, cannot change shape once data is written, and changing a type's format later makes its data unreadable too. Nino gives every type one of three formats, the values of the `NinoFormat` enum, chosen with `[NinoType(format: ...)]`:

  { label: 'Append members to a type without subclasses', cells: ['no', 'yes', 'yes'] },
  { label: 'Append members to a base class', cells: ['no', 'no', 'yes'] },
  { label: 'Insert, remove or reorder members', cells: ['no', 'no', 'yes'] },
  { label: 'Rename members', cells: ['yes', 'yes', 'yes: with [NinoFormerName]'] },
  { label: 'New code reads old data', cells: ['no', 'yes', 'yes'] },
  { label: 'Old code reads new data', cells: ['no', 'yes', 'yes'] },
  { label: 'Overhead on the wire', cells: ['none', '4 bytes per object', '8 bytes per member, plus 4 per object'] },
  { label: 'Speed', cells: ['fastest', 'close to positional: one length per object', 'the most work: a key and length per member, a key check per member when reading'] },
]} />

`Positional` is the default; the others are `[NinoType(format: NinoFormat.VersionTolerant)]` and `[NinoType(format: NinoFormat.Keyed)]`. [Choosing](#choosing) picks one in three questions.

In every format, **changing a member's type** is not tolerated. **Renaming a member** is free in positional and version-tolerant types, which write no names; a keyed member and a type written with its type id keep their old name with `[NinoFormerName]` ([Renaming](#renaming)).

## Positional

A bare `[NinoType]` writes the members one after another with no names, lengths or keys. It is the fastest and smallest format, and the right one for data that is written and read by the same build: network messages between matching client and server versions, caches you can rebuild, snapshots in memory.

<Callout type="warn">

Any change to the member list (adding, removing, reordering, changing an index) makes old data unreadable: reading it throws or, worse, produces wrong values.

</Callout>

A [raw struct](/en/docs/v4/defining-types#structs) is copied as its memory, so its field order and its `StructLayout` are part of the format too. A `NinoFormat.VersionTolerant` or `NinoFormat.Keyed` struct is written member by member instead.

## Version Tolerance

Version 1.1 of an app adds a font size to its settings file. Users still have files written by 1.0:

```csharp
[NinoType(format: NinoFormat.VersionTolerant)] // [!code highlight]
public class Settings
{
    public string Theme = "light";
    public bool Notifications;
    public int FontSize = 14; // [!code ++]
}
```

An object's members (those of its `[NinoType]` base classes first) are written after a single 4-byte length, however deep the hierarchy is:

- **Old data, new code:** members missing from the data keep the value they already have: the existing instance's value when you deserialize into it, otherwise whatever the constructor set, field initializers included. A 1.0 file loaded by 1.1 gets `FontSize = 14`, not `0`. Types re-created through a constructor (positional records, get-only members) get `default` for a missing constructor argument, not the parameter's default value.
- **New data, old code:** bytes the old code does not know are skipped.
- Members can be appended to the **most derived type**, which is the end of the object's data. This works at any nesting depth: each tolerant object carries its own length, inside collections, dictionaries and polymorphic members too.

<Callout type="warn">

Not tolerated: appending members to a base class that has `[NinoType]` subclasses (see [below](#appending-to-a-base-class)), inserting, removing or reordering members, appending members to a `[NinoType]` interface, and adding or removing a `[NinoType]` class in the hierarchy. With `[NinoType(false)]`, give a new member an index greater than every existing one.

</Callout>

### Appending to a Base Class [#appending-to-a-base-class]

In a version-tolerant hierarchy, append members only to the classes that have no subclasses. If a base class needs a new member, make the hierarchy [`NinoFormat.Keyed`](#keyed-members) instead. Here is why.

All levels of the hierarchy share the object's single length, and their members are written root first. A member appended to a base class therefore lands **before** the members of its subclasses and shifts them:

```csharp
// Version 2 appends Revision to the base class
[NinoType(format: NinoFormat.VersionTolerant)]
public class Document
{
    public int Id;
    public int Revision; // [!code ++]
}

public sealed class Invoice : Document
{
    public int CustomerId;
}
```

After its header, an `Invoice { Id = 1, Revision = 2, CustomerId = 7 }` is written as:

<Bytes rows={[
  { title: 'Version 1', fields: [{ hex: '08 00 00 00', kind: 'length', label: 'length 8' }, { hex: '01 00 00 00', kind: 'value', label: 'Id' }, { hex: '07 00 00 00', kind: 'value', label: 'CustomerId' }] },
  { title: 'Version 2', fields: [{ hex: '0C 00 00 00', kind: 'length', label: 'length 12' }, { hex: '01 00 00 00', kind: 'value', label: 'Id' }, { hex: '02 00 00 00', kind: 'changed', label: 'Revision: where version 1 expects CustomerId' }, { hex: '07 00 00 00', kind: 'value', label: 'CustomerId: skipped by version 1' }] },
]} />

- **Version 2 reads version 1 data:** `Revision` gets the bytes of `CustomerId`, and the data ends before `CustomerId`, which keeps its value like any missing member (`0` in a new `Invoice`).
- **Version 1 reads version 2 data:** `CustomerId` gets the bytes of `Revision`, and the real `CustomerId` is skipped as an unknown trailing member.

Here the two members have the same type, so the values are merely wrong. When the types differ, the bytes are misread as another type, and the result is wrong values or a `NinoDataException`. The generator sees only one version of your code, so only a [layout baseline](#layout-baseline), which remembers the last one, reports the mistake (NINO034 on each subclass). To see what each byte of such a message is read as, run [`nino-gen inspect`](/en/docs/v4/advanced/codegen#inspect) on it.

Instances of `Document` itself are not affected (`Revision` is their last member); the data of every subclass is. So append members only to the classes at the bottom of a hierarchy, such as sealed message classes. Put a member that every subclass needs into each subclass, or make the hierarchy [`NinoFormat.Keyed`](#keyed-members), where members can be added to any class.

## Keyed Members

```csharp
[NinoType(format: NinoFormat.Keyed)] // [!code highlight]
public class ConnectionConfig
{
    public string Host;
    public int Port;      // reorder, remove or insert members freely
    public float TimeoutSeconds;
}
```

Each member is written with a **key** (the 32-bit FNV-1a hash of its name, computed by the generator) and its length. This is much like MessagePack's `[Key("name")]`, except that no strings are written:

- Unknown keys in the data are skipped; members missing from the data keep their value, following the same rule as [version tolerance](#version-tolerance) (field initializers apply).
- Reading first assumes the declaration order, so data written by the same schema is read with one 8-byte compare per unmanaged member; at the first mismatch it falls back to dispatching each key.
- If two member names in a type (inherited ones included) hash to the same key, that is a compile-time error (NINO014), so a collision cannot corrupt data.
- Keyed structs are never written as raw memory. Polymorphism works as usual: the type id comes before the body.

This is the format for data kept for a long time and edited by many releases: configuration, documents, settings files, content authored in tools.

## Choosing

| Question | Answer | Use |
| --- | --- | --- |
| Do the writer and the reader always run the same build? | yes | `Positional` |
| Will you only append members, to classes without subclasses? | yes | `VersionTolerant` |
| Will you remove, reorder, or add members to a base class? | yes | `Keyed` |


<Accordions type="single">
<Accordion title="Messages between a client and a server">

Positional, when both sides always run the same build. If clients and servers are upgraded at different times (rolling upgrades, old app versions in the wild), use `NinoFormat.VersionTolerant` and only ever **append** fields to the message classes themselves (not to their shared base class), or `NinoFormat.Keyed` if you also need to retire fields or add them to the base. See [Networking](/en/docs/v4/advanced/networking).

</Accordion>
<Accordion title="Saved documents and user files">

`NinoFormat.VersionTolerant` if you only add fields over time, to classes without subclasses; `NinoFormat.Keyed` if you want the freedom to remove and reorder them. Add [`trackReferences`](/en/docs/v4/reference-tracking) when the saved graph shares objects or has cycles. See [Persistence](/en/docs/v4/advanced/persistence).

</Accordion>
<Accordion title="Configuration edited by people">

`NinoFormat.Keyed`: the people who maintain it add, remove and reorder fields all the time, and the cost (8 bytes per member) rarely matters for configuration.

</Accordion>
<Accordion title="Caches and in-memory snapshots">

Positional. If the schema changes, throw the cache away and rebuild it.

</Accordion>
</Accordions>

<Callout type="idea">

The options can be mixed: a keyed settings file can hold positional raw structs (such as `Guid` or your own `[NinoType]` structs) inside it. Each type has its own format.

</Callout>

## Renaming [#renaming]

Positional and version-tolerant types write no member names, so renaming one of their members needs nothing. Two renames change what is written, and `[NinoFormerName]` keeps the old data readable: a type whose values carry a type id, and a member of a keyed type.

### Renaming Types [#former-name]

A value stored in a member, element or variable declared as a non-sealed class, an abstract class, an interface or `object` is written with the <Term id="type-id">type id</Term> of its runtime type: a 32-bit hash of that type's full name, so it can be read back as the right type ([Polymorphism](/en/docs/v4/polymorphism#how-a-polymorphic-value-is-written)). Renaming the type or moving it to another namespace changes the id, for sealed subtypes too (such as the message classes sent through a `Message` base).

A typical case: you move your protocol classes from `MyApp.Net` to `MyApp.Protocol`, while stored files or clients from the previous release still use the old ids. Keep reading old data with `[NinoFormerName]`:

```csharp
namespace MyApp.Protocol
{
    [NinoType]
    [NinoFormerName("MyApp.Net.OrderPlaced")] // [!code highlight]
    public class OrderPlaced
    {
        public long OrderId;
    }
}
```

The former name is the **runtime form** of the full name: `Namespace.Type`, `+` between a nested type and its container (`Namespace.Outer+Inner`), no `global::`. The type id is computed from the former name, so the renamed type keeps writing and reading the id that existing data and older readers use. `NinoTypeId.Of(typeof(T))` returns the id a type writes.

- A type takes a single `[NinoFormerName]`, since its id comes from one name; a second one is error NINO026.
- On a generic type the former name replaces the whole name, type arguments included, so every instantiation (`Box<int>`, `Box<string>`) gets the same id: two of them written with their type id cannot be told apart (warning NINO027). Put former names on non-generic types only.

### Renaming Keyed Members [#renaming-keyed-members]

Put `[NinoFormerName("OldName")]` on the renamed field or property, once per earlier name. Reading accepts the current name and every former name; writing always uses the current name.

```csharp
[NinoType(format: NinoFormat.Keyed)]
public class UserProfile
{
    [NinoFormerName("Nick")]                 // [!code highlight]
    [NinoFormerName("Nickname")]             // [!code highlight]
    public string DisplayName;               // reads data written as Nick, Nickname or DisplayName
    public string Email;
}
```

- A former name that collides with another member of the type is a compile-time error.
- In positional and version-tolerant types the attribute has no effect, since they write no names; the analyzer warns about it there (NINO024).
- Old code still knows only the old name, so data written after the rename loses this member when old code reads it.

## Layout Baseline [#layout-baseline]

Data you save or send outlives the build that wrote it. A layout baseline is a file in your project that records the [layout](#layout-metadata) of every type whose bytes outlive a build: each version-tolerant and keyed `[NinoType]`, and every type their members reach (positional types and polymorphic subtypes included). The analyzer compares your types with it as you type and reports, on the member or type that changed, when a change breaks old data or old builds.

```csharp title="NinoLayouts.cs"
[assembly: Nino.Core.NinoLayouts(@"
['MyGame.Save.PlayerData']
format = 'Keyed'
header = 'Presence'
id = 0x3DEFB1B5
members = [
  { name = 'Health', type = 'int', encoding = 'raw(4)', key = 0x99A16761 },
  { name = 'Name', type = 'string', encoding = 'string', key = 0x3085B3E2 },
]
")]
```

- **Create it** with the refactoring *Create the layout baseline (NinoLayouts.cs)*, offered on any `[NinoType]` declaration, or with `nino-gen layouts --assembly MyGame.dll --out NinoLayouts.cs`. Commit the file. You never write it by hand: the code fixes and the command keep it up to date.
- **It costs nothing at run time.** `NinoLayoutsAttribute` is conditional, so the compiler checks it and the analyzer reads it from source, but it never reaches your assembly. Because it is a C# file, it works the same in Unity, and each assembly (csproj or asmdef) has its own.
- **What it reports**, for each of two kinds of reader: this build reading data written before the change, and builds before the change reading data written after it (clients not updated yet, old nodes in a rolling deployment):
  - [NINO034](/en/docs/v4/analyzers#nino034) (warning) for a change that breaks either: a member inserted, removed or moved in a version-tolerant type, any member change in a positional type that stored data reaches, `sealed` added or removed, a member's type or encoding changed, a type written with its type id renamed or moved, a type removed.
  - [NINO035](/en/docs/v4/analyzers#nino035) (warning) for a keyed member renamed without [`[NinoFormerName]`](#renaming-keyed-members), whose value would be lost without an error.
  - [NINO036](/en/docs/v4/analyzers#nino036) (info) for a change that is compatible with a condition: a keyed member removed, or renamed with its former name (deploy readers before writers).
  - Appending to a version-tolerant type and adding a keyed member are compatible and report nothing.
- **Fix or accept.** Each finding offers the fix that undoes the break, where there is one: a former name, `sealed` back, the inserted member moved to the end. When old data or old builds no longer matter, *Accept the change into the layout baseline* rewrites that type's section, and Fix All accepts every change at once. The change then shows in the baseline's diff, in the pull request.
- **In CI**, `nino-gen layouts --assembly MyGame.dll --out NinoLayouts.cs --check` runs the same rules on a built assembly and exits with 1 on NINO034 or NINO035. To fail the build itself instead, set `dotnet_diagnostic.NINO034.severity = error` in `.editorconfig`.
- **A baseline the analyzer cannot read** (a hand edit that broke its TOML) is warning [NINO037](/en/docs/v4/analyzers#nino037), and nothing is checked until it is fixed: write it again with the refactoring or `nino-gen layouts`.
- **Not checked**, because a layout does not show it: enum values renumbered (an enum is just its bytes), what a [custom formatter](/en/docs/v4/custom-formatters) writes, and polymorphic subtypes removed while old data may still hold them.

## Layout Metadata

For every `[NinoType]`, the generator records how the type is written in the assembly's metadata, as an `[assembly: NinoTypeLayout]`: the format, the header in front of the body (`None` for a struct, `Presence` for a sealed class, `TypeId` otherwise), whether references are tracked, whether the type is a raw struct, its type id, whether a body nested too deep is [deferred](/en/docs/v4/reference-tracking#deep-object-graphs) (`deferrable`, which readers in other languages need), and its members in the order they are written, inherited ones included, so each type's layout reads without its base types'. [nino-gen](/en/docs/v4/advanced/codegen) reads it to generate code and to write the [layout baseline](#layout-baseline); tools of your own (a diff between two builds, a migration tool) can read it too, instead of re-implementing Nino's rules:

```csharp
using System.Reflection; // GetCustomAttributes<T>()

foreach (var layout in typeof(Move).Assembly.GetCustomAttributes<NinoTypeLayoutAttribute>())
    Console.WriteLine($"{layout.Type}: {layout}");

// Game.Move: format=Positional; header=None; trackReferences=false; raw=true; id=0x…; deferrable=false;
//            members=raw(8){VelocityX:float@0:raw(4),VelocityY:float@4:raw(4)}
```

Members are listed in the order they are written, separated by `;`. Each member is written as `name:type:encoding`, and the encoding describes the bytes, not the formatter class that writes them, so a tool can read and write them without knowing Nino.Core's formatters ([nino-gen](/en/docs/v4/advanced/codegen) does). The encodings are listed below.

<Accordions>
<Accordion title="Member encodings" id="layout-encodings" value="layout-encodings">

- `raw(n)` or `raw(n){...}`: a value copied as raw memory (see below); `raw` alone: one whose size is known only at run time;
- `string`: a string in the default encoding; `utf8`: a `[NinoUtf8]` string;
- `type(T)`: a `[NinoType]`, as its own layout describes it; `object`: a `[NinoType]` behind its type id;
- `nullable(E)`: a presence byte, then `E`;
- `seq(E)`: an `int32` count (`-1` = null), then the elements; `map(K,V)`: a count, then each key and value; `grid(rank,E)`: each dimension's length, then the elements in row-major order;
- `pair(K,V)` and `tuple(E,...)`: the items in order; `group(K,E)`: an element count, the key, then the elements;
- `datetimeoffset`, `bigint`, `version`, `bits`, `timezone`: those built-in types;
- `formatter(F)`: written by `F`, a formatter outside Nino.Core: a [custom formatter](/en/docs/v4/custom-formatters), another library's, or those of `Nino.Immutable` and of Unity's `AnimationCurve`, `Gradient` and `RectOffset`.

A `Dictionary<string, int[]> Inventory` reads `Inventory:System.Collections.Generic.Dictionary<string, int[]>:map(string,seq(raw(4)))`. In a keyed type each member ends with `:key=0x…`, its key, and `:former=0x…,0x…` for the keys of its [former names](#renaming-keyed-members). A `[NinoType]` collection starts with `[elements]::` and the encoding of its elements. Up to 4.0.0-rc.5, members that were not raw named their formatter class instead.

</Accordion>
</Accordions>

- A raw layout is the value's bytes in Nino's canonical layout: `raw(n)` for a primitive, enum, `decimal`, `Guid`, `DateTime` or `TimeSpan` of `n` bytes, and `raw(n){name:type@offset:encoding,...}` for a struct of `n` bytes, with each field at its offset. An id such as `readonly record struct PlayerId(long Value)` shows as `Id:Game.PlayerId:raw(8){Value:long@0:raw(8)}`. Every struct inside a raw value is spelled out, `[NinoType]` or not, so a changed field, `[StructLayout]` `Pack` or `Size`, or `[FieldOffset]` changes the layout. A raw struct's members are just its raw layout, as `Move` shows above.
- A generic type is recorded once, as its open definition (`typeof(Box<>)`), with type id 0: the id of each closed type is computed at run time.
- Two types have the same layout exactly when Nino writes them the same way. A member of another `[NinoType]` reads `type(T)` and refers to that type's own layout, so a change inside it shows up only in its own entry; a member copied as raw memory spells out its bytes in place. To catch every change, record the layouts of all your types, keyed by `layout.Type`, and compare each `layout.ToString()` with what you recorded for the last release: any difference means the bytes changed. Whether old data still reads correctly then depends on the format, as described above.
- Because the layout is metadata, a tool can also read it from referenced assemblies, even without loading them (`System.Reflection.Metadata`). A project gets the same layouts in every target framework.

## Pitfalls [#pitfalls]

| Mistake | What happens | Caught by |
| --- | --- | --- |
| Appending a member to a version-tolerant base class that has `[NinoType]` subclasses | The subclasses' data reads wrong values, or throws `NinoDataException` | a [layout baseline](#layout-baseline) (NINO034 on the subclass); see [Appending to a Base Class](#appending-to-a-base-class) |
| Changing a member's type, or a type's format, once data exists | Old data is misread or does not read | a [layout baseline](#layout-baseline) (NINO034) |
| Renaming or moving a type that is written with its type id | Old data's type id is unknown: `NinoDataException` | a [layout baseline](#layout-baseline) (NINO034, whose code fix adds [`[NinoFormerName]`](#former-name)) |
| `[NinoFormerName]` on a generic type written with its type id | Every instantiation writes the same id, and reads cannot tell them apart | [NINO027](/en/docs/v4/analyzers#nino027) |
| Renaming a keyed member without `[NinoFormerName]` | Old data's value for it is skipped as an unknown key | a [layout baseline](#layout-baseline) (NINO035, whose code fix adds the former name) |
| Two keyed members (or a former name) that hash to the same key | The build fails | [NINO014](/en/docs/v4/analyzers#nino014) |
| `[NinoFormerName]` on a member of a positional or version-tolerant type | No effect: those formats write no names | [NINO024](/en/docs/v4/analyzers#nino024), with a code fix |
| A project that still defines `WEAK_VERSION_TOLERANCE` (rc.8 and earlier made every positional type version-tolerant with it) | The types it made version tolerant would be positional and stop reading their data | [NINO032](/en/docs/v4/analyzers#nino032), whose code fix keeps the bytes |
