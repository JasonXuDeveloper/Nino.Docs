[MemoryPack](https://github.com/Cysharp/MemoryPack) 是一个出色的序列化库，也是我们衡量 Nino 时用的标杆。本页对比 Nino v4 和 MemoryPack **1.21.4**：MemoryPack 的功能以它自己的 README 为准，Nino 的功能以 Nino 源码为准。无法核实的功能，两边都不列出。

## MemoryPack 仍然领先的地方 [#where-memorypack-is-ahead]

坦白说，以下功能 MemoryPack 支持，Nino v4 不支持：

- **`Type` 值。** MemoryPack 可以序列化 `System.Type`；Nino 有意不支持：由数据指定要创建的类型，是一种广为人知的反序列化攻击手段。MemoryPack 列出的其他内置类型（`BigInteger`、`Uri`、`Lazy<T>`、`Memory<T>`、`ILookup<,>`、所有不可变集合等）从 4.0.0-rc.5 起 [Nino 也都内置支持](/zh/docs/v4/types#other-built-in-types)，`MemoryPack.Unity` 支持的 Unity 类（`AnimationCurve`、`Gradient`、`RectOffset`）也一样（参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)）。*变通方法：*自己保存类型 ID 或名称，再映射到你允许的类型。
- **TypeScript 与 ASP.NET Core。** MemoryPack 可以生成 TypeScript 读写代码，并提供 MVC 输入/输出格式化器。Nino 两者都没有。*替代方案：* 对于浏览器客户端，把客户端的序列化部分构建成 .NET `browser-wasm` 应用，再通过 `[JSExport]` 从 JavaScript 调用；它与服务端共用 C# 类型、写出相同的字节，代价是浏览器要下载 .NET 运行时。在 ASP.NET Core 中，自己用 `NinoDeserializer` 读取请求体、用 `NinoSerializer` 写出响应。参见[浏览器与 JavaScript 客户端](/zh/docs/v4/advanced/browser)。
- **依赖注入与选项。** MemoryPack 的每次调用都可以传入 `MemoryPackSerializerOptions`（字符串编码、`IServiceProvider`）。Nino 没有按调用传入的选项：设置要么是进程级的（`NinoSettings`），要么是标在类型上的特性。

流、异步 I/O、`ReadOnlySequence<byte>` 输入、序列化回调和压缩不在这个列表里：它们都只需在 Nino 的 `IBufferWriter<byte>` 和 `ReadOnlySpan<byte>` API 之上写几行代码。可以直接复制的写法参见[流、异步、回调与压缩](/zh/docs/v4/advanced/streams)。

## 基准测试中发现的 MemoryPack 问题 [#memorypack-bugs-found-while-benchmarking]

对比两个库共同支持的所有内置类型时，我们在计时前先让每个值在 MemoryPack 1.21.4 中往返一次。有两个类型失败，所以基准中这两个类型只测 Nino：

- **`BigInteger`。** 它的格式化器在 255 字节的栈缓冲区上写的是 `temp.Slice(written)`，本意是 `temp.Slice(0, written)`：写出的是缓冲区未使用的尾部，而不是这个值。任何 255 字节以内的 `BigInteger`（包括 `3^10`）读回来都是另一个值，在所有运行时上都是如此；更大的值走另一条路径，可以正确往返。
- **.NET 10 上的 `BitArray`。** 它的格式化器把 `BitArray` 强转为 `{ int[] m_array; int m_length }`，这是 .NET 8 上的布局。.NET 10 的 `BitArray` 改为保存 `byte[] _array`，于是 MemoryPack 写出错误的字节，读取时会破坏堆内存并导致进程崩溃。

Nino 把 `BigInteger` 写成它的二进制补码字节，`BitArray` 通过公开 API 读写，都不依赖运行时的私有布局。参见[其他内置类型](/zh/docs/v4/types#other-built-in-types)。

## 类型 ID 与 Union 标签 [#type-ids-and-union-tags]

MemoryPack 写入 1 字节的 Union 标签（超过 249 时 3 字节），Nino 写入 4 字节的类型 ID。这是有意的取舍：

- Nino 的 ID 由类型本身决定（类型名的 FNV-1a 哈希），所以子类型不需要标签。子类型可以放在任何程序集中（插件、HybridCLR 热更新、继承你的基类的库），增删子类型时 ID 也不会重新编号。
- MemoryPack 要在基类上用 `[MemoryPackUnion(tag, type)]` 列出所有子类型，或者通过 Union 格式化器手动注册，标签还得自己保证不变。

代价是每个多态值多 3 字节。参见[多态](/zh/docs/v4/polymorphism)。

## Nino 领先的地方 [#where-nino-is-ahead]

- **速度**：序列化最高快 <BenchValue k="serialize.max" />，反序列化类和多态对象图最高快 <BenchValue k="deserialize.max" />，数据见上文。
- **零分配复用**：复用反序列化原地填充嵌套的对象、列表和字典；有 `[NinoPooled]` 对象池；每个被丢弃的实例都能交给回收器。
- **数据可以演进**：键控成员在继承体系的任意一个类中都可以调整顺序、删除和插入，无需维护顺序编号；无论键控类型还是版本容错类型，旧代码都能读取新数据。
- **多态无需维护**：没有标签，任何非密封类都可以作为基类，其他程序集和热更新 DLL 中的子类型也能自动找到。
- **可移植、确定的字节**：在 CoreCLR、Mono、IL2CPP 以及 64 位和 32 位平台上完全相同，填充字节清零。
- **适用范围更广**：支持 `netstandard2.0`，Unity 有 OpenUPM 包，HybridCLR 无需初始化调用。
- **构建时间**：每个类型一个生成文件，源生成器是真正增量的。

## 如何选择 [#when-to-choose-which]

<Cards>
  <Card title="适合选 Nino 的情况">
    在 .NET 服务器、Unity 或 Godot 上高频序列化消息、缓存值、存储的记录或应用状态；需要不用标签表的多态、可演进的数据、共享引用，或借助池化做到零 GC；或者需要 Unity、IL2CPP 与服务器之间字节完全一致。
  </Card>
  <Card title="适合选 MemoryPack 的情况">
    需要生成的 TypeScript 读写代码（浏览器客户端不带 .NET 运行时）、ASP.NET Core MVC 格式化器、按调用设置的选项，或者需要 `System.Type` 值。
  </Card>
</Cards>

<Callout type="idea">

两者都采用 MIT 许可证，都基于源生成，都可以放心用于 AOT。拿不定主意时，就用你自己的类型测一测：[基准测试项目](https://github.com/JasonXuDeveloper/Nino/tree/main/src/Nino.Benchmark)会把 Nino 和 MemoryPack 放在一起运行。
