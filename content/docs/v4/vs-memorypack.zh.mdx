[MemoryPack](https://github.com/Cysharp/MemoryPack) 是一个出色的序列化库，也是我们给 Nino 定的对标。这一页对比 Nino v4 和 MemoryPack **1.21.4**：MemoryPack 的功能以它自己的 README 为准，Nino 的以 Nino 源码为准。哪一边核实不了的功能，就不列。想看其他语言也能读的格式，见 [Nino 与 MessagePack 对比](/zh/docs/v4/vs-messagepack)和 [Nino 与 protobuf-net 对比](/zh/docs/v4/vs-protobuf-net)。

## 不可信输入 [#untrusted-input]

MemoryPack 的 README 现在开头就是一段警告：它是“仅用于可信数据的高性能序列化格式”（“a high-performance serialization format for trusted data only”），“在输入可能来自不可信方的场景，例如公开的网络端点或用户提供的文件，我们不再推荐使用 MemoryPack”；面向跨边界通信的功能，包括 TypeScript 代码生成器，“将在下一个 MemoryPack 版本中移除”（[MemoryPack README](https://github.com/Cysharp/MemoryPack#readme)）。

Nino 生来就是为读不可信数据设计的，快速路径也守着这些保证：

- **数据里没有类型名。** 值只能是声明类型已注册的子类型之一，由类型 ID 选出；回引用必须指向已经读过、类型和槽位相符的对象。`System.Type` 不能序列化，所以数据永远没法指定要创建什么类型。
- **分配之前先查长度。** 每个元素个数都要和剩余字节比一次，一个集合在读到元素之前，最多预先分配输入剩余字节数的 16 倍：几个字节谎称不出几 GB。
- **栈的用量有上限。** 嵌套很深的数据推迟到较浅的层级再读，或者到 `NinoSettings.MaxDepth`（默认 512 层）就停，途中还检查剩余栈空间：抛异常，而不是栈溢出把进程搞崩。
- **没有哈希洪泛。** 某个键在它的哈希桶里碰到超过 `NinoSettings.MaxHashCollisions` 个键就抛异常，所以构造出来的键没法让填充字典或 Set 的时间变成平方级；`NinoSettings.Untrusted` 还会用每个进程的密钥给整数、`char`、`Guid` 和 `string` 键算哈希。
- **只有一种异常。** 所有无效输入，包括被类型自己拒绝的值，都抛 `NinoDataException`（一种 `InvalidOperationException`），消息以 `Nino:` 开头，在边界上一个 `catch` 就能全接住；[Nino.AspNetCore](/zh/docs/v4/advanced/aspnetcore) 会返回 400。

我们用 fuzz 生成的和手工构造的数据，把每个内置类型、每种类型声明方式都验了一遍，发现的问题都已在 4.0.0-rc.7 修复。仍然要应用自己负责的事（值本身、消息大小、版本）见[不可信数据](/zh/docs/v4/security#what-stays-your-job)。在这条边界上传递 Nino 数据的 Nino.Codegen（TypeScript、Go 和 Rust 读取器）和 Nino.AspNetCore 都会继续保留。

### 带填充的结构体和元组 [#padded-values]

[常用类型与集合](/zh/docs/v4/benchmarks#common-types-and-collections)里有两个用例的值在内存里带填充：`InventoryItem[1000]`（一个 `int`、一个 `short` 和一个 `bool`：7 字节的成员占 8 字节）和 `List<(int, long)>`（x64 上 12 字节的元素占 16 字节，.NET 把 `long` 排在前面）。MemoryPack 把它们的内存连同填充原样拷贝。Nino 则自己规定字节：`InventoryItem` 按 8 字节写，填充字节清零，MemoryPack 普通拷贝，Nino 带掩码拷贝，这就是 Nino 在这个用例上多花的时间。`(int, long)` 按两个元素写，占 12 字节，MemoryPack 写 16 字节，这就是两边数据大小的差别。

拷贝填充，代价不只是体积：

- **填充是内存里原来的东西。** 相等的值可能序列化成不同的字节，残留的内存也跟着写出去。用 MemoryPack 1.21.4 测：两个值相等的 `InventoryItem[2]`，其中一个在原先装满 `0xCD` 的缓冲区里构造，序列化出来的字节就不一样，每个填充字节都是 `CD`；同样构造的 `List<(int, long)>`，每个元素后面都跟着 `CDCDCDCD`。Nino 给两者写的字节一样，填充为零。
- **布局跟着平台走。** `(int, long)` 在 Windows 的 32 位 x86 .NET 上占 12 字节内存，在 x64 和 Arm32 上占 16 字节（.NET 10 在各目标上的布局，从 crossgen2 为它编译出的代码里读出），所以照搬内存的话，到了那里大小就变了。Mono 上元素的顺序也不一样：见[基准测试中发现的 MemoryPack 问题](#memorypack-bugs-found-while-benchmarking)。

Nino 跨平台、跨运行时字节一致：[原始值](/zh/docs/v4/wire-format#raw-values)按 64 位布局写，填充清零；元组逐个元素写。

## MemoryPack 仍然领先的地方 [#where-memorypack-is-ahead]

直说吧，下面这些 MemoryPack 能做，Nino v4 做不了：

- **`Type` 值。** MemoryPack 能序列化 `System.Type`；Nino 故意不支持：让数据指定要创建的类型，是出了名的反序列化攻击手法。MemoryPack 列出的其他内置类型（`BigInteger`、`Uri`、`Lazy<T>`、`Memory<T>`、`ILookup<,>`、所有不可变集合等），从 4.0.0-rc.5 起 [Nino 也都内置了](/zh/docs/v4/types#other-built-in-types)，`MemoryPack.Unity` 支持的 Unity 类（`AnimationCurve`、`Gradient`、`RectOffset`）也一样（见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)）。*变通方法：*自己保存类型 ID 或名称，再映射到你允许的类型。
- **依赖注入与选项。** MemoryPack 每次调用都能传 `MemoryPackSerializerOptions`（字符串编码、`IServiceProvider`）。Nino 没有按调用传的选项：设置要么是进程级的（`NinoSettings`），要么是标在类型上的特性。

压缩不在这张单子上：在 Nino 的缓冲区和 span API 上写几行就有（[压缩](/zh/docs/v4/advanced/streams#compression)）。流、异步 I/O 和序列化回调都已内置。

## Nino 领先的地方 [#where-nino-is-ahead]

- **不可信输入**：Nino 本来就是为读网络对端和用户文件的数据设计的（见[不可信输入](#untrusted-input)）；MemoryPack 现在只用于可信数据。
- **速度**：<IfWorkloads>真实负载上序列化最高快 <BenchValue k="workloads.memorypack.serialize.max" />，反序列化最高快 <BenchValue k="workloads.memorypack.deserialize.max" /></IfWorkloads><IfWorkloads not>序列化最高快 <BenchValue k="serialize.max" />，反序列化类和多态对象图最高快 <BenchValue k="deserialize.max" /></IfWorkloads>，数据见上文。
- **零分配复用**：复用反序列化直接填充嵌套的对象、列表和字典；有 `[NinoPooled]` 对象池；每个被丢弃的实例都能交给回收器。
- **数据能演进**：键控成员在继承体系的任何一个类里都能调整顺序、删除、插入，不用维护顺序编号；键控类型和版本容错类型，旧代码都能读新数据；有了[布局基线](/zh/docs/v4/evolving-data#layout-baseline)，改出会读坏旧数据的改动时，写代码的当下就会报出来（NINO034）。
- **多态不用记账**：没有标签，任何非密封类都能当基类，泛型基类（`Box<T>`、`IRepository<T>`）也行，别的程序集和热更新 DLL 里的子类型也能自动找到。MemoryPack 的 Union 特性不能加在泛型类型上：每个封闭类型都要手动注册 Union 格式化器（见[泛型基类型基准测试](/zh/docs/v4/benchmarks#more-cases)）。
- **可移植、确定的字节**：CoreCLR、Mono、IL2CPP，64 位和 32 位，字节都一样，填充清零。
- **覆盖面更广**：支持 `netstandard2.0`，Unity 有 OpenUPM 包，HybridCLR 不用初始化调用。
- **构建时间**：每个类型一个生成文件，源生成器是真正的增量生成。
- **基于布局生成 TypeScript**：[Nino.Codegen](/zh/docs/v4/advanced/codegen) 在构建之后运行，读的正是生成 C# 格式化器所用的那份布局，所以结构体、`char`、`decimal`、64 位枚举、键控和版本容错类型都支持，运行时也随包更新。MemoryPack 在源生成器里面写 TypeScript，只支持类，而且下个版本就要移除；见[对比](/zh/docs/v4/advanced/typescript#compared-with-memorypack)。

## 如何选择 [#when-to-choose-which]

<Cards>
  <Card title="这些情况选 Nino">
    数据可能来自网络对端、用户文件或其他你管不了的来源；在 .NET 服务器、Unity 或 Godot 上高频序列化消息、缓存值、存储的记录或应用状态；需要不用维护标签表的多态（包括泛型基类）、能演进的数据、共享引用，或者靠对象池做到零 GC；或者需要 Unity、IL2CPP 和服务器之间字节完全一致。
  </Card>
  <Card title="这些情况选 MemoryPack">
    需要按调用传的选项（`IServiceProvider`、每次调用不同的字符串编码），或者要序列化 `System.Type` 值。
  </Card>
</Cards>

<Callout type="idea">

两者都是 MIT 许可证，都基于源生成，都能放心用于 AOT。拿不定主意，就用你自己的类型测一测：[基准测试项目](https://github.com/JasonXuDeveloper/Nino/tree/main/benchmarks/Nino.Benchmark)会把 Nino 和 MemoryPack 放在一起运行。

</Callout>

## 从 MemoryPack 迁移 [#switching-from-memorypack]

MemoryPack 代码里的大部分写法都能一一对应：

| MemoryPack | Nino |
| --- | --- |
| `[MemoryPackable] partial class` | `[NinoType] class`；只有 .NET 8 之前的[非公共成员](/zh/docs/v4/defining-types#private-members)和 `[NinoPooled]` 才需要 `partial` |
| `[MemoryPackIgnore]` | `[NinoIgnore]` |
| 非公共成员上的 `[MemoryPackInclude]` | `[NinoType(includeNonPublicMembers: true)]` 写出所有非公共成员；或者用 `[NinoType(false, true)]`，在每个要写的成员上加 `[NinoMember(index)]` |
| `[MemoryPackOrder(n)]` | `[NinoType(false)]` 加 `[NinoMember(n)]` |
| `[MemoryPackConstructor]` | `[NinoConstructor]`（[构造函数](/zh/docs/v4/constructors)） |
| 基类型上的 `[MemoryPackUnion(tag, typeof(T))]` | 基类型上的 `[NinoType]`：子类型自动继承，不需要标签（[多态](/zh/docs/v4/polymorphism)） |
| `GenerateType.VersionTolerant` | `format: NinoFormat.Keyed`（按名字识别成员，不需要序号）；只会追加成员的类型也可以用 `NinoFormat.VersionTolerant`（[数据演进](/zh/docs/v4/evolving-data)） |
| `GenerateType.CircularReference` | `trackReferences: true`（[引用追踪](/zh/docs/v4/reference-tracking)） |
| `GenerateType.Collection` | 不需要：[自定义集合](/zh/docs/v4/types#user-collections)直接可用 |
| `[MemoryPackOnSerializing]`、`[MemoryPackOnSerialized]`、`[MemoryPackOnDeserializing]`、`[MemoryPackOnDeserialized]` | `[NinoOnSerializing]`、`[NinoOnSerialized]`、`[NinoOnDeserializing]`、`[NinoOnDeserialized]`：方法不带参数，是 `public` 或 `internal`；除了 `[NinoOnDeserializing]` 可以是静态的，其余都是实例方法（[回调](/zh/docs/v4/defining-types#callbacks)） |
| `MemoryPackSerializer.Serialize(value)` | `NinoSerializer.Serialize(value)` |
| `MemoryPackSerializer.Serialize(bufferWriter, value)` | `NinoSerializer.Serialize(value, bufferWriter)`：值在前 |
| `MemoryPackSerializer.Deserialize<T>(bytes)`, `Deserialize(bytes, ref value)` | `NinoDeserializer.Deserialize<T>(bytes)`, `Deserialize(bytes, ref value)` |
| `SerializeAsync(stream, value)`、`DeserializeAsync<T>(stream)` | `NinoSerializer.SerializeAsync(value, stream)`、`NinoDeserializer.DeserializeAsync<T>(stream)`：值在前；同步版本是 `Serialize(value, stream)` 和 `Deserialize<T>(stream)`（[流](/zh/docs/v4/advanced/streams#streams)） |
| UTF-8 字符串 | 所有字符都不超过 U+00FF 时每字符一个字节，否则 UTF-16；按成员用 `[NinoUtf8]`（[字符串编码](/zh/docs/v4/defining-types#string-encoding)） |

两个库写的字节不一样，所以已经存下的数据要转换。两个库能装在同一个项目里：转换期间类型上同时留着两种特性，用 MemoryPack 读出每个存下的值，再用 Nino 写回去，最后移除 MemoryPack。给转换后的数据加上[文件头](/zh/docs/v4/advanced/persistence#add-a-file-header)，以后的版本就知道该用哪个读取器。进程之间的消息不用转换：两端一起升级就行。

```csharp title="Messages.cs"
using MemoryPack;
using Nino.Core;

[MemoryPackable]
[MemoryPackUnion(0, typeof(Ping))]
[MemoryPackUnion(1, typeof(Chat))]
[NinoType]                       // [!code ++]
public partial interface IMessage { }

[MemoryPackable]
public sealed partial class Ping : IMessage
{
    public long SentAt { get; set; }
}

[MemoryPackable]
public sealed partial class Chat : IMessage
{
    public string Text { get; set; }
    [MemoryPackIgnore, NinoIgnore]   public int Cached;
}
```

```csharp
using MemoryPack;

byte[] old = MemoryPackSerializer.Serialize<IMessage>(new Chat { Text = "hi" });
IMessage message = MemoryPackSerializer.Deserialize<IMessage>(old); // MemoryPack 存下的数据
byte[] bytes = NinoSerializer.Serialize(message);                   // 用 Nino 重新写出
IMessage back = NinoDeserializer.Deserialize<IMessage>(bytes);      // 一个 Chat
```

## 类型 ID 与 Union 标签 [#type-ids-and-union-tags]

MemoryPack 写 1 字节的 Union 标签（超过 249 时 3 字节），Nino 写 4 字节的类型 ID。这是有意的取舍：

- Nino 的 ID 由类型本身决定（类型名的 FNV-1a 哈希），所以子类型不用标签。子类型可以放在任何程序集里（插件、HybridCLR 热更新、继承你基类的库），增删子类型时 ID 也不会重新编号。
- MemoryPack 要在基类上用 `[MemoryPackUnion(tag, type)]` 列出所有子类型，或者用 Union 格式化器手动注册，标签还得自己保证不变。

代价是每个多态值多 3 字节。见[多态](/zh/docs/v4/polymorphism)。

## 基准测试中发现的 MemoryPack 问题 [#memorypack-bugs-found-while-benchmarking]

对比两个库都支持的所有内置类型时，我们在计时之前先让每个值在 MemoryPack 1.21.4 里写出再读回一次。两个类型没通过，所以基准测试里这两个只测 Nino；还有一个换个运行时就读错：

- **`BigInteger`。** 它的格式化器在 255 字节的栈缓冲区上写的是 `temp.Slice(written)`，本意是 `temp.Slice(0, written)`：写出去的是缓冲区没用到的尾巴，不是这个值。255 字节以内的 `BigInteger`（包括 `3^10`）读回来都变成了别的值，哪个运行时都一样；更大的值走另一条路径，能正确读回。
- **.NET 10 上的 `BitArray`。** 它的格式化器把 `BitArray` 强转成 `{ int[] m_array; int m_length }`，那是 .NET 8 上的布局。.NET 10 的 `BitArray` 里存的是 `byte[] _array`，于是 MemoryPack 写出错的字节，读的时候还会破坏堆，把进程搞崩。

- **跨运行时的非托管元组。** MemoryPack 把非托管值（包括 `(int, long)`）按内存原样拷贝。`ValueTuple` 是 `LayoutKind.Auto`：CoreCLR 把 `long` 排在前面，Mono 按声明顺序排。所以在 .NET 上写的 `(1, 2L)`（`02000000 00000000 01000000 00000000`，最后 4 字节是填充），到 Mono 上读回来（Mono 6.8 实测）是 `(2, 1)`，Unity 也一样，它的 Mono 和 IL2CPP 后端都这样排元组；填充字节写出去的也是内存里残留的东西。基准测试里的 `(int, long)` 列表只在 .NET 上能正确读回。

Nino 把 `BigInteger` 写成二进制补码字节，`BitArray` 经公开 API 读写，元组按声明顺序逐项写、不带填充（`(int, long)` 是 12 字节），都不依赖运行时的私有布局。见[其他内置类型](/zh/docs/v4/types#other-built-in-types)和[可移植的设计](/zh/docs/v4/platforms#portable-by-design)。
