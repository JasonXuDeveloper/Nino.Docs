Nino writes the same bytes on every platform. Where a platform has vector instructions, each runtime uses them for the work that gains most from them: moving values whose bytes differ from their memory (tuples, padded structs), large block copies, and converting strings between the encodings of the [wire format](/en/docs/v4/wire-format#values) and the language's own. Every vector path is found at run time (or when the code is compiled for its target), and every one has a portable fallback that writes the same bytes; the tests compare the two.

The tables below list the vector paths in Nino's source today, platform by platform, with the benchmark that measures each.

## .NET [#dotnet]

The `net8.0` and `net10.0` builds of `Nino.Core` use .NET's hardware intrinsics. The JIT compiles only the path the CPU has (`IsSupported` checks are constants to it), so the others cost nothing. The full list of what each instruction set does is in [SIMD by Platform](/en/docs/v4/platforms#simd).

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| x64 with AVX-512 | 64-byte block copies with aligned stores; byte permutes (AVX-512 VBMI, or 4-byte word permutes with AVX-512F) that write and read tuples and `KeyValuePair`s with padding 64 bytes at a time; 512-bit masked copies that clear the padding of raw structs | [Benchmarks](/en/docs/v4/benchmarks), x64 |
| x64 with AVX2 | 32-byte block copies; tuples and pairs with padding moved a group of 32-byte vectors at a time (`vpshufb`, `vperm2i128`); strings narrowed to Latin-1 and widened back 32 bytes at a time | [Benchmarks](/en/docs/v4/benchmarks), x64 |
| x64 with SSSE3 | tuples and pairs with padding moved a group of 16-byte vectors at a time (`pshufb`); strings narrowed and widened 16 bytes at a time | [Benchmarks](/en/docs/v4/benchmarks) |
| Arm64 (AdvSimd) | table lookups (`TBL`) for tuples and pairs with padding, a group of 16-byte vectors at a time; block copies with load and store pairs (`LDP`/`STP`); strings narrowed and widened 16 bytes at a time | [Benchmarks](/en/docs/v4/benchmarks), Arm64 tab |
| WebAssembly with SIMD (.NET 10) | two swizzles (`i8x16.swizzle`) per 16-byte vector for tuples and pairs with padding | — |
| Arm32, or hardware intrinsics turned off (`DOTNET_EnableHWIntrinsic=0`) | none: values moved one at a time, blocks over 64 bytes through `memmove`; the same bytes | — |

.NET Framework and .NET Core 3.0 to .NET 7 load the netstandard builds, which have no intrinsics; they narrow and widen long Latin-1 strings with `Vector<T>` where the JIT accelerates it (never on Mono or Unity).

## Unity [#unity]

Unity loads the netstandard build of `Nino.Core`. With `com.unity.burst` 1.8 or later installed, the Unity package registers [Burst-compiled kernels](/en/docs/v4/advanced/unity#burst-kernels) at startup through `NinoKernels`, a table of native function pointers that only the netstandard builds call (each pointer is kept in a static field and called directly, after one compare against its threshold) (every build declares it, so a library that registers kernels loads on .NET 8 and later too, which keep their own paths). Burst compiles the kernels for each CPU target of its AOT settings, picks the variant the CPU runs at startup, and each checks its instruction set when it is registered.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| x64 with AVX2, Burst AVX2 target | `Permute` for blocks of 256 values or more of up to 16 bytes: two or more values per 32-byte vector, one `vpshufb` mask, lanes joined with `vpermd` or stored as two 16-byte halves; the rest, wider values and strings take the SSSE3 paths below | [Unity benchmark](/en/docs/v4/perf-unity) |
| x86 and x64 with SSSE3 (in x64 players, the SSE4 target) | `Permute`: arrays and lists of 2 or more tuples, pairs and blocked `[NinoType]` structs written and read with one byte shuffle (`pshufb`) per 16 bytes, and 16 or more raw structs with padding copied with it cleared; `Narrow` and `Widen`: Latin-1 strings of 16 chars or more, 16 chars at a time; `NarrowAscii` and `WidenAscii`: the ASCII text of `[NinoUtf8]` strings of 16 chars or more, up to the first other char, which .NET's UTF-8 encoder and strict decoder take from there | [Unity benchmark](/en/docs/v4/perf-unity) |
| Arm64 (Neon) | the same kernels with `tbl`, and `uzp1`/`zip` for strings | — |
| WebGL built with WebAssembly SIMD (Unity 6's Target WebAssembly 2023, or `-msimd128` on 2022.3) | no Burst there: the same kernels in C (`Nino.WebGL`) with `i8x16.swizzle` and vector narrowing and widening, for Latin-1 strings and the ASCII text of `[NinoUtf8]` strings of 16 chars or more and 32 values or more of the rest. See [WebGL](/en/docs/v4/advanced/unity#webgl-kernels) | — |
| Armv7, WebGL without SIMD, x86 and x64 without SSSE3 (or without the target that has it), IL2CPP and Mono players without Burst (install Burst for the kernels) | none: Nino's scalar netstandard paths; the same bytes | [Unity benchmark](/en/docs/v4/perf-unity), "Without Burst" |

## Go [#go]

The Go runtime's vector code is assembly for strings, one kernel per instruction set, the best the processor has taken at run time (`CPUID`, and `XGETBV` for whether the system saves the vector registers; on macOS, AVX-512 is detected through `sysctl` as golang.org/x/sys/cpu does, from macOS 12.2 on). The writer checks the text is WTF-8 and writes it as Latin-1 or UTF-16 in one pass; `WriteStrings` writes a whole list in one call, a string of 64 bytes or more through the single-string kernel, which reserves the longest header the text could need and moves the text down when the header is shorter.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| amd64 with AVX-512 (F, BW, VL, VBMI2) | the writer 32 bytes at a time with masked loads and compress instructions, no tables; with VBMI too, the reader converts Latin-1 and UTF-16 to UTF-8 with AVX-512 | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#go), string cases |
| amd64 with AVX2 (and POPCNT) | the writer 32 bytes at a time; the reader takes the SSSE3 kernels | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#go) |
| amd64 with SSSE3 | the writer and the reader 16 bytes at a time with `PSHUFB` and `PALIGNR` | — |
| arm64 (NEON) | the writer and the reader 16 bytes at a time; the writer does in scalar registers what needs no vector (the ASCII test of a block, the movemask) | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#go), Arm64 |
| amd64 without SSSE3, every other platform, or built with `-tags purego` | none: Go loops over 8-byte words (long runs of ASCII copied or widened 16 bytes at a time with SSE2 or NEON); the same bytes | — |

## Rust [#rust]

The Rust crate's vector code is in `src/simd.rs` and its submodules `simd/x86.rs` and `simd/neon.rs`, its only code allowed `unsafe`, tested under Miri on x86_64 (SSE2 only, SSSE3, SSE4.1, AVX2, AVX-512), Arm64 and big-endian s390x. Writing a string transcodes its UTF-8 to Latin-1 or UTF-16 straight into the buffer in one pass; reading one decodes Latin-1 or UTF-16 straight into the `String`. Each instruction set has its own kernel, found once at run time on x86_64 and cached, and kept only where it measured faster on the CPUs it targets.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| x86_64 with AVX-512 (F, BW, VL, VBMI2; crate built with Rust 1.89 or later) | writes 64 bytes a step with masked loads and stores, packed by `vpcompressb`/`vpcompressw`; reads Latin-1 of 32 bytes or more and UTF-16 of 24 units or more with AVX-512 | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#rust), string cases |
| x86_64 with AVX2 (and BMI1, BMI2, LZCNT) | writes in 32-byte windows | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#rust) |
| x86_64 with SSE4.1 | writes in 16-byte windows; reads UTF-16 of 24 units or more (Latin-1 with SSSE3) | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#rust) |
| x86_64 with SSSE3 or SSE2 only | text up to 64 bytes char by char, longer text 16 bytes a block (SSSE3 for two-byte chars in text of 48 bytes or more) | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#rust) |
| Arm64, little-endian (NEON) | writes text over 64 bytes in 32-byte windows, runs of three-byte chars (CJK) 48 bytes a step (`ld3`), shorter text char by char; reads Latin-1 of 32 bytes or more and UTF-16 of 24 units or more | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#rust) |
| 32-bit targets, WebAssembly, big-endian | none: two 8-byte words a block; the same bytes | — |

## TypeScript [#typescript]

The TypeScript runtime reads and writes with `DataView` and typed arrays. Its vector code is for strings in browsers and Deno: a small [WebAssembly module](/en/docs/v4/advanced/codegen#text-in-browsers) embedded in `nino.ts`, found when it is first needed.

| Engine | Vector paths | Benchmark |
| --- | --- | --- |
| Browsers and Deno with WebAssembly SIMD, GC and the JS String Builtins | longer UTF-16 and Latin-1 text read, and text of more than 64 chars written, 8 or 16 chars at a time in SIMD registers (`useWasm(false)` turns it off) | — |
| Node, Bun, Deno with Node's `Buffer` | none of Nino's: `Buffer`'s native Latin-1 and UTF-16 methods | [Benchmarks in Other Languages](/en/docs/v4/perf-runtimes#typescript) |
| Engines without them, or a Content Security Policy that blocks compiling WebAssembly | none: the JavaScript paths and the engine's built-in decoders; the same bytes | — |
