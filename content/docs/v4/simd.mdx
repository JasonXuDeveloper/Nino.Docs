Nino writes the same bytes on every platform. Where a platform has vector instructions, each runtime uses them for the work that gains most from them: moving values whose bytes differ from their memory (tuples, padded structs), large block copies, and converting strings between the encodings of the [wire format](/en/docs/v4/wire-format#values) and the language's own. Every vector path is found at run time (or when the code is compiled for its target), and every one has a portable fallback that writes the same bytes; the tests compare the two.

The tables below list the vector paths in Nino's source today, platform by platform, with the benchmark that measures each.

## .NET [#dotnet]

The `net8.0` and `net10.0` builds of `Nino.Core` use .NET's hardware intrinsics. The JIT compiles only the path the CPU has (`IsSupported` checks are constants to it), so the others cost nothing. Tuples and `KeyValuePair`s below mean those of raw items, whose memory differs from their bytes.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| x64 with AVX-512 | 64-byte vector copies with aligned stores for blocks of 129 bytes to 32 KB; tuples and pairs whose memory has padding written as whole 64-byte vectors from an aligned destination by two-source permutes (16 `(int, long)` in three), of 4-byte words where each is a whole word of memory (AVX-512F, no VBMI needed), otherwise of bytes (AVX-512 VBMI), and read the same way, each 64-byte vector of memory stored at an aligned address; other such items 64 bytes at a time (VBMI); 512-bit masked copies that clear the padding of raw structs | [.NET Benchmarks](/en/docs/v4/benchmarks), x64 |
| x64 with AVX2 | blocks of 33 to 128 bytes copied inline as two or four overlapping 32-byte vectors (with AVX-512 too); 32-byte vector copies with aligned stores for blocks of 256 bytes to 16 KB (also on AVX-512 CPUs where .NET prefers 256-bit vectors); tuples and pairs with padding moved a group at a time, written and read: each 16-byte lane of a 32-byte vector shuffled (`vpshufb`) from at most two 16-byte windows of the source, loads shared across a group's vectors and lanes far apart joined by one lane permute (`vperm2i128`), stores on 32-byte boundaries where the values allow; values whose group would take more than four vectors (5-byte blocks such as `(byte, int)`) a group of as many values as one to four vectors hold (six `(byte, int)` a 32-byte vector); otherwise an SSSE3 16-byte shuffle per value for such tuples and pairs of up to 16 bytes; strings narrowed to Latin-1 and widened back 32 bytes at a time | [.NET Benchmarks](/en/docs/v4/benchmarks), x64 |
| x64 with SSSE3 | tuples and pairs with padding moved a group of 16-byte vectors at a time, each two shuffles (`pshufb`) ORed (twelve `(byte, int)` in four vectors, as on AVX2 for blocks whose group would take more than four); otherwise the 16-byte shuffle per value; blocks of 33 to 64 bytes copied inline as four 16-byte moves, `memmove` for larger blocks; strings narrowed and widened 16 bytes at a time | [.NET Benchmarks](/en/docs/v4/benchmarks) |
| Arm64 (AdvSimd) | table lookups (`TBL`) that move tuples and pairs with padding a group of 16-byte vectors at a time, written and read: where a group's windows lie on the 16-byte grid they are loaded once each, as pairs (`LDP`), and each lookup takes one window or two consecutive ones (four `(int, long)` written from two pairs of loads by three lookups); padding masked with pairs of 16-byte loads and stores (`LDP`/`STP`); otherwise the 16-byte shuffle per value (`TBL`), and values of up to 8 bytes eight at a time, each 16 bytes written by one lookup in just the 16-byte quarters of the 64 loaded that its bytes come from (one to four registers), only the bytes of the values stored; blocks of 33 to 64 bytes copied inline as four 16-byte moves, 65 bytes to 64 KB 64 bytes a step as load and store pairs (`LDP`/`STP`) from an aligned source address, `memmove` beyond; strings narrowed and widened 16 bytes at a time | [.NET Benchmarks](/en/docs/v4/benchmarks), Arm64 tab |
| WebAssembly with SIMD (.NET 10) | two swizzles (`i8x16.swizzle`) per 16-byte vector for tuples and pairs with padding, written and read a group at a time as on SSSE3; otherwise the 16-byte shuffle per value (`PackedSimd`) | — |
| Arm32, or hardware intrinsics turned off (`DOTNET_EnableHWIntrinsic=0`) | none: values rearranged one at a time, blocks over 64 bytes through `memmove`; the same bytes | — |

Where a group copy stores to aligned addresses, the unaligned start and end of the output are covered by whole groups that overlap the rest, so its speed does not depend on where the output buffer starts.

.NET Framework and .NET Core 3.0 to .NET 7 load the netstandard builds, which have no intrinsics and convert [one-byte strings](/en/docs/v4/wire-format#strings) four chars at a time; they narrow and widen long Latin-1 strings with `Vector<T>` where the JIT accelerates it (never on Mono or Unity: Mono runs `Vector.Narrow` and `Vector.Widen` in software, slower than the scalar code).

On every build and runtime:

- Blocks of up to 64 bytes (most strings) are copied inline on 64-bit runtimes; on 32-bit x86 and WebAssembly and on .NET on Arm32, where unaligned 8-byte loads cannot fault, the same way in one call; Mono and IL2CPP on Arm32 call `memmove`.
- Raw values read in blocks of 6 KB or more (into new or existing arrays) are copied with `memmove`, whose `rep movsb` on Intel x64 writes fresh cache lines without reading them first; on AMD x64 CPUs, where it is slower than vector stores, with Nino's vector loop.
- Padding is masked with 512-bit vectors on AVX-512, otherwise with `Vector<T>` where the runtime accelerates it (on Mono only with the System.Numerics.Vectors package; never in Unity, whose `Vector<T>` Mono does not accelerate even where it reports itself accelerated), else 8 bytes at a time.
- In [`Untrusted` mode](/en/docs/v4/security#untrusted-mode), the `bool`, `DateTime`, `decimal`, `DateOnly` and `TimeOnly` fields of runs of raw values are checked as whole `Vector<T>`s on .NET 8 and later where the fields are dense enough, with masks repeated with the values' stride; otherwise one field at a time over the run, without a branch per value. `[NinoUtf8]` strings are transcoded by .NET's own UTF-8 converters (`Utf8.FromUtf16` and `Utf8.ToUtf16` on .NET 8+), with their vector paths.
- On Intel's Ice Lake generation (Ice Lake, Tiger Lake and Rocket Lake, recognized by CPU model), where a 64-byte load across two cache lines costs about twice an aligned one: padding is masked with 32-byte vectors instead of 64-byte ones, tuples and pairs whose groups move whole 4-byte words are written from loads that start on a cache line, and on Linux blocks of about 2 to 32 KB are copied by the C library's `rep movsb`. Every other CPU keeps the paths above; the bytes are the same.

## Unity [#unity]

Unity loads the netstandard build of `Nino.Core`. With `com.unity.burst` 1.8 or later installed, the Unity package registers [Burst-compiled kernels](/en/docs/v4/advanced/unity#burst-kernels) at startup through `NinoKernels`, a table of native function pointers that only the netstandard builds call (each pointer is kept in a static field and called directly, after one compare against its threshold) (every build declares it, so a library that registers kernels loads on .NET 8 and later too, which keep their own paths). Other hosts of the netstandard builds can [register kernels of their own](#registering-kernels). Burst compiles the kernels for each CPU target of its AOT settings, picks the variant the CPU runs at startup, and each checks its instruction set when it is registered.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| x64 with AVX2, Burst AVX2 target | `Permute` for blocks of 256 values or more of up to 16 bytes: two or more values per 32-byte vector, one `vpshufb` mask, lanes joined with `vpermd` or stored as two 16-byte halves; the rest, wider values and strings take the SSSE3 paths below | [Unity benchmark](/en/docs/v4/benchmarks-unity) |
| x86 and x64 with SSSE3 (in x64 players, the SSE4 target) | `Permute`: arrays and lists of 2 or more tuples, pairs and blocked `[NinoType]` structs written and read with one byte shuffle (`pshufb`) per 16 bytes, and 16 or more raw structs with padding copied with it cleared; `Narrow` and `Widen`: Latin-1 strings of 16 chars or more, 16 chars at a time; `NarrowAscii` and `WidenAscii`: the ASCII text of `[NinoUtf8]` strings of 16 chars or more, up to the first other char, which .NET's UTF-8 encoder and strict decoder take from there | [Unity benchmark](/en/docs/v4/benchmarks-unity) |
| Arm64 (Neon) | the same kernels with `tbl`, and `uzp1`/`zip` for strings | — |
| WebGL built with WebAssembly SIMD (Unity 6's Target WebAssembly 2023, or `-msimd128` on 2022.3) | no Burst there: the same kernels in C (`Nino.WebGL`) with `i8x16.swizzle` and vector narrowing and widening, for Latin-1 strings and the ASCII text of `[NinoUtf8]` strings of 16 chars or more and 32 values or more of the rest. See [WebGL](/en/docs/v4/advanced/unity#webgl-kernels) | — |
| Armv7, WebGL without SIMD, x86 and x64 without SSSE3 (or without the target that has it), IL2CPP and Mono players without Burst (install Burst for the kernels) | none: Nino's scalar netstandard paths; the same bytes | [Unity benchmark](/en/docs/v4/benchmarks-unity), "Without Burst" |

## Go [#go]

The Go runtime's vector code is assembly for strings, one kernel per instruction set, the best the processor has taken at run time (`CPUID`, and `XGETBV` for whether the system saves the vector registers; on macOS, AVX-512 is detected through `sysctl` as golang.org/x/sys/cpu does, from macOS 12.2 on). The writer checks the text is WTF-8 and writes it as Latin-1 or UTF-16 in one pass; `WriteStrings` writes a whole list in one call, a string of 64 bytes or more through the single-string kernel, which reserves the longest header the text could need and moves the text down when the header is shorter.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| amd64 with AVX-512 (F, BW, VL, VBMI2) | the writer 32 bytes at a time with masked loads and compress instructions, no tables; with VBMI too, the reader converts Latin-1 and UTF-16 to UTF-8 with AVX-512 | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#go), string cases |
| amd64 with AVX2 (and POPCNT) | the writer 32 bytes at a time; the reader takes the SSSE3 kernels | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#go) |
| amd64 with SSSE3 | the writer and the reader 16 bytes at a time with `PSHUFB` and `PALIGNR` | — |
| arm64 (NEON) | the writer and the reader 16 bytes at a time; the writer does in scalar registers what needs no vector (the ASCII test of a block, the movemask) | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#go), Arm64 |
| amd64 without SSSE3, every other platform, or built with `-tags purego` | none: Go loops over 8-byte words (long runs of ASCII copied or widened 16 bytes at a time with SSE2 or NEON); the same bytes | — |

## Rust [#rust]

The Rust crate's vector code is in `src/simd.rs` and its submodules `simd/x86.rs` and `simd/neon.rs`, its only code allowed `unsafe`, tested under Miri on x86_64 (SSE2 only, SSSE3, SSE4.1, AVX2, AVX-512), Arm64 and big-endian s390x. Writing a string transcodes its UTF-8 to Latin-1 or UTF-16 straight into the buffer in one pass; reading one decodes Latin-1 or UTF-16 straight into the `String`. Each instruction set has its own kernel, found once at run time on x86_64 and cached, and kept only where it measured faster on the CPUs it targets.

| Hardware | Vector paths | Benchmark |
| --- | --- | --- |
| x86_64 with AVX-512 (F, BW, VL, VBMI2; crate built with Rust 1.89 or later) | writes 64 bytes a step with masked loads and stores, packed by `vpcompressb`/`vpcompressw`; reads Latin-1 of 32 bytes or more and UTF-16 of 24 units or more with AVX-512 | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#rust), string cases |
| x86_64 with AVX2 (and BMI1, BMI2, LZCNT) | writes in 32-byte windows | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#rust) |
| x86_64 with SSE4.1 | writes in 16-byte windows; reads UTF-16 of 24 units or more (Latin-1 with SSSE3) | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#rust) |
| x86_64 with SSSE3 or SSE2 only | text up to 64 bytes char by char, longer text 16 bytes a block (SSSE3 for two-byte chars in text of 48 bytes or more) | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#rust) |
| Arm64, little-endian (NEON) | writes text over 64 bytes in 32-byte windows, runs of three-byte chars (CJK) 48 bytes a step (`ld3`), shorter text char by char; reads Latin-1 of 32 bytes or more and UTF-16 of 24 units or more | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#rust) |
| 32-bit targets, WebAssembly, big-endian | none: two 8-byte words a block; the same bytes | — |

## TypeScript [#typescript]

The TypeScript runtime reads and writes with `DataView` and typed arrays. Its vector code is for strings in browsers and Deno: a small [WebAssembly module](/en/docs/v4/advanced/typescript#text-in-browsers) embedded in `nino.ts`, found when it is first needed.

| Engine | Vector paths | Benchmark |
| --- | --- | --- |
| Browsers and Deno with WebAssembly SIMD, GC and the JS String Builtins | longer UTF-16 and Latin-1 text read, and text of more than 64 chars written, 8 or 16 chars at a time in SIMD registers (`useWasm(false)` turns it off) | — |
| Node, Bun, Deno with Node's `Buffer` | none of Nino's: `Buffer`'s native Latin-1 and UTF-16 methods | [Other-Language Benchmarks](/en/docs/v4/benchmarks-runtimes#typescript) |
| Engines without them, or a Content Security Policy that blocks compiling WebAssembly | none: the JavaScript paths and the engine's built-in decoders; the same bytes | — |

## Registering Your Own Kernels [#registering-kernels]

The kernels Unity's package registers ([above](#unity)) go through a public API, `NinoKernels`, which any host of the netstandard builds can use: .NET Framework, Mono, and .NET Core 3.0 to .NET 7. It helps where those builds have no vector path of their own: arrays and lists of tuples, `KeyValuePair`s and blocked `[NinoType]` structs, arrays of raw structs with padding, Latin-1 strings and the ASCII text of `[NinoUtf8]` strings. Skip it on .NET 8 and later: their builds use their own vector paths and never call the kernels (registering there does nothing).

Each kernel is a native `cdecl` function you pass as a function pointer; `NinoKernels.Register` copies the pointers into static fields, and Nino calls them directly. A pointer left `null` keeps Nino's own path for that work.

| Kernel | Signature | Must do (reference: `NinoKernels.PermuteScalar`, `NarrowScalar`, ...) |
| --- | --- | --- |
| `Permute` | `void (byte* source, int sourceStride, byte* destination, int destinationStride, byte* table, int count)` | For each of `count` values, `sourceStride` bytes apart at `source` and `destinationStride` bytes apart at `destination`: destination byte `j` = source byte `table[j]`, or `0` where `table[j]` is `0xFF`. Writes every destination byte. Strides are 1 to 64; the ranges do not overlap. |
| `Narrow` | `int (ushort* source, byte* destination, int length)` | Writes each of the `length` UTF-16 chars as one byte (Latin-1); returns `1` when all are at most U+00FF, `0` when one is above (having written any part of them: Nino then writes the string as UTF-16). |
| `Widen` | `void (byte* source, ushort* destination, int length)` | Widens `length` Latin-1 bytes to UTF-16 chars. |
| `NarrowAscii` | `int (ushort* source, byte* destination, int length)` | Writes the leading chars below U+0080 as a byte each and returns how many (`length` when all are); it may write bytes past those, up to `length`. Nino encodes the rest. |
| `WidenAscii` | `int (byte* source, ushort* destination, int length)` | Widens the leading bytes below `0x80` to a char each and returns how many (`length` when all are); it may write chars past those, up to `length`. Nino decodes and validates the rest. |

On .NET Framework, Nino already narrows and widens long Latin-1 strings with `Vector<T>` where the JIT accelerates it; a registered `Narrow` or `Widen` is called instead of that path, so measure both.

The rules every kernel follows:

- **The same bytes.** A kernel must produce exactly what its reference produces: the wire format does not depend on which path ran, and data written with kernels reads without them, and in every other runtime. Test each kernel against its `...Scalar` reference on random input and every length around your vector width.
- **No alignment, no state, no exceptions.** Pointers have any alignment. Every thread that serializes may call them at the same time, so they keep no mutable state. Nothing may unwind out of them.
- **Thresholds.** Nino calls a kernel only for runs long enough to pay for the call: `MinBlocks` values for `Permute` (default 16, at least 1; copies of raw structs with padding start at 16 whatever you set), `MinChars` chars for the four text kernels (default 32, at least 16). Unity's Burst kernels use 2 and 16, its WebGL kernels 32 and 16: measure on your target and set the lengths where your kernel starts to win.

A minimal example: the two Latin-1 kernels in C, built as a DLL and loaded on Windows (C# 9 or later for function pointers).

```c title="nino_kernels.c"
#include <stdint.h>

/* Loops simple enough for an optimizing compiler (-O3, /O2) to vectorize. */
__declspec(dllexport) int nino_narrow(const uint16_t* source, uint8_t* destination, int32_t length)
{
    uint16_t all = 0;
    for (int32_t i = 0; i < length; i++)
    {
        all |= source[i];
        destination[i] = (uint8_t)source[i];
    }
    return all <= 0xFF; /* 1: every char was Latin-1 */
}

__declspec(dllexport) void nino_widen(const uint8_t* source, uint16_t* destination, int32_t length)
{
    for (int32_t i = 0; i < length; i++)
        destination[i] = source[i];
}
```

```csharp title="NinoNativeKernels.cs"
using System;
using System.Runtime.InteropServices;
using Nino.Core;

// .NET Framework on Windows: register at startup, before the first serialization.
public static unsafe class NinoNativeKernels
{
    [DllImport("kernel32", CharSet = CharSet.Unicode, SetLastError = true)]
    private static extern IntPtr LoadLibrary(string path);

    [DllImport("kernel32", CharSet = CharSet.Ansi, ExactSpelling = true)]
    private static extern IntPtr GetProcAddress(IntPtr module, string name);

    public static bool Register(string path)
    {
        IntPtr library = LoadLibrary(path); // never freed: Nino may call the kernels until the process exits
        if (library == IntPtr.Zero)
            return false;                   // Nino keeps its own paths

        NinoKernels.Register(new NinoKernels
        {
            MinChars = 64, // the length from which your kernels measure faster
            Narrow = (delegate* unmanaged[Cdecl]<ushort*, byte*, int, int>)GetProcAddress(library, "nino_narrow"),
            Widen = (delegate* unmanaged[Cdecl]<byte*, ushort*, int, void>)GetProcAddress(library, "nino_widen"),
            // Permute, NarrowAscii and WidenAscii left null: Nino's own paths
        });
        return true;
    }
}
```

<Callout type="warn" title="Register once, at startup, from one thread">

`NinoKernels.Register(kernels)` replaces whatever was registered (`null` goes back to Nino's own paths), and `NinoKernels.Current` returns the instance registered last. It is not frozen like the settings: a call while other threads serialize switches them over safely, but two `Register` calls at once may leave a mix of both. Changing the instance after registering it changes nothing until it is registered again. A call already in flight may still run the old kernels, so keep their code loaded for the life of the process. In Unity, the package's Burst or WebGL kernels register before the first scene loads, and in the editor after each domain reload: kernels you registered before that are replaced, so register yours after them.

</Callout>
