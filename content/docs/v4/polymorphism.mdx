Nino serializes the runtime type of a value, so a value declared as a base class or interface is read back as the type it really is. This is what you need for a skill's list of effects in a config table, the events of a replay, or the messages of a network protocol: one declared type, many concrete ones.

```csharp title="Effects.cs"
[NinoType] // [!code highlight]
public abstract class Effect
{
    public float Duration;
}

public sealed class Damage : Effect   // inherits [NinoType]
{
    public int Amount;
}

public sealed class Heal : Effect
{
    public int Amount;
}

public sealed class Stun : Effect { }
```

```csharp
var fireball = new List<Effect>
{
    new Damage { Amount = 40 },
    new Stun { Duration = 1.5f },
};
byte[] bytes = NinoSerializer.Serialize(fireball);
List<Effect> effects = NinoDeserializer.Deserialize<List<Effect>>(bytes);
// effects[0] is a Damage, effects[1] is a Stun
```

<Callout type="info">

In v4, subtypes **inherit** `[NinoType]` (including its options) from their nearest `[NinoType]` base class or interface, unless the base sets `allowInheritance: false`. You can still put `[NinoType]` on a subtype to give it its own options.

</Callout>

## Interfaces and Abstract Classes

Interfaces and abstract classes work the same way. Mark the interface or abstract class with `[NinoType]`; implementing classes and structs inherit it:

<Tabs items={["Interface example", "Abstract class example"]}>

<Tab value="Interface example">

```csharp
[NinoType] // [!code highlight]
public interface IBase
{
    int A { get; set; }
}

public class Impl : IBase
{
    public int A { get; set; }
}

public struct ImplStruct : IBase
{
    public int A { get; set; }
}
```

</Tab>

<Tab value="Abstract class example">

```csharp
[NinoType] // [!code highlight]
public abstract class Base
{
    public int A { get; set; }
}

public class Derived : Base
{
    public int B { get; set; }
}
```

</Tab>
</Tabs>

A `[NinoType]` interface serializes its own members through the implementing type's members of the same name. A struct read through an interface or `object` slot is boxed.

## How a Polymorphic Value Is Written

The header depends on the **declared** type of the slot (member, element, top-level type argument):

| Declared type | Header | Polymorphic |
| --- | --- | :---: |
| `struct` | none | no |
| `sealed class` | 1 byte null flag | no |
| non-sealed class, abstract class, interface | 4-byte type id (`0` = null) | yes |
| `object` | 4-byte type id | yes, any `[NinoType]` |

The type id is the FNV-1a hash of the runtime type's full name, computed by the generator, so there are no tags to assign and nothing to keep in sync between assemblies. Rename or move a type with [`[NinoFormerName]`](/en/docs/v4/defining-types#former-name).

<Callout type="idea">

Seal classes that have no subtypes. A sealed class costs 1 byte and no dispatch; a non-sealed one costs 4 bytes and a type check, even when no subtype exists.

</Callout>

### Inspecting Type Ids

`NinoTypeId` computes the same ids at run time, for logging, protocol checks or a handshake that compares message sets between peers:

```csharp
int id = NinoTypeId.Of(typeof(Move));          // the id Move is written with ([NinoFormerName] honored)
string name = NinoTypeId.GetName(typeof(Move)); // its runtime-form name, e.g. "MyGame.Net.Move"
```

Ids are never `0`, which encodes `null`.

## Dispatch

Nino uses hybrid dispatch:

- **Generated dispatch** for subtypes declared in the same assembly as their base: writing is a chain of exact type checks and reading is a `switch` on the type id, and both call the subtype's formatter directly.
- **A lock-free registry** for everything else: subtypes in other assemblies, closed generic types, tracked types, and hierarchies with more than 64 subtypes.

When reading, Nino checks that the type in the data really derives from the declared type; data that names an unrelated type throws instead of being stored.

## Subtypes in Other Assemblies

Subtypes are found automatically wherever they are declared, including assemblies loaded later (plugins, HybridCLR hot-update DLLs): when a type id is unknown, Nino looks in the registries of newly loaded assemblies before it fails. There is no registration call. For example, a hot update adds `public sealed class Freeze : Effect` in its own DLL. Once the DLL is loaded, the battle code in the AOT assembly reads a `List<Effect>` that contains a `Freeze`, with no change to that code. The subtype's assembly must reference `Nino.Core`, so the generator runs there too; an id whose type is in no loaded assembly throws `InvalidOperationException`.

The one exception is a closed generic subtype (`Box<int>`) that the process only **reads**, and never names in code or writes. Register it at startup:

```csharp
NinoPolymorphic.Register<Box<int>>();
```

## Opting Out

`[NinoType(allowInheritance: false)]` stops subtypes from inheriting the attribute: they are not serializable through the base unless they declare `[NinoType]` themselves (NINO003, with a code fix).

## Reuse Deserialization

When you deserialize into an existing value whose runtime type differs from the type in the data, the old instance is dropped (and recycled, see [pooling](/en/docs/v4/pooling)) and a new one of the right type is created. When the types match, the instance is filled in place.
