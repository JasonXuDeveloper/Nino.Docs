[MemoryPack](https://github.com/Cysharp/MemoryPack) is an excellent serializer and the one we measure Nino against. This page compares Nino v4 with MemoryPack **1.22.0**, using MemoryPack's own README for its features and Nino's source for Nino's. Where we could not verify a feature on either side, it is left out. How both compare with MessagePack, protobuf and System.Text.Json is on [Choosing a Serializer](/en/docs/v4/compare).

## Two Formats [#formats]

Both write binary without per-value tags, read through your C# types. The difference is where the bytes come from: MemoryPack copies an unmanaged value as it lies in memory, while Nino defines every byte, so the data is the same on every runtime and CPU.

| | Nino v4 | MemoryPack |
| --- | --- | --- |
| An unmanaged struct | its [raw value](/en/docs/v4/wire-format#raw-values) in the 64-bit layout, padding zeroed | its memory, padding included, in the layout of the platform that wrote it |
| A tuple such as `(int, long)` | its items in declaration order, 12 bytes | its memory: 16 bytes on x64, 12 on 32-bit x86, items in another order on Mono |
| A `T?` | a presence byte and the value | its memory (the flag, padding, the value); `SafeNullable<T>` has no padding |
| A subtype | a 4-byte type id, a hash of the type's name | a 1-byte union tag (3 bytes above 249) listed on the base |
| Strings | one byte a char when every char is at most U+00FF, else UTF-16; UTF-8 with [`[NinoUtf8]`](/en/docs/v4/defining-types#string-encoding) | UTF-8, option for UTF-16 |
| `DateTimeOffset` | UTC ticks and offset minutes | its memory layout, which differs on .NET 9 and earlier, .NET 10 and Unity; `Net10DateTimeOffset` or `UnityDateTimeOffset` in its place (MEMPACK043) |

The type id costs 3 bytes more per polymorphic value than a union tag, and buys subtypes without tags: Nino derives the id from the type itself (an FNV-1a hash of its name), so subtypes can live in any assembly (a plugin, a HybridCLR hot update, a library that extends your base class) and ids never renumber when subtypes are added or removed. MemoryPack lists every subtype on the base with `[MemoryPackUnion(tag, type)]`, or registers them by hand with a union formatter, and you keep the tags stable yourself. See [Polymorphism](/en/docs/v4/polymorphism).

Strings depend on the text: ASCII takes one byte a char in both; other Latin-1 text and CJK text are smaller in Nino (one and two bytes a char, against two and three in UTF-8); mostly-ASCII text with a few wider chars is smaller in UTF-8.

### Padded Structs and Tuples [#padded-values]

Two cases of the [common types and collections](/en/docs/v4/benchmarks#common-types-and-collections) hold values with padding in memory: `InventoryItem[1000]` (an `int`, a `short` and a `bool`: 7 bytes of members in 8) and `List<(int, long)>` (12 bytes of items in 16 on x64, where .NET puts the `long` first). MemoryPack copies their memory as it is, padding included. Nino defines the bytes instead. It writes an `InventoryItem` in its 8 bytes with the padding byte set to zero, a masked copy where MemoryPack makes a plain one, which is the extra work in Nino's time for that case. It writes a `(int, long)` as its two items, 12 bytes where MemoryPack writes 16, which is the difference in their payload sizes.

Copying the padding costs more than size:

- **The padding is whatever the memory held.** Equal values can serialize to different bytes, and stale memory goes out with them. In a test with MemoryPack 1.22.0, two `InventoryItem[2]` with equal values, one of them built in a buffer that had held `0xCD` bytes, serialized to different bytes, with `CD` in each padding byte; a `List<(int, long)>` built the same way carried `CDCDCDCD` after every item. Nino wrote the same bytes for both, padding zero.
- **Nullable values carry it too.** MemoryPack writes a `T?` as its memory (the flag, padding, the value), so an `int?` carries 3 bytes of whatever was there. Its 1.22.0 adds `SafeNullable<T>`, a type without padding to use instead of `T?`, compatible with `T?`'s bytes only for primitives and enums. Nino needs no such type: a `T?` member is a presence byte and the value, and a `T?[]` or `List<T?>` of raw values (the [fixed stride](/en/docs/v4/wire-format#collections)) and a `Nullable` field inside a raw struct are written with their padding, and the value of each one without a value, as zeros. [Nullable Values](/en/docs/v4/nullable-values) has the bytes of each, and `NinoNullable<T>` for arrays and lists written often.
- **The layout is the platform's.** `(int, long)` is 12 bytes in memory on 32-bit x86 .NET for Windows, and 16 on x64 and Arm32 (.NET 10's layout for each target, read from the code crossgen2 compiles for it), so a copy of its memory has another size there. On Mono the items are also in another order: see [MemoryPack Bugs Found While Benchmarking](#memorypack-bugs-found-while-benchmarking).

Nino's bytes are the same on every platform: [raw values](/en/docs/v4/wire-format#raw-values) in the 64-bit layout with zeroed padding, tuples item by item.

## Untrusted Input [#untrusted-input]

MemoryPack's README now opens with a warning: it is "a high-performance serialization format for trusted data only", "we no longer recommend using MemoryPack where the input can come from an untrusted party, such as public network endpoints or user-supplied files", and its features for cross-boundary communication, the TypeScript code generator among them, "will be removed in the next MemoryPack release" ([MemoryPack README](https://github.com/Cysharp/MemoryPack#readme)).

Nino reads untrusted data in its default mode, fast paths included, checked against fuzzed and hand-crafted payloads for every built-in type and every way of declaring one; [`NinoSettings.Untrusted`](/en/docs/v4/security#untrusted-mode) adds the checks that cost time on every read. What each guarantee means is on [Untrusted Data](/en/docs/v4/security#guarantees).

## Where MemoryPack Is Ahead [#where-memorypack-is-ahead]

MemoryPack does these things and Nino v4 does not:

- **`System.Type` values**, which Nino leaves out on purpose: data that names the types to create is a well-known deserialization attack.
- **Options per call**: `MemoryPackSerializerOptions` passes the string encoding and an `IServiceProvider` through every call. Nino's settings are process-wide or attributes on the types.
- **Compression built in**: `BrotliCompressor` and `[BrotliFormatter]`. With Nino, you compress the output with `System.IO.Compression` in a few lines.
- **Streaming collections**: `MemoryPack.Streaming` writes an `IAsyncEnumerable<T>`; with Nino, each element is a frame.

The workaround for each, and what Nino leaves out whatever you compare it with, is on [Limitations](/en/docs/v4/compare#limitations). Which to choose for which job: [Which to Choose](/en/docs/v4/compare#which-to-choose).

## Switching from MemoryPack [#switching-from-memorypack]

Most of a MemoryPack codebase maps one to one:

| MemoryPack | Nino |
| --- | --- |
| `[MemoryPackable] partial class` | `[NinoType] class`; `partial` only for [non-public members](/en/docs/v4/defining-types#private-members) before .NET 8 and for `[NinoPooled]` |
| `[MemoryPackIgnore]` | `[NinoIgnore]` |
| `[MemoryPackInclude]` on a non-public member | `[NinoType(includeNonPublicMembers: true)]` for every non-public member, or `[NinoType(false, true)]` with `[NinoMember(index)]` on each member to write |
| `[MemoryPackOrder(n)]` | `[NinoType(false)]` with `[NinoMember(n)]` |
| `[MemoryPackConstructor]` | `[NinoConstructor]` ([Constructors](/en/docs/v4/constructors)) |
| `[MemoryPackUnion(tag, typeof(T))]` on the base | `[NinoType]` on the base: subtypes inherit it, with no tags ([Polymorphism](/en/docs/v4/polymorphism)) |
| `GenerateType.VersionTolerant` | `format: NinoFormat.Keyed` (members by name, no order numbers), or `NinoFormat.VersionTolerant` for types that only grow ([Evolving Your Data](/en/docs/v4/evolving-data)) |
| `GenerateType.CircularReference` | `trackReferences: true` ([Reference Tracking](/en/docs/v4/reference-tracking)) |
| `GenerateType.Collection` | nothing: [your own collections](/en/docs/v4/types#user-collections) work as they are |
| `[MemoryPackOnSerializing]`, `[MemoryPackOnSerialized]`, `[MemoryPackOnDeserializing]`, `[MemoryPackOnDeserialized]` | `[NinoOnSerializing]`, `[NinoOnSerialized]`, `[NinoOnDeserializing]`, `[NinoOnDeserialized]`: methods without parameters, `public` or `internal`, and instance methods except a static `[NinoOnDeserializing]` ([Callbacks](/en/docs/v4/defining-types#callbacks)) |
| `MemoryPackSerializer.Serialize(value)` | `NinoSerializer.Serialize(value)` |
| `MemoryPackSerializer.Serialize(bufferWriter, value)` | `NinoSerializer.Serialize(value, bufferWriter)`: the value comes first |
| `MemoryPackSerializer.Deserialize<T>(bytes)`, `Deserialize(bytes, ref value)` | `NinoDeserializer.Deserialize<T>(bytes)`, `Deserialize(bytes, ref value)` |
| `SerializeAsync(stream, value)`, `DeserializeAsync<T>(stream)` | `NinoSerializer.SerializeAsync(value, stream)`, `NinoDeserializer.DeserializeAsync<T>(stream)`: the value comes first; `Serialize(value, stream)` and `Deserialize<T>(stream)` are their synchronous forms ([Streams](/en/docs/v4/advanced/streams#streams)) |
| `SafeNullable<T>` | `T?`, which is always safe in Nino; `NinoNullable<T>` for arrays and lists written often ([Nullable Values](/en/docs/v4/nullable-values#from-memorypack)) |
| UTF-8 strings | one byte a char up to U+00FF, else UTF-16; `[NinoUtf8]` per member ([String Encoding](/en/docs/v4/defining-types#string-encoding)) |

The two libraries write different bytes, so stored data has to be converted; both can be installed in one project while you do ([Switching to Nino](/en/docs/v4/compare#switching) has the steps). Keep both attributes on your types, read each stored value with MemoryPack and write it again with Nino:

```csharp title="Messages.cs"
using MemoryPack;
using Nino.Core;

[MemoryPackable]
[MemoryPackUnion(0, typeof(Ping))]
[MemoryPackUnion(1, typeof(Chat))]
[NinoType]                       // [!code ++]
public partial interface IMessage { }

[MemoryPackable]
public sealed partial class Ping : IMessage
{
    public long SentAt { get; set; }
}

[MemoryPackable]
public sealed partial class Chat : IMessage
{
    public string Text { get; set; }
    [MemoryPackIgnore, NinoIgnore]   public int Cached;
}
```

```csharp
using MemoryPack;

byte[] old = MemoryPackSerializer.Serialize<IMessage>(new Chat { Text = "hi" });
IMessage message = MemoryPackSerializer.Deserialize<IMessage>(old); // what MemoryPack stored
byte[] bytes = NinoSerializer.Serialize(message);                   // written again with Nino
IMessage back = NinoDeserializer.Deserialize<IMessage>(bytes);      // a Chat
```

## MemoryPack Bugs Found While Benchmarking [#memorypack-bugs-found-while-benchmarking]

Comparing every built-in type both libraries share, we round-tripped each value through MemoryPack before timing it. One type fails in 1.22.0, so the benchmarks time it for Nino only; a second failed up to 1.21.4, and a third reads back wrong on another runtime:

- **`BigInteger`.** Its formatter writes `temp.Slice(written)` of a 255-byte stack buffer where `temp.Slice(0, written)` is meant: the unused end of the buffer instead of the value. Any `BigInteger` of up to 255 bytes, `3^10` included, reads back as another value (0 in 1.22.0), on every runtime; larger values take another path and round-trip.
- **`BitArray` on .NET 10, up to 1.21.4.** Its formatter reinterpreted a `BitArray` as `{ int[] m_array; int m_length }`, its layout on .NET 8. .NET 10's `BitArray` holds a `byte[] _array` instead, so MemoryPack wrote the wrong bytes and reading one corrupted the heap and crashed the process. 1.22.0 writes it through its public API, and the benchmarks time both libraries.

- **Tuples of unmanaged items between runtimes.** MemoryPack copies an unmanaged value, `(int, long)` included, as its memory. `ValueTuple` is `LayoutKind.Auto`: CoreCLR puts the `long` first, Mono lays the items out in order. So `(1, 2L)` written on .NET (`02000000 00000000 01000000 00000000`, the last four bytes padding) reads back as `(2, 1)` on Mono (measured with Mono 6.8), and so in Unity, whose Mono and IL2CPP backends both lay tuples out that way; padding bytes go out as whatever was in memory. The benchmark's list of `(int, long)` round-trips on .NET alone.

Nino writes a `BigInteger` as its two's-complement bytes, a `BitArray` through its public API, and a tuple as its items in declaration order with no padding (`(int, long)` is 12 bytes), so none depends on the runtime's private layout. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types) and [Portable by Design](/en/docs/v4/platforms#portable-by-design).
