[MemoryPack](https://github.com/Cysharp/MemoryPack) is an excellent serializer and the one we measure Nino against. This page compares Nino v4 with MemoryPack **1.21.4**, using MemoryPack's own README for its features and Nino's source for Nino's. Where we could not verify a feature on either side, it is left out. For the formats other languages read, see [Nino vs MessagePack](/en/docs/v4/vs-messagepack) and [Nino vs protobuf-net](/en/docs/v4/vs-protobuf-net).

## Untrusted Input [#untrusted-input]

MemoryPack's README now opens with a warning: it is "a high-performance serialization format for trusted data only", "we no longer recommend using MemoryPack where the input can come from an untrusted party, such as public network endpoints or user-supplied files", and its features for cross-boundary communication, the TypeScript code generator among them, "will be removed in the next MemoryPack release" ([MemoryPack README](https://github.com/Cysharp/MemoryPack#readme)).

Nino reads untrusted data by design, and the fast paths keep these guarantees:

- **No type names in the data.** A value is one of the declared type's registered subtypes, chosen by a type id, and a back reference must point to an object already read, of the slot's type. `System.Type` is not serializable, so data can never name a type to create.
- **Lengths checked before allocating.** Every count is checked against the bytes left, and a collection allocates ahead of its elements at most 16 times the bytes left in the input: a few bytes cannot claim gigabytes.
- **A bounded stack.** Deeply nested data is read from a shallow level or stops at `NinoSettings.MaxDepth` (512 levels by default), with the stack checked on the way: it throws instead of overflowing the stack, which would end the process.
- **No hash flooding.** A key that finds more than `NinoSettings.MaxHashCollisions` keys in its hash bucket throws, so crafted keys cannot make filling a dictionary or set quadratic; `NinoSettings.Untrusted` also hashes integer, `char`, `Guid` and `string` keys with a per-process secret.
- **One exception.** Every invalid input throws a `NinoDataException` (an `InvalidOperationException`) whose message starts with `Nino:`, including values their own type rejects, so one `catch` at the boundary handles all of it; [Nino.AspNetCore](/en/docs/v4/advanced/aspnetcore) answers it with 400.

We checked these against fuzzed and hand-crafted payloads for every built-in type and every way of declaring one, and fixed what they found in 4.0.0-rc.7. What stays the application's job (the values themselves, the size of a message, versioning) is in [Untrusted Data](/en/docs/v4/security#what-stays-your-job). Nino.Codegen's TypeScript, Go and Rust readers and Nino.AspNetCore, which carry Nino data across that boundary, stay.

### Padded Structs and Tuples [#padded-values]

Two cases of the [common types and collections](/en/docs/v4/benchmarks#common-types-and-collections) hold values with padding in memory: `InventoryItem[1000]` (an `int`, a `short` and a `bool`: 7 bytes of members in 8) and `List<(int, long)>` (12 bytes of items in 16 on x64, where .NET puts the `long` first). MemoryPack copies their memory as it is, padding included. Nino defines the bytes instead. It writes an `InventoryItem` in its 8 bytes with the padding byte set to zero, a masked copy where MemoryPack makes a plain one, which is the extra work in Nino's time for that case. It writes a `(int, long)` as its two items, 12 bytes where MemoryPack writes 16, which is the difference in their payload sizes.

Copying the padding costs more than size:

- **The padding is whatever the memory held.** Equal values can serialize to different bytes, and stale memory goes out with them. In a test with MemoryPack 1.21.4, two `InventoryItem[2]` with equal values, one of them built in a buffer that had held `0xCD` bytes, serialized to different bytes, with `CD` in each padding byte; a `List<(int, long)>` built the same way carried `CDCDCDCD` after every item. Nino wrote the same bytes for both, padding zero.
- **The layout is the platform's.** `(int, long)` is 12 bytes in memory on 32-bit x86 .NET for Windows, and 16 on x64 and Arm32 (.NET 10's layout for each target, read from the code crossgen2 compiles for it), so a copy of its memory has another size there. On Mono the items are also in another order: see [MemoryPack Bugs Found While Benchmarking](#memorypack-bugs-found-while-benchmarking).

Nino's bytes are the same on every platform: [raw values](/en/docs/v4/wire-format#raw-values) in the 64-bit layout with zeroed padding, tuples item by item.

## Where MemoryPack Is Ahead

To put it plainly, MemoryPack does these things and Nino v4 does not:

- **`Type` values.** MemoryPack serializes `System.Type`; Nino does not, on purpose: data that names the types to create is a well-known deserialization attack. Every other built-in type MemoryPack lists (`BigInteger`, `Uri`, `Lazy<T>`, `Memory<T>`, `ILookup<,>`, every immutable collection...) is [built into Nino too](/en/docs/v4/types#other-built-in-types) since 4.0.0-rc.5, and so are the Unity classes of `MemoryPack.Unity` (`AnimationCurve`, `Gradient`, `RectOffset`; see [Unity Classes](/en/docs/v4/advanced/unity#unity-classes)). *Workaround:* store a type id or name of your own and map it to the types you allow.
- **Dependency injection and options.** MemoryPack passes `MemoryPackSerializerOptions` (string encoding, an `IServiceProvider`) through every call. Nino has no per-call options: its settings are either process-wide (`NinoSettings`) or per-type attributes.

Compression is not on this list: it takes a few lines on top of Nino's buffer and span APIs ([Compression](/en/docs/v4/advanced/streams#compression)). Streams, async I/O and serialization callbacks are built in.

## Where Nino Is Ahead

- **Untrusted input**: Nino is built to read data from network peers and user files (see [Untrusted Input](#untrusted-input)); MemoryPack is now for trusted data only.
- **Speed**: up to <BenchValue k="serialize.max" /> faster serialization and up to <BenchValue k="deserialize.max" /> faster deserialization of classes and polymorphic graphs, with the numbers above.
- **Zero-allocation reuse**: reuse deserialization that fills nested objects, lists and dictionaries in place, `[NinoPooled]` pools, and a recycler for every dropped instance.
- **Data that changes**: keyed members can be reordered, removed and inserted in any class of a hierarchy, with no order numbers to maintain; old code reads new data in both keyed and version-tolerant types; and a [layout baseline](/en/docs/v4/evolving-data#layout-baseline) reports, as you type, a change that would break the data you already wrote (NINO034).
- **Polymorphism without bookkeeping**: no tags, any non-sealed class can be a base, generic bases (`Box<T>`, `IRepository<T>`) included, and subtypes in other assemblies and hot-update DLLs are found automatically. MemoryPack's union attribute cannot be put on a generic type: each closed type needs a union formatter registered by hand (see the [generic base benchmark](/en/docs/v4/benchmarks#more-cases)).
- **Portable, deterministic bytes**: identical on CoreCLR, Mono and IL2CPP, 64-bit and 32-bit, with padding zeroed.
- **Wider reach**: `netstandard2.0`, OpenUPM for Unity, HybridCLR without init calls.
- **Build time**: one generated file per type and a truly incremental generator.
- **TypeScript from the layouts**: [Nino.Codegen](/en/docs/v4/advanced/codegen) runs after the build and reads the same layouts the C# formatters are generated from, so structs, `char`, `decimal`, 64-bit enums, keyed and version-tolerant types are covered and the runtime is updated with the package. MemoryPack writes its TypeScript from inside the source generator, for classes only, and will remove it in its next release; see the [comparison](/en/docs/v4/advanced/typescript#compared-with-memorypack).

## Switching from MemoryPack [#switching-from-memorypack]

Most of a MemoryPack codebase maps one to one:

| MemoryPack | Nino |
| --- | --- |
| `[MemoryPackable] partial class` | `[NinoType] class`; `partial` only for [non-public members](/en/docs/v4/defining-types#private-members) before .NET 8 and for `[NinoPooled]` |
| `[MemoryPackIgnore]` | `[NinoIgnore]` |
| `[MemoryPackInclude]` on a non-public member | `[NinoType(includeNonPublicMembers: true)]` for every non-public member, or `[NinoType(false, true)]` with `[NinoMember(index)]` on each member to write |
| `[MemoryPackOrder(n)]` | `[NinoType(false)]` with `[NinoMember(n)]` |
| `[MemoryPackConstructor]` | `[NinoConstructor]` ([Constructors](/en/docs/v4/constructors)) |
| `[MemoryPackUnion(tag, typeof(T))]` on the base | `[NinoType]` on the base: subtypes inherit it, with no tags ([Polymorphism](/en/docs/v4/polymorphism)) |
| `GenerateType.VersionTolerant` | `format: NinoFormat.Keyed` (members by name, no order numbers), or `NinoFormat.VersionTolerant` for types that only grow ([Evolving Your Data](/en/docs/v4/evolving-data)) |
| `GenerateType.CircularReference` | `trackReferences: true` ([Reference Tracking](/en/docs/v4/reference-tracking)) |
| `GenerateType.Collection` | nothing: [your own collections](/en/docs/v4/types#user-collections) work as they are |
| `[MemoryPackOnSerializing]`, `[MemoryPackOnSerialized]`, `[MemoryPackOnDeserializing]`, `[MemoryPackOnDeserialized]` | `[NinoOnSerializing]`, `[NinoOnSerialized]`, `[NinoOnDeserializing]`, `[NinoOnDeserialized]`: methods without parameters, `public` or `internal`, and instance methods except a static `[NinoOnDeserializing]` ([Callbacks](/en/docs/v4/defining-types#callbacks)) |
| `MemoryPackSerializer.Serialize(value)` | `NinoSerializer.Serialize(value)` |
| `MemoryPackSerializer.Serialize(bufferWriter, value)` | `NinoSerializer.Serialize(value, bufferWriter)`: the value comes first |
| `MemoryPackSerializer.Deserialize<T>(bytes)`, `Deserialize(bytes, ref value)` | `NinoDeserializer.Deserialize<T>(bytes)`, `Deserialize(bytes, ref value)` |
| `SerializeAsync(stream, value)`, `DeserializeAsync<T>(stream)` | `NinoSerializer.SerializeAsync(value, stream)`, `NinoDeserializer.DeserializeAsync<T>(stream)`: the value comes first; `Serialize(value, stream)` and `Deserialize<T>(stream)` are their synchronous forms ([Streams](/en/docs/v4/advanced/streams#streams)) |
| UTF-8 strings | one byte a char up to U+00FF, else UTF-16; `[NinoUtf8]` per member ([String Encoding](/en/docs/v4/defining-types#string-encoding)) |

The two libraries write different bytes, so stored data has to be converted. Both can be installed in one project: keep both attributes on your types while you convert, read each stored value with MemoryPack and write it again with Nino, then remove MemoryPack. Mark the converted data with a [file header](/en/docs/v4/advanced/persistence#add-a-file-header) so that a later build knows which reader it needs. Messages between processes need no conversion: upgrade both ends together.

```csharp title="Messages.cs"
using MemoryPack;
using Nino.Core;

[MemoryPackable]
[MemoryPackUnion(0, typeof(Ping))]
[MemoryPackUnion(1, typeof(Chat))]
[NinoType]                       // [!code ++]
public partial interface IMessage { }

[MemoryPackable]
public sealed partial class Ping : IMessage
{
    public long SentAt { get; set; }
}

[MemoryPackable]
public sealed partial class Chat : IMessage
{
    public string Text { get; set; }
    [MemoryPackIgnore, NinoIgnore]   public int Cached;
}
```

```csharp
using MemoryPack;

byte[] old = MemoryPackSerializer.Serialize<IMessage>(new Chat { Text = "hi" });
IMessage message = MemoryPackSerializer.Deserialize<IMessage>(old); // what MemoryPack stored
byte[] bytes = NinoSerializer.Serialize(message);                   // written again with Nino
IMessage back = NinoDeserializer.Deserialize<IMessage>(bytes);      // a Chat
```

## Type Ids and Union Tags

MemoryPack writes a 1-byte union tag (3 bytes above 249) where Nino writes a 4-byte type id. This is a deliberate trade-off:

- Nino derives the id from the type itself (an FNV-1a hash of its name), so subtypes need no tags. They can live in any assembly (a plugin, a HybridCLR hot update, a library that extends your base class), and ids never renumber when subtypes are added or removed.
- MemoryPack lists every subtype on the base with `[MemoryPackUnion(tag, type)]`, or registers them by hand with a union formatter, and you have to keep the tags stable yourself.

The cost is 3 more bytes per polymorphic value. See [Polymorphism](/en/docs/v4/polymorphism).

## MemoryPack Bugs Found While Benchmarking

Comparing every built-in type both libraries share, we round-tripped each value through MemoryPack 1.21.4 before timing it. Two types fail, so the benchmarks time them for Nino only, and a third reads back wrong on another runtime:

- **`BigInteger`.** Its formatter writes `temp.Slice(written)` of a 255-byte stack buffer where `temp.Slice(0, written)` is meant: the unused end of the buffer instead of the value. Any `BigInteger` of up to 255 bytes, `3^10` included, reads back as another value, on every runtime; larger values take another path and round-trip.
- **`BitArray` on .NET 10.** Its formatter reinterprets a `BitArray` as `{ int[] m_array; int m_length }`, its layout on .NET 8. .NET 10's `BitArray` holds a `byte[] _array` instead, so MemoryPack writes the wrong bytes and reading one corrupts the heap and crashes the process.

- **Tuples of unmanaged items between runtimes.** MemoryPack copies an unmanaged value, `(int, long)` included, as its memory. `ValueTuple` is `LayoutKind.Auto`: CoreCLR puts the `long` first, Mono lays the items out in order. So `(1, 2L)` written on .NET (`02000000 00000000 01000000 00000000`, the last four bytes padding) reads back as `(2, 1)` on Mono (measured with Mono 6.8), and so in Unity, whose Mono and IL2CPP backends both lay tuples out that way; padding bytes go out as whatever was in memory. The benchmark's list of `(int, long)` round-trips on .NET alone.

Nino writes a `BigInteger` as its two's-complement bytes, a `BitArray` through its public API, and a tuple as its items in declaration order with no padding (`(int, long)` is 12 bytes), so none depends on the runtime's private layout. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types) and [Portable by Design](/en/docs/v4/platforms#portable-by-design).
