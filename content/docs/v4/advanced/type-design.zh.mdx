在[高性能序列化](/zh/docs/v4/advanced/high-performance)里，每次调用已经做到了 0 B：复用缓冲区、直接读已有的内存、复用反序列化和对象池。剩下每次调用还要做多少事，由你的类型决定：结构体能不能整块拷贝，类型写哪种格式，类要不要写类型 ID，成员声明成哪种集合。这一页逐一讲这些选择，各自的开销，以及热路径上该怎么声明。两页的所有手段都列在[手段一览](/zh/docs/v4/advanced/high-performance#levers)里。

## 批量数据保持原始内存格式 [#keep-bulk-data-raw]

非托管数据会按原始内存整块拷贝：

```csharp
[NinoType]
public struct Sample            // 非托管、顺序布局：按原始内存写出
{
    public long Timestamp;
    public double Value;
    public int SensorId;
}

[NinoType]
public sealed class SampleBlock
{
    public long SeriesId;
    public Sample[] Samples;    // 整个数组一次整块复制
}
```

- 非托管元素的数组和 `List<T>` 只需一次拷贝。
- 含有 `string` 或数组的结构体不能按原始内存写入；如果这个结构体处在热路径上，把这些字段挪到单独的类里。
- `NinoFormat.VersionTolerant`、`NinoFormat.Keyed` 和自定义成员格式化器都会关闭该结构体的原始内存拷贝。
- 只由非托管成员组成的结构体或密封类是[固定大小的](/zh/docs/v4/performance#fixed-size-types)：`NinoSerializer.Serialize(value)` 会把它直接写进大小正好的 `byte[]`，不经过暂存缓冲区，也没有拷贝。固定大小的记录还可以在文件或共享内存中按下标定位：见[固定大小的记录](/zh/docs/v4/advanced/zero-allocation#fixed-size-records)。

**热路径上的结构体布局不留填充。** 没有填充的结构体是一次普通的块拷贝；有填充的结构体要经过一个把空隙清零的掩码拷贝，开销稍高；声明为 `[StructLayout(LayoutKind.Auto)]` 的结构体根本不按原始内存拷贝，而是逐个字段写入。把字段按从大到小排列，或设置 `Pack`，就能去掉填充。两者都会改变字节，所以要在保存数据之前定好布局。参见[结构体布局](/zh/docs/v4/performance#struct-layout)。

### 确定性的字节 [#deterministic-bytes]

Nino 会把填充字节清零，所以相等的值总是产生相同的字节，即使结构体是在未初始化的内存中构造的（`stackalloc`、`SkipLocalsInit`）。因此可以直接对数据做哈希或比较，例如跳过发送没有变化的状态：

```csharp
buffer.ResetWrittenCount();
NinoSerializer.Serialize(state, buffer);
ulong hash = XxHash64.HashToUInt64(buffer.WrittenSpan); // System.IO.Hashing
if (hash != lastHash) { Send(buffer.WrittenSpan); lastHash = hash; }
```

## 选择开销最小的格式 [#choose-the-cheapest-format]

每个 `[NinoType]` 都要选定自己的[格式](/zh/docs/v4/evolving-data)，以及是否追踪引用。默认之外的每个选项，都会让这个类型的每个值多花字节和时间，所以只给真正需要的类型使用：

| 选项 | 额外字节 | 额外工作 |
| --- | --- | --- |
| 按位置（只写 `[NinoType]`） | 无 | 无：原始结构体按内存拷贝，[固定大小的类型](/zh/docs/v4/performance#fixed-size-types)直接写进它的 `byte[]` |
| `format: NinoFormat.VersionTolerant` | 每个对象 4 字节 | 每个对象一个长度；该类型不再按原始内存拷贝，也不再是固定大小 |
| `format: NinoFormat.Keyed` | 每个成员 8 字节，外加每个对象 4 字节 | 每个成员一个键和一个长度，读取时每个成员要检查一次键；该类型不再按原始内存拷贝，也不再是固定大小 |
| `trackReferences: true` | 每个被追踪的对象 4 字节 | 每个被追踪的对象一次身份查找，外加每次顶层调用一点固定开销 |

- 由同一版本写入和读取的消息和缓存保持按位置格式；只有要跨版本保留的数据才用版本容错或键控成员，参见[如何选择](/zh/docs/v4/evolving-data#choosing)。
- 只给真正被共享、或者构成环的类型开启引用追踪：在[组织结构图](/zh/docs/v4/reference-tracking)的例子里，只有 `Department` 被追踪，`Employee` 不付出任何开销。树形数据不论多深都不需要追踪。

## 密封类，以及通过基类分派 [#sealed-and-polymorphic]

Nino 在类的值前面写什么，取决于存放它的位置的声明类型（参见[多态值如何写入](/zh/docs/v4/polymorphism#how-a-polymorphic-value-is-written)）：

- **没有子类型的类声明为 `sealed`。** 密封类只需一个存在字节，无需分派；未密封的类即使没有任何子类型，也要写 4 字节的类型 ID 并做一次类型检查。
- **通过共同的 `[NinoType]` 基类分派。** 对于与基类声明在同一程序集中的子类型，生成的代码写入时依次做精确的类型检查，读取时按类型 ID `switch`，直接调用各子类型的格式化器。来自其他程序集的子类型、泛型子类型、开启引用追踪的类型，以及子类型超过 64 个的层次结构的写入，则改走无锁的注册表（参见[分派](/zh/docs/v4/polymorphism#dispatch)）。
- **热路径上不要用 `object` 和装箱 API。** 声明为 `object` 的位置要通过包含所有 `[NinoType]` 的全局注册表分派；`SerializeBoxed`/`DeserializeBoxed` 按 `Type` 查找格式化器，还要对值类型装箱（参见[运行时类型](/zh/docs/v4/basic#runtime-types)）。

## 选择能整块拷贝的集合 [#collections]

- **批量数据放进原始元素的数组和列表。** 非托管值或原始结构体的 `T[]`、`List<T>` 只需一次整块拷贝；元素全是原始值的值元组和 `KeyValuePair` 的数组和列表也一样（CPU 支持时用 [SIMD](/zh/docs/v4/simd#dotnet) 重排）。完整列表见[非托管数据按原始内存拷贝](/zh/docs/v4/performance#raw-memory-for-unmanaged-data)。
- **数量会变化时用 `List<T>`。** 复用反序列化会原地填充列表并保留它的容量；数组只有在新数据长度相同时才会被复用。字典按键合并。
- **声明你希望创建的类型。** 声明为 `IList<T>`、`IEnumerable<T>` 或 `IReadOnlyList<T>` 的成员读回来是 `List<T>`，`ISet<T>` 读回来是 `HashSet<T>`，`IDictionary<TKey, TValue>` 读回来是 `Dictionary<TKey, TValue>`（参见[集合类型](/zh/docs/v4/types#collection-types)）。可空原始元素只有放在数组或 `List<T?>` 中才整块写入；声明为接口时，每个元素单独写入。
- **集合是值。** 同一个集合出现在两个成员中会被写两次；引用追踪只覆盖 `[NinoType]` 类，不覆盖集合。

## 字符串 [#strings]

- 默认编码下，所有字符都不超过 U+00FF 的文本每个字符写一个字节，其他文本按 UTF-16 写出，都只需一遍。`[NinoUtf8]` 要做转码，还要多写字节数（UTF-8 不超过 127 字节时占 1 字节），只有以 ASCII 为主、夹杂少量更宽字符的文本才划算（参见[字符串编码](/zh/docs/v4/defining-types#string-encoding)）。
- 复用反序列化会保留内容没有变化的字符串，所以稳定的文本（名称、键、类似枚举的代码）每条消息不产生任何开销；`[NinoUtf8]` 字符串只有在内容是 ASCII 时才会保留。

## 热路径上的自定义格式化器 [#custom-formatters]

[自定义格式化器](/zh/docs/v4/custom-formatters)是一个结构体，Nino 直接调用它，JIT 会把它内联，和生成的格式化器一样。让它也走同样的快速路径：

- **连续的非托管数据整块拷贝**：`Writer.Write<T>(ReadOnlySpan<T>)` 一次拷贝写出长度和全部元素；`WriteUnmanagedRaw` / `ReadUnmanagedRaw` 不带长度，直接读写你已有的内存。泛型格式化器的元素参数标上 `[NinoRaw]`，它就只会绑定到 Nino 按原始字节拷贝的类型（[示例](/zh/docs/v4/custom-formatters#example-grid)）。
- **读入当前的值。** `Deserialize(ref Reader reader, ref T value)` 收到的是调用方持有的实例：结构合适时就填充它，并用 `reader.ReadString(current)` 保留它的字符串，文本没变时它直接返回 `current` 本身。这样复用反序列化经过你的类型时仍然是 0 B。
- **分配之前先检查长度**：用 `ReadLength(minElementSize)`，剩余字节容纳不下那么多元素时它会抛出异常。
- **开销：** 成员上的 `[NinoMemberFormatter]` 会让它所在的类型不再按原始内存拷贝，也不再是固定大小。热点结构体尽量使用内置的成员类型。

`Writer` 和 `Reader` 提供的方法见 [Writer 与 Reader](/zh/docs/v4/custom-formatters#writer-and-reader)。

## 散落在内存中的大型集合 [#large-collections]

类的 `T[]` 或 `List<T>` 中，每个元素都是堆上单独的对象。集合的顺序与对象分配的顺序一致时，CPU 的硬件预取器会在循环用到之前取来后面的对象；一旦对象在创建后被替换、打乱或排序，每个元素都是硬件无法预测的缓存未命中，集合比缓存大时，循环大部分时间都在等内存。

在发起调用的项目中设置 MSBuild 属性 `NinoPrefetchLargeCollections`，Nino 就会自己提前取这些对象（软件预取）：

```xml title="MyApp.csproj"
<PropertyGroup>
  <NinoPrefetchLargeCollections>true</NinoPrefetchLargeCollections>
</PropertyGroup>
```

设置后，以下调用会预取：

- `NinoSerializer.Serialize(collection)`（带或不带 `IBufferWriter<byte>`），以及 `NinoDeserializer.Deserialize(bytes, ref collection)` 读入元素个数相同的现有集合（其中的对象被复用，所以读入的正是这些散落的对象）；
- 其中 `collection` 是非泛型 `[NinoType]` 类（包括抽象基类）的 `T[]` 或 `List<T>`，且该类不是[固定大小](/zh/docs/v4/performance#fixed-size-types)的；集合被直接写入或读取（而不是作为其他类型的成员），并且调用经由[拦截器](/zh/docs/v4/advanced/high-performance#per-call-overhead)转发（项目用 .NET 8 SDK 或更高版本构建），运行在 x64 或 Arm64 上的 .NET 8 或更高版本；
- 并且只在集合大于 CPU 末级缓存的四分之一、且前几个对象不是按分配顺序排列时。其他集合的读写与之前完全相同。

无论设置与否，字节一致。热路径会序列化这类集合时再设置，并用你自己的数据[测量](/zh/docs/v4/advanced/high-performance#measure)：放得进缓存的集合，或对象仍按分配顺序排列的集合，不会更快。Unity 项目不受影响：Unity 使用生成器的 Roslyn 4.3 版本编译，没有拦截器，这个属性在 Unity 中不起作用。

**代价：** 不设置（默认）时没有任何代价：生成的代码与之前完全相同。设置后，这类集合的每次顶层调用都会在循环前判断长度，在我们的基准测试中，短集合的调用因此慢了几个百分点，所以只在处理这类集合的项目中设置。
