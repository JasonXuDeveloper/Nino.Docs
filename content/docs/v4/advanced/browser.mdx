A browser reads and writes Nino's bytes in one of two forms: **generated TypeScript**, the recommended way for every TypeScript or JavaScript front end, or **.NET itself** on WebAssembly, for apps that already are .NET (Blazor WebAssembly) and for the rare front end that needs a member the TypeScript leaves out. This page covers the two .NET forms; pick your way first.

## Which Way to Take [#which-way]

| Your browser code | Use | What it costs |
| --- | --- | --- |
| TypeScript or JavaScript (React, Vue, Angular, plain pages), or Node | **Generated TypeScript**, the recommended way: [TypeScript](/en/docs/v4/advanced/typescript) | no .NET runtime: plain TypeScript classes and codecs, and a runtime of one file |
| A Blazor WebAssembly app, or other .NET code already running in the browser | **Nino as in any .NET project**: [Blazor WebAssembly](#blazor) | Nino.Core's own assembly: the app already loads .NET |
| TypeScript or JavaScript that needs a member the TypeScript leaves out (`DateTimeOffset`, multi-dimensional arrays, custom formatters: [What TypeScript Leaves Out](/en/docs/v4/advanced/typescript#not-supported)) | **A .NET module called through `[JSExport]`**: [A .NET Module for JavaScript](#jsexport) | the browser downloads the .NET runtime ([Trade-Offs](#trade-offs)) |

Data that people read, or a public API for teams outside .NET, may fit JSON better: [When Not to Use It](/en/docs/v4#when-not-to-use-it).

## Put the Types in a Shared Project [#put-the-types-in-a-shared-project]

Both .NET forms start here.

Declare the types once, in a class library (`net10.0` here) that both the server and the browser app reference, and add Nino to it (for a Unity client, target `netstandard2.1` instead: see [Sharing Types with a .NET Server](/en/docs/v4/advanced/unity#shared-types)):

```shell
dotnet new classlib -n Shop.Contracts -f net10.0
dotnet add Shop.Contracts package Nino --prerelease
```

```csharp title="Shop.Contracts/Order.cs"
using System.Collections.Generic;
using Nino.Core;

namespace Shop.Contracts;

[NinoType(format: NinoFormat.VersionTolerant)] // browser and server may update at different times
public class Order
{
    public long Id;
    public string Customer;
    public List<OrderLine> Lines;
}

[NinoType]
public struct OrderLine
{
    public int ProductId;
    public int Quantity;
    public double UnitPrice;
}
```

Pages already open keep running the old code, a module or a Blazor app, until they reload, so choose a format that tolerates changes for anything they exchange with the server; see [Evolving Your Data](/en/docs/v4/evolving-data).

<Callout type="info">

Nino's [interceptors](/en/docs/v4/performance#interceptors) work in the browser with the usual rule: calls on `[NinoType]`s declared in another assembly, such as `Shop.Contracts` here, are not intercepted and go through the formatter cache, as on the server. Declare the types in the browser project itself (or link the same source file into it) if you want those calls intercepted.

</Callout>

## Blazor WebAssembly [#blazor]

A Blazor WebAssembly app is .NET, so Nino works in it as on the server: reference the shared project from the Blazor project and call `NinoSerializer` and `NinoDeserializer` directly. There is no `[JSExport]` layer and no generated TypeScript.

```shell
dotnet add Shop.Client reference Shop.Contracts/Shop.Contracts.csproj
```

What differs from a server:

| | In Blazor WebAssembly |
| --- | --- |
| HTTP | `HttpClient` goes through the browser's `fetch`; send and read bodies as any .NET client does ([Clients](/en/docs/v4/advanced/aspnetcore#clients)). Nino.AspNetCore stays on the server: it depends on ASP.NET Core. |
| SIMD | the net10.0 build of Nino.Core uses WebAssembly SIMD where the runtime has it ([SIMD](/en/docs/v4/simd#dotnet)); every path writes the same bytes |
| Publishing | trimmed, as Blazor publishes: Nino adds no trimming warnings and one assembly to `_framework` ([Trade-Offs](#trade-offs)) |

## A .NET Module for JavaScript [#jsexport]

When a TypeScript or JavaScript front end needs what the generated TypeScript leaves out, run the C# types themselves: a small .NET `browser-wasm` app that references Nino and the shared project, a few functions exposed with `[JSExport]`, called from your front end. The browser then runs the same types and generated formatters as the server, so every member type works and the bytes are the same; JavaScript sees only `Uint8Array`s, numbers, strings and arrays. The price is the .NET runtime's download and start ([Trade-Offs](#trade-offs)).

Every snippet comes from a project built with the .NET 10 SDK and run in headless Chromium. In it, an order serialized in the browser was byte for byte equal to the same order serialized by a .NET 10 console app, and the browser decoded bytes from the console app and from an ASP.NET Core endpoint.

<Steps>
<Step>

### Create the browser project

A `browser-wasm` app is an ordinary project on the `Microsoft.NET.Sdk.WebAssembly` SDK:

```xml title="Shop.Browser/Shop.Browser.csproj"
<Project Sdk="Microsoft.NET.Sdk.WebAssembly">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <OutputType>Exe</OutputType>
    <AllowUnsafeBlocks>true</AllowUnsafeBlocks> <!-- [!code highlight] -->
    <InvariantGlobalization>true</InvariantGlobalization>
  </PropertyGroup>
  <ItemGroup>
    <ProjectReference Include="../Shop.Contracts/Shop.Contracts.csproj" />
  </ItemGroup>
</Project>
```

```csharp title="Shop.Browser/Program.cs"
// The runtime is started from JavaScript; Main has nothing to do.
return;
```

- `AllowUnsafeBlocks` is required by the `[JSExport]` generator (error SYSLIB1075 without it), not by Nino.
- No workload is needed: the project builds and publishes with the plain .NET SDK. The `wasm-tools` workload only matters for AOT compilation or native relinking.
- `InvariantGlobalization` is optional; it drops culture data the codec does not need.

</Step>
<Step>

### Export functions with `[JSExport]`

Write a `static partial class` whose methods JavaScript calls. Keep them coarse: one call per message, with the C# side doing the work.

```csharp title="Shop.Browser/OrderCodec.cs"
using System.Collections.Generic;
using System.Runtime.InteropServices.JavaScript;
using System.Runtime.Versioning;
using Nino.Core;
using Shop.Contracts;

namespace Shop.Browser;

[SupportedOSPlatform("browser")] // silences CA1416 on the interop attributes
public static partial class OrderCodec
{
    // JavaScript values in, Nino bytes out
    [JSExport]
    public static byte[] EncodeOrder(
        [JSMarshalAs<JSType.Number>] long id,
        string customer,
        int[] productIds,
        int[] quantities,
        double[] unitPrices)
    {
        var order = new Order { Id = id, Customer = customer, Lines = new List<OrderLine>(productIds.Length) };
        for (int i = 0; i < productIds.Length; i++)
            order.Lines.Add(new OrderLine { ProductId = productIds[i], Quantity = quantities[i], UnitPrice = unitPrices[i] });
        return NinoSerializer.Serialize(order); // [!code highlight]
    }

    // Nino bytes in, what the UI needs out
    // WebAssembly runs one thread: one Order and its list, refilled in place on every call
    private static Order _order = new();

    [JSExport]
    public static string GetCustomer(byte[] data)
    {
        NinoDeserializer.Deserialize(data, ref _order); // [!code highlight]
        return _order.Customer;
    }

    [JSExport]
    [return: JSMarshalAs<JSType.Number>]
    public static long GetId(byte[] data)
    {
        NinoDeserializer.Deserialize(data, ref _order);
        return _order.Id;
    }

    [JSExport]
    public static double GetTotal(byte[] data)
    {
        NinoDeserializer.Deserialize(data, ref _order);
        double total = 0;
        foreach (OrderLine line in _order.Lines) total += line.Quantity * line.UnitPrice;
        return total;
    }

    [JSExport]
    public static int CountLines(byte[] data)
    {
        NinoDeserializer.Deserialize(data, ref _order);
        return _order.Lines.Count;
    }
}
```

What `[JSExport]` marshals, as used here:

| C# | JavaScript |
| --- | --- |
| `byte[]` | `Uint8Array` (copied across the boundary in each direction) |
| `int[]`, `double[]` | an array of numbers |
| `string`, `int`, `double` | `string`, `number` |
| `long` with `[JSMarshalAs<JSType.Number>]` | `number` (exact up to 2^53) |
| `long` with `[JSMarshalAs<JSType.BigInt>]` | `bigint` |

A `long` must say which of the two it maps to. A `Span<byte>` parameter marked `[JSMarshalAs<JSType.MemoryView>]` does not accept a `Uint8Array` from JavaScript (the call fails with `Expected MemoryViewType.Byte`), so take `byte[]`.

</Step>
<Step>

### Load the module from JavaScript

Add a page and a module script to the project's `wwwroot` folder:

```html title="Shop.Browser/wwwroot/index.html"
<!doctype html>
<html>
  <head>
    <meta charset="utf-8" />
    <script type="module" src="./main.js"></script>
  </head>
  <body></body>
</html>
```

```js title="Shop.Browser/wwwroot/main.js"
import { dotnet } from './_framework/dotnet.js';

const runtime = await dotnet.create();
const exports = await runtime.getAssemblyExports('Shop.Browser.dll');
const codec = exports.Shop.Browser.OrderCodec; // namespace, then class // [!code highlight]

const bytes = codec.EncodeOrder(42, 'Ada', [7, 9], [2, 1], [9.5, 20]); // a Uint8Array
codec.GetTotal(bytes); // 39
```

Exports are reached by namespace and class name: `Shop.Browser.OrderCodec` above.

Publish and serve the output folder with any static web server:

```shell
dotnet publish Shop.Browser -c Release
# serve Shop.Browser/bin/Release/net10.0/publish/wwwroot
```

</Step>
<Step>

### Type the exports in TypeScript

`getAssemblyExports` returns `any`. The exports are your own functions, so write their shape by hand, next to `OrderCodec.cs`, and update it when the C# signatures change:

```ts title="order-codec.d.ts"
export interface OrderCodec {
  EncodeOrder(id: number, customer: string, productIds: number[], quantities: number[], unitPrices: number[]): Uint8Array;
  GetCustomer(data: Uint8Array): string;
  GetId(data: Uint8Array): number;
  GetTotal(data: Uint8Array): number;
  CountLines(data: Uint8Array): number;
}
```

```ts title="main.ts"
import { dotnet } from './_framework/dotnet.js';
import type { OrderCodec } from './order-codec';

const runtime = await dotnet.create();
const exports = await runtime.getAssemblyExports('Shop.Browser.dll');
const codec: OrderCodec = exports.Shop.Browser.OrderCodec;
```

This describes a handful of functions, not your data model: the types themselves stay in C#.

</Step>
</Steps>

### Sending and Receiving [#sending-and-receiving]

The bytes are an ordinary `Uint8Array`, so any browser API that carries binary data works.

With `fetch`, post them as the request body and read the reply as an `ArrayBuffer`:

```js
const reply = await fetch('/orders', {
  method: 'POST',
  headers: { 'Content-Type': 'application/x-nino' },
  body: codec.EncodeOrder(42, 'Ada', [7, 9], [2, 1], [9.5, 20]),
});
const replyBytes = new Uint8Array(await reply.arrayBuffer());
codec.GetCustomer(replyBytes);
```

The server deserializes and answers with the same `Order` type. With [Nino.AspNetCore](/en/docs/v4/advanced/aspnetcore), the endpoint takes the body as a `NinoBody<Order>` and returns a `NinoResults.Ok`, both as `application/x-nino`:

```csharp title="Program.cs (ASP.NET Core)"
app.MapPost("/orders", (NinoBody<Order> order) =>
{
    // ... handle order.Value ...
    return NinoResults.Ok(order.Value);
});
```

With a WebSocket, set `binaryType` to `'arraybuffer'`; each WebSocket message is one Nino payload, so no framing is needed:

```js
const socket = new WebSocket(`wss://${location.host}/ws`);
socket.binaryType = 'arraybuffer';
socket.onopen = () => socket.send(codec.EncodeOrder(7, 'Grace', [1], [3], [2.5]));
socket.onmessage = (e) => {
  const data = new Uint8Array(e.data);
  console.log(codec.GetTotal(data)); // one call, one decode per message
};
```

On the server side, read and write WebSocket messages as in [WebSocket and UDP](/en/docs/v4/advanced/networking#websocket-and-udp).

## Trade-Offs [#trade-offs]

**Download size.** The browser downloads the .NET runtime along with your code; a Blazor app pays this already, and Nino adds the `Nino.Core` row. For the module above, a trimmed Release publish with the .NET 10.0.404 SDK (runtime 10.0.15):

| Files in `_framework` | Uncompressed | Brotli | Gzip |
| --- | --- | --- | --- |
| All (runtime, CoreLib, Nino, app) | 5.18 MB | 1.72 MB | 2.09 MB |
| `Nino.Core` | 352 KB | 179 KB | |
| `dotnet.native.wasm` (the runtime) | 3.00 MB | 0.98 MB | |

`dotnet publish` writes `.br` and `.gz` copies next to each file; configure your host to serve them, and cache `_framework` for a long time (the file names carry content hashes).

**Startup.** Nothing can be encoded or decoded until the runtime has downloaded and started. In the test (headless Chromium, served from localhost), the page went from navigation to its first decoded results in 0.4 to 0.7 s; over a real network the download dominates. Start the runtime as the page loads, not on the first message.

**Crossing the boundary** (the module only). Each call copies its `byte[]` arguments and results between JavaScript and WebAssembly memory. Export a few coarse functions (encode a message, decode the fields a view needs) rather than a getter per member.

**Trimming.** Nino.Core is marked trimmable and AOT-compatible, and the generated code carries the annotations the trimmer needs, so a trimmed publish gives no warnings from Nino. Still check your own types with a Release publish before shipping.
