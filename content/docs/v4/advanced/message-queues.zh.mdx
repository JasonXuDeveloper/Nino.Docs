Kafka、RabbitMQ、Azure Service Bus、NATS 这类消息中间件只管搬运字节，不关心内容。负载交给 Nino：生产者序列化事件，消费者把收到的字节反序列化，负载紧凑，两端读起来都快。自建的事件流（走 socket 或写文件）也一样。

这篇讲它和请求/响应式通信不一样的地方：消息会在主题里留好几天，消费者跑的代码可能比生产者旧，也可能更新，事件量也大。

## 定义事件 [#define-the-events]

一个流里的事件都从同一个基类派生。Nino 随每个值写入它的运行时类型，所以消费者按 `OrderEvent` 读，拿到的就是 `OrderPlaced`，不用自己加类型头：

```csharp title="OrderEvents.cs"
using System;
using System.Collections.Generic;
using Nino.Core;

[NinoType(format: NinoFormat.VersionTolerant)] // 子类型继承 [NinoType] 及其选项
public abstract class OrderEvent
{
    public Guid OrderId;
    public DateTime OccurredAt;
}

public sealed class OrderPlaced : OrderEvent
{
    public long CustomerId;
    public List<OrderLine> Lines;
}

public sealed class OrderShipped : OrderEvent
{
    public string Carrier;
    public string TrackingNumber;
}

public sealed class OrderCancelled : OrderEvent
{
    public string Reason;
}

[NinoType]
public struct OrderLine          // 非托管：按原始内存复制，它的列表整块复制
{
    public int ProductId;
    public int Quantity;
    public decimal UnitPrice;
}
```

```csharp
switch (NinoDeserializer.Deserialize<OrderEvent>(payload))
{
    case OrderPlaced placed:       Reserve(placed); break;
    case OrderShipped shipped:     Notify(shipped); break;
    case OrderCancelled cancelled: Release(cancelled); break;
}
```

类型 ID 是类型全名的哈希：事件改名时要加 [`[NinoFormerName]`](/zh/docs/v4/evolving-data#former-name)，否则主题里的旧消息就读不出来了。见[多态](/zh/docs/v4/polymorphism)。

## Kafka [#kafka]

[Confluent.Kafka](https://github.com/confluentinc/confluent-kafka-dotnet) 要求键和值的类型各配一个序列化器和反序列化器。它的反序列化器拿到的是 `ReadOnlySpan<byte>`，Nino 直接就能读：

```shell
dotnet add package Nino --prerelease
dotnet add package Confluent.Kafka
```

```csharp title="NinoKafkaSerializer.cs"
using System;
using Confluent.Kafka;
using Nino.Core;

public sealed class NinoKafkaSerializer<T> : ISerializer<T>, IDeserializer<T>
{
    public static readonly NinoKafkaSerializer<T> Instance = new();

    public byte[] Serialize(T data, SerializationContext context) => NinoSerializer.Serialize(data);

    public T Deserialize(ReadOnlySpan<byte> data, bool isNull, SerializationContext context) =>
        isNull ? default : NinoDeserializer.Deserialize<T>(data);
}
```

然后照常生产和消费，只有序列化器换成 Nino 的：

```csharp title="OrderStream.cs"
using System;
using System.Threading;
using System.Threading.Tasks;
using Confluent.Kafka;

public sealed class OrderProducer : IDisposable
{
    private readonly IProducer<Guid, OrderEvent> _producer; // 整个进程一个：它是线程安全的

    public OrderProducer(string bootstrapServers) =>
        _producer = new ProducerBuilder<Guid, OrderEvent>(new ProducerConfig { BootstrapServers = bootstrapServers })
            .SetKeySerializer(NinoKafkaSerializer<Guid>.Instance) // [!code highlight]
            .SetValueSerializer(NinoKafkaSerializer<OrderEvent>.Instance) // [!code highlight]
            .Build();

    public Task PublishAsync(OrderEvent evt) =>
        _producer.ProduceAsync("orders", new Message<Guid, OrderEvent> { Key = evt.OrderId, Value = evt });

    public void Dispose()
    {
        _producer.Flush(TimeSpan.FromSeconds(10)); // 发出队列里还没发的消息
        _producer.Dispose();
    }
}

public static class OrderConsumer
{
    public static void Run(string bootstrapServers, Action<OrderEvent> handle, CancellationToken cancel)
    {
        var config = new ConsumerConfig
        {
            BootstrapServers = bootstrapServers,
            GroupId = "order-handlers",
            AutoOffsetReset = AutoOffsetReset.Earliest,
        };
        using var consumer = new ConsumerBuilder<Guid, OrderEvent>(config)
            .SetKeyDeserializer(NinoKafkaSerializer<Guid>.Instance) // [!code highlight]
            .SetValueDeserializer(NinoKafkaSerializer<OrderEvent>.Instance) // [!code highlight]
            .Build();
        consumer.Subscribe("orders");
        try
        {
            while (true)
            {
                ConsumeResult<Guid, OrderEvent> result;
                try
                {
                    result = consumer.Consume(cancel);
                }
                catch (ConsumeException e) when (e.Error.Code is ErrorCode.Local_KeyDeserialization
                                                     or ErrorCode.Local_ValueDeserialization)
                {
                    continue; // 这个版本读不了的消息：跳过（或转到死信主题，e.ConsumerRecord 里有原始字节）
                }
                handle(result.Message.Value);
            }
        }
        catch (OperationCanceledException) { }
        finally
        {
            consumer.Close(); // 立即离开消费组
        }
    }
}
```

Kafka 的 `ISerializer<T>` 必须返回 `byte[]`，所以每条消息都要分配一个数组。`NinoSerializer.Serialize(data)` 先写进当前线程的暂存缓冲区，再把写好的字节原样拷出来，这个数组就是唯一的分配。消费时不用拷贝：反序列化器直接读客户端给的 span。`Guid` 键是原始值：16 字节，读写各一次拷贝。

## 其他消息中间件 [#other-brokers]

其他客户端大多用 `ReadOnlyMemory<byte>` 接收消息体。序列化到复用的 `NinoArrayBufferWriter`，再把 `WrittenMemory` 传进去，你这边每条消息都不分配内存。以 RabbitMQ.Client 7 为例（`dotnet add package RabbitMQ.Client`）：

```csharp title="OrderPublisher.cs"
using System.Threading.Tasks;
using Nino.Core;
using RabbitMQ.Client;

public sealed class OrderPublisher
{
    private readonly IChannel _channel;
    private readonly NinoArrayBufferWriter _buffer = new(1024); // 每个发布者一个

    public OrderPublisher(IChannel channel) => _channel = channel;

    // 每次调用都要 await 完再发下一条：缓冲区是复用的
    public ValueTask PublishAsync(OrderEvent evt) // 不加 async：直接返回客户端的 ValueTask
    {
        _buffer.ResetWrittenCount();
        NinoSerializer.Serialize(evt, _buffer); // [!code highlight]
        return _channel.BasicPublishAsync(exchange: "orders", routingKey: "", body: _buffer.WrittenMemory);
    }
}
```

```csharp title="OrderSubscriber.cs"
using System;
using System.Threading.Tasks;
using Nino.Core;
using RabbitMQ.Client;
using RabbitMQ.Client.Events;

public static class OrderSubscriber
{
    public static async Task StartAsync(IChannel channel, Action<OrderEvent> handle)
    {
        await channel.QueueDeclareAsync("orders", durable: true, exclusive: false, autoDelete: false);
        await channel.QueueBindAsync("orders", exchange: "orders", routingKey: "");

        var consumer = new AsyncEventingBasicConsumer(channel);
        consumer.ReceivedAsync += (_, delivery) =>
        {
            // 消息体的内存只在处理函数内有效：在这里反序列化
            handle(NinoDeserializer.Deserialize<OrderEvent>(delivery.Body.Span)); // [!code highlight]
            return Task.CompletedTask;
        };
        await channel.BasicConsumeAsync("orders", autoAck: true, consumer);
    }
}
```

```csharp title="Program.cs"
using System;
using RabbitMQ.Client;

var factory = new ConnectionFactory { HostName = "localhost" };
await using IConnection connection = await factory.CreateConnectionAsync();
await using IChannel channel = await connection.CreateChannelAsync();
await channel.ExchangeDeclareAsync("orders", ExchangeType.Fanout, durable: true);

await OrderSubscriber.StartAsync(channel, evt => Console.WriteLine($"{evt.GetType().Name} {evt.OrderId}"));
var publisher = new OrderPublisher(channel);
await publisher.PublishAsync(new OrderShipped
{
    OrderId = Guid.NewGuid(), OccurredAt = DateTime.UtcNow, Carrier = "DHL", TrackingNumber = "JD0146",
});
Console.ReadLine(); // 一直消费，直到按下回车
```

- 发布调用完成后（`await` 之后）才能重置缓冲区，因为客户端可能还在读它。多个线程共用的发布者，要么每个线程一个缓冲区，要么加锁。
- Azure Service Bus 也一样：`new ServiceBusMessage(buffer.WrittenMemory)` 直接包住这段内存，不拷贝；收到的消息用 `NinoDeserializer.Deserialize<OrderEvent>(message.Body.ToMemory().Span)` 读。
- 只收 `byte[]` 消息体的客户端，就传 `NinoSerializer.Serialize(evt)`：和 Kafka 一样，一个数组，大小正好是负载的长度。
- 消费端把收到的消息体（`ReadOnlyMemory<byte>.Span` 或数组）直接交给 `NinoDeserializer.Deserialize<T>`，不用先拷贝。如果中间件在处理函数返回后会复用消息体的内存，就在处理函数里反序列化；反序列化的结果不引用输入的字节。

<Callout type="info" title="这些代码测试过什么">

本站每次改动，都会用 Confluent.Kafka 2 和 RabbitMQ.Client 7 编译本页的 C# 代码。Nino 这一侧（`NinoKafkaSerializer`、发布者的缓冲区、下面的批量读写）在不连中间件的测试里实际跑过；和中间件的连接（`BootstrapServers`、`ConnectionFactory`、队列和交换机）没有跑过，这些设置请对照所用中间件的文档核对。

</Callout>

## 批量发送 [#batching]

小事件（一次点击、一次价格变动、一个指标）往往攒成一批发更划算：一条消息、一次网络往返、一个消息头。先写数量，再把事件一个接一个写进复用的缓冲区（写一批不分配内存），然后像上面那样发送 `buffer.WrittenMemory`：

```csharp title="EventBatch.cs"
using System;
using System.Collections.Generic;
using Nino.Core;

public static class EventBatch
{
    public static void Write(NinoArrayBufferWriter buffer, IReadOnlyList<OrderEvent> events)
    {
        buffer.ResetWrittenCount();
        var writer = new Writer(buffer);
        writer.WriteLength(events.Count);
        for (int i = 0; i < events.Count; i++)
            NinoSerializer.Serialize(events[i], ref writer); // [!code highlight]
        writer.Flush();
        writer.ReleaseReferences(); // 结束这次调用，和 NinoSerializer 一样
    }

    public static void Read(ReadOnlySpan<byte> payload, Action<OrderEvent> handle)
    {
        var reader = new Reader(payload);
        int count = reader.ReadLength(minElementSize: 4); // 每个事件以 4 字节的类型 ID 开头
        for (int i = 0; i < count; i++)
            handle(NinoDeserializer.Deserialize<OrderEvent>(ref reader));
        reader.ReleaseReferences();
    }
}
```

- 每个事件保留自己的类型，同一批里可以混着 `OrderPlaced` 和 `OrderShipped`。
- 数量超出负载能装下的范围时，`ReadLength(minElementSize: 4)` 直接拒绝，损坏的批次在进循环之前就抛异常。
- 写入器和读取器最后都调用 `ReleaseReferences`，和 `NinoSerializer` 一样；见[连续写入多个值](/zh/docs/v4/advanced/high-performance#several-values-back-to-back)。

在 `[NinoType]` 类里放一个 `List<OrderEvent>` 成员效果一样，还能顺带放批次级的字段（生产者 ID、序号）。

## 遥测与行情数据流 [#telemetry-and-tick-streams]

指标、链路追踪和行情数据来得又快又多，每条都是又小又扁平的记录。把记录定义成非托管结构体，放进列表发送：

```csharp title="Samples.cs"
using System;
using System.Collections.Generic;
using Nino.Core;

[NinoType]
public struct Sample             // 固定大小，按原始内存复制
{
    public long Timestamp;
    public int SeriesId;
    public float Value;
}

[NinoType]
public sealed class SampleBatch
{
    public string Host;
    public long Sequence;
    public List<Sample> Samples;   // 整块复制；批次之间保留容量
}

public sealed class SampleConsumer
{
    private SampleBatch _batch;     // 每条消息都复用它

    public void OnMessage(ReadOnlySpan<byte> payload)
    {
        NinoDeserializer.Deserialize(payload, ref _batch); // [!code highlight]
        foreach (Sample sample in _batch.Samples)
            Record(sample);
    }
}
```

- 样本列表不管多长，读写都只是**一次整块拷贝**。
- 读入同一个 `SampleBatch` 时，对象本身、列表的底层数组和 `Host` 字符串都会复用（字符串内容不变就原样保留）：同一台主机源源不断发来的批次不分配内存，只有换了主机的批次才会把主机名读成新字符串。
- 要按位置查找的记录（一个文件里一整天的 tick），见[固定大小的记录](/zh/docs/v4/advanced/zero-allocation#fixed-size-records)。

## 比部署活得更久的主题 [#topics-that-outlive-a-deployment]

今天写的消息可能下个月才有人消费，读它的代码在写的时候还不存在；消费者也可能从头重放整个主题。

- 每个事件类型都用 [`NinoFormat.VersionTolerant`](/zh/docs/v4/evolving-data#version-tolerance)（追加字段）或 [`NinoFormat.Keyed`](/zh/docs/v4/evolving-data#keyed-members)（任意修改）。这样消费者会跳过不认识的字段，旧消息里没有的字段保留构造函数或初始化器给的值。
- `NinoFormat.VersionTolerant` 的继承体系里，只往具体的事件类（`OrderPlaced` 等）追加成员，别加到 `OrderEvent` 上：基类追加一个成员，每个子类的成员都会往后挪。基类确实要加成员，就改用 `NinoFormat.Keyed`。见[向基类追加成员](/zh/docs/v4/evolving-data#appending-to-a-base-class)。
- 消费者收到不认识的事件**类型**就读不了：反序列化抛 `NinoDataException`（未知的类型 ID）。先部署消费者，再部署发新事件类型的生产者；或者把新类型放到新主题上。
- 同一次部署内就消费完的消息（几秒内清空的任务队列），用[按位置](/zh/docs/v4/evolving-data#positional)的类型（不带参数的 `[NinoType]`）就行。成员一改，它们的字节就变。
- 给事件所在的程序集提交一份[布局基线](/zh/docs/v4/evolving-data#layout-baseline)：改出主题里已有的消息或还没更新的消费者读不了的改动时，分析器在你敲代码时就会在改动的成员上报出来（NINO034、NINO035），CI 里 `nino-gen layouts --check` 也会失败。

文件里的追加日志（在本地存储上做事件溯源）见[追加日志](/zh/docs/v4/advanced/persistence#append-only-logs)。

## 检查清单 [#checklist]

- [ ] 事件都从同一个 `[NinoType]` 基类派生；改过名的事件带 `[NinoFormerName]`。
- [ ] 长期保留的主题上，事件类型用 `NinoFormat.VersionTolerant` 或 `NinoFormat.Keyed`，并提交了布局基线。
- [ ] 新事件类型先部署到消费者，生产者再开始发。
- [ ] 小而频繁的事件批量发送；记录是列表里的非托管结构体。
- [ ] 热点主题上的消费者读入复用的实例。
