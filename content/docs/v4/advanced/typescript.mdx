**Nino.TypeScript** is a build package. After each compile it reads how your `[NinoType]`s are written from the [layout metadata](/en/docs/v4/evolving-data#layout-metadata) of the built assembly and writes two files: `<Assembly>.ts`, with a class per type, an `as const` object per enum and a codec per type, and `nino.ts`, the runtime that reads and writes Nino's format. A browser or Node client then exchanges the same bytes as your .NET code, with no .NET runtime to download.

<Callout type="info">

Nino.TypeScript needs Nino **4.0.0-rc.6** or later: it reads the byte encodings that the generator publishes in the layout metadata since that release.

</Callout>

## How It Works [#how-it-works]

- **From the built assembly.** An MSBuild target runs after `CoreCompile` and starts the `nino-ts` tool in its own process. The tool reads the `[assembly: NinoTypeLayout]` attributes of the assembly and of every assembly it references, without loading them, so the project's target framework does not matter.
- **The same layouts as the formatters.** The generator writes each layout from the same model as the type's formatter, so the TypeScript reads and writes the members in the order, encoding and format the .NET code uses. Nino's tests serialize a sample with every supported kind of member in .NET, read it and write it back in Node and compare the bytes, check that .NET reads values made in TypeScript, and compile the generated code with `tsc --strict`.
- **Quiet on unchanged builds.** Each file is written only when its text changes, so watchers and incremental TypeScript builds see no change, and the tool runs again only when the assembly, its references, the tool or the options change. It does not run in the IDE's design-time builds. A file it wrote before and no longer writes (after renaming the assembly) is deleted.
- **One runtime per version.** `nino.ts` is rewritten whenever the package version changes it, and carries that version in `ninoVersion`.

## Setup [#setup]

<Steps>
<Step>

### Add the package

Add it to the project that declares your `[NinoType]`s, or to a project that references them (a server project): the generated file holds the types of the assembly and of the assemblies it references.

```shell
dotnet add Shop.Contracts package Nino --prerelease
dotnet add Shop.Contracts package Nino.TypeScript --prerelease
```

Nino.TypeScript is a development dependency: `dotnet add package` marks it `PrivateAssets="all"`, it adds nothing to your build output, and projects that reference yours do not inherit it.

```xml title="Shop.Contracts.csproj"
<PackageReference Include="Nino.TypeScript" Version="..." PrivateAssets="all" />
```

</Step>
<Step>

### Build

```shell
dotnet build Shop.Contracts
# nino-ts: Shop.Contracts.ts and nino.ts -> .../Shop.Contracts/ts/
```

The files go to `ts/` next to the project file. Point [`NinoTypeScriptOutput`](#options) at your front end's source folder to write them there instead. Commit them if your front end is built without running `dotnet build` first.

</Step>
<Step>

### Import them

```ts
import { deserialize, serialize } from './ts/nino';
import { Order, OrderCodec } from './ts/Shop.Contracts';
```

The generated code is plain TypeScript: classes, `const` objects and functions, no decorators and no dependencies. It needs a target with `BigInt` (ES2020 or later).

</Step>
</Steps>

### Options [#options]

Set these MSBuild properties in the project file:

| Property | Default | |
| --- | --- | --- |
| `NinoTypeScriptOutput` | `ts/` next to the project file | The folder the two files are written to. |
| `NinoTypeScriptImportExtension` | empty | The extension of the generated file's import of `nino.ts`: empty for bundlers (Vite, webpack, esbuild), `.js` for Node ESM compiled with `tsc`, `.ts` for Deno and Node's type stripping, or `.mjs`, `.mts`. |
| `NinoTypeScriptNames` | `camel` | `camel` writes member names in camelCase (`UnitPrice` → `unitPrice`, `URL` → `url`); `keep` keeps them as in C#. |
| `NinoTypeScriptTargetFramework` | the first one | With several target frameworks, the one whose build writes the files. |
| `NinoTypeScriptEnabled` | `true` | `false` turns it off. |

```xml title="Shop.Contracts.csproj"
<PropertyGroup>
  <NinoTypeScriptOutput>$(MSBuildProjectDirectory)/../web/src/nino/</NinoTypeScriptOutput>
  <NinoTypeScriptImportExtension>.js</NinoTypeScriptImportExtension>
</PropertyGroup>
```

## Example [#example]

The types, declared once in C#:

```csharp title="Shop.Contracts/Order.cs"
using System;
using System.Collections.Generic;
using Nino.Core;

namespace Shop.Contracts;

public enum OrderStatus { Pending, Paid, Shipped }

[NinoType(format: NinoFormat.VersionTolerant)]
public class Order
{
    public long Id;
    public string Customer;
    public OrderStatus Status;
    public DateTime PlacedAt;
    public decimal Total;
    public List<OrderLine> Lines;
}

[NinoType]
public struct OrderLine
{
    public int ProductId;
    public int Quantity;
    public double UnitPrice;
}
```

What the build writes to `ts/Shop.Contracts.ts` (an excerpt; the functions are left out):

```ts title="ts/Shop.Contracts.ts"
export const OrderStatus = {
  Pending: 0,
  Paid: 1,
  Shipped: 2,
} as const;
export type OrderStatus = (typeof OrderStatus)[keyof typeof OrderStatus];

/** `Shop.Contracts.OrderLine`, copied as raw memory (16 bytes). */
export class OrderLine {
  productId: number = 0;
  quantity: number = 0;
  unitPrice: number = 0;
}

/** `Shop.Contracts.Order`. */
export class Order {
  id: bigint = 0n;
  customer: string | null = null;
  status: OrderStatus = 0 as OrderStatus;
  placedAt: Date = new Date(-62135596800000);
  total: string = "0";
  lines: OrderLine[] | null = null;
}

export const OrderCodec: NinoCodec<Order | null> = types.codec<Order>([1504254414]);
export const OrderLineCodec: NinoCodec<OrderLine> = { read: readOrderLine, write: writeOrderLine };
```

Each member starts at the value .NET gives it by default (`0`, `null`, `DateTime.MinValue`). Since `Order` is version tolerant, its reader stops at the end of the members an older version wrote and skips those of a newer one, as in .NET.

Using it:

```ts
import { deserialize, serialize } from './ts/nino';
import { Order, OrderCodec, OrderLine, OrderStatus } from './ts/Shop.Contracts';

const order = new Order();
order.id = 42n;
order.customer = 'Ada';
order.status = OrderStatus.Paid;
order.placedAt = new Date(Date.UTC(2026, 9, 18, 12, 0, 0));
order.total = '39.00';
const line = new OrderLine();
line.productId = 7;
line.quantity = 2;
line.unitPrice = 9.5;
order.lines = [line];

const bytes = serialize(OrderCodec, order);  // what NinoSerializer.Serialize(order) writes in .NET // [!code highlight]
const copy = deserialize(OrderCodec, bytes); // an Order again
```

### With an ASP.NET Core Server [#with-aspnet-core]

With [Nino.AspNetCore](/en/docs/v4/advanced/aspnetcore) on the server, a request and its response are one call each:

```csharp title="Program.cs (ASP.NET Core)"
app.MapPost("/orders", (NinoBody<Order> order) =>
{
    // ... save order.Value ...
    return NinoResults.Ok(order.Value);
});
```

```ts title="orders.ts"
import { deserialize, serialize } from './ts/nino';
import { type Order, OrderCodec } from './ts/Shop.Contracts';

export async function placeOrder(order: Order): Promise<Order | null> {
  const response = await fetch('/orders', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-nino', Accept: 'application/x-nino' },
    body: serialize(OrderCodec, order) as BodyInit, // newer DOM typings want a Uint8Array over an ArrayBuffer
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return deserialize(OrderCodec, new Uint8Array(await response.arrayBuffer()));
}
```

A WebSocket works the same way: send the result of `serialize`, set `binaryType = 'arraybuffer'` and `deserialize(codec, new Uint8Array(event.data))`. Each message is one value, so no framing is needed.

## API [#api]

- **`serialize(codec, value)`** returns a `Uint8Array` with what `NinoSerializer.Serialize<T>` writes in .NET. The bytes are written into one buffer kept between calls and then copied out, so each call allocates only the array it returns. Small results are views into a shared, pooled `ArrayBuffer` (as Node's `Buffer`s are): pass the `Uint8Array` itself to `fetch`, `WebSocket.send`, `Blob` or a stream, which use its `byteOffset` and `length`, and never its `.buffer`. Call `bytes.slice()` when you need an array with a buffer of its own.
- **`deserialize(codec, bytes)`** reads one value from a `Uint8Array` (a Node `Buffer` works too).
- **`XCodec`** for every type `X`: reads and writes the value with the header .NET writes for its declared type. A struct has none (`NinoCodec<X>`), a sealed class a null flag (`NinoCodec<X | null>`), and a class that is not sealed or an interface a type id, so `AnimalCodec` reads and writes any generated subtype of `Animal`, as `Serialize<Animal>` does.
- **`NinoWriter` and `NinoReader`** write several values into one buffer and read them back in order, like `Writer` and `Reader` in .NET: `codec.write(writer, value)`, then `writer.toBytes()`; `codec.read(new NinoReader(bytes))`.
- **`NinoError`** is thrown for data that is not a valid value of the type read (truncated data, a length past the end, an unknown type id) and for values that cannot be written.

<Callout type="warn" title="Create polymorphic values with new">

A value written behind a type id (a member declared as a class that is not sealed, an interface or `object`) is looked up by its constructor, so it must be an instance of a generated class: `new Cat()`, not an object literal shaped like one. A literal throws `NinoError` (`Object is not a type that can be written here`).

</Callout>

## Type Mapping [#type-mapping]

| C# | TypeScript | Notes |
| --- | --- | --- |
| `bool` | `boolean` | |
| `byte`, `sbyte`, `short`, `ushort`, `int`, `uint`, `float`, `double` | `number` | |
| `long`, `ulong`, `nint`, `nuint` | `bigint` | |
| `char` | `string` | one UTF-16 code unit |
| `decimal` | `string` | its exact decimal text, such as `"-12.345"` |
| `Guid` | `string` | read as `xxxxxxxx-xxxx-…`; the `D`, `N` and `B` forms are accepted when writing |
| `DateTime` | `Date` | to the millisecond; the kind is not kept when reading, and a `Date` is written as UTC |
| `TimeSpan` | `bigint` | ticks of 100 ns |
| `string` (also with `[NinoUtf8]`) | `string \| null` | |
| `byte[]` | `Uint8Array \| null` | a copy of the bytes |
| arrays, `List<T>` and other sequences | `T[] \| null` | |
| `HashSet<T>` and other sets | `Set<T> \| null` | |
| `Dictionary<TKey, TValue>` and other dictionaries | `Map<K, V> \| null` | |
| `ValueTuple`, `KeyValuePair` | `[A, B, ...]` | a TypeScript tuple, up to 7 items |
| `Tuple<...>` | `[A, ...] \| null` | |
| `T?`, `Lazy<T>` | `T \| null` | |
| enum | `as const` object and a type of its values | a `[Flags]` enum is `number` (`bigint` for a 64-bit one); 64-bit enums have `bigint` values |
| `[NinoType]` class | class | `extends` its generated base class, `implements` its generated interfaces; abstract stays abstract |
| `[NinoType]` interface | interface | |
| struct, `[NinoType]` or copied as raw memory | class | a raw struct is read and written field by field at its offsets, padding zeroed |
| `object` | `unknown` | any generated `[NinoType]`, by its type id |
| keyed and version-tolerant types | as above | read and written in their [format](/en/docs/v4/evolving-data), former keys included |

## Not Supported [#not-supported]

A type that cannot be written in TypeScript is left out, with a build warning, and so is every type that holds one:

```text
nino-ts : warning NINOTS002: Samples.Node is not written to TypeScript: reference tracking (trackReferences) is not supported.
```

- generic `[NinoType]`s;
- types with [`trackReferences: true`](/en/docs/v4/reference-tracking);
- `[NinoType]`s that are collections themselves;
- members whose encoding has no TypeScript form yet: multi-dimensional arrays, `DateTimeOffset`, `BigInteger`, `Version`, `BitArray`, `TimeZoneInfo`, `Uri`, `CultureInfo`, `StringBuilder`, `Memory<T>`, `ILookup` and `IGrouping`, tuples of more than 7 items, and members written by a [custom formatter](/en/docs/v4/custom-formatters).

Invalid arguments, or an assembly the tool cannot read, fail the build with `NINOTS001`.

## Compared with MemoryPack's TypeScript [#compared-with-memorypack]

[MemoryPack](https://github.com/Cysharp/MemoryPack) also generates TypeScript, for classes marked `[GenerateTypeScript]`. It does so inside its Roslyn source generator, which writes the `.ts` files to disk while it compiles C#. The differences follow from that choice:

| | Nino.TypeScript | MemoryPack `[GenerateTypeScript]` |
| --- | --- | --- |
| When it runs | after each build, in its own process, from the built assembly | inside the source generator, on every compilation, the IDE's included |
| What it reads | the published [layout metadata](/en/docs/v4/evolving-data#layout-metadata), the layouts the formatters were generated from | the C# source, with TypeScript readers and writers of its own |
| Setup | a package reference; optional MSBuild properties | MSBuild properties made visible to the compiler with `CompilerVisibleProperty` items, and an attribute on each type |
| Runtime file | rewritten whenever its version changes it | written only when the file does not exist, so upgrading MemoryPack does not update a copy already written |
| Renamed types | the old file is deleted | stale `.ts` files stay ([#315](https://github.com/Cysharp/MemoryPack/issues/315), closed as not planned) |
| Structs | ✅ | ❌ classes only |
| `char`, `decimal`, 64-bit enums | ✅ | ❌ |
| Version tolerance | ✅ version tolerant and keyed | ❌ |
| Generics, reference tracking | ❌ (left out with a warning) | ❌ |
| Import extension | empty, `.js`, `.ts`, `.mjs` or `.mts` | `.js` by default ([#170](https://github.com/Cysharp/MemoryPack/issues/170)) |

Roslyn has no supported way for a source generator to write files other than C# ([dotnet/roslyn#49935](https://github.com/dotnet/roslyn/issues/49935)), and analyzer rule RS1035 bans file I/O in generators; MemoryPack leaves off the extended analyzer rules that include it. Since its TypeScript readers and writers are written apart from its C# formatters, they can disagree: in [#309](https://github.com/Cysharp/MemoryPack/issues/309) TypeScript writes the has-value flag of a `float?` or `double?` at the wrong width, so C# reads `null`, and in [#166](https://github.com/Cysharp/MemoryPack/issues/166) empty strings were written wrong. Users have also reported generated code that fails a strict `tsconfig` ([#426](https://github.com/Cysharp/MemoryPack/issues/426)), imports of base types that have no `.ts` file ([#174](https://github.com/Cysharp/MemoryPack/issues/174)) and mixed line endings ([#311](https://github.com/Cysharp/MemoryPack/issues/311)).

Nino.TypeScript avoids these by running after the build, from the same layouts the C# formatters come from, with byte-for-byte round trips between .NET and Node and `tsc --strict` in its tests. For other approaches (Protocol Buffers, MessagePack), see [When Not to Use It](/en/docs/v4#when-not-to-use-it).
