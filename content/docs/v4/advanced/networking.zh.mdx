本指南实现一个 TCP 协议中与序列化相关的部分：消息继承体系、直接写入 `PipeWriter` 的长度前缀帧、从 `PipeReader` 无拷贝地读取帧，以及按连接复用消息对象。传输层（socket、Kestrel 连接、引擎自带的网络模块）由你决定；只要能提供 `PipeReader`/`PipeWriter`、`Stream` 或原始缓冲区，做法都一样。

## 定义消息 [#define-the-messages]

让所有消息继承同一个 `[NinoType]` 基类。每条消息写入时都带有 4 字节的**类型 ID**（类型全名的稳定哈希），接收方无需手工维护操作码表，就能还原出正确的子类型。

```csharp title="Messages.cs"
using Nino.Core;

[NinoType(versionTolerant: true)] // subtypes inherit [NinoType] and its options
public abstract class Message
{
    public int RequestId;
}

public sealed class Login : Message
{
    public string User;
    public byte[] Token;
}

public sealed class Move : Message
{
    public int EntityId;
    public Vector3 Target;
}

public sealed class Chat : Message
{
    [NinoUtf8] public string Text; // UTF-8: smaller for mostly-ASCII text
}
```

- 把消息和 `Message` 声明在同一个程序集中：这样 Nino 会用生成的代码分派（写入时是一串类型判断，读取时是对 ID 的 `switch`），而不是查注册表。把它们声明为 `sealed`，这样声明为 `Move` 的成员只需 1 字节头部，而不是 4 字节 ID。
- 类型 ID 来自类型名，所以给消息类改名或换命名空间会导致旧版本的对端无法识别。改名时请使用 [`[NinoFormerName]`](/zh/docs/v4/defining-types#former-name)。
- `versionTolerant` 让你以后可以添加字段，参见[滚动升级](#rolling-upgrades)。子类型会随 `[NinoType]` 一起继承它；如果给某个消息单独加了 `[NinoType]`，记得在那里也写上 `versionTolerant: true`。

用普通的模式匹配分发消息：

```csharp
void Handle(Message message)
{
    switch (message)
    {
        case Login login: OnLogin(login); break;
        case Move move:   OnMove(move);   break;
        case Chat chat:   OnChat(chat);   break;
    }
}
```

## 分帧 [#frame-the-stream]

TCP 是字节流，每条消息都需要分帧。最简单的做法是加 4 字节小端序的长度前缀。Nino 的 `Writer` 可以先预留 4 字节，在后面序列化消息，再回填长度，全部在同一个缓冲区里完成：

```csharp title="FrameWriter.cs"
using System.IO.Pipelines;
using Nino.Core;

public sealed class FrameWriter
{
    private readonly NinoArrayBufferWriter _buffer = new(4096); // one per connection

    public void Write(PipeWriter output, Message message)
    {
        _buffer.ResetWrittenCount();
        var writer = new Writer(_buffer);
        int lengthPosition = writer.ReserveInt32();   // 4 bytes for the length
        NinoSerializer.Serialize(message, ref writer);
        writer.PatchLength(lengthPosition);           // bytes written after the slot
        writer.Flush();

        output.Write(_buffer.WrittenSpan);            // PipeWriter is an IBufferWriter<byte>
    }
}

// sending
frameWriter.Write(pipe.Output, new Move { EntityId = 7, Target = target });
await pipe.Output.FlushAsync();
```

<Callout type="info">

如果传输层本身已经分帧（WebSocket 消息、UDP 数据报、消息队列），就不需要长度前缀，直接序列化到传输层的 `IBufferWriter<byte>` 即可：`NinoSerializer.Serialize(message, pipeWriter)`。

</Callout>

## 读取帧 [#reading-frames]

从管道给出的 `ReadOnlySequence<byte>` 中切出每一帧，直接在管道自己的内存上反序列化：

```csharp title="FrameReader.cs"
using System.Buffers;
using System.IO.Pipelines;
using Nino.Core;

public static class FrameReader
{
    public const int MaxFrameSize = 1 << 20; // reject absurd lengths before buffering them

    public static async Task ReadLoopAsync(PipeReader input, Action<Message> handle)
    {
        while (true)
        {
            ReadResult result = await input.ReadAsync();
            ReadOnlySequence<byte> buffer = result.Buffer;

            while (TryReadFrame(ref buffer, out ReadOnlySequence<byte> frame))
                handle(Decode(frame));

            input.AdvanceTo(buffer.Start, buffer.End);
            if (result.IsCompleted) break;
        }
        await input.CompleteAsync();
    }

    private static bool TryReadFrame(ref ReadOnlySequence<byte> buffer, out ReadOnlySequence<byte> frame)
    {
        var reader = new SequenceReader<byte>(buffer);
        frame = default;
        if (!reader.TryReadLittleEndian(out int length))
            return false;
        if ((uint)length > MaxFrameSize)
            throw new InvalidDataException($"Frame of {length} bytes");
        if (reader.Remaining < length)
            return false;

        frame = buffer.Slice(4, length);
        buffer = buffer.Slice(4 + length);
        return true;
    }

    public static Message Decode(ReadOnlySequence<byte> frame)
    {
        if (frame.IsSingleSegment)                       // the common case: no copy
            return NinoDeserializer.Deserialize<Message>(frame.First.Span);

        int length = (int)frame.Length;                  // spans two segments: copy once
        if (length <= 512)
        {
            Span<byte> stack = stackalloc byte[length];
            frame.CopyTo(stack);
            return NinoDeserializer.Deserialize<Message>(stack);
        }
        byte[] rented = ArrayPool<byte>.Shared.Rent(length);
        try
        {
            frame.CopyTo(rented);
            return NinoDeserializer.Deserialize<Message>(rented.AsSpan(0, length));
        }
        finally { ArrayPool<byte>.Shared.Return(rented); }
    }
}
```

<Callout type="info">

Nino 在分配内存之前，会把数据中的每个长度与剩余字节数比对，所以恶意的帧无法让它分配巨大的数组；数据被截断时会抛出异常，而不会越界读取。但你仍然应该像上面那样自己限制帧的大小，以免对端让管道缓冲数 GB 的数据。嵌套深度没有限制，所以客户端能发送的消息中不要包含递归类型（节点里又包含节点）：嵌套很深的数据会让服务器栈溢出。参见[无效数据](/zh/docs/v4/basic#invalid-data)。

</Callout>

## 按连接复用消息 [#reuse-messages-per-connection]

繁忙的连接会反复反序列化同样几种消息。有两种办法避免为它们分配内存：

<Tabs items={["池化消息", "每种类型一个实例"]}>
<Tab value="池化消息">

给高频消息加上 `[NinoPooled]`。Nino 每次创建实例时都会先从池中取，通过 `Message` 基类型读取 `Move` 时也一样。处理完之后把它还回去：

```csharp
[NinoPooled] // [NinoType] and versionTolerant are inherited from Message
public sealed partial class Move : Message
{
    public int EntityId;
    public Vector3 Target;

    private static partial IEnumerable<Move> OnNinoPoolWarmup() => null; // start empty
    private partial void OnNinoPoolReturn() { }
}

// in the read loop
Message message = FrameReader.Decode(frame);
Handle(message);
if (message is INinoPooled pooled)
    pooled.ReturnToPool();
```

对象池是线程安全的，并且每个线程有自己的栈，所以不同线程上的连接之间不会争用。

</Tab>
<Tab value="每种类型一个实例">

如果消息是同步处理、处理完不会保留，就用复用反序列化填充上一个实例。下一条消息类型相同时原地填充；类型不同时，旧实例会被丢弃（如果是池化类型，会被回收）：

```csharp
private Message _last; // per connection, used by one thread at a time

void OnFrame(ReadOnlySpan<byte> frame)
{
    NinoDeserializer.Deserialize(frame, ref _last);
    Handle(_last);
}
```

</Tab>
</Tabs>

## 线程 [#threads]

- `NinoSerializer` 和 `NinoDeserializer` 可以在任意多个线程上同时调用，无需加锁。
- 但你的缓冲区和复用的消息对象不行：每个连接（或每个发送线程）用一个 `FrameWriter`，并且绝不能让两个线程反序列化到同一个实例。
- 交给其他线程（游戏主循环、任务队列）的消息，在那个线程用完之前，不能复用，也不能归还到池中。

## 滚动升级 [#rolling-upgrades]

当客户端和服务器不总是运行同一个构建版本时，选择格式要把升级考虑进去：

| 改动 | 按位置 | `versionTolerant` | `keyed` |
| --- | :---: | :---: | :---: |
| 在消息末尾新增字段 | ✗ | ✓ | ✓ |
| 在 `Message` 基类中新增字段 | ✗ | ✓ | ✓ |
| 删除或重排字段 | ✗ | ✗ | ✓ |
| 新增消息类型 | 旧对端无法读取 | 旧对端无法读取 | 旧对端无法读取 |

- 在基类上设置 `versionTolerant`（所有消息都会继承），旧对端会跳过它不认识的字段，新对端上缺失的字段保留消息构造时的值（可以用 `public int Priority = 1;` 这样的字段初始化器为旧版发送方指定默认值）。复用或池化的消息是原地填充的，这时缺失的字段保留的是**上一条**消息的值：请在 `OnNinoPoolReturn` 中重置这些字段，或者在还有旧版对端连接时不要复用实例。
- 对端收到**它不认识的消息类型**时无法反序列化，调用会抛出 `InvalidOperationException`（未知的类型 ID）。请在握手时协商协议版本，只向声明支持的对端发送新的消息类型；如果想交换消息类型列表，`NinoTypeId.Of(typeof(T))` 可以给出每种消息的 ID。
- 如果两端总是一起发布（游戏客户端和它的专用服务器），就保持按位置格式：它最小也最快。

具体规则参见[数据演进](/zh/docs/v4/evolving-data)。
