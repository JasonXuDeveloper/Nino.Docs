缓存里存的都是字节：Redis 字符串、`IDistributedCache` 条目、memcached 数据项，或者你自己字典里的 `byte[]`。Nino 负责值和字节之间的来回转换，不用反射，每次调用自身也不分配内存；序列化出的数据紧凑，同样的内存放得下更多条目，走网络的数据也更少。

下面的例子都使用这个用户资料类型：

```csharp title="UserProfile.cs"
using System;
using System.Collections.Generic;
using Nino.Core;

[NinoType(format: NinoFormat.VersionTolerant)] // 缓存的数据会活过一次部署，见下文
public sealed class UserProfile
{
    public long Id;
    public string DisplayName;
    public string Email;
    public DateTime UpdatedAt;
    public List<string> Roles;
}
```

## Redis [#redis]

Redis 客户端读写的值都是字节。以 [StackExchange.Redis](https://stackexchange.github.io/StackExchange.Redis/) 为例：序列化到复用的缓冲区，直接把它的内存传进去；读取时用 `StringGetLease`，拿到的是池化的字节，不用新分配 `byte[]`：

```csharp title="RedisProfileCache.cs"
using System;
using Nino.Core;
using StackExchange.Redis;

public sealed class RedisProfileCache
{
    private readonly IDatabase _db;
    [ThreadStatic] private static NinoArrayBufferWriter t_buffer;

    public RedisProfileCache(IConnectionMultiplexer redis) => _db = redis.GetDatabase();

    private static RedisKey Key(long id) => $"profile:v1:{id}"; // 键里带着schema 版本

    public void Set(UserProfile profile, TimeSpan ttl)
    {
        var buffer = t_buffer ??= new NinoArrayBufferWriter(1024);
        buffer.ResetWrittenCount();
        NinoSerializer.Serialize(profile, buffer); // [!code highlight]
        try
        {
            _db.StringSet(Key(profile.Id), buffer.WrittenMemory, ttl); // 同步调用：返回之后才复用缓冲区
        }
        catch
        {
            t_buffer = null; // 超时的命令之后仍可能发出：它的缓冲区不再复用
            throw;
        }
    }

    public UserProfile Get(long id)
    {
        using Lease<byte> lease = _db.StringGetLease(Key(id));      // 池化的字节，每次读取不分配 byte[]
        if (lease == null)
            return null;
        try
        {
            return NinoDeserializer.Deserialize<UserProfile>(lease.Span);
        }
        catch (NinoDataException)
        {
            _db.KeyDelete(Key(id)); // 读不出来（schema 不同或数据损坏）：按未命中处理
            return null;
        }
    }
}
```

这里的 Redis 调用只是示意，换成任何客户端，Nino 这部分都一样。如果用异步 API（`StringSetAsync`），要等它完成后再重置缓冲区，或者改用 `NinoSerializer.Serialize(profile)` 直接传 `byte[]`。

## IDistributedCache [#idistributedcache]

`IDistributedCache`（Redis、SQL Server 以及 ASP.NET Core 的其他缓存实现）存取的是 `byte[]`。两个扩展方法就够了：

```csharp title="DistributedCacheExtensions.cs"
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.Caching.Distributed;
using Nino.Core;

public static class DistributedCacheExtensions
{
    public static Task SetNinoAsync<T>(this IDistributedCache cache, string key, T value,
        DistributedCacheEntryOptions options, CancellationToken ct = default) =>
        cache.SetAsync(key, NinoSerializer.Serialize(value), options, ct);

    public static async Task<T> GetNinoAsync<T>(this IDistributedCache cache, string key,
        CancellationToken ct = default)
    {
        byte[] bytes = await cache.GetAsync(key, ct);
        if (bytes == null)
            return default;
        try
        {
            return NinoDeserializer.Deserialize<T>(bytes);
        }
        catch (NinoDataException)
        {
            await cache.RemoveAsync(key, ct); // 读不出来（schema 不同或数据损坏）：按未命中处理
            return default;
        }
    }
}
```

这个接口按数组收发数据，所以每次调用都会分配一个 `byte[]`：这是缓存 API 的开销，不是 Nino 的。如果提供程序还实现了 `IBufferDistributedCache`（Microsoft.Extensions.Caching.StackExchangeRedis 10 就实现了），就能直接用缓冲区读写；下面的 `HybridCache` 在提供程序支持时会自动走这个接口，所以访问频繁的缓存用 `HybridCache`，不要用这两个方法。

如果存储给你的是 `Stream`（blob 容器、S3 对象、文件缓存），就不用自己准备缓冲区：`await NinoSerializer.SerializeAsync(profile, upload, ct)` 写入，`await NinoDeserializer.DeserializeAsync<UserProfile>(download, ct)` 读回（[异步](/zh/docs/v4/advanced/streams#async)）。

## HybridCache [#hybridcache]

`HybridCache`（`Microsoft.Extensions.Caching.Hybrid` 包）写入时交给序列化器一个 `IBufferWriter<byte>`，读取时交给它一个 `ReadOnlySequence<byte>`，正好对上 Nino 的 API：

```csharp title="NinoHybridSerializer.cs"
using System.Buffers;
using Microsoft.Extensions.Caching.Hybrid;
using Nino.Core;

public sealed class NinoHybridSerializer<T> : IHybridCacheSerializer<T>
{
    public void Serialize(T value, IBufferWriter<byte> target) => NinoSerializer.Serialize(value, target);

    public T Deserialize(ReadOnlySequence<byte> source) => NinoDeserializer.Deserialize<T>(source); // [!code highlight]
}
```

序列只有一段时，`Deserialize` 直接在原内存上读；有多段时先拷贝一次到池化缓冲区（[多段输入](/zh/docs/v4/advanced/streams#readonlysequence-input)）。

- 每种要缓存的类型用 `AddSerializer` 注册一个序列化器（见[注册](#registration)）。
- `HybridCache` 给的缓冲区写入器不是 `NinoArrayBufferWriter`，所以 Nino 先序列化到当前线程的暂存缓冲区，再一次性复制过去。每次调用都不分配内存。
- 序列化器读不出的值，`HybridCache` 不会当作未命中：`NinoDataException` 会直接从 `GetOrCreateAsync` 抛出来。捕获它，调用 `cache.RemoveAsync(key)`，再取一次，这次就会从数据源重新加载。
- 泛型序列化器里的调用[拦截器](/zh/docs/v4/performance#interceptors)接管不了，因为 `T` 在那里是类型参数；这些调用走常规路径，每次多花几纳秒。

<Callout title="rc.9 及更早的版本">

`NinoDeserializer` 从 rc.10 起才能读 `ReadOnlySequence<byte>`。更早的版本里，`Deserialize` 改为返回 [rc.9 及更早版本用的序列辅助方法](/zh/docs/v4/advanced/streams#sequence-helpers-rc9)的结果。

</Callout>

## 注册 [#registration]

上面三个适配器都要在宿主里注册各自的客户端。装好这些包：

```shell
dotnet add package Nino --prerelease
dotnet add package StackExchange.Redis
dotnet add package Microsoft.Extensions.Caching.StackExchangeRedis
dotnet add package Microsoft.Extensions.Caching.Hybrid
```

三种都用上的 ASP.NET Core 宿主长这样（用不到的删掉）：

```csharp title="Program.cs"
using System.Threading;
using Microsoft.AspNetCore.Builder;
using Microsoft.Extensions.Caching.Distributed;
using Microsoft.Extensions.Caching.Hybrid;
using Microsoft.Extensions.DependencyInjection;
using StackExchange.Redis;

var builder = WebApplication.CreateBuilder(args);
const string redis = "localhost:6379";

// 直接用 StackExchange.Redis：整个进程一个 multiplexer
builder.Services.AddSingleton<IConnectionMultiplexer>(_ => ConnectionMultiplexer.Connect(redis));
builder.Services.AddSingleton<RedisProfileCache>();

// 基于 Redis 的 IDistributedCache
builder.Services.AddStackExchangeRedisCache(options =>
{
    options.Configuration = redis;
    options.InstanceName = "dc:"; // 自己的键空间：RedisProfileCache 在同一个 Redis 里写 profile:v1:*
});

// HybridCache：在这个 IDistributedCache 前面加一层内存缓存，用户资料用 Nino 读写
builder.Services.AddHybridCache()
    .AddSerializer<UserProfile, NinoHybridSerializer<UserProfile>>(); // [!code highlight]

var app = builder.Build();
app.MapGet("/profiles/{id}", (long id, HybridCache cache, CancellationToken ct) =>
    cache.GetOrCreateAsync($"profile:v1:{id}", id, static (profileId, token) => LoadProfileAsync(profileId, token), // 带 state 的重载：每个请求都不必分配闭包
        cancellationToken: ct));
// HybridCache 在 IDistributedCache 的同一个键下存自己的封装格式：直接读的条目用另一个键（由 SetNinoAsync 写入）
app.MapGet("/profiles/{id}/stored", (long id, IDistributedCache cache, CancellationToken ct) =>
    cache.GetNinoAsync<UserProfile>($"profile-blob:v1:{id}", ct));
app.Run();
```

<Callout type="info" title="这些代码测试过什么">

本站每次改动，都会用 StackExchange.Redis 3、Microsoft.Extensions.Caching.StackExchangeRedis 10 和 Microsoft.Extensions.Caching.Hybrid 10 编译本页的 C# 代码。`DistributedCacheExtensions`、`NinoHybridSerializer` 和 `BlobCache` 在测试里实际跑过：两个 `HybridCache` 实例后面接一个内存版 `IDistributedCache`，代替 Redis。`RedisProfileCache` 和 Redis 连接没有实际跑过，相关设置请对照 Redis 的文档核对。

</Callout>

## 进程内的序列化数据缓存 [#in-process-blob-caches]

进程内缓存通常直接存对象。改存序列化后的字节，有三点不同：

- **隔离。** 每次读取都反序列化出一份新副本。调用方改了自己拿到的值，既破坏不了缓存里的数据，也不会和其他线程争用。
- **占用。** 垃圾回收器只需跟踪一个 `byte[]`，不用跟踪对象、列表和字符串连成的一整张图。
- **复用。** 调用方留着实例的话，可以用 `ref` 读入这个已有实例，除了内容变了的字符串，什么都不分配。

```csharp title="BlobCache.cs"
using System.Collections.Concurrent;
using Nino.Core;

/// <summary>以字节保存值：紧凑，每个读取方都拿到自己的副本。</summary>
public sealed class BlobCache<TKey, TValue>
{
    private readonly ConcurrentDictionary<TKey, byte[]> _entries = new();

    // 缓存项就是这个数组：Serialize(value) 按准确大小分配它
    public void Set(TKey key, TValue value) => _entries[key] = NinoSerializer.Serialize(value);

    public bool TryGet(TKey key, out TValue value)
    {
        if (_entries.TryGetValue(key, out byte[] bytes))
        {
            value = NinoDeserializer.Deserialize<TValue>(bytes);
            return true;
        }
        value = default;
        return false;
    }

    /// <summary>读入调用方保留的实例：实例的结构一旦对上，只有变化的字符串才分配内存。</summary>
    public bool TryGetInto(TKey key, ref TValue value)
    {
        if (!_entries.TryGetValue(key, out byte[] bytes))
            return false;
        NinoDeserializer.Deserialize(bytes, ref value);
        return true;
    }
}
```

代价是每次读取都要反序列化一次。如果值读得远比改得多，读取方也从不修改它，直接缓存对象更划算。

## 跨部署的 schema 变化 [#schema-changes]

共享缓存比写它的进程活得久：滚动部署期间，新旧实例会读到对方写的条目。每种缓存的类型从前两种做法里选一种，再加上第三种：

| 做法 | 方式 | 适用场景 |
| --- | --- | --- |
| 容错类型 | [`format: NinoFormat.VersionTolerant`](/zh/docs/v4/evolving-data#version-tolerance)（追加成员）或 [`format: NinoFormat.Keyed`](/zh/docs/v4/evolving-data#keyed-members)（任意修改） | 条目需要在部署后继续可用。 |
| 带版本的键 | 在键里加上 schema 版本（`profile:v2:42`），类型变化时递增 | 类型的改动超出上面两个选项能应付的范围，或者重新填充缓存的代价很低。 |
| 失败即未命中 | 捕获无效数据抛出的 `NinoDataException`，删除该条目，再从数据源加载 | 一律加上，给前两种做法兜底。 |

兜底替代不了前两种做法：另一个类型写的字节，只要布局兼容，就可能不报错地读出来。用容错类型时，给缓存类型所在的程序集提交一份[布局基线](/zh/docs/v4/evolving-data#layout-baseline)：改出线上部署写的条目读不了的改动时，分析器在你敲代码时就会在改动的成员上报出来（NINO034、NINO035），CI 里 `nino-gen layouts --check` 也会失败。

[按位置](/zh/docs/v4/evolving-data#positional)的类型（不带参数的 `[NinoType]`）最小、最快，但成员的任何改动都会让旧条目无法读取。缓存的值要用它，就得配上带版本的键。

Nino 读取时检查每个长度和边界，条目被截断或损坏时会抛异常，不会越界读取。不过字节里不带 schema，见[无效数据](/zh/docs/v4/basic#invalid-data)。

## 检查清单 [#checklist]

- [ ] 每种缓存的类型都是 `NinoFormat.VersionTolerant` 或 `NinoFormat.Keyed`，或者键里带 schema 版本。
- [ ] 写入时每个线程复用一个缓冲区；异步写入要等完成后再重置缓冲区。
- [ ] 客户端提供池化内存（`Lease<byte>`、`ReadOnlySequence<byte>`）时，直接从这块内存反序列化。
- [ ] 反序列化失败按缓存未命中处理。
