`NinoSerializer.Serialize(value)` 和 `NinoDeserializer.Deserialize<T>(bytes)` 你已经在[序列化与反序列化](/zh/docs/v4/basic)里用过了。它们本身已经很快，只是每次调用都要为结果分配内存。这一页讲怎样让同样的调用做到**每次调用 0 B**：每种调用写到哪里（复用的缓冲区、任意 `IBufferWriter<byte>`、`Stream`）、从哪里读（span、`ReadOnlySequence<byte>`、`Stream`）、开销多少，然后是启动、每次调用的固定开销、线程安全和怎样测量。类型本身怎么写才能让调用一直快（格式、密封类与多态类、集合、字符串、自定义格式化器），放在下一页[面向性能的类型设计](/zh/docs/v4/advanced/type-design)。[下表](#levers)把这两页的手段列在一处。

性能部分从这一页开始，后面几页依次深入：[面向性能的类型设计](/zh/docs/v4/advanced/type-design)、[复用与对象池](/zh/docs/v4/pooling)（复用反序列化和对象池的具体规则）、[零分配模式](/zh/docs/v4/advanced/zero-allocation)（可以直接复制的做法和检查清单）、[构建配置](/zh/docs/v4/advanced/build-configuration)（Release、分层编译、Native AOT、Unity 的 IL2CPP 与 Burst）。内部实现（内联的格式化器、结构体布局）见[性能原理](/zh/docs/v4/performance)。

## 序列化到复用的缓冲区 [#serialize-into-a-reused-buffer]

`NinoArrayBufferWriter` 是 Nino 自带的 `IBufferWriter<byte>`，底层数组租自 `ArrayPool<byte>.Shared`。Nino 直接写入其中；最初几次调用之后，它就增长到了你需要的大小，此后序列化不再分配内存。

```csharp
private readonly NinoArrayBufferWriter _buffer = new(64 * 1024);

public ReadOnlySpan<byte> Encode(Quote quote)
{
    _buffer.ResetWrittenCount();
    NinoSerializer.Serialize(quote, _buffer); // [!code highlight]
    return _buffer.WrittenSpan;   // 下次调用 Encode 之前有效
}
```

- **开销：** 数组增长到位之后，每次调用 0 B；增长时从池中租用更大的数组，`Dispose()` 时归还。
- 预先按最大的消息设定大小（构造函数的 `initialCapacity`，或 `EnsureCapacity(sizeHint)`），热路径上就不会再增长。想从自己的池里租数组（比如固定的 socket 缓冲区），见[自己的数组池](#own-array-pool)。
- `ResetWrittenCount()` 复用同一个数组，所以 `WrittenSpan` 只在下一次重置之前有效：先拷贝或发送。
- 缓冲区不是线程安全的。每个线程、连接或编码器各用一个；[编码器与线程静态缓冲区的做法](/zh/docs/v4/advanced/zero-allocation#reuse-one-buffer)给出了这两种写法。

### 自己的数组池 [#own-array-pool]

想让 Nino 直接写进你自己管理的缓冲区，就传入自己的 `ArrayPool<byte>`：`new NinoArrayBufferWriter(initialCapacity, pool)` 从这个池租数组，扩容时换下的数组和 `Dispose()` 时的数组都还给它。比如服务器把 socket 缓冲区分配在固定对象堆（POH）上，消息就能直接序列化进去，省掉一次拷贝。扩容时旧数组会还给池，所以要在最后一次写入之后再取 `WrittenMemory`，并且只在下一次写入或 `ResetWrittenCount()` 之前使用。

```csharp
// pinnedPool：你自己的 ArrayPool<byte>，例如由 GC.AllocateUninitializedArray<byte>(n, pinned: true) 数组组成的池
var socketBuffer = new NinoArrayBufferWriter(4096, pinnedPool);
```

### 连续写入多个值 [#several-values-back-to-back]

`Writer` 写入 `NinoArrayBufferWriter`。用它可以把多个值放进同一个缓冲区，或者预留空间稍后回填。自己创建的 `Writer` 要像 `NinoSerializer` 那样收尾：先 `Flush`，再 `ReleaseReferences`；`Reader` 则以 `ReleaseReferences` 收尾：

```csharp
buffer.ResetWrittenCount();  // 一个你保留下来的 NinoArrayBufferWriter
var writer = new Writer(buffer);
NinoSerializer.Serialize(header, ref writer);
NinoSerializer.Serialize(body, ref writer);
writer.Flush();              // 提交到 buffer.WrittenCount
writer.ReleaseReferences();  // 结束这次调用：归还 writer 租用的资源

// 按同样的顺序读回来
var reader = new Reader(buffer.WrittenSpan);
var h = NinoDeserializer.Deserialize<Header>(ref reader);
var b = NinoDeserializer.Deserialize<Body>(ref reader);
reader.ReleaseReferences();
```

- `ReleaseReferences` 会交还 `Writer` 为 `trackReferences` 类型（或嵌套过深、无法内联写入的数据）租用的线程级状态。不调用它，这份状态就会被丢弃，下一个 `Writer` 只能重新分配（每次调用几百字节，而不是 0 B）。
- 序列化抛出异常时，这份状态只是不再复用，所以不需要 `try`/`finally`。
- 同一个 `Writer` 写入的多个值共用一张引用表，因此要用同一个 `Reader` 读回。

基于它的做法：[批量写入](/zh/docs/v4/advanced/zero-allocation#batches)和[分帧读写流](/zh/docs/v4/advanced/zero-allocation#framed-streams)。

## 序列化到任意 IBufferWriter [#serialize-into-any-ibufferwriter]

任何 `IBufferWriter<byte>` 都可以作为写入目标：`PipeWriter`、Kestrel 的响应体写入器、`ArrayBufferWriter<byte>`。写之前就知道大小的值，Nino 按这个大小调一次 `GetSpan`，直接写进写入器；其他值先写进每个线程各自的<Term id="scratch-buffer" lang="zh">暂存缓冲区</Term>，再一次性拷到写入器。两种情况每次调用都不分配内存：

```csharp
NinoSerializer.Serialize(message, pipeWriter); // 复制一次，写进管道的内存
await pipeWriter.FlushAsync();
```

- **直接写入的值：** 原始值（非托管结构体、基元类型）、由它们组成的数组和列表、[固定大小的类型](/zh/docs/v4/performance#fixed-size-types)，还有原始值的 `ArraySegment<T>`、背后是数组的 `Memory<T>` 和只有一段的 `ReadOnlySequence<T>`。.NET 8 及以上再加上原始值的多维数组。
- **开销：** 最多往写入器的内存拷贝一次；0 B。
- 只有 `NinoArrayBufferWriter` 不管写什么值都直接写入。需要在写完之后回填字节时（例如长度前缀，参见[分帧](/zh/docs/v4/advanced/networking#frame-the-stream)），请使用它。
- 要序列化到你已有的内存里（环形缓冲区的槽位、预先分配的发送缓冲区），用一个很小的 `IBufferWriter<byte>` 包住它：见[写入你自己的内存](/zh/docs/v4/advanced/zero-allocation#write-into-memory-you-own)。

## 需要 `byte[]` 的时候 [#exact-size-arrays]

有些 API 接收一个 `byte[]` 并保留它：缓存客户端、消息代理、游戏引擎的网络调用。`NinoSerializer.Serialize(value)` 返回的数组大小正好等于数据，这是拿到 `byte[]` 最便宜的办法：

- **固定大小的类型**（只由非托管成员组成的结构体和密封类），以及**元素整块拷贝的数组和列表**，会直接写进按最终大小分配的数组：不经过暂存缓冲区，也没有拷贝。
- 其他值先写入每个线程的暂存缓冲区，再拷贝出来一次，和对你自己的缓冲区调用 `ToArray()` 一样。
- **开销：** 每次调用都分配这个数组。如果字节只需要送到一个 span（套接字、管道、文件），改为序列化到复用的缓冲区。

`NinoSerializer.GetFixedSize<T>()` 返回固定大小类型的字节数，其他类型返回 `-1`。用它来确定槽位和记录的大小，或者在启动时检查热点记录（例如批量写入示例中的 [`Tick`](/zh/docs/v4/advanced/zero-allocation#batches)）在修改之后是否仍是固定大小：

```csharp
// 给 Tick 加上一个字符串或列表，它就不再是固定大小，它的记录也就无法再按下标定位。
if (NinoSerializer.GetFixedSize<Tick>() < 0)
    throw new InvalidOperationException("Tick is no longer fixed-size.");
```

固定大小的密封类的 `null` 实例写成 1 字节；其他每个值都正好占 `GetFixedSize<T>()` 字节。什么样的类型是固定大小的：见[固定大小的类型](/zh/docs/v4/performance#fixed-size-types)。

## 直接从已有内存反序列化 [#deserialize-from-the-memory-you-have]

`NinoDeserializer` 读取的是 `ReadOnlySpan<byte>`，字节在哪个缓冲区里（池化的接收缓冲区、管道的一段内存、内存映射文件），就直接传那块缓冲区的切片，不必再拷贝到新的 `byte[]`；读取时只分配它返回的对象（见[哪些调用会分配内存](/zh/docs/v4/advanced/zero-allocation#what-allocates)）。[接收循环](/zh/docs/v4/advanced/zero-allocation#receive-loop)每个 socket 只租一次缓冲区，而不是每条消息租一次。

`ReadOnlySequence<byte>`（来自 `System.IO.Pipelines`）也一样，直接调 `NinoDeserializer.Deserialize<T>(sequence)`：只有一段时直接在原内存上读，有多段时拷贝一次（见[多段输入](/zh/docs/v4/advanced/streams#readonlysequence-input)；从管道里切帧见[读取帧](/zh/docs/v4/advanced/networking#reading-frames)）。

## 读写流 [#streams]

一个文件、HTTP 请求体或 blob 里只放一个值时，直接把 `Stream` 交给 Nino，不要自己先拿 `byte[]` 再写：

```csharp
NinoSerializer.Serialize(checkpoint, file);                 // 每次调用不分配 byte[]
NinoDeserializer.Deserialize(file, ref checkpoint);         // 填充你保留的实例
```

- **开销：** 写入时先序列化到线程级暂存缓冲区，再一次 `Write` 交给流：0 B。读取时把流里的字节读进从 `ArrayPool<byte>.Shared` 租来的数组（缓冲区可公开访问的 `MemoryStream`、`UnmanagedMemoryStream` 和内存映射视图直接在原内存上读），读完就还回去。I/O 立刻完成时，`SerializeAsync` 和 `DeserializeAsync` 也不会多分配。
- 先 `NinoSerializer.Serialize(value)` 再 `stream.Write(bytes)`，就多分配了一个流重载本来能省掉的数组。
- 一次调用读到流的结尾，所以一个流只放一个值。一个流上要传多条消息就得分帧：见[流与压缩](/zh/docs/v4/advanced/streams#frames)，以及不分配内存的[分帧读写流](/zh/docs/v4/advanced/zero-allocation#framed-streams)做法。

## 反序列化到已有对象 [#deserialize-into-existing-objects]

用 `ref` 传入上一次的结果，Nino 把数据读入这个实例：还是同一个对象，同样的嵌套对象、列表、数组和字典。这样，结构相同的消息源源不断地到来，也不会分配内存；基准测试里，它比 MemoryPack 的覆盖模式最高快 <BenchValue k="reuse.max" />（见[基准测试：.NET 运行速度](/zh/docs/v4/benchmarks#pooling)）。每种读取重载都有这个形式：span、`ReadOnlySequence<byte>`、`Stream` 和 `ref Reader`。

```csharp
MetricsBatch batch = null;
NinoDeserializer.Deserialize(payload, ref batch);   // 第一次调用构建对象图
NinoDeserializer.Deserialize(payload, ref batch);   // 之后的调用原地填充：0 B
```

在热路径上：

- 每个持有者（一个连接、一个消费者）各留一个实例，读下一条消息之前先用完它：下一条消息会读进同一批对象。
- 条数会变就用 `List<T>`：列表保留容量，数组只在新数据**长度相同**时才复用（见[集合](/zh/docs/v4/advanced/type-design#collections)）。
- 字符串尽量少变：文本没变的字符串原样保留，文本变了就是一个新字符串（见[字符串](/zh/docs/v4/advanced/type-design#strings)）。

哪些对象原地填充、哪些要重新创建、丢弃的实例去哪里，见[反序列化到已有实例](/zh/docs/v4/pooling#deserializing-into-existing-instances)。外层的循环怎么写，见[复用反序列化的结果](/zh/docs/v4/advanced/zero-allocation#reuse-what-you-deserialize)。

## 池化新建的对象 [#pool-what-you-create]

复用反序列化填的是你手里已有的对象。给类加上 `[NinoPooled]`，Nino 需要**新建**的实例（列表变长了、`null` 成员有了值、你要交给别处代码的消息）就从对象池里取，丢弃的实例也回到池里。这样即使消息的结构在变，池填满之后也是 0 B。

热路径上要做到两点：从 Nino 手里拿走的每个池化实例（`Deserialize` 直接返回给你的值）都调用一次 `ReturnToPool()`；启动时按最大的一波高峰设好池容量，超出的部分就要分配内存。怎么声明、两个钩子方法和具体规则见[内置对象池：`[NinoPooled]`](/zh/docs/v4/pooling#ninopooled)，容量上限见[对象池与回收器](/zh/docs/v4/settings#pools)，用自己的池（`[NinoFactory]`、`SetRecycler<T>`）见[选哪种复用方式](/zh/docs/v4/pooling#which-mechanism)。

## 启动与第一次调用 [#startup]

每个类型的第一次调用要付出之后的调用不再有的开销：Nino 要找到该类型的格式化器（在它所在程序集的生成注册表中，注册表在 Nino 第一次需要时加载；在 JIT 上，生成器没有见过的类型，例如只在运行时出现的集合，要通过反射构建格式化器），JIT 要编译代码，`[NinoPooled]` 类型还要运行它的 `OnNinoPoolWarmup()`。要让这些开销不落在第一条消息上：

- 对运行时加载的程序集（插件、热更新）调用 `NinoRegistry.EnsureInitialized(assembly)`，或者调用 `NinoRegistry.EnsureAllInitialized()` 处理所有已加载的程序集，提前加载注册表。两者都是可选的：注册表本来就会在第一次使用时加载。
- 在启动阶段或加载界面中，把每个热点类型的一个典型值序列化、反序列化一次。这会构建它们的格式化器、填满它们的对象池，并让你的缓冲区增长到工作时的大小。
- 在这两步之前配置好 `NinoSettings`。

**开销：** 启动时间，以及对象池现在持有的实例所占的内存。预热调用运行的是未经优化的 Tier-0 代码，所以它不能代替[测量](#measure)之前的预热。

## 每次调用的固定开销 [#per-call-overhead]

不再分配内存之后，剩下的就是每次调用几纳秒的开销；在紧凑的循环里序列化小值时，这部分最明显。用 Roslyn 4.8 或更高版本（.NET 8 SDK 及以上）编译，调用处类型已知的调用就会直达生成的格式化器，省去格式化器缓存的查找和那次虚调用。泛型代码中的调用、在其他程序集中声明的 `[NinoType]`，以及 Unity 项目（使用 Roslyn 4.3 版本）走常规路径，字节一致。参见[拦截器](/zh/docs/v4/performance#interceptors)。

## 线程安全 [#thread-safety]

`NinoSerializer` 和 `NinoDeserializer` 的所有方法都可以并发调用，不需要加锁；但你自己持有的状态不是线程安全的：`NinoArrayBufferWriter`、`Writer` 或 `Reader`，以及你反序列化进去的对象。所以每个做法都给每个线程或每个持有者各配一个缓冲区。详见[线程安全](/zh/docs/v4/performance#thread-safety)。

## 测量 [#measure]

- **先预热。** 最初几次调用会让缓冲区增长、填满对象池，运行的还是未经优化的 Tier-0 代码；在这之后再测量。
- **按线程统计字节数。** `GC.GetAllocatedBytesForCurrentThread()` 统计当前线程分配的每一个字节，单元测试可以把热路径的分配钉死在 0 B：见[验证](/zh/docs/v4/advanced/zero-allocation#verify-it)。对整个服务而言，BenchmarkDotNet 的 `[MemoryDiagnoser]` 会按每次操作报告同样的数字。
- **计时要跑得够久**，并用复用的实例测量反序列化：原因见[测量](/zh/docs/v4/performance#measuring)。

付诸实践时，从[零分配模式](/zh/docs/v4/advanced/zero-allocation)中的做法入手，再对照它的[检查清单](/zh/docs/v4/advanced/zero-allocation#checklist)检查你的热路径。
