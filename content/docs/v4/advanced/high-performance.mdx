`NinoSerializer.Serialize(value)` and `NinoDeserializer.Deserialize<T>(bytes)` are already fast, but each call allocates its result. This page explains the mechanisms that take both directions down to **0 B per call** (where each call writes, what it reads from, what it costs), then the choices in your own types that keep calls fast: formats, sealed and polymorphic classes, collections, strings and custom formatters, then startup and how to measure. The [table below](#levers) lists every lever in one place.

For copy-paste recipes built on these mechanisms, and the checklist, see [Zero-Allocation Patterns](/en/docs/v4/advanced/zero-allocation); for the internals (inlined formatters, struct layout), see the [Performance Guide](/en/docs/v4/performance).

## Levers at a Glance [#levers]

| Lever | Use it when | What it costs |
| --- | --- | --- |
| [A reused `NinoArrayBufferWriter`](#serialize-into-a-reused-buffer) | you serialize more than once | the array, held by its owner; one buffer per thread or connection |
| [The caller's `IBufferWriter<byte>`](#serialize-into-any-ibufferwriter) | the transport hands you one (pipes, Kestrel) | one copy into it |
| [`Serialize(value)` into an exact-size `byte[]`](#exact-size-arrays) | an API needs a `byte[]` | one allocation per call |
| [`Writer` and `Reader`](#several-values-back-to-back) | several values share one buffer | `Flush` and `ReleaseReferences` once per message |
| [Deserializing from the memory you have](#deserialize-from-the-memory-you-have) | always | nothing |
| [Reuse deserialization (`ref`)](#deserialize-into-existing-objects) | messages of the same shape, one at a time | you keep the instance, and it changes with every read |
| [`[NinoPooled]`](#pool-what-you-create) and [pool sizes](#pool-sizes) | instances created, kept or dropped at a high rate | `sealed partial` classes, a `ReturnToPool()` per instance you own, memory the pools hold |
| [Unmanaged structs and their layout](#keep-bulk-data-raw) | bulk and hot data | the layout is part of the format |

## Serialize into a Reused Buffer

`NinoArrayBufferWriter` is Nino's `IBufferWriter<byte>`, backed by `ArrayPool<byte>.Shared`. Nino writes into it in place, and after the first few calls it has grown to the size you need, so serializing allocates nothing.

```csharp
private readonly NinoArrayBufferWriter _buffer = new(64 * 1024);

public ReadOnlySpan<byte> Encode(Quote quote)
{
    _buffer.ResetWrittenCount();
    NinoSerializer.Serialize(quote, _buffer); // [!code highlight]
    return _buffer.WrittenSpan;   // valid until the next Encode
}
```

- **Cost:** 0 B per call once the array has grown; growth rents a larger array from the pool, and `Dispose()` returns it.
- Size it for your largest message up front (the constructor's `initialCapacity`, or `EnsureCapacity(sizeHint)`), so it never grows on the hot path. To serialize into arrays you manage (pinned socket buffers), pass your own `ArrayPool<byte>`: see [Reusing a Buffer](/en/docs/v4/basic#reusing-a-buffer).
- `ResetWrittenCount()` reuses the same array, so `WrittenSpan` is only valid until the next reset: copy or send it first.
- A buffer is not thread safe. Give each thread, connection or encoder its own; the [encoder and thread-static buffer recipes](/en/docs/v4/advanced/zero-allocation#reuse-one-buffer) show both.

### Several Values Back to Back

A `Writer` writes into a `NinoArrayBufferWriter`. Use it to put several values in one buffer, or to reserve space and fill it in later. End a writer you create the way `NinoSerializer` ends its own, with `Flush` and then `ReleaseReferences`, and a reader with `ReleaseReferences`:

```csharp
buffer.ResetWrittenCount();  // a NinoArrayBufferWriter you keep
var writer = new Writer(buffer);
NinoSerializer.Serialize(header, ref writer);
NinoSerializer.Serialize(body, ref writer);
writer.Flush();              // commit to buffer.WrittenCount
writer.ReleaseReferences();  // end the call: hand back what the writer rented

// reading them back in the same order
var reader = new Reader(buffer.WrittenSpan);
var h = NinoDeserializer.Deserialize<Header>(ref reader);
var b = NinoDeserializer.Deserialize<Body>(ref reader);
reader.ReleaseReferences();
```

- `ReleaseReferences` hands back the per-thread state that the writer rents for a `trackReferences` type, or for nesting too deep to write inline. Without the call that state is dropped and the next writer allocates it again (a few hundred bytes per call instead of 0 B).
- If serialization throws, the state is simply not reused, so no `try`/`finally` is needed.
- Values written by one writer share its reference table, so read them back with one reader.

Recipes built on this: [batches](/en/docs/v4/advanced/zero-allocation#batches) and [framed streams](/en/docs/v4/advanced/zero-allocation#framed-streams).

## Serialize into Any IBufferWriter

Any `IBufferWriter<byte>` works as a destination: a `PipeWriter`, Kestrel's response body writer, an `ArrayBufferWriter<byte>`. Nino writes into a per-thread [scratch buffer](/en/docs/v4/basic#terms) and then copies the result into the writer once, so nothing is allocated per call:

```csharp
NinoSerializer.Serialize(message, pipeWriter); // one copy into the pipe's memory
await pipeWriter.FlushAsync();
```

- **Cost:** one copy into the writer's memory; 0 B. A raw value (an unmanaged struct, a primitive) skips the scratch buffer and is written straight into the writer's span.
- Only a `NinoArrayBufferWriter` is written in place. Use one when you need to patch bytes after writing (a length prefix, see [framing](/en/docs/v4/advanced/networking#frame-the-stream)).
- To serialize into memory you already own (a ring-buffer slot, a pre-allocated send buffer), wrap it in a small `IBufferWriter<byte>`: see [Write into Memory You Own](/en/docs/v4/advanced/zero-allocation#write-into-memory-you-own).

## When You Need a `byte[]` [#exact-size-arrays]

Some APIs take a `byte[]` and keep it: a cache client, a message broker, a game engine's network call. `NinoSerializer.Serialize(value)` returns one of exactly the data's size, and is the cheapest way to get it:

- **Fixed-size types** (structs and sealed classes made only of unmanaged members) and **arrays and lists whose elements are copied as one block** are written straight into an array allocated at their final size: no scratch buffer and no copy.
- Other values are written into a per-thread scratch buffer and copied out once, as `ToArray()` on a buffer of your own would.
- **Cost:** the array, on every call. When the bytes only have to reach a span (a socket, a pipe, a file), serialize into a reused buffer instead.

`NinoSerializer.GetFixedSize<T>()` returns the size of a fixed-size type, and `-1` for every other type. Use it to size slots and records, or to check at startup that a hot record, such as the [`Tick`](/en/docs/v4/advanced/zero-allocation#batches) of the batch recipe, is still fixed-size after a change:

```csharp
// A string or a list added to Tick would make it variable-size, and its records could no longer be indexed.
if (NinoSerializer.GetFixedSize<Tick>() < 0)
    throw new InvalidOperationException("Tick is no longer fixed-size.");
```

A `null` instance of a fixed-size sealed class is written as 1 byte; every other value takes exactly `GetFixedSize<T>()` bytes. What makes a type fixed-size: [Fixed-Size Types](/en/docs/v4/performance#fixed-size-types).

## Deserialize from the Memory You Have

`NinoDeserializer` reads a `ReadOnlySpan<byte>`, so pass a slice of whatever buffer the bytes are already in: a pooled receive buffer, a pipe segment, a memory-mapped file. There is no need to copy them into a fresh `byte[]`, and reading allocates only the objects it returns ([what allocates](/en/docs/v4/advanced/zero-allocation#what-allocates)). A [receive loop](/en/docs/v4/advanced/zero-allocation#receive-loop) rents its buffer once per socket, not per message.

For `ReadOnlySequence<byte>` (from `System.IO.Pipelines`), see [Network Layer](/en/docs/v4/advanced/networking#reading-frames).

## Deserialize into Existing Objects

Pass the previous result by `ref` and Nino fills it in place: the same object, the same nested objects, lists, arrays and dictionaries. A steady stream of messages of the same shape then allocates nothing.

```csharp
MetricsBatch batch = null;
NinoDeserializer.Deserialize(payload, ref batch);   // first call builds the graph
NinoDeserializer.Deserialize(payload, ref batch);   // later calls fill it: 0 B
```

- Lists are reused element by element and keep their capacity, so a batch with a different count is read into the same list. An array is reused when the new data has the **same length**; otherwise a new array is allocated. Dictionaries are merged by key.
- Arrays and lists of unmanaged structs are one block copy in both directions.
- Types that cannot be filled in place (positional records, `init`-only or get-only members) are re-created.
- A string whose text is unchanged is kept and costs nothing; changed text is read into a new string. Non-ASCII `[NinoUtf8]` text is decoded into a new string every time, changed or not.
- When an existing instance is **dropped** (the data holds `null`, a list shrinks, a key disappears, the polymorphic type changes), it is handed once to the [recycler](/en/docs/v4/pooling#where-dropped-instances-go) of the member or element that held it, instead of being silently overwritten. This is what makes reuse deserialization safe with pools; see [Reuse Deserialization and Pooling](/en/docs/v4/pooling#deserializing-into-existing-instances).

The loop around it, and how to keep strings and counts from allocating: [Reuse What You Deserialize](/en/docs/v4/advanced/zero-allocation#reuse-what-you-deserialize).

## Pool What You Create

Reuse deserialization reuses what you already hold. `[NinoPooled]` covers the rest: whenever Nino has to **create** an instance of the type (the value you deserialize, a member, an element of a growing list), it takes one from a pool first, and dropped instances go back to that pool automatically.

<Steps>
<Step>

### Mark the class

```csharp
[NinoType, NinoPooled] // [!code highlight]
public sealed partial class TelemetryEvent
{
    public long Timestamp;
    public int SourceId;
    public int Kind;
    public List<double> Values;

    // Called once, before Nino first deserializes the type: pre-fill the pool.
    private static partial IEnumerable<TelemetryEvent> OnNinoPoolWarmup() =>
        Enumerable.Range(0, 256).Select(_ => new TelemetryEvent { Values = new List<double>(8) });

    // Called by ReturnToPool(): release state Nino does not deserialize.
    private partial void OnNinoPoolReturn() { }
}
```

The class must be `sealed`, `partial`, and filled in place (NINO018, NINO002). The analyzer offers a fix that adds both hooks (NINO019).

</Step>
<Step>

### Deserialize as usual

```csharp
[NinoType]
public sealed class EventBatch
{
    public long Sequence;
    public List<TelemetryEvent> Events;
}

EventBatch batch = null;
NinoDeserializer.Deserialize(frame1, ref batch); // events come from the pool
NinoDeserializer.Deserialize(frame2, ref batch); // events that disappeared go back to it
```

</Step>
<Step>

### Return what you own

When you are done with an instance that `Deserialize` returned to you, hand it back:

```csharp
var telemetryEvent = NinoDeserializer.Deserialize<TelemetryEvent>(data);
Process(telemetryEvent);
telemetryEvent.ReturnToPool(); // its List<double> stays attached and is reused next time
```

Returning an instance twice throws `InvalidOperationException`. An instance that is never returned is simply garbage collected.

</Step>
</Steps>

### Pool Sizes [#pool-sizes]

Size the pools at startup if the defaults (256 in the shared stack, plus up to 64 per thread) do not fit:

```csharp
NinoSettings.SetPoolMaxRetained<TelemetryEvent>(4096);
```

A larger limit keeps more instances alive between bursts, for the life of the process; with a smaller one, a burst larger than the pool allocates what does not fit. `NinoSettings.PoolMaxRetained` sets the limit of every pool created afterwards. Set both before the first call on any thread: see [Settings](/en/docs/v4/pooling#settings).

<Callout type="idea">

Already have your own pools? Mark a public static factory method `[NinoFactory]` to make Nino create instances through it, and register `NinoSettings.SetRecycler<T>(...)` to receive the instances it drops. See [Reuse Deserialization and Pooling](/en/docs/v4/pooling#creating-instances-with-ninofactory).

</Callout>

## Keep Bulk Data Raw

Unmanaged data is copied as raw memory, in blocks:

```csharp
[NinoType]
public struct Sample            // unmanaged, sequential: written as raw memory
{
    public long Timestamp;
    public double Value;
    public int SensorId;
}

[NinoType]
public sealed class SampleBlock
{
    public long SeriesId;
    public Sample[] Samples;    // one block copy for the whole array
}
```

- Arrays and `List<T>` of unmanaged elements are one copy.
- A struct with a `string` or an array inside is not raw; keep those in a separate class if the struct is hot.
- `NinoFormat.VersionTolerant`, `NinoFormat.Keyed` and custom member formatters turn raw copying off for that struct.
- A struct or sealed class made only of unmanaged members is [fixed-size](/en/docs/v4/performance#fixed-size-types): `NinoSerializer.Serialize(value)` writes it straight into a `byte[]` of its size, with no scratch buffer or copy. Records of a fixed size can also be addressed by index in a file or shared memory: see [Fixed-Size Records](/en/docs/v4/advanced/zero-allocation#fixed-size-records).

**Lay out hot structs without padding.** A struct without padding is a plain block copy; one with padding is copied through a mask that zeroes the gaps, which costs a little more; a struct declared `[StructLayout(LayoutKind.Auto)]` is not raw at all and is written field by field. Order the fields largest first, or set `Pack` to remove the padding. Both change the bytes, so settle the layout before you store data. See [Struct Layout](/en/docs/v4/performance#struct-layout).

### Deterministic Bytes

Nino zeroes padding bytes, so equal values always produce equal bytes, even for structs built in uninitialized memory (`stackalloc`, `SkipLocalsInit`). You can hash or compare payloads directly, for example to skip sending unchanged state:

```csharp
buffer.ResetWrittenCount();
NinoSerializer.Serialize(state, buffer);
ulong hash = XxHash64.HashToUInt64(buffer.WrittenSpan); // System.IO.Hashing
if (hash != lastHash) { Send(buffer.WrittenSpan); lastHash = hash; }
```

## Choose the Cheapest Format [#choose-the-cheapest-format]

Each `[NinoType]` picks its [format](/en/docs/v4/evolving-data) and whether it tracks references. Every option beyond the default costs bytes and time on every value of the type, so give it only to the types that need it:

| Option | Extra bytes | Extra work |
| --- | --- | --- |
| Positional (a bare `[NinoType]`) | none | none: raw structs are copied as memory, and [fixed-size types](/en/docs/v4/performance#fixed-size-types) are written straight into their `byte[]` |
| `format: NinoFormat.VersionTolerant` | 4 per object | one length per object; the type is no longer raw or fixed-size |
| `format: NinoFormat.Keyed` | 8 per member, plus 4 per object | a key and a length per member, and a key check per member when reading; the type is no longer raw or fixed-size |
| `trackReferences: true` | 4 per tracked object | an identity lookup per tracked object, plus a small fixed cost per top-level call |

- Keep messages and caches that are written and read by the same build positional, and give version tolerance or keys only to the data that outlives a release: see [Choosing](/en/docs/v4/evolving-data#choosing).
- Track references only on the types that are actually shared or form cycles: in the [organization chart](/en/docs/v4/reference-tracking), only `Department` is tracked, and `Employee` pays nothing. Tree-shaped data needs no tracking, however deep it is.
- Prefer the per-type `format` to `WEAK_VERSION_TOLERANCE`: the symbol makes every positional type of the project version-tolerant, so its structs are no longer copied as raw memory.

## Seal Classes, and Dispatch Through a Base [#sealed-and-polymorphic]

What Nino writes in front of a class value depends on the declared type of its slot ([How a Polymorphic Value Is Written](/en/docs/v4/polymorphism#how-a-polymorphic-value-is-written)):

- **Seal classes that have no subtypes.** A sealed class costs a 1-byte null flag and no dispatch; a class that is not sealed costs a 4-byte type id and a type check, even when it has no subtype.
- **Dispatch through a common `[NinoType]` base.** For subtypes declared in the base's assembly, generated code writes through a chain of exact type checks and reads through a `switch` on the type id, calling each subtype's formatter directly. Subtypes from other assemblies, generic subtypes, tracked types, and writes in hierarchies of more than 64 subtypes go through a lock-free registry instead ([Dispatch](/en/docs/v4/polymorphism#dispatch)).
- **Keep `object` and the boxed API off hot paths.** A slot declared as `object` dispatches through the global registry of every `[NinoType]`, and `SerializeBoxed`/`DeserializeBoxed` find the formatter by `Type` and box value types ([Runtime Types](/en/docs/v4/basic#runtime-types)).

## Choose Collections That Copy as Blocks [#collections]

- **Bulk data in arrays and lists of raw elements.** A `T[]` or `List<T>` of unmanaged values or raw structs is one block copy, and so are arrays and lists of value tuples and `KeyValuePair`s of raw items (rearranged with [SIMD](/en/docs/v4/platforms#simd) where the CPU allows). The full list is in [Raw Memory for Unmanaged Data](/en/docs/v4/performance#raw-memory-for-unmanaged-data).
- **`List<T>` for counts that vary.** Reuse deserialization fills a list in place and keeps its capacity; an array is reused only when the new data has the same length. A dictionary is merged by key.
- **Declare the type you want created.** A member declared as `IList<T>`, `IEnumerable<T>` or `IReadOnlyList<T>` is read back as a `List<T>`, `ISet<T>` as a `HashSet<T>`, `IDictionary<TKey, TValue>` as a `Dictionary<TKey, TValue>` ([Collection Types](/en/docs/v4/types#collection-types)). Nullable raw elements are one block only in an array or a `List<T?>`: declared as an interface, each element is written on its own.
- **Collections are values.** The same collection in two members is written twice; reference tracking covers `[NinoType]` classes, not collections.

## Strings [#strings]

- The default encoding writes text whose chars are all at most U+00FF in one byte a char and other text as UTF-16, each in one pass. `[NinoUtf8]` costs a transcode and a byte count (one byte up to 127 bytes of UTF-8), and pays off only for text that is mostly ASCII with a few wider chars ([String Encoding](/en/docs/v4/defining-types#string-encoding)).
- Reuse deserialization keeps a string whose text did not change, so stable text (names, keys, enum-like codes) costs nothing per message; a `[NinoUtf8]` string is kept only when its text is ASCII.

## Custom Formatters on Hot Paths [#custom-formatters]

A [custom formatter](/en/docs/v4/custom-formatters) is a struct that Nino calls directly and the JIT inlines, like a generated one. Keep it on the same fast paths:

- **Copy unmanaged runs as one block**: `Writer.Write<T>(ReadOnlySpan<T>)` writes a length and the elements in one copy, and `WriteUnmanagedRaw` / `ReadUnmanagedRaw` move them without a length into memory you already have. Mark a generic formatter's element parameter `[NinoRaw]` so it is bound only to types Nino copies as raw bytes ([example](/en/docs/v4/custom-formatters#example-grid)).
- **Read into the current value.** `Deserialize(ref T value, ref Reader reader)` receives the instance the caller holds: fill it when its shape fits, and keep its strings with `reader.ReadString(current)`, which returns `current` itself when the text is unchanged. Reuse deserialization then stays at 0 B through your type.
- **Check lengths before allocating** with `ReadLength(minElementSize)`, which throws when the bytes left cannot hold that many elements.
- **Cost:** a `[NinoMemberFormatter]` on a member means its type is no longer copied as raw memory and is no longer fixed-size. Give hot structs built-in member types where you can.

The methods `Writer` and `Reader` offer: [Writer and Reader](/en/docs/v4/custom-formatters#writer-and-reader).

## Startup and the First Call [#startup]

The first call for each type pays costs that later calls do not: Nino finds the type's formatter (in the generated registry of its assembly, loaded the first time Nino needs it; on a JIT, a type the generator did not see, such as a collection that only appears at run time, gets a formatter built through reflection), the JIT compiles the code, and a `[NinoPooled]` type runs its `OnNinoPoolWarmup()`. To keep these off the first message:

- Call `NinoRegistry.EnsureInitialized(assembly)` for an assembly you load at run time (a plugin, a hot update), or `NinoRegistry.EnsureAllInitialized()` for every loaded assembly, to load the registries now. Both are optional: registries load on first use anyway.
- Serialize and deserialize one representative value of each hot type during startup or a loading screen. That builds their formatters, fills their pools and grows your buffers to their working size.
- Configure `NinoSettings` before either.

**Cost:** startup time, and the memory of the instances the pools now hold. Warm-up calls run unoptimized Tier-0 code, so they do not replace warming up before you [measure](#measure).

## Large Collections of Scattered Objects [#large-collections]

Each element of a `T[]` or `List<T>` of classes is an object of its own on the heap. While the collection's order is the order its objects were allocated in, the CPU's hardware prefetcher fetches the next ones before the loop needs them. Once objects were replaced, shuffled or sorted after they were created, each element is a cache miss the hardware cannot predict, and on a collection larger than the cache the loop spends most of its time waiting for memory.

The MSBuild property `NinoPrefetchLargeCollections` makes Nino fetch those objects ahead itself (software prefetch), in the project that makes the calls:

```xml title="MyApp.csproj"
<PropertyGroup>
  <NinoPrefetchLargeCollections>true</NinoPrefetchLargeCollections>
</PropertyGroup>
```

With it set, these calls prefetch:

- `NinoSerializer.Serialize(collection)`, with or without an `IBufferWriter<byte>`, and `NinoDeserializer.Deserialize(bytes, ref collection)` into an existing collection holding as many elements (its objects are reused, so the scattered ones are read into);
- where `collection` is a `T[]` or `List<T>` of a non-generic `[NinoType]` class (an abstract base included) that is not [fixed-size](/en/docs/v4/performance#fixed-size-types), written or read directly (not as a member of another type) through a call the [interceptors](#per-call-overhead) route (a project built with the .NET 8 SDK or later), running on .NET 8 or later on x64 or Arm64;
- and only when the collection takes more than a quarter of the CPU's last-level cache and its first objects are not in allocation order. Every other collection is written and read as before.

The bytes are the same either way. Set it when a hot path serializes such collections, and [measure](#measure) it on your data: collections that fit in the cache, or whose objects are still in allocation order, gain nothing. Unity projects are unaffected: Unity compiles with the generator's Roslyn 4.3 build, which has no interceptors, so the property does nothing there.

**Cost:** without the property (the default), nothing: the generated code is the same as before. With it, each top-level call of such a collection tests its length before its loop, which made calls on short collections a few percent slower in our benchmarks, so set it only in projects that handle such collections.

## Per-Call Overhead [#per-call-overhead]

Once nothing allocates, what is left is a few nanoseconds per call, which matters most when small values are serialized in a tight loop. Build with Roslyn 4.8 or later (the .NET 8 SDK and later): calls whose type is known at the call site then go straight to the generated formatter, without the formatter cache lookup and its virtual call. Calls inside generic code, calls for `[NinoType]`s declared in another assembly, and Unity projects (which use the Roslyn 4.3 build) take the regular path, with the same bytes. See [Interceptors](/en/docs/v4/performance#interceptors).

## Thread Safety [#thread-safety]

Every `NinoSerializer` and `NinoDeserializer` method is safe to call concurrently without locks, but the state you own is not: a `NinoArrayBufferWriter`, a `Writer` or `Reader`, and the objects you deserialize into. That is why every recipe keeps one buffer per thread or per owner. Details: [Thread Safety](/en/docs/v4/performance#thread-safety).

## Measure [#measure]

- **Warm up first.** The first calls grow the buffers, fill the pools and run unoptimized Tier-0 code; measure after that.
- **Count bytes per thread.** `GC.GetAllocatedBytesForCurrentThread()` counts every byte the current thread allocates, so a unit test can pin a hot path at 0 B: see [Verify It](/en/docs/v4/advanced/zero-allocation#verify-it). For a whole service, BenchmarkDotNet's `[MemoryDiagnoser]` reports the same number per operation.
- **Time long runs.** Use BenchmarkDotNet or other long runs, and measure deserialization with reused instances: for large collections, allocating and zeroing the result often costs more than reading it. See [Measuring](/en/docs/v4/performance#measuring).

To put all of this into practice, start from the recipes in [Zero-Allocation Patterns](/en/docs/v4/advanced/zero-allocation) and check your hot path against its [checklist](/en/docs/v4/advanced/zero-allocation#checklist).
