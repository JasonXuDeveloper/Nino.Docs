Nino supports Unity 2022.3 and later on Mono and IL2CPP, every player platform, and HybridCLR hot-update assemblies without any initialization call. This guide covers installation, assembly definitions, the optional Burst kernels, the Unity classes Nino serializes, IL2CPP builds, hot updates and GC-free frames.

## Setup

<Steps>
<Step>

### Install the package

Install Nino from [OpenUPM](https://openupm.com/packages/com.jasonxudeveloper.nino/):

```shell
openupm add com.jasonxudeveloper.nino
```

The package contains `Nino.Core.dll`, the source generator `Nino.Generator.dll` (labelled `RoslynAnalyzer`, so Unity runs it on your scripts), its code fixes `Nino.Generator.CodeFixes.dll` (for Rider and Visual Studio), `Nino.UnityTypes.dll` (formatters for the [Unity classes](#unity-classes) below), and the `System.Buffers`, `System.Memory` and `System.Runtime.CompilerServices.Unsafe` assemblies Nino.Core needs.

</Step>
<Step>

### Reference it from your assembly definitions

Assemblies with an `.asmdef` see `Nino.Core.dll` when **Auto Referenced** is on. If an assembly uses **Override References**, add `Nino.Core.dll` to its list explicitly. The generator runs on every assembly that references `Nino.Core`.

</Step>
<Step>

### Mark your types

```csharp
using Nino.Core;
using UnityEngine;

[NinoType]
public class PlayerState
{
    public string Name;
    public Vector3 Position;      // Unity structs are unmanaged: written as raw memory
    public Quaternion Rotation;
    public Color32[] Palette;     // one block copy
}
```

</Step>
</Steps>

## What Differs from .NET

- **`partial` is required for private members.** Unity compiles against .NET Standard, which has no `[UnsafeAccessor]`, so a type that serializes non-public members (or is `[NinoPooled]`) must be `partial`, and so must every type that contains it. The analyzer reports this as NINO002. The code fix that adds `partial` works in Rider and Visual Studio as well; in other editors, add it yourself.
- **No interceptors.** The Unity package ships the generator's Roslyn 4.3 build, the oldest compiler Unity supports, so calls use the regular path. The bytes are identical, and the difference is a few nanoseconds per call.
- **Same bytes as .NET.** Data written by a .NET server can be read by a Unity client and the other way round, including 32-bit IL2CPP players and old Mono runtimes. See [Platforms and Binary Format](/en/docs/v4/platforms).

## Burst-Accelerated Kernels [#burst-kernels]

Unity runs the netstandard build of `Nino.Core`, which has no hardware intrinsics: on its own it moves tuples, padded structs and Latin-1 text a field or a word at a time. Install **Burst** and Nino moves them with SIMD instead, with no change to your code:

1. Open **Window > Package Manager**, select **Unity Registry** and install **Burst** (`com.unity.burst`) 1.8 or later. Projects that use Entities or Collections have it already, as both depend on it.
2. That is all. The Nino package's `Nino.Burst` assembly compiles as soon as Burst is in the project (it is skipped without it) and registers its kernels at startup, before the first scene loads, and in the editor after every domain reload.

| Kernel | What it speeds up | From |
| --- | --- | --- |
| Permute | Writing and reading arrays and lists of value tuples, `KeyValuePair`s and `[NinoType]` structs whose bytes differ from their memory (padding, tuple or pair members), and copying arrays of raw structs with padding, which is cleared on the way; values of up to 64 bytes. On x64 CPUs with AVX2, values of up to 16 bytes go two or more per 32-byte vector | 16 values (AVX2: 256) |
| Narrow, Widen | Writing and reading strings in the one-byte (Latin-1) form, ASCII included: 16 chars at a time | 32 chars |

Shorter arrays and strings stay on the scalar paths, where the call to a kernel would cost more than it saves. Arrays of raw structs without padding (`Vector3[]`, `Color32[]`, your own unmanaged structs) are one memory copy with or without Burst.

<UnityHighlights lang="en" />

**Instruction sets.** The kernels use AVX2 (`vpshufb`) and SSSE3 (`pshufb`) on x86 and x64 and Neon (`tbl`) on Arm64, in the editor, in Mono and IL2CPP players, and for HybridCLR hot-update code, which calls them through the AOT `Nino.Core`. Where they cannot run, Nino registers none and keeps its scalar paths: Armv7 (32-bit Android), WebGL, x86 and x64 CPUs without SSSE3, players where Burst does not run, and the editor with Burst compilation turned off (**Jobs > Burst > Enable Compilation**).

**x64 players: enable SSE4 and AVX2.** Burst compiles a player's code once for each x64 CPU target in **Edit > Project Settings > Burst AOT Settings** and picks the variant the CPU runs at startup. The AVX2 target gives AVX2 CPUs the 32-byte permute; the SSE4 target gives CPUs with SSSE3 but no AVX2 the 16-byte kernels. The SSE2 variant has no byte shuffle, so without an SSE4 target such a CPU gets no kernels at all. The default list depends on the Burst version (1.8.29's is SSE2 and AVX2), so check that it includes SSE4 and AVX2, as Nino's own test project does (SSE2, SSE4 and AVX2).

**Same bytes.** Each kernel writes exactly the bytes of the scalar path it replaces, so players with and without Burst, .NET servers and the [Go, Rust and TypeScript runtimes](/en/docs/v4/advanced/codegen) all read each other's data. Nino's CI checks every kernel against its scalar reference byte for byte, in the editor and in IL2CPP players, on Unity 2022.3 and 6000.3. The [Unity benchmark](/en/docs/v4/perf-unity) times an IL2CPP player with and without the kernels for every release.

To check or switch them at run time, use the `Nino.Burst.NinoBurst` class (code in an assembly definition of yours needs a reference to the `Nino.Burst` assembly definition to call it):

```csharp
using Nino.Burst;

Debug.Log($"Nino Burst kernels: {NinoBurst.Registered}, {NinoBurst.IsaName}"); // Isa: 3 AVX2, 1 SSSE3, 2 Neon, 0 none
NinoBurst.Unregister(); // back to the scalar paths, e.g. to compare frame times
NinoBurst.Register();   // false where Burst is off or the CPU has none of the instruction sets
NinoBurst.Register(NinoBurst.Ssse3); // keep an AVX2 CPU on the 16-byte kernels (the same bytes)
```

## Unity Classes

Unity's structs (`Vector3`, `Quaternion`, `Color32`, `Bounds`...) are unmanaged, so Nino writes them as raw memory with no formatter. Three Unity classes have formatters in `Nino.UnityTypes.dll`, which ships in the Unity package beside `Nino.Core.dll`, so they work as members, list elements or top-level values:

| Class | Written as |
| --- | --- |
| `AnimationCurve` | its keys (time, value, tangents, weights and weighted mode of each), then its pre- and post-wrap modes |
| `Gradient` | its color keys, its alpha keys, then its mode |
| `RectOffset` | its left, right, top and bottom |

`null` is supported, and deserializing with `ref` into an existing instance refills it. If an assembly uses **Override References**, add `Nino.UnityTypes.dll` to its list too. Other Unity classes (`Texture2D`, `Material`, `ScriptableObject`...) are assets, not data: serialize the values you need from them, or write a [custom formatter](/en/docs/v4/custom-formatters).

## IL2CPP

- Generated code is plain C#: no reflection at serialization time, no `System.Reflection.Emit`.
- Each generated registry is marked `[RuntimeInitializeOnLoadMethod]` (and `[InitializeOnLoadMethod]` in the editor), which runs it at startup and keeps it from being stripped by the IL2CPP linker. Without it, registration would still happen lazily on first use.
- Generic `[NinoType]` instantiations and built-in generic collections that your code **names** (member types, `NinoSerializer.Serialize<List<MyStruct>>` calls) are registered by the generator, so IL2CPP compiles them ahead of time.
- An instantiation that you only create through reflection and only **read** polymorphically needs one line at startup: `NinoPolymorphic.Register<Box<MyStruct>>()`.

## HybridCLR Hot Update

Nino needs **no initialization call** in hot-update code. Generated registries are found lazily: the first time Nino meets a type of a newly loaded assembly, or a type id it does not know yet, it finds that assembly's registry. So:

```csharp
Assembly hotUpdate = Assembly.Load(dllBytes); // HybridCLR
// nothing else to do: types in hotUpdate serialize, including subtypes of AOT base classes
```

A typical split: the AOT shell (launcher, network layer) declares the `Message` base class and reads every frame as a `Message`; the hot-update DLL declares the gameplay messages and config types. When an update adds `public sealed class EnterDungeon : Message`, the shell's network code reads it as soon as the new DLL is loaded, with no registration call and no rebuilt shell.

- Put hot-update types in an assembly definition that references `Nino.Core`, or build them in a separate C# project that installs Nino from NuGet and load the DLL as usual.
- Follow HybridCLR's own rules for AOT generics: load supplementary metadata for the AOT assemblies your hot-update code instantiates generics from.
- Hot-update code runs in HybridCLR's interpreter, which does not inline calls. For this reason, Nino's generated code calls `Nino.Core` directly, without wrapper layers.
- Registration is lazy, so the first serialization of a hot-update type pays for loading its registry. To pay that during a loading screen instead, call `NinoRegistry.EnsureInitialized(hotUpdate)` after loading the assembly (or `NinoRegistry.EnsureAllInitialized()` for every loaded assembly). Both are optional.

## Startup Checklist

Most projects need none of these steps. Run the ones you need once, before the first serialization call:

| Step | Needed when | Not needed when |
| --- | --- | --- |
| `NinoSettings` (`DefaultPoolMaxRetained`, `SetPoolMaxRetained<T>`, `SetRecycler<T>`) | You want other pool sizes than the defaults (256 shared, 64 per thread), or your own pools should receive dropped instances. Set them **first**: they are read without synchronization. | The defaults suit you. |
| HybridCLR supplementary metadata | Hot-update code instantiates generics defined in AOT assemblies. Follow HybridCLR's rules; Nino adds none of its own. | There is no hot update. |
| `Assembly.Load` of hot-update DLLs | Before reading data that contains their types. | |
| `NinoRegistry.EnsureInitialized(assembly)` or `EnsureAllInitialized()` | You want the one-time registry load on a loading screen instead of the first call that meets the assembly. | Always optional: registries load on first use. |
| `NinoPolymorphic.Register<T>()` | A closed generic `[NinoType]` such as `Box<MyStruct>` that this process only **reads** through a base type, and never names in code or writes. | Ordinary subtypes in any assembly, hot update included: they are found automatically. |

```csharp
public static class NinoStartup
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.BeforeSceneLoad)]
    private static void Init()
    {
        NinoSettings.SetPoolMaxRetained<Bullet>(1024); // only if the defaults do not fit
        NinoPolymorphic.Register<Box<MyStruct>>();     // only for read-only closed generics
    }
}

// after HybridCLR has loaded its supplementary metadata:
Assembly hotUpdate = Assembly.Load(dllBytes);
NinoRegistry.EnsureInitialized(hotUpdate);             // optional: pay the registry load now
```

## Config Tables

Game data authored in spreadsheets or the editor (items, levels, drop tables) is a good fit for Nino: export it to a `.bytes` file once, and load it at runtime without any parsing. Give the table types `format: NinoFormat.Keyed`, so that adding or reordering a column does not break files exported before:

```csharp title="ItemTable.cs"
[NinoType(format: NinoFormat.Keyed)]
public sealed class ItemTable
{
    public List<ItemRow> Rows;
}

[NinoType(format: NinoFormat.Keyed)]
public sealed class ItemRow
{
    public int Id;
    public string Name;
    public int Price;
}

// Editor: export after the table is edited (a menu item, or an import step for your spreadsheets)
File.WriteAllBytes("Assets/Config/items.bytes", NinoSerializer.Serialize(table));

// Player: .bytes files import as TextAsset
var asset = Resources.Load<TextAsset>("Config/items");
ItemTable items = NinoDeserializer.Deserialize<ItemTable>(asset.bytes);
```

## Frame-Time Tips

- **No GC spikes from network or replay data:** deserialize each tick into the previous tick's object with `ref`, and mark the classes you create in bulk (bullets, events) `[NinoPooled]`. See [Zero-Allocation Patterns](/en/docs/v4/advanced/zero-allocation).
- **Reuse one `NinoArrayBufferWriter`** per sender for outgoing data instead of calling `Serialize(value)` and allocating a `byte[]` each frame.
- **Keep bulk data unmanaged:** arrays of `Vector3`, `Color32` or your own unmanaged `[NinoType]` structs are one memory copy.

<Callout type="warn">

With **Enter Play Mode Options** and domain reload disabled, static state survives between play sessions, including `[NinoPooled]` pools and `NinoSettings`. If stale instances would be a problem, clear the pools you use when play mode starts: `NinoPool<Bullet>.Shared.Clear()`.

</Callout>

## Troubleshooting

<Accordions type="single">
<Accordion title="My types are not serialized / the generator does not run">

Check that the assembly references `Nino.Core.dll` (Auto Referenced, or listed under Override References) and that `Nino.Generator.dll` is still labelled `RoslynAnalyzer` in its import settings. Then try the `Nino.Unity` sample project from the GitHub repository, which includes a test suite you can run with the Test Runner.

</Accordion>
<Accordion title="error NINO002: Type must be partial">

The type serializes private members, or is `[NinoPooled]`, and Unity has no `[UnsafeAccessor]`. Make the type and every type containing it `partial` (the code fix does this in Rider and Visual Studio).

</Accordion>
<Accordion title="Data from an older build cannot be read">

Nino's default format is positional: changing a type's members breaks old data. Use `NinoFormat.VersionTolerant` or `NinoFormat.Keyed` for anything that is stored. See [Evolving Your Data](/en/docs/v4/evolving-data). Data written by Nino v3 cannot be read by v4 at all; see [Migrating from v3](/en/docs/v4/migration).

</Accordion>
</Accordions>
