Short answers to the questions people ask most about Nino, each with a link to the full page. The last ones cover the errors and surprises people run into most.

## What is Nino?

Nino is a general-purpose, high-performance binary serializer for C# and .NET. You mark a type with `[NinoType]`, and a Roslyn source generator writes its serialization code at compile time; at run time you call `NinoSerializer.Serialize` and `NinoDeserializer.Deserialize`. There is no reflection, no runtime code generation, no schema file and no registration step. Nino is open source under the MIT license: [github.com/JasonXuDeveloper/Nino](https://github.com/JasonXuDeveloper/Nino). See [Introduction](/en/docs/v4).

## How do I install Nino?

In a .NET or Godot project, run `dotnet add package Nino --prerelease` (v4 is still a prerelease: without the flag NuGet installs the stable 3.9.x, a test build of v4 features that is not compatible with v4); the `Nino` package brings in the runtime (`Nino.Serialization`) and the source generator (`Nino.Generator`). In Unity, install `com.jasonxudeveloper.nino` from OpenUPM (`openupm add com.jasonxudeveloper.nino`), which includes the generator. Optional packages add immutable collections (`Nino.Immutable`), ASP.NET Core bodies (`Nino.AspNetCore`) and generated TypeScript, Go or Rust (`Nino.Codegen`). See [Quick Start](/en/docs/v4/start).

## Which platforms and .NET versions does Nino support?

The runtime targets `netstandard2.0`, `netstandard2.1`, `net8.0` and `net10.0`. Nino runs on .NET servers and desktop apps, Unity 2022.3 and later (Mono and IL2CPP, every player platform), Godot 4 .NET projects and HybridCLR hot update, and every target writes identical bytes. The generator needs Roslyn 4.3 or later and the project must use C# 9 or later. See [Platforms and Binary Format](/en/docs/v4/platforms).

## Does Nino use reflection? Does it work with IL2CPP and NativeAOT?

No reflection: the generator writes one formatter per type at compile time, so Nino works under IL2CPP, NativeAOT and HybridCLR, where runtime code generation is unavailable. See [Performance Guide](/en/docs/v4/performance).

Nino.Core's net8.0 and net10.0 builds are also annotated for trimming and Native AOT: publishing with `PublishTrimmed` or `PublishAot` gives no warnings from Nino. Under Native AOT, Nino uses only the formatters the generator wrote, so every type you serialize must appear in code the generator sees (as a member type, or as the type argument of a `Serialize` or `Deserialize` call). A type that only exists at run time fails with an error that names it, never with wrong data. See [Trimming and Native AOT](/en/docs/v4/platforms#trimming-and-native-aot).

## How fast is Nino compared with MemoryPack?

In the same benchmark run, Nino v4 serializes up to <BenchValue k="serialize.max" /> faster than MemoryPack and deserializes classes and polymorphic graphs up to <BenchValue k="deserialize.max" /> faster; on raw struct arrays the two are at least on par. Serializing into a reused buffer allocates nothing. See [Benchmarks](/en/docs/v4/benchmarks) and [Nino vs MemoryPack](/en/docs/v4/vs-memorypack).

## What can I use Nino for?

Anything that turns .NET objects into compact bytes and back: network protocols and RPC between services, message queues and event streams, caches, files and other persistent storage, inter-process communication, and data pipelines. The same code runs on .NET servers, desktop apps, Unity and Godot. See [Advanced Guides](/en/docs/v4/advanced).

## Can I change my types after data has been written?

Yes, if you choose a format for it. A plain `[NinoType]` is positional and the fastest. `[NinoType(format: NinoFormat.VersionTolerant)]` lets you append members, and `[NinoType(format: NinoFormat.Keyed)]` lets you add, remove and reorder members. See [Evolving Your Data](/en/docs/v4/evolving-data).

## Does Nino support polymorphism and shared references?

Yes. A value declared as a base class or interface is read back as its runtime type, with no union tags to maintain. Reference tracking, enabled per type, preserves shared references and cycles. See [Polymorphism](/en/docs/v4/polymorphism) and [Reference Tracking](/en/docs/v4/reference-tracking).

## How do I serialize many message types, or a type known only at run time?

Give the types a common `[NinoType]` base class or interface and call `Serialize<TBase>` / `Deserialize<TBase>`: generated code writes the type id and dispatches on it, it is the fastest option, and it works with reuse deserialization and pooling so a message allocates nothing but strings whose text changed. This covers RPC and message dispatch, plugin systems and editor tooling. Only when the type is known only as a `Type` and the types share no common base (reflection-driven tooling over arbitrary types), use `SerializeBoxed(value, type)` and `DeserializeBoxed(data, type)`. Avoid `object` as the type argument: it accepts only `[NinoType]` values and dispatches through the global registry, which costs more. See [Runtime Types](/en/docs/v4/basic#runtime-types).

## Is Nino thread safe?

Yes. `NinoSerializer` and `NinoDeserializer` are static and can be called from any number of threads without locking. A `NinoArrayBufferWriter` that you create yourself is not thread safe: use one per thread or per connection. See [Serialize and Deserialize](/en/docs/v4/basic).

## Can Nino v4 read data written by Nino v3?

No. v4 has a new binary format and cannot read data written by v3 or by the v4 betas and previews, so stored v3 data has to be converted once. See [Migrating from v3](/en/docs/v4/migration). Between v4 release candidates, see [Upgrading from an Earlier Release Candidate](/en/docs/v4/migration#upgrading-from-an-earlier-release-candidate).

## Can I use Nino from JavaScript or TypeScript?

Yes. [Nino.Codegen](/en/docs/v4/advanced/codegen#typescript) generates TypeScript classes, enums and codecs for your `[NinoType]`s after each build, with the `nino.ts` runtime, so browsers and Node read and write exactly the bytes .NET writes, without the .NET runtime. It leaves out generic types, reference tracking and a few built-in types ([What TypeScript Leaves Out](/en/docs/v4/advanced/codegen#not-supported)). For those, run the C# types themselves in the browser: a .NET `browser-wasm` app that references Nino, called from JavaScript through `[JSExport]`, at the cost of downloading the .NET runtime. See [Browser and JavaScript Clients](/en/docs/v4/advanced/browser).

## Can ASP.NET Core read and write Nino bodies?

Yes, with [Nino.AspNetCore](/en/docs/v4/advanced/aspnetcore) (4.0.0-rc.6 and later): `AddNinoFormatters()` adds MVC input and output formatters for `application/x-nino`, and Minimal APIs take a `NinoBody<T>` parameter and return `NinoResults.Ok(value)`. Bodies are read from the request pipe and written to the response pipe without allocations of their own.

## When should I not use Nino?

When people need to read or edit the data (use JSON, YAML or TOML), or when a program in a language other than C#, TypeScript, JavaScript, Go or Rust must read it: the format is defined by your C# types, with no schema file and no generator for those languages, so use Protocol Buffers, FlatBuffers or MessagePack for that. JavaScript, TypeScript, Go and Rust programs use Nino through [generated code](/en/docs/v4/advanced/codegen), and browsers can also run the C# types on [.NET WebAssembly](/en/docs/v4/advanced/browser). See [Limitations](/en/docs/v4/limit).

## Why does Nino say there is no formatter for a type? [#no-formatter]

`Nino: no formatter for T` means Nino does not know how to write `T`. Mark it `[NinoType]`, or declare a formatter for it with [`[assembly: NinoFormatter]`](/en/docs/v4/custom-formatters#for-a-type-assembly-ninoformatter) (or [`[NinoMemberFormatter]`](/en/docs/v4/custom-formatters#for-one-member) on the member). For a member, the analyzer already reports this as you type (NINO007). The generator must also run in the project that declares the type: install the `Nino` package there, and in Unity let its assembly reference `Nino.Core`.

Under Native AOT the message says the runtime cannot build formatters at run time: only the closed types the generator saw exist. Name the exact type in a `[NinoType]` member or a `Serialize`/`Deserialize` call. See [Trimming and Native AOT](/en/docs/v4/platforms#trimming-and-native-aot).

## Why does reading throw that a type id is not a registered subtype? [#unknown-type-id]

The data names a type the reader cannot find under the declared type. Usually the subtype lives in an assembly that is not loaded yet (load it first; there is nothing to register), the type was renamed or moved without [`[NinoFormerName]`](/en/docs/v4/defining-types#former-name), or the data was written for another declared type. A closed generic subtype that the process only reads needs `NinoPolymorphic.Register<T>()` at startup. When *writing* throws that a type is not a registered subtype, the runtime type is not a `[NinoType]`: its base sets `allowInheritance: false` (NINO003), or the generator does not run in its assembly. See [Subtypes in Other Assemblies](/en/docs/v4/polymorphism#subtypes-in-other-assemblies).

## Why does serializing throw that the object graph has a cycle? [#cycle]

An object refers back to itself through its members, and nothing tracks references, so it would be written forever. Mark the types on the cycle [`trackReferences: true`](/en/docs/v4/reference-tracking). The same goes for an error that a type is nested more than 512 objects deep: classes created by their constructor or compared by value cannot be deferred, so give a deeply recursive type a parameterless constructor and settable members. See [Deep Object Graphs](/en/docs/v4/basic#deep-object-graphs).

## Why does old data no longer deserialize, or come back with wrong values? [#old-data]

A bare `[NinoType]` is positional: adding, removing or reordering members changes the bytes, and reading older data then throws (`unexpected end of data`, `invalid length`) or, worse, returns wrong values, since the bytes carry no schema. Give stored data `NinoFormat.VersionTolerant` or `NinoFormat.Keyed` before writing any, and in a version-tolerant hierarchy append members only to the classes without subclasses. To catch a change in CI, compare the [layout metadata](/en/docs/v4/evolving-data#layout-metadata) of each build. See [Evolving Your Data](/en/docs/v4/evolving-data).

## Why are my calls not intercepted? [#not-intercepted]

Interceptors need Roslyn 4.8 or later (the .NET 8 SDK and later); Unity uses the Roslyn 4.3 build and never intercepts. Calls inside generic code, calls for `[NinoType]`s declared in another assembly and calls for raw values take the regular path on purpose. If your project sets `InterceptorsNamespaces` itself, append to it instead of replacing it. Either way the bytes are the same. See [Interceptors](/en/docs/v4/performance#interceptors).

## Why does my hot path still allocate? [#still-allocates]

Check, in order: you serialize into a reused `NinoArrayBufferWriter` (or another `IBufferWriter<byte>`) rather than calling `Serialize(value)`, which returns a new `byte[]`; you deserialize into an existing value with `ref`; a `Writer` or `Reader` you create yourself ends with `ReleaseReferences()`; arrays keep the same length (use `List<T>` for counts that vary); the classes Nino has to create are `[NinoPooled]`; and you measure after warming up. Text that changes is always a new string. See [What Allocates](/en/docs/v4/advanced/zero-allocation#what-allocates) and the [checklist](/en/docs/v4/advanced/zero-allocation#checklist).
