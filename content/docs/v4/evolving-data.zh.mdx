数据往往比代码活得更久。保存的文档、缓存的资源、旧版客户端发来的消息，都要由新版本的类型来读，有时反过来也一样。所以数据离开进程之前，就要定好每个类型的格式：默认的按位置格式，数据一旦写出，成员就不能再动；以后改格式，已有的数据同样读不了。Nino 为每个类型提供三种格式，也就是 `NinoFormat` 枚举的三个值，用 `[NinoType(format: ...)]` 选定：

`Positional` 是默认格式；另外两种是 `[NinoType(format: NinoFormat.VersionTolerant)]` 和 `[NinoType(format: NinoFormat.Keyed)]`。拿不准用哪种，看[如何选择](#choosing)里的三个问题。

无论哪种格式，都**不能修改成员的类型**。按位置和版本容错格式不写成员名，所以可以随意**重命名成员**；键控成员和连同类型 ID 写出的类型改名时，要用 `[NinoFormerName]` 留住旧名称（见[重命名](#renaming)）。

## 按位置 [#positional]

不带参数的 `[NinoType]` 会依次写出各个成员，不带名称、长度或键。这是最快、最小的格式，适合写入和读取都在同一个构建里的数据：版本一致的客户端与服务器之间的网络消息、可以重建的缓存、内存中的快照。

<Callout type="warn">

只要成员列表有任何变化（新增、删除、重排、修改索引），旧数据就无法读取：读取时要么抛出异常，要么（更糟）读出错误的值。

</Callout>

[原始结构体](/zh/docs/v4/defining-types#structs)按内存原样拷贝，所以它的字段顺序和 `StructLayout` 也是格式的一部分。`NinoFormat.VersionTolerant` 或 `NinoFormat.Keyed` 的结构体则逐个成员写出。

## 版本容错 [#version-tolerance]

应用的 1.1 版在设置文件里加了字号，而用户手里还是 1.0 写出的文件：

```csharp
[NinoType(format: NinoFormat.VersionTolerant)] // [!code highlight]
public class Settings
{
    public string Theme = "light";
    public bool Notifications;
    public int FontSize = 14; // [!code ++]
}
```

无论继承体系有多深，对象的成员（`[NinoType]` 基类的成员在前）都写在同一个 4 字节长度之后：

- **新代码读旧数据：** 数据里缺少的成员保留原有的值：读入已有实例时是这个实例当前的值，否则是构造函数设置的值（包括字段初始化器）。1.1 读取 1.0 的文件时，`FontSize` 是 `14`，而不是 `0`。通过构造函数重新创建的类型（带主构造函数的记录、只读成员），缺少的构造函数参数传 `default`，而不是参数声明的默认值。
- **旧代码读新数据：** 旧代码不认识的字节直接跳过。
- 成员可以追加到**最末端的派生类型**，也就是对象数据的末尾。嵌套多深都可以：每个版本容错对象都带有自己的长度，在集合、字典和多态成员里也一样。

<Callout type="warn">

以下改动不在容错范围内：向有 `[NinoType]` 子类的基类追加成员（参见[下文](#appending-to-a-base-class)），插入、删除或重排成员，向 `[NinoType]` 接口追加成员，以及在继承体系中增加或移除 `[NinoType]` 类。使用 `[NinoType(false)]` 时，新成员的索引必须大于所有已有成员。

</Callout>

<Callout type="info">

到 4.0.0-rc.8 为止，在项目中定义符号 `WEAK_VERSION_TOLERANCE` 会让项目里所有按位置格式的类型变为版本容错。这个符号已经移除：项目仍定义它时，错误 [NINO032](/zh/docs/v4/analyzers#nino032) 会标出每个这样的类型，代码修复给它加上 `format: NinoFormat.VersionTolerant`，字节不变。之后再删掉这个符号。

</Callout>

### 向基类追加成员 [#appending-to-a-base-class]

在版本容错的继承体系中，只能向没有子类的类追加成员。如果基类需要新成员，请把整个继承体系改成 [`NinoFormat.Keyed`](#keyed-members)。原因如下。

继承体系的各层共用对象的这一个长度，成员从根类开始依次写出。因此追加到基类的成员会落在子类成员**之前**，把它们往后挤：

```csharp
// 第 2 版在基类末尾追加 Revision
[NinoType(format: NinoFormat.VersionTolerant)]
public class Document
{
    public int Id;
    public int Revision; // [!code ++]
}

public sealed class Invoice : Document
{
    public int CustomerId;
}
```

`Invoice { Id = 1, Revision = 2, CustomerId = 7 }` 在头之后写成：

<Bytes rows={[
  { title: '版本 1', fields: [{ hex: '08 00 00 00', kind: 'length', label: '长度 8' }, { hex: '01 00 00 00', kind: 'value', label: 'Id' }, { hex: '07 00 00 00', kind: 'value', label: 'CustomerId' }] },
  { title: '版本 2', fields: [{ hex: '0C 00 00 00', kind: 'length', label: '长度 12' }, { hex: '01 00 00 00', kind: 'value', label: 'Id' }, { hex: '02 00 00 00', kind: 'changed', label: 'Revision：正是版本 1 期待 CustomerId 的位置' }, { hex: '07 00 00 00', kind: 'value', label: 'CustomerId：版本 1 当作未知成员跳过' }] },
]} />

- **版本 2 读取版本 1 的数据：** `Revision` 读到的是 `CustomerId` 的字节；数据在 `CustomerId` 之前就结束了，`CustomerId` 像其他缺少的成员一样保留原有的值（新建的 `Invoice` 中为 `0`）。
- **版本 1 读取版本 2 的数据：** `CustomerId` 读到的是 `Revision` 的字节，真正的 `CustomerId` 则当作未知的尾部成员跳过。

这里两个成员类型相同，所以只是值错了。类型不同时，字节就按另一种类型来读：结果是错误的值，或抛出 `NinoDataException`。编译期不会报告这种错误，因为生成器只能看到代码的一个版本。

`Document` 自身的实例不受影响（`Revision` 是它们的最后一个成员），受影响的是所有子类的数据。因此只向继承体系最底层的类追加成员，例如密封的消息类。所有子类都需要的成员，就分别加到每个子类里；或者把整个继承体系改成 [`NinoFormat.Keyed`](#keyed-members)，这样任何一层的类都可以添加成员。

## 键控成员 [#keyed-members]

```csharp
[NinoType(format: NinoFormat.Keyed)] // [!code highlight]
public class ConnectionConfig
{
    public string Host;
    public int Port;      // 成员可以随意调整顺序、删除或插入
    public float TimeoutSeconds;
}
```

每个成员写入时都带上一个**键**和它的长度。键是成员名的 32 位 FNV-1a 哈希，由生成器计算。这和 MessagePack 的 `[Key("name")]` 类似，只是不写入字符串：

- 数据里不认识的键直接跳过；缺少的成员保留原有的值，规则与[版本容错](#version-tolerance)相同（字段初始化器同样生效）。
- 读取时先假定成员按声明顺序排列，所以同一 schema 写出的数据，每个非托管成员只需一次 8 字节比较；一旦不匹配，就改为逐个按键分派。
- 同一类型中（包括继承来的成员）如果两个成员名哈希到同一个键，会在编译期报错（NINO014），所以哈希冲突不会损坏数据。
- 键控结构体从不按原始内存写。多态照常工作：类型 ID 写在成员数据之前。

这种格式适合需要长期保存、会经历多个版本修改的数据：配置、文档、设置文件、用工具编辑的内容数据。

## 重命名 [#renaming]

按位置和版本容错的类型不写成员名，给它们的成员改名什么都不用做。有两种改名会改变写出的内容：一是值带类型 ID 的类型，二是键控类型的成员。两种都用 `[NinoFormerName]` 让旧数据照样能读。

### 重命名类型 [#former-name]

成员、元素或变量的声明类型是非密封类、抽象类、接口或 `object` 时，值会连同它运行时类型的<Term id="type-id" lang="zh">类型 ID</Term> 一起写出。类型 ID 是类型全名的 32 位哈希，读取时靠它还原成正确的类型（见[多态](/zh/docs/v4/polymorphism#how-a-polymorphic-value-is-written)）。类型改名或换命名空间，ID 就变了，密封的子类型也一样（比如通过 `Message` 基类发送的各个消息类）。

典型场景：你把协议类从 `MyApp.Net` 挪到了 `MyApp.Protocol`，而上个版本存下的文件或客户端用的还是旧 ID。加上 `[NinoFormerName]` 就能继续读旧数据：

```csharp
namespace MyApp.Protocol
{
    [NinoType]
    [NinoFormerName("MyApp.Net.OrderPlaced")] // [!code highlight]
    public class OrderPlaced
    {
        public long OrderId;
    }
}
```

旧名称用全名的**运行时形式**：`Namespace.Type`，嵌套类型和外层类型之间用 `+` 连接（`Namespace.Outer+Inner`），不带 `global::`。类型 ID 由旧名称算出，所以改名后的类型读写的仍是已有数据和旧版读取方用的那个 ID。`NinoTypeId.Of(typeof(T))` 返回某个类型写出的 ID。

- 一个类型只能有一个 `[NinoFormerName]`，因为 ID 只能由一个名称算出；再加一个就报错 NINO026。
- 泛型类型上的旧名称会替换整个名称，连类型实参一起，所以每个封闭泛型类型（`Box<int>`、`Box<string>`）都得到同一个 ID：其中两个都连同类型 ID 写出时，读取方分不清谁是谁（警告 NINO027）。旧名称只加在非泛型类型上。

### 重命名键控成员 [#renaming-keyed-members]

在改名的字段或属性上加 `[NinoFormerName("OldName")]`，每个旧名称加一个。读取时，当前名称和所有旧名称都能识别；写入时始终使用当前名称。

```csharp
[NinoType(format: NinoFormat.Keyed)]
public class UserProfile
{
    [NinoFormerName("Nick")]                 // [!code highlight]
    [NinoFormerName("Nickname")]             // [!code highlight]
    public string DisplayName;               // 能读取以 Nick、Nickname 或 DisplayName 写出的数据
    public string Email;
}
```

- 旧名称与这个类型的其他成员冲突时，编译期报错。
- 按位置和版本容错的类型不写成员名，这个特性在那里不起作用，分析器会警告（NINO024）。
- 旧代码只认识旧名称，所以旧代码读改名后写出的数据时，会丢掉这个成员。

## 布局元数据 [#layout-metadata]

生成器会在程序集元数据里为每个 `[NinoType]` 记录一条 `[assembly: NinoTypeLayout]`，说明这个类型是怎么写出的：格式、主体前面的头（结构体是 `None`，密封类是 `Presence`，其他是 `TypeId`）、是否追踪引用、是否按原始内存整体拷贝、类型 ID、嵌套过深时主体是否[推迟](/zh/docs/v4/reference-tracking#deep-object-graphs)（`deferrable`，其他语言的读取器需要它），以及按写入顺序排列的成员。做数据兼容检查的工具（CI 里的 schema 检查、两次构建的对比、迁移工具）直接读这些信息就行，不用自己再实现一遍 Nino 的规则：

```csharp
using System.Reflection; // GetCustomAttributes<T>()

foreach (var layout in typeof(Move).Assembly.GetCustomAttributes<NinoTypeLayoutAttribute>())
    Console.WriteLine($"{layout.Type}: {layout}");

// Game.Move: format=Positional; header=None; trackReferences=false; raw=true; id=0x…; deferrable=false;
//            members=raw(8){VelocityX:float@0:raw(4),VelocityY:float@4:raw(4)}
```

- 成员按写出的顺序列出，用 `;` 分隔。每个成员写成 `name:type:encoding`，即成员名、类型和编码方式。编码描述的是字节本身，而不是写出它的格式化器类，因此工具不必了解 Nino.Core 的格式化器就能读写这些字节（[nino-gen](/zh/docs/v4/advanced/codegen) 就是这样做的）：
  - `raw(n)` 或 `raw(n){...}`：按原始内存拷贝的值（见下一条）；单独的 `raw`：大小要到运行时才知道的这类值；
  - `string`：默认编码的字符串；`utf8`：`[NinoUtf8]` 字符串；
  - `type(T)`：一个 `[NinoType]`，按它自己的布局写出；`object`：带类型 ID 的 `[NinoType]`；
  - `nullable(E)`：一个存在字节，然后是 `E`；
  - `seq(E)`：`int32` 元素个数（`-1` = null），然后是各元素；`map(K,V)`：元素个数，然后是每个键和值；`grid(rank,E)`：每一维的长度，然后按行优先顺序排列的元素；
  - `pair(K,V)` 和 `tuple(E,...)`：按顺序排列的各项；`group(K,E)`：元素个数、键，然后是各元素；
  - `datetimeoffset`、`bigint`、`version`、`bits`、`timezone`：这几种内置类型；
  - `formatter(F)`：由 Nino.Core 以外的格式化器 `F` 写出：[自定义格式化器](/zh/docs/v4/custom-formatters)、其他库的格式化器，或者 `Nino.Immutable` 以及 Unity 的 `AnimationCurve`、`Gradient`、`RectOffset` 的格式化器。

  比如 `Dictionary<string, int[]> Inventory` 写成 `Inventory:System.Collections.Generic.Dictionary<string, int[]>:map(string,seq(raw(4)))`。键控类型的每个成员末尾都有 `:key=0x…`，即它的键；有[旧名称](#renaming-keyed-members)时还有 `:former=0x…,0x…`，即旧名称对应的键。`[NinoType]` 集合类型的开头是 `[elements]::` 加上元素的编码。在 4.0.0-rc.5 及之前，非原始内存的成员写的是格式化器类名。
- 原始布局描述的是这个值在 Nino 规范布局下的字节：基本类型、枚举、`decimal`、`Guid`、`DateTime` 和 `TimeSpan` 写成 `raw(n)`，`n` 是字节数；`n` 字节的结构体写成 `raw(n){name:type@offset:encoding,...}`，列出每个字段和它的偏移。比如 `readonly record struct PlayerId(long Value)` 这样的 ID，会写成 `Id:Game.PlayerId:raw(8){Value:long@0:raw(8)}`。原始值里的每个结构体都会展开，不管它是不是 `[NinoType]`，所以改了字段、`[StructLayout]` 的 `Pack` 或 `Size`、或者 `[FieldOffset]`，布局都会跟着变。原始内存结构体的成员部分就是它自己的原始布局，如上面的 `Move`。
- 泛型类型只记录一次，记录的是开放定义（`typeof(Box<>)`），类型 ID 为 0：每个封闭类型的 ID 在运行时计算。
- 两个类型的布局相同，当且仅当 Nino 以相同的方式写出它们。另一个 `[NinoType]` 类型的成员写成 `type(T)`，这里只引用那个类型自己的布局，所以它内部的变化只会体现在它自己的记录里；按原始内存拷贝的成员则会把字节直接展开在这里。要发现所有变化，就按 `layout.Type` 记下全部类型的布局，再把每个 `layout.ToString()` 和上个版本记下的结果对比：有差异，就说明写出的字节变了。旧数据还能不能正确读出，要看类型用的是哪种格式，见上文。
- 布局记录在元数据里，所以工具也能读取所引用程序集里的布局，甚至不必加载程序集（用 `System.Reflection.Metadata` 即可）。同一个项目在不同目标框架下得到的布局完全一样。

## 布局基线 [#layout-baseline]

存下来或发出去的数据，往往比写它的那个版本活得更久。布局基线是项目里的一个文件，记录所有字节会跨版本存在的类型的[布局](#layout-metadata)：每个版本容错和键控的 `[NinoType]`，以及它们的成员用到的所有类型（包括按位置的类型和多态子类型）。分析器在你写代码时就拿类型和它比对，一旦某个改动会让旧数据或旧版本读不了，就在改动的成员或类型上报出来。

```csharp title="NinoLayouts.cs"
[assembly: Nino.Core.NinoLayouts(@"
['MyGame.Save.PlayerData']
format = 'Keyed'
header = 'Presence'
id = 0x3DEFB1B5
members = [
  { name = 'Health', type = 'int', encoding = 'raw(4)', key = 0x99A16761 },
  { name = 'Name', type = 'string', encoding = 'string', key = 0x3085B3E2 },
]
")]
```

- **怎么创建**：在任意 `[NinoType]` 声明上用重构“Create the layout baseline (NinoLayouts.cs)”，或者运行 `nino-gen layouts --assembly MyGame.dll --out NinoLayouts.cs`，然后把文件提交进仓库。这个文件不用手写，代码修复和命令会负责更新它。
- **运行时零开销**：`NinoLayoutsAttribute` 是条件特性，编译器会检查它，分析器从源码里读它，但它不会写进程序集。它就是一个 C# 文件，所以在 Unity 里用法完全一样，每个程序集（csproj 或 asmdef）各有一份。
- **会报什么**：每条都分两种读者来看，一是这个版本读改动之前写的数据，二是改动之前的版本读改动之后写的数据（还没更新的客户端、滚动发布时的老节点）：
  - [NINO034](/zh/docs/v4/analyzers#nino034)（警告）：任意一方会读不了。比如版本容错类型里插入、删除或调换了成员；被存储数据用到的按位置类型改了成员；加上或去掉 `sealed`；成员的类型或编码变了；写出类型 ID 的类型改了名或换了命名空间；类型被删除。
  - [NINO035](/zh/docs/v4/analyzers#nino035)（警告）：键控成员改了名却没加 [`[NinoFormerName]`](#renaming-keyed-members)，它的值会悄无声息地丢掉。
  - [NINO036](/zh/docs/v4/analyzers#nino036)（提示）：兼容，但有前提。比如删了键控成员，或者改名时加了旧名（这时要先发布读的一方，再发布写的一方）。
  - 往版本容错类型末尾追加成员、给键控类型加成员，都是兼容的，不会报。
- **修复还是接受**：能撤销的改动，诊断会直接给出修法：加旧名、恢复 `sealed`、把插入的成员挪到末尾。如果旧数据或旧版本已经不用管了，用“Accept the change into the layout baseline”改写基线里这个类型那一段；“全部修复”可以一次接受所有改动。改动随后会出现在基线文件的 diff 里，评审 PR 时一眼就能看到。
- **在 CI 里**：`nino-gen layouts --assembly MyGame.dll --out NinoLayouts.cs --check` 对编译好的程序集跑同一套规则，遇到 NINO034 或 NINO035 时以 1 退出。想直接让构建失败，就在 `.editorconfig` 里设置 `dotnet_diagnostic.NINO034.severity = error`。
- **查不到的**：布局里看不出来的东西不检查：枚举值重新编号（枚举只是它的字节），[自定义格式化器](/zh/docs/v4/custom-formatters)内部写了什么，以及删掉的多态子类型在旧数据里是否还有实例。

## 如何选择 [#choosing]

| 问题 | 回答 | 用 |
| --- | --- | --- |
| 写入方和读取方总是同一个构建？ | 是 | `Positional` |
| 只追加成员，而且只加在没有子类的类上？ | 是 | `VersionTolerant` |
| 要删除、重排成员，或给基类加成员？ | 是 | `Keyed` |


<Accordions type="single">
<Accordion title="客户端与服务器之间的消息">

两端始终运行同一构建版本时，用按位置格式。如果客户端和服务器的升级时间不一致（滚动升级、用户手里还有旧版本），用 `NinoFormat.VersionTolerant`，并且只向各个消息类本身**追加**字段（不要加到它们共同的基类上）；如果还需要删除字段，或要向基类添加字段，就用 `NinoFormat.Keyed`。参见[网络](/zh/docs/v4/advanced/networking)。

</Accordion>
<Accordion title="保存的文档与用户文件">

如果只会陆续向没有子类的类添加字段，用 `NinoFormat.VersionTolerant`；想自由地删除和重排字段，用 `NinoFormat.Keyed`。如果保存的对象图有共享对象或循环，再加上 [`trackReferences`](/zh/docs/v4/reference-tracking)。参见[持久化](/zh/docs/v4/advanced/persistence)。

</Accordion>
<Accordion title="由人手工维护的配置">

用 `NinoFormat.Keyed`：维护配置的人会频繁增删、调整字段，而每个成员 8 字节的开销对配置来说几乎可以忽略。

</Accordion>
<Accordion title="缓存与内存快照">

用按位置格式。schema 变了就丢掉缓存重新生成。

</Accordion>
</Accordions>

<Callout type="idea">

这些选项可以混用：键控的设置文件里可以包含按位置写入的原始结构体（如 `Guid` 或你自己的 `[NinoType]` 结构体）。每个类型使用自己的格式。

</Callout>

## 常见陷阱 [#pitfalls]

| 错误 | 后果 | 由谁发现 |
| --- | --- | --- |
| 给有 `[NinoType]` 子类的版本容错基类追加成员 | 子类的数据读出错误的值，或抛出 `NinoDataException` | [布局基线](#layout-baseline)（在子类上报 NINO034）；参见[向基类追加成员](#appending-to-a-base-class) |
| 数据已经存在后，修改成员的类型或类型的格式 | 旧数据读错或读不出来 | [布局基线](#layout-baseline)（NINO034） |
| 重命名或移动一个连同类型 ID 写出的类型 | 旧数据的类型 ID 认不出来：`NinoDataException` | [布局基线](#layout-baseline)（NINO034，代码修复会加上 [`[NinoFormerName]`](#former-name)） |
| 在连同类型 ID 写出的泛型类型上用 `[NinoFormerName]` | 所有封闭泛型类型写出同一个 ID，读取时分不清 | [NINO027](/zh/docs/v4/analyzers#nino027) |
| 重命名键控成员却不加 `[NinoFormerName]` | 旧数据里这个成员的值当作未知的键跳过 | [布局基线](#layout-baseline)（NINO035，代码修复会加上旧名） |
| 两个键控成员（或一个旧名称）哈希到同一个键 | 无法编译 | [NINO014](/zh/docs/v4/analyzers#nino014) |
| 在按位置格式或版本容错的类型的成员上用 `[NinoFormerName]` | 不起作用：这两种格式不写名字 | [NINO024](/zh/docs/v4/analyzers#nino024)，带代码修复 |
| 项目仍定义 `WEAK_VERSION_TOLERANCE` | 靠它变成版本容错的类型会变回按位置格式，读不了已有的数据 | [NINO032](/zh/docs/v4/analyzers#nino032)，代码修复保持字节不变 |
