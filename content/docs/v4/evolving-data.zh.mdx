数据往往比代码活得更久。存档、缓存的资源、旧版客户端发来的消息，都会被新版本的类型读取，有时反过来也一样。Nino 为每个类型提供三种格式，在 `[NinoType]` 上选择：

| | 按位置（默认） | `versionTolerant: true` | `keyed: true` |
| --- | :---: | :---: | :---: |
| 在末尾追加成员 | ✗ | ✓ | ✓ |
| 向基类追加成员 | ✗ | ✓ | ✓ |
| 插入、删除或重排成员 | ✗ | ✗ | ✓ |
| 重命名成员 | ✓ | ✓ | ✗ |
| 新代码读旧数据 | ✗ | ✓ | ✓ |
| 旧代码读新数据 | ✗ | ✓ | ✓ |
| 额外开销 | 无 | 每层继承 4 字节 | 每个成员 8 字节，每个对象另加 4 字节 |
| 速度 | 最快 | 基本相同 | 比按位置慢一些（参见[基准测试](/zh/docs/v4/perf)） |

格式本身也是数据的一部分：给某个类型打开或关闭 `versionTolerant`、`keyed`，都会让之前写出的数据无法读取。请在保存任何数据之前做好选择。

无论哪种格式，都**不能修改成员的类型**。按位置和版本兼容格式不写成员名，所以**重命名成员**没有影响；键控格式则不行，它的键是成员名的哈希，改名后的成员会被当作“删掉一个、新增一个”。重命名*类型*请使用 [`[NinoFormerName]`](/zh/docs/v4/defining-types#former-name)。

## 按位置 [#positional]

不带参数的 `[NinoType]` 会依次写出各个成员，不带名称、长度或键。这是最快、最小的格式，适合由同一个构建版本写入和读取的数据：版本一致的客户端与服务器之间的网络消息、可以重建的缓存、内存中的快照。

<Callout type="warn">

只要成员列表有任何变化（新增、删除、重排、修改索引），旧数据就无法读取：读取时要么抛出异常，更糟的是读出错误的值。

</Callout>

## 版本兼容 [#version-tolerance]

```csharp
[NinoType(versionTolerant: true)] // [!code highlight]
public class SaveData
{
    public int Id;
    public string Name;
    public bool Tutorial; // [!code ++]
}
```

继承体系中的每一层（从根到当前类型的每个 `[NinoType]` 类）都写在各自的 4 字节长度之后：

- **新代码读旧数据：** 数据中缺少的成员保持当前值（反序列化到已有实例时）或默认值。
- **旧代码读新数据：** 旧代码不认识的字节会被跳过。
- 可以向类型本身**或它的任意基类**追加成员，并且在任意嵌套深度都成立：集合、字典和多态成员中也一样。

<Callout type="warn">

以下改动不被兼容：在同一层内插入、删除或重排成员，向 `[NinoType]` 接口追加成员（请追加到类中），以及在继承体系中增加或移除 `[NinoType]` 类。使用 `[NinoType(false)]` 时，新成员的索引必须大于所有已有成员。

</Callout>

<Callout type="info">

在项目中定义符号 `WEAK_VERSION_TOLERANCE`，会为该项目中声明的所有类型打开 `versionTolerant`；引用的其他程序集中的类型保持各自的格式。更推荐按类型设置。

</Callout>

## 键控成员 [#keyed-members]

```csharp
[NinoType(keyed: true)] // [!code highlight]
public class EnemyConfig
{
    public string Name;
    public int Health;    // reorder, remove or insert members freely
    public float Speed;
}
```

每个成员都带着一个**键**写入（键是成员名的 32 位 FNV-1a 哈希，由生成器计算）以及它的长度。这与 MessagePack 的 `[Key("name")]` 类似，但不写入字符串：

- 数据中不认识的键会被跳过；数据中缺少的成员保持当前值或默认值。
- 读取时先假定成员按声明顺序排列，所以同一 schema 写出的数据，每个非托管成员只需一次 8 字节比较；一旦不匹配，就改为逐个按键分派。
- 同一类型中（包括继承来的成员）如果两个成员名的哈希相同，会在编译期报错（NINO014），所以哈希冲突不会损坏数据。
- 键控结构体永远不会按原始内存写入。多态照常工作：类型 ID 写在成员数据之前。

这种格式适合在编辑器中编辑、需要长期保存的数据：游戏配置、关卡数据、设置文件。

## 如何选择 [#choosing]

<Accordions type="single">
<Accordion title="客户端与服务器之间的消息">

两端始终运行同一构建版本时，用按位置格式。如果客户端和服务器的升级时间不一致（滚动升级、玩家手里还有旧版本），用 `versionTolerant` 并且只**追加**字段；如果还需要淘汰字段，用 `keyed`。参见[网络层](/zh/docs/v4/advanced/networking)。

</Accordion>
<Accordion title="游戏存档与用户文件">

只会不断增加字段时用 `versionTolerant`，想自由地删除和重排字段时用 `keyed`。如果存档中的对象图有共享对象或循环，再加上 [`trackReferences`](/zh/docs/v4/reference-tracking)。参见[存档与持久化](/zh/docs/v4/advanced/persistence)。

</Accordion>
<Accordion title="在 Unity 编辑器中编辑的配置">

用 `keyed`：策划会频繁增删、调整字段，而每个成员 8 字节的开销对配置来说几乎可以忽略。

</Accordion>
<Accordion title="缓存与内存快照">

用按位置格式。schema 变了就丢掉缓存重新生成。

</Accordion>
</Accordions>

<Callout type="idea">

这些选项可以混用：键控的存档里可以包含按位置写入的原始内存结构体（如 `Vector3` 或你自己的 `[NinoType]` 结构体）。每个类型使用自己的格式。

</Callout>
