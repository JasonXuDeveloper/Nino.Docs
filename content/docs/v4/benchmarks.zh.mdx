## 测量方法 [#setup]

| | |
| --- | --- |
| 机器 | 发布时跑基准测试的 GitHub 托管 `ubuntu-26.04` runner，每组数据下方那行写明了具体 CPU |
| 运行时 | .NET 10，服务器 GC；每组数据下方那行写明了运行时的具体版本 |
| 测试框架 | BenchmarkDotNet 0.15.8，每个用例跑 3 个进程，每个进程预热 5 次、测量 15 次，取三个进程的平均（只跑一个进程时，一个 12 ns 的用例最多偏差 13%）；各基准测试类分到每种架构的多台 runner 上并行跑（[`benchmarks/shards.json`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/shards.json)），同一个用例的所有序列化库都在同一台 runner 上 |
| 项目 | [`benchmarks/Nino.Benchmark`](https://github.com/JasonXuDeveloper/Nino/tree/main/benchmarks/Nino.Benchmark) |

- **序列化**测试写进一个缓冲区写入器，它只创建一次，每次调用前重置（Nino 用 `NinoArrayBufferWriter`，其他库用 `ArrayBufferWriter<byte>`），所以测的是序列化本身，不是数组分配。每个库用的都是它能直接写入的写入器：换成其他 `IBufferWriter<byte>`，原始值和固定大小的值 Nino 照样直接写入，其他值先写进池化的缓冲区再整体复制过去，比这些表格多一次复制。
- **反序列化**测试读的是各个库启动时写好的字节，每次调用都创建新对象。
- **先验证**：跑基准测试之前，`--verify`（[`Verify.cs`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Harness/Verify.cs)）把每个用例跑一遍，检查每个序列化用例写出的正是载荷的字节，各个库读回的值也逐层比较、完全相同。测试数据用固定种子，每次跑序列化的都是同样的值。
- **1 ns 以下**（大约三个时钟周期）的耗时分不出快慢：读一个 40 字节的结构体，扣掉 BenchmarkDotNet 的空方法开销后，两个库测出来都在 0.05 到 0.8 ns 之间晃。两边都低于 1 ns 记为持平；Nino 低于 1 ns、对方测得出时，写成下限“> 1.4×”，即对方耗时除以 1 ns：Nino 用时不到 1 ns，这个倍数只会更大；直接相除只会得到噪声。区间统计不计入这类用例。相差 5% 以内也记为持平。
- **复用**测试读入已有的对象：Nino 用 `ref` 和 `[NinoPooled]` 对象池，MemoryPack 用它的覆盖模式。
- **MessagePack 与 protobuf-net** 用同样的类型，读写和 Nino、MemoryPack 一样的值，各自用文档推荐的最快 API；见 [MessagePack 与 protobuf-net](#messagepack-and-protobuf-net)。
- **v3** 跑的是基准测试类移植到 NuGet 上 Nino 3.3.13 的版本（除 `ReferenceTest` 外每个类都有，3.3.13 能表达的用例都移植了；移植之前的发布报告里 v3 的行少一些），在同一台 runner 上、紧挨着 v4 的对应用例之前跑一次。两次都带 MemoryPack，它前后两次的耗时差就是机器本身的波动。每张 v3 图表下面都注明了数据出自哪次运行。
- **Arm64**：发布时的基准测试还会用同样的设置，在 GitHub 的 Arm64 runner（`ubuntu-26.04-arm`）上跑同样的基准测试类。某个版本的发布报告有了这些结果后，Nino 对比 MemoryPack 的运行时表格和图表会在 **x64** 旁边多一个 **Arm64** 标签页，选哪个标签页，全站的基准测试表格和图表都跟着切换。两种 runner 不一样，只在同一架构内比较 Nino 和 MemoryPack，别跨架构比耗时。和 v3 的对比只有 x64。

### MessagePack 与 protobuf-net [#messagepack-and-protobuf-net]

MessagePack 3（MessagePack-CSharp）和 protobuf-net 3 用同样的类型，读写和 Nino、MemoryPack 一样的值：`[MessagePackObject]` 配合整数 `[Key]`，子类型用 `[Union]`；`[ProtoContract]` 配合 `[ProtoMember]` 和 `[ProtoInclude]`。速度以外的区别见[序列化库选型](/zh/docs/v4/compare)。

- **MessagePack** 用 `MessagePackSerializer.Serialize(IBufferWriter<byte>, value)` 序列化到复用的 `ArrayBufferWriter<byte>`，用 `Deserialize<T>(ReadOnlyMemory<byte>)` 反序列化，用默认选项；默认的解析器会用上 MessagePack 源生成器在编译时为基准测试类型生成的格式化器。不可变集合交给 `ImmutableCollectionResolver`（MessagePack.ImmutableCollection 包）处理。
- **protobuf-net** 用 `Serializer.Serialize(Stream, value)` 序列化到复用的 `MemoryStream`，用 `Serializer.Deserialize<T>(ReadOnlySpan<byte>)` 反序列化，用默认的运行时模型：某个类型第一次用到时，才为它编译序列化器。写流是 protobuf-net 最快的写法：它的 `IBufferWriter<byte>` 写入器在写每条嵌套消息之前，都要先算一遍消息的大小。`FixedSizeTest` 测的是返回 `byte[]` 的 API：protobuf-net 没有这种 API，所以先写进复用的流，再把字节复制到新数组。

某个库没法用相同数据表达的用例，就不给它写测试方法，绝不换成别的数据来测；表格里它的单元格是 “—”，图表里也没有它的条：

| 测试类 | 没有 MessagePack | 没有 protobuf-net |
| --- | --- | --- |
| `ReferenceTest` | 不支持引用追踪：写不出共享对象和环 | 同上（protobuf-net 3 没有实现 `AsReference`） |
| `PooledTest`、`PooledGraphTest` | 覆盖和池化用例：它只能读出新实例 | 同上：读入已有实例时是合并（往它的列表里追加），不是覆盖 |
| `GenericPolymorphicTest` | 五个泛型基类型：它的 Union 是基类型上的特性，没法按类型实参指定不同的子类型 | — |
| `CommonTypesTest` | — | `Tree`：protobuf 分不清空列表和没有列表，叶子节点的空子列表读回来是 null |
| `BclTypesTest` | `CultureInfo`、`TimeZoneInfo`、`BlockingCollection<T>`：遇到就抛异常 | 除 `Uri` 和不可变集合以外全部没有：其他类型 protobuf-net 没有序列化器 |

各种格式写的内容不一样，载荷大小就看得出来：MessagePack 把 `Guid` 写成 36 个字符的字符串，把 `DateTime` 写成 UTC 时间戳；protobuf-net 给类层次的每一层套一条消息，`DateTime` 也单独写成一条消息。

每个基准测试的代码见[基准测试代码](#benchmark-code)。

### 真实负载 [#workloads]

照着真实应用的数据造的负载（[`WorkloadTest`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Workloads/WorkloadTest.cs)，类型在 [`Workloads/`](https://github.com/JasonXuDeveloper/Nino/tree/main/benchmarks/Nino.Benchmark/Workloads)），每个库都写一遍、读一遍，本站和 Nino README 的头条数字都出自这里。其中两个是常见序列化基准自带的数据：jvm-serializers 的 `MediaContent`，和一页 Stack Exchange API 数据（Jil、MessagePack-CSharp、MemoryPack 的基准用的都是这套模型）。四个是服务端会发的：结果为接口、带泛型实现的 RPC 调用，上个版本写进缓存的用户资料（Nino 用键控格式、MemoryPack 用版本容错格式来读），两层事件继承外加泛型信封的事件流，以及 1,000 条日志。六个是游戏会发的：组件是接口、读进客户端已有对象的状态同步快照，8 名玩家的帧同步输入帧，MMO 的 AOI 增量，城池、军队和动作共享对象的 SLG 地图区域与卡牌战斗回放，以及上个版本的放置游戏存档，读进游戏手里已有的存档对象。重点看需要绕法的库（见[下文](#workarounds)）：绕法的代价也算在它们的耗时里。这一组和基础类型、多态、可空值三组还多测两个库：

- **Google.Protobuf 3.36.2** 用它自己的消息类型，由 `protoc` 从 [`workloads.proto`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Workloads/workloads.proto)（其他几组是 `cases.proto`）生成：schema 就是同一套模型的 protobuf-net 契约生成的，数据也是从 protobuf-net 写出的字节解析而来，两者写出的 protobuf 消息一样，大小也一样。写用 `WriteTo`，写进复用的 `ArrayBufferWriter<byte>`；读用 `Parser.ParseFrom(ReadOnlySpan<byte>)`。
- **System.Text.Json**（.NET 10）用源生成器（`JsonSerializerContext`），通过复用的 `Utf8JsonWriter` 把 UTF-8 写进 `ArrayBufferWriter<byte>`，读的也是 UTF-8 字节。

#### 各库怎么处理难点 [#workarounds]

这些负载用到的功能，不是每个库都有。各库都按自己用户的常规写法来写，缺的功能用常见的绕法补上，保证处理的数据一样：

| 库 | 基类或接口的子类型 | 被多处引用的同一个对象 | 读进已有对象 |
| --- | --- | --- | --- |
| Nino | 基类标 `[NinoType]` | 只写一次 | 原地读入 |
| MemoryPack | 每个子类型一个 `[MemoryPackUnion]` | 只写一次 | 覆盖写入 |
| MessagePack | 每个子类型一个 `[Union]` | **绕法：** 每个引用一份副本 | **绕法：** 新建对象 |
| protobuf-net、Google.Protobuf | 每个子类型一个 `[ProtoInclude]`（`oneof`） | **绕法：** 每个引用一份副本 | **绕法：** 新建对象 |
| System.Text.Json | 每个子类型一个 `[JsonDerivedType]` | `$id`、`$ref`（`Preserve`） | **绕法：** 新建对象 |

上个版本写的数据各库都能读，不需要绕法：Nino 用键控或版本容错格式，MemoryPack 用版本容错格式，其他库靠整数键、字段编号或属性名。Nino 的生成器会自己找到子类型，泛型子类型和其他程序集里的也能找到；其他库都要在基类上逐个列出，protobuf 还要每层继承嵌套一层消息，System.Text.Json 每个值都要写上子类型名。原地读入时，Nino 会保留没变的字符串、复用列表；protobuf-net 读进已有对象是合并而不是覆盖，所以也只能新建。

绕法本身有代价：共享对象每个引用都写一遍、读一遍；每次读都新建一整棵对象图，Nino 能复用的内存它们都得重新分配。这些代价也算进了测出来的数字，因为应用实际就要付这些代价。同样的模型在 Nino 里只需要标 `[NinoType]`：不用逐个列出子类型，也不用维护副本。

### 基础类型与结构体 [#basic-types]

最简单的几种形状，单个值或数组（[`SimpleTest`](#simpletest)、[`FixedSizeTest`](#fixedsizetest)）：一个由基元类型、字符串和集合组成的类，单个和 100 个的数组；`SimpleStruct`（`int` + `DateTime`）和它的数组；`Vector4[10000]`；还有固定大小的类型：一个 40 字节的结构体、成员相同的密封类、100 个这种类组成的数组，都用两个库返回 `byte[]` 的 API 测，所以每次调用都算上了分配结果数组的开销。各库每次调用的固定开销在这一组最明显。序列化时 Nino 和 MemoryPack 都不分配内存；各种格式写出来有多大，看大小那张表。

<BenchGroup group="basic" lang="zh" />

`SimpleStruct` 声明了 `[StructLayout(LayoutKind.Sequential, Pack = 4)]`，所以占 12 字节、没有填充，每个序列化库都整块拷贝它；不加 `Pack` 的话它占 16 字节，其中 4 字节是填充，Nino 写的时候会把填充清零（[结构体布局](/zh/docs/v4/performance#struct-layout)）。反序列化那个 40 字节的固定大小结构体只是一次拷贝，两个库都只要一个时钟周期左右，所以这几行都贴着 1 ns 的下限。`Vector4[10000]` 每次调用都在大对象堆上分配一个 160 KB 的数组，测的主要是第 2 代垃圾回收，而不是序列化库（标 †）；拷贝本身在两个库里都只是一次 `memcpy`。

### 多态 [#polymorphism]

声明为抽象基类或接口、读回时还原成运行时类型的值（[`PolymorphicTest`](#polymorphictest)、[`GenericPolymorphicTest`](#genericpolymorphictest)）：一个 `PolymorphicClass`，列表里有 1,000 个 `Foo` 子类型实例、字典里有 12 个；100 个这样的对象；1,000 个元素的 `Foo[]`，共 20 种子类型，继承最深 9 层；还有 8 种类型的 1,000 个子类型实例，分别经非泛型基类型和泛型基类型的封闭实例读写（`Box<int>`、`Box<(int, long)>`、`Box<(int, string)>`，以及装着一个密封类和一个有子类型的类的元组）。Nino 给每个值写一个 4 字节的类型 ID，用生成的代码分派；MemoryPack 用 `[MemoryPackUnion]` 标签，MessagePack 用 `[Union]` 的键，protobuf-net 在继承层次的每一层嵌一条消息（`[ProtoInclude]`）。MemoryPack 的 Union 特性不能加在泛型类型上，所以泛型基类型那几个用例要给每个封闭基类型注册一个 `DynamicUnionFormatter`，MessagePack 则没有这几个用例。见[多态](/zh/docs/v4/polymorphism)。

### 可空值 [#nullable-values]

可空的成员和元素（[`NullableTest`](#nullabletest) 和 `CollectionsTest` 里的可空集合）：一个有 8 个可空成员、一半为 null 的类，单个和 100 个的数组；一个 `SimpleStruct?` 和 `SimpleStruct?[100]`；一个为 null 的 `SimpleClass` 引用，和每 5 个有 1 个 null 的 `SimpleClass[100]`；以及 `long?[1000]`、`List<int?>` 和 `decimal?[1000]`，每 5 个值有 1 个 null。各库都按自己用户的惯用写法来写。MessagePack 和 System.Text.Json 原生就能写 null。MemoryPack 用 `SafeNullable<T>`：它直接写 `Nullable<T>` 时会把值的内存原样拷出去，填充字节没有初始化，同一个值可能写出不同的字节；`SafeNullable<T>` 没有填充，和 Nino 的字节一样确定。protobuf 的 repeated 字段里没有 null，顶层也没有 null，所以 protobuf-net 给每个元素套一层带可选值的消息（`[NullWrappedValue]`），单个可空值写成只有一个可选字段的消息（为 null 时是空消息），Google.Protobuf 读写同样的消息；可空结构体在 repeated 字段里 protobuf-net 套不了包装，`SimpleStruct?[100]` 就写成这种单字段消息的数组，字节完全一样。可空字段则用 `google.protobuf` 的包装类型（`Int32Value` 等）、`Timestamp`，`Guid` 和 `decimal` 写成字符串。

可空结构体和可空集合还按用户可能选的其他写法各测了一组，单独成柱：**Nino (NinoNullable)** 是模型里用 [`NinoNullable<T>`](/zh/docs/v4/nullable-values#nino-nullable) 代替 `T?`（字节相同）；**MemoryPack (converted)** 是在计时内把模型的 `T?` 转成 `SafeNullable<T>`、读完再转回来，也就是模型本来用 `T?` 时 MemoryPack 安全写法的真实成本；**MemoryPack (T?, unsafe)** 是直接把 `T?` 交给 MemoryPack，快，但字节里带着未初始化的填充。普通的 MemoryPack 柱子写的是事先转好的 `SafeNullable<T>`。Nino 的 `T?` 始终是安全的。

<BenchGroup group="nullable" lang="zh" />

### 集合与常用类型 [#common-types-and-collections]

基础类库里的集合和类型，凡是能写出相同数据的库都一起比，序列化到复用的缓冲区写入器，反序列化成新实例：

- **集合**（[`CollectionsTest`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Cases/Collections/CollectionsTest.cs)），各 1,000 个元素：`List<(int, long)>`、`KeyValuePair<int, int>[]`、`HashSet<int>`、`Dictionary<int, int>`、`Queue<int>`、`LinkedList<int>`、`SortedSet<int>`、`SortedDictionary<int, int>`、`SortedList<int, int>` 和 `ConcurrentDictionary<int, int>`；另有 `SelfTree`，一个包含自身的 `List` 子类，6 层、每层 4 个。
- **常用类型**（[`CommonTypesTest`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Cases/Collections/CommonTypesTest.cs)）：一棵 `TreeNode` 树（1,365 个节点）、`InventoryItem[1000]`（带填充的结构体）、`Waypoint[1000]`（含一个元组的固定大小结构体，写出 15 字节，内存里占 20 字节）和 `Dictionary<string, string>`（1,000 项）。
- **BCL 类型**（[`BclTypesTest`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Cases/Collections/BclTypesTest.cs)）：`BigInteger`（3^1000）、`Uri`、`Version`、`StringBuilder`（1,000 个字符）、`BitArray`（1,000 位）、`CultureInfo`、`TimeZoneInfo`、`Lazy<string>`，以及各 1,000 个元素的 `Memory<int>`、`ReadOnlySequence<int>`、`ReadOnlyCollection<int>`、`IReadOnlyList<string>`（藏在接口后面、要逐个写的字符串）、`ILookup<int, int>`、`BlockingCollection<int>` 和 `Nino.Immutable` 里的不可变集合。

有几行测的主要是设计差异，不是速度。`TimeZoneInfo`：Nino 按 ID 写系统时区，读的时候直接取系统缓存的时区；MemoryPack 每次都写出并解析时区完整的序列化字符串。`InventoryItem` 和 `(int, long)` 在内存里有填充，MemoryPack 原样拷贝，Nino 写成零或干脆不写（[带填充的结构体和元组](/zh/docs/v4/vs-memorypack#padded-values)）。`BigInteger` 只和 MessagePack 比：MemoryPack 1.22.0 写出去再读回来就不对（[基准测试中发现的 MemoryPack 问题](/zh/docs/v4/vs-memorypack#memorypack-bugs-found-while-benchmarking)）。

### 复用与对象池 [#pooling]

读进已经存在的对象（[`PooledTest`](#pooledtest)、[`PooledGraphTest`](#pooledgraphtest)）：一个池化的类、一个池化的节点和一列叶子，各自读成新对象、再读进已有对象。Nino 把数据读入已有的对象图（[复用反序列化](/zh/docs/v4/pooling)），要新实例时从 `[NinoPooled]` 对象池里取；MemoryPack 覆盖已有实例。MessagePack 和 protobuf-net 不能读进已有对象，只有读成新对象的那几行。把每行“读进已有对象”和同一用例“新对象”那行对照着看，再看分配：原地读入时 Nino 一个字节都不分配。

### 引用追踪与版本容错 [#reference-tracking-and-version-tolerance]

两个会改变类型写法的功能，各自对照 MemoryPack 最接近的模式；MessagePack 和 protobuf-net 能写出相同数据时也一起比（这两个都不支持引用追踪）：

- **引用追踪**（[`ReferenceTest`](#referencetest)）：一张 200 个节点的对象图，有共享对象，也有环。Nino 用 `[NinoType(trackReferences: true)]`，MemoryPack 用 `GenerateType.CircularReference`。
- **版本容错**（[`VersionTolerantTest`](#versiontoleranttest)）：把 `SimpleClass` 的成员放进一个以后还能加成员的类型，单个对象和 100 个的数组各测一次。Nino 用 `format: NinoFormat.VersionTolerant`（每个对象一个长度），MemoryPack 用 `GenerateType.VersionTolerant`（每个成员一个长度）。

### 其他 [#others]

每个只测一种场景的用例：

- **分散的对象**（[`ScatteredTest`](https://github.com/JasonXuDeveloper/Nino/blob/main/benchmarks/Nino.Benchmark/Cases/Graphs/ScatteredTest.cs)）：一百万个对象的数组，数组里的顺序和它们在内存里的顺序不一样，就像程序运行久了、对象换过也排过序之后那样：一组是声明为抽象基类的形状，一组是带字符串的小类，都在分配之后打乱，每个元素都是一次缓存未命中。作为对照，还测了按分配顺序排列的同一批形状，以及 8,192 个能留在缓存里的形状。打乱的小类还会读回到已有的数组里（Nino 和 MemoryPack）。Nino 用默认设置，没有打开 [`NinoPrefetchLargeCollections`](/zh/docs/v4/advanced/type-design#large-collections)。

### ReferenceTest [#referencetest]

一张 200 个节点的对象图，有共享的标签、共享的对等节点，还有经过根对象的环，写进复用的缓冲区写入器再读回来。Nino 用 `trackReferences` 追踪引用，MemoryPack 用 `GenerateType.CircularReference`（要求每个成员都有 `[MemoryPackOrder]`）；两者都只把每个对象写一次，读回时共享引用和环仍然指向同一个实例。结果见[引用追踪与版本容错](#reference-tracking-and-version-tolerance)一组里的“对象图”各行。

```csharp title="ReferenceTest.cs" excerpt tab="类型" tab-group="bench-code"
[NinoType(trackReferences: true)]
[MemoryPackable(GenerateType.CircularReference)]
public sealed partial class RefNode
{
    [MemoryPackOrder(0)] public int Id;
    [MemoryPackOrder(1)] public double Weight;
    [MemoryPackOrder(2)] public RefGraph Graph;   // 指回根：形成环
    [MemoryPackOrder(3)] public RefTag Tag;       // 16 个共享标签之一
    [MemoryPackOrder(4)] public RefNode Peer;     // 更早的一个节点
}

[NinoType(trackReferences: true)]
[MemoryPackable(GenerateType.CircularReference)]
public sealed partial class RefTag
{
    [MemoryPackOrder(0)] public int Id;
    [MemoryPackOrder(1)] public string Name;
}

[NinoType(trackReferences: true)]
[MemoryPackable(GenerateType.CircularReference)]
public sealed partial class RefGraph
{
    [MemoryPackOrder(0)] public int Version;
    [MemoryPackOrder(1)] public List<RefNode> Nodes;
    [MemoryPackOrder(2)] public List<RefTag> Tags;
}
```

```csharp title="ReferenceTest.cs" nocheck tab="数据" tab-group="bench-code"
// RefGraph 中：count 个节点共享 16 个标签；每个节点的 peer 是更早的一个节点
// （向后引用，嵌套因此保持很浅），并且每个节点都引用回图本身。
public static RefGraph Create(int count)
{
    var r = new Random(3);
    var graph = new RefGraph { Version = 1, Nodes = new List<RefNode>(count) };
    graph.Tags = Enumerable.Range(0, 16).Select(i => new RefTag { Id = i, Name = "tag" + i }).ToList();
    for (int i = 0; i < count; i++)
    {
        graph.Nodes.Add(new RefNode
        {
            Id = i, Weight = r.NextDouble(), Graph = graph, Tag = graph.Tags[r.Next(graph.Tags.Count)],
            Peer = i == 0 ? null : graph.Nodes[r.Next(i)]
        });
    }

    return graph;
}

// ReferenceTest 中：
private static readonly RefGraph Graph = RefGraph.Create(200);
private static readonly byte[] NinoGraph = NinoSerializer.Serialize(Graph);
private static readonly byte[] MemoryPackGraph = MemoryPackSerializer.Serialize(Graph);
```

```csharp title="ReferenceTest.cs" excerpt tab="方法" tab-group="bench-code"

}
```

### FixedSizeTest [#fixedsizetest]

值总是占同样字节数的类型（[固定大小的类型](/zh/docs/v4/performance#fixed-size-types)）：`Serialize(value)` 按这个大小分配一个新 `byte[]` 返回，把值直接写进去，不经过暂存缓冲区和写入器，也不拷贝。用两个序列化库返回 `byte[]` 的 API 测，所以每次序列化都算上了分配结果数组的开销；另外还测了 100 个这种类组成的数组，它的长度不固定，走常规路径。结果见[基础类型与结构体](#basic-types)一组里的 `FixedStruct` 和 `FixedClass` 各行。

### GenericPolymorphicTest [#genericpolymorphictest]

数组里是 8 种类型的 1,000 个子类型实例，顺序随机，分别经非泛型基类型和泛型基类型的封闭实例读写。MemoryPack 的 `[MemoryPackUnion]` 不能加在泛型类型上（会报 MEMPACK013 或 MEMPACK014），所以基准测试给每个封闭基类型注册一个 `DynamicUnionFormatter`；Nino 只要 `[NinoType]`。结果见[多态](#polymorphism)一组里的泛型基类型各行。

```csharp title="GenericPolymorphicTest.cs" nocheck

public abstract partial class ProbeBase { public int V; }
[NinoType, MemoryPackable] public sealed partial class ProbeA : ProbeBase { } // ... ProbeH

[NinoType] public abstract class ProbeBox<T> { public T V; }
[NinoType, MemoryPackable] public sealed partial class ProbeBoxA : ProbeBox<int> { }                  // ... H
[NinoType, MemoryPackable] public sealed partial class ProbeTupA : ProbeBox<(int, long)> { }          // ... H
[NinoType, MemoryPackable] public sealed partial class ProbeStrA : ProbeBox<(int, string)> { }        // ... H
[NinoType, MemoryPackable] public sealed partial class ProbeScA : ProbeBox<(ProbeSealedItem, int)> { } // ... H
[NinoType, MemoryPackable] public sealed partial class ProbeOcA : ProbeBox<(ProbeOpenItem, int)> { }   // ... H

// 只有 MemoryPack 需要：每个封闭泛型基类型一个 Union 格式化器，并指定标签。
MemoryPackFormatterProvider.Register(new DynamicUnionFormatter<ProbeBox<int>>(
    (0, typeof(ProbeBoxA)), (1, typeof(ProbeBoxB)), /* ... */ (7, typeof(ProbeBoxH))));
```

## 复现 [#reproducing]

克隆 [Nino 仓库](https://github.com/JasonXuDeveloper/Nino)，装好 .NET 10 SDK 和 Python 3，然后：

```shell
# 运行时，与发布的数据相同：先 v3 3.3.13，再完整的 v4 套件（约六小时）
benchmarks/run.sh

# 运行时，只测 v4 的一部分
dotnet run -c Release --project benchmarks/Nino.Benchmark -- --filter '*SimpleTest*' --launchCount 3 --warmupCount 5 --iterationCount 15

# 真实负载，所有库
dotnet run -c Release --project benchmarks/Nino.Benchmark -- --filter '*WorkloadTest*'

# 引用追踪、版本容错和固定大小的类型
dotnet run -c Release --project benchmarks/Nino.Benchmark -- --filter '*ReferenceTest*' '*VersionTolerantTest*' '*FixedSizeTest*'
```

- `benchmarks/run.sh` 会构建 v3 版的基准测试（同一套 `SimpleTest`、`PolymorphicTest`、`NullableTest` 和可空集合，引用 NuGet 上的 Nino 3.3.13），紧挨着 v4 之前跑一次，再逐个用例输出 **v4 对比 v3**。
- 每次发布，CI 都按同样的流程跑，各基准测试类按上面的方式分到各台 runner 上（v3 在对应 v4 用例所在的 runner 上、紧挨着它们之前跑），结果写进发布说明：Performance Report，以及 **v3 3.3.13 vs v4 (same machine)** 一节。本站的运行时数据取自带这些数据的最新 v4 版本。
- 源生成器的基准测试也在这个发布流程里跑；怎么跑见[基准测试：构建时间](/zh/docs/v4/benchmarks-build#reproducing)。
- Go、Rust 和 TypeScript 的基准测试也在这个发布流程里跑；怎么跑见[基准测试：Go、Rust 与 TypeScript](/zh/docs/v4/benchmarks-runtimes#reproducing)。
- `benchmarks/members` 把 `SimpleClass` 按成员一个个拆开，分别对比 v3 和 v4，找出某个用例的时间花在哪个成员上。见 [benchmarks README](https://github.com/JasonXuDeveloper/Nino/tree/main/benchmarks)。
