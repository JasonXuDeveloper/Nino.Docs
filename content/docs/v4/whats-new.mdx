Nino v4 rewrites the runtime and the source generator. It runs faster than v3 and MemoryPack, builds much faster, and adds keyed and version-tolerant types, reference tracking, object pools, analyzers and many more built-in types. This page covers all of v4 as released through **4.0.0-rc.5**, grouped by area, plus what **4.0.0-rc.6**, **4.0.0-rc.7** and **4.0.0-rc.8** add (marked *rc.6*, *rc.7* and *rc.8*); the [Changelog](/en/docs/v4/changelog) lists what each release changed.

<Callout type="warn">

The v4 binary format is **not compatible** with v3 or the earlier v4 betas/previews, and the API changed. See [Migrating from v3](/en/docs/v4/migration).

</Callout>

## Performance [#performance]

### Faster than v3 [#faster-than-v3]

The baseline is v3 **3.3.13**, the last release of the v3 API (the 3.9.x releases were test builds of v4 features), run back to back with v4 on the same machine.

<BenchmarkChart chart={['v3-serialize', 'v3-deserialize']} lang="en" />

Serializing classes is clearly faster, deserializing is as fast as v3 or a little faster, and arrays of unmanaged structs are on par. Why: [v3 vs v4](/en/docs/v4/v3-vs-v4#runtime).

### Faster than MemoryPack [#faster-than-memorypack]

Measured against MemoryPack in the same run. Nino wins clearly when serializing (up to <BenchValue k="serialize.max" />), leads on classes and polymorphic graphs when deserializing (up to <BenchValue k="deserialize.max" />), and is at least on par on arrays of unmanaged values, where both do a single `memcpy`.

<BenchSource lang="en" />

<BenchmarkChart chart={['serialize', 'deserialize']} lang="en" />

Deserializing by `ref` into the objects you already have, with new instances taken from [`[NinoPooled]`](/en/docs/v4/pooling) pools, is up to **<BenchValue k="reuse.max" /> faster** than MemoryPack's overwrite mode and allocates **0 B** per call on the pooled paths ([pooling results](/en/docs/v4/benchmarks#pooling)). Neither library allocates when serializing, and payloads are about the same size (`SimpleClass`: <BenchValue k="payload.v4" /> bytes in Nino, <BenchValue k="payload.memorypack" /> in MemoryPack). See the [full comparison](/en/docs/v4/vs-memorypack), including [where MemoryPack is still ahead](/en/docs/v4/vs-memorypack#where-memorypack-is-ahead).

### Faster to Build [#faster-to-build]

The v3 generator inlined the body of every subtype into each polymorphic base and re-emitted every type on every keystroke. v4 emits one file per type, once, and re-generates only what you edit.

<BenchmarkChart chart="compile" lang="en" />

The larger the project, the bigger the gap: [Build Time and Generated Code](/en/docs/v4/benchmarks#build-time-and-generated-code).

### Where the Speed Comes From [#where-the-speed-comes-from]

- **Interceptors**: on Roslyn 4.8+ (the .NET 8 SDK and later), each `NinoSerializer`/`NinoDeserializer` call with a known type is redirected at compile time to the generated formatter. Always on; Unity (the generator's Roslyn 4.3 build) and older compilers take the regular path and write the same bytes. See [Interceptors](/en/docs/v4/performance#interceptors).
- **Struct formatters the JIT and AOT compilers inline**, and the bodies of small classes inlined into the loops of the collections that hold them. See [Struct Formatters, Inlined](/en/docs/v4/performance#struct-formatters-inlined).
- **One block instead of a loop**: unmanaged `[NinoType]` structs, and arrays and lists of them, are copied as raw memory. So are `Stack<T>`, `Queue<T>` and collections declared as interfaces of such elements, and arrays and lists of `DateTimeOffset`, value tuples and `KeyValuePair`s of unmanaged values, whose bytes are rearranged with SIMD where their memory differs. See [Raw Memory for Unmanaged Data](/en/docs/v4/performance#raw-memory-for-unmanaged-data) and [Collection Types](/en/docs/v4/types#collection-types).
- **Each collection through its own internals**: `SortedSet<T>`, `SortedDictionary<TKey, TValue>`, `SortedList<TKey, TValue>`, `LinkedList<T>`, the concurrent collections and the immutable collections are written and read through their fields, constructors and bulk methods instead of an element-by-element loop. Where those fields differ between runtimes (.NET Framework and Mono), the layout is checked once at startup and the public API is used when it does not match. See [Collection internals](/en/docs/v4/platforms#portable-by-design).
- **SIMD on every CPU that has it**: 64-byte vectors and masked copies with AVX-512, 32-byte vectors with AVX2, table lookups on Arm64, and byte shuffles with WebAssembly SIMD on .NET 10. See [SIMD by Platform](/en/docs/v4/platforms#simd).
- **Fixed-size types** are written straight into a `byte[]` of their exact size; `NinoSerializer.GetFixedSize<T>()` returns it. See [Fixed-Size Types](/en/docs/v4/performance#fixed-size-types).
- **Measured on x64 and Arm64**: each release is benchmarked on x64 and on GitHub's Arm64 runners; see [Benchmarks](/en/docs/v4/benchmarks).

None of these change the bytes: every path writes what the plain path writes.

## Untrusted Data [#untrusted-data]

Nino v4 is built to read data from sources you do not trust: messages from a network peer, files a user hands you, request bodies. Data crafted against a reader cannot crash the process, read past the end of the input, allocate out of proportion to its size or make Nino create a type you did not declare. For *rc.7*, fuzzed and hand-crafted payloads were run against every built-in type, and what they found is fixed (see the [Changelog](/en/docs/v4/changelog)).

- **No type names in the data**: a polymorphic value is a type id, which can only be one of the declared type's registered subtypes, and a back reference must point to an object already read, of the slot's type. `System.Type` is left out on purpose.
- **Bounded allocation**: every length is checked against the bytes left before anything is allocated, and since *rc.7* a collection allocates ahead of its elements at most 16 times the bytes left in the input; a larger count is grown into as elements are actually read.
- **Bounded stack**: objects nested more than 128 levels deep are deferred and read from a shallow level; since *rc.7* what cannot be deferred (structs that hold themselves, types built by their constructor) is limited to 512 levels (`NinoSettings.MaxDepth` since *rc.8*), with the stack checked on the way. See [Deep Object Graphs](/en/docs/v4/basic#deep-object-graphs).
- **One exception** (*rc.7*): every invalid input throws one exception type whose message starts with `Nino:`, including a value its own type rejects (a malformed `Uri`, an unknown culture, a null dictionary key), with the original exception as `InnerException`. Since *rc.8* it is `NinoDataException`, an `InvalidOperationException`. One `catch` where the data comes in is enough.
- **Strict bytes and limits** (*rc.8*): bytes Nino never writes (a `bool` or null flag other than 0 or 1, a keyed member with bytes left, a malformed section of deferred bodies) are rejected; keys built to collide in a hash table throw (`NinoSettings.MaxHashCollisions`); `NinoSettings.MaxDepth` and `MaxCollectionLength` tighten the limits, and `NinoSettings.Untrusted` adds the checks that cost time on every read. See [Untrusted Data](/en/docs/v4/security).
- **No stale memory** (*rc.7*): a failed read into an existing value never leaves an array of uninitialized memory in it.

Values themselves are not validated (a negative health reads as it is written), and the bytes carry no schema, so check what your logic depends on and cap the size of a message before you buffer it. See [Untrusted Data](/en/docs/v4/security) for what Nino checks and what stays your code's job, and [Untrusted Input](/en/docs/v4/vs-memorypack#untrusted-input) for how this compares with MemoryPack, which recommends itself for trusted data only.

## Evolving Data and Object Graphs [#data-and-object-graphs]

- **One option for the format**: `[NinoType(format: ...)]` takes a `NinoFormat`. `Positional` (the default) is the fastest; `VersionTolerant` lets you append members to the most derived type at any nesting depth, at 4 bytes per object, and old code skips the members it does not know; `Keyed` writes members by name hash, so they can be reordered, removed and inserted in any class of a hierarchy. Defining `WEAK_VERSION_TOLERANCE` in a project turns its `Positional` types into `VersionTolerant` ones. See [Evolving Your Data](/en/docs/v4/evolving-data).
- **Layout metadata**: the generator records how each `[NinoType]` is written as an `[assembly: NinoTypeLayout]`, including the size and field offsets of every value copied as raw memory, so tools can compare layouts between builds and catch a change in the bytes before it ships. Since *rc.6* each member is described by the bytes it is written as (`seq(string)`, `map(K,V)`, `type(T)`...), with its key in keyed types. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata).
- **Renamed types** keep their data with [`[NinoFormerName]`](/en/docs/v4/defining-types#former-name), and so do renamed keyed members.
- **Reference tracking**: `[NinoType(trackReferences: true)]` keeps shared references and cycles: an object reached twice is written once and read back as one instance, at 4 bytes per tracked object. See [Reference Tracking](/en/docs/v4/reference-tracking).
- **Polymorphism without tags**: type ids are hashes of type names, any non-sealed class or interface can be a base, and subtypes in other assemblies (plugins, hot updates) are found on their own. See [Polymorphism](/en/docs/v4/polymorphism).
- **Deep object graphs**: objects nested more than 128 levels deep are deferred, then written and read from a shallower level, so recursive types of any depth, and hostile data, cannot overflow the stack. See [Deep Object Graphs](/en/docs/v4/basic#deep-object-graphs).

## Defining Types [#defining-types]

- **Private members** with `includeNonPublicMembers`: on .NET 8 and later they are reached through `[UnsafeAccessor]` without `partial` (generic types: .NET 9 and later, since rc.8). See [Private Members](/en/docs/v4/defining-types#private-members).
- **Constructors, records and `required` members**: Nino calls the constructor that fits, or the one marked `[NinoConstructor]`. See [Constructors](/en/docs/v4/constructors).
- **Compact strings** (*rc.6*, *rc.8*): text whose chars are all at most U+00FF (ASCII, Latin-1) is written in one byte a char, other text as UTF-16, behind a header of one byte up to 63 chars ([Strings](/en/docs/v4/wire-format#strings)). [`[NinoUtf8]`](/en/docs/v4/defining-types#string-encoding) writes UTF-8 per member.
- **Subtypes inherit `[NinoType]`** from their base class or interface, and generic types work as members, elements and top-level values. See [Defining Types](/en/docs/v4/defining-types).

## Supported Types [#supported-types]

- **The BCL types of everyday code**: `BigInteger`, `Uri`, `Version`, `StringBuilder`, `BitArray`, `CultureInfo`, `TimeZoneInfo`, `Lazy<T>`, `Memory<T>`, `ReadOnlyMemory<T>` and `ReadOnlySequence<T>`, besides primitives, enums, strings, `Nullable<T>`, tuples, `KeyValuePair`, `DateTimeOffset` and `nint`. `System.Type` is left out on purpose. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types).
- **Every BCL collection**: arrays of rank 1 to 4, `List<T>`, `HashSet<T>`, `Queue<T>`, `Stack<T>`, `LinkedList<T>`, the sorted and concurrent collections, `BlockingCollection<T>`, `PriorityQueue<TElement, TPriority>` (.NET 8 and later), `ObservableCollection<T>`, the read-only wrappers (`ReadOnlyCollection<T>`, `ReadOnlyObservableCollection<T>`, `ReadOnlyDictionary<TKey, TValue>`), `ILookup<TKey, TElement>`, `IGrouping<TKey, TElement>` and the collection interfaces. See [Collection Types](/en/docs/v4/types#collection-types).
- **Every immutable collection** with the optional `Nino.Immutable` package, from `ImmutableArray<T>` to `ImmutableSortedDictionary<TKey, TValue>`, each with the bytes of its mutable counterpart. See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Your own collections**: types derived from `List<T>`, `Dictionary<TKey, TValue>` and friends, or implementing `ICollection<T>`, `IDictionary<TKey, TValue>` or `IProducerConsumerCollection<T>`, without attributes. See [User Collections](/en/docs/v4/types#user-collections).
- **Unity's `AnimationCurve`, `Gradient` and `RectOffset`**: the Unity package ships `Nino.UnityTypes.dll` with their formatters. Unity's and Godot's structs (`Vector3`, `Quaternion`...) are copied as raw memory. See [Unity Classes](/en/docs/v4/advanced/unity#unity-classes).
- **Pluggable formatters**: `[assembly: NinoFormatter(typeof(MyFormatter<,>))]` teaches Nino a new type, yours or a third-party one. Type arguments and element formatters are inferred (`[NinoRaw]` restricts a parameter to raw types), generated code calls it directly, and Nino's own BCL formatters are declared the same way. `[NinoMemberFormatter]` changes the encoding of one member. See [Custom Formatters](/en/docs/v4/custom-formatters).

## Allocation and Pooling [#allocation-and-pooling]

- **Reuse deserialization**: `NinoDeserializer.Deserialize(data, ref value)` fills existing objects, lists, arrays and dictionaries in place, and keeps a string whose text is unchanged.
- **Pooled deserialization**: mark a class `[NinoPooled]` and Nino deserializes into instances you hand back with `ReturnToPool()`, reusing their lists, arrays and dictionaries. Dropped instances (the payload is `null`, a list shrinks, the type changes) go to a handler registered with `NinoSettings.SetRecycler<T>`, or else back to their pool.
- **`[NinoFactory]` factories** let Nino take new instances from your own pools.

See [Reuse Deserialization and Pooling](/en/docs/v4/pooling).

## API [#api]

- **Two entry points**: `NinoSerializer.Serialize` to a `byte[]`, an `IBufferWriter<byte>` (a `PipeWriter`, for example) or a `Writer`, and `NinoDeserializer.Deserialize` from a `ReadOnlySpan<byte>` or a `Reader`. Every `Serialize` overload takes the value as `in T`, so a struct read from a field is written without a copy. See [Serialize and Deserialize](/en/docs/v4/basic).
- **`NinoArrayBufferWriter`**: a reusable buffer that makes serializing allocation-free, and with `new NinoArrayBufferWriter(initialCapacity, pool)` rents its arrays from your own `ArrayPool<byte>`. See [Reusing a Buffer](/en/docs/v4/basic#reusing-a-buffer).
- **`Writer` and `Reader`** write several values into one buffer and read them back, and are the API of custom formatters. See [Writer and Reader](/en/docs/v4/custom-formatters#writer-and-reader).
- **A boxed API for runtime types**: `SerializeBoxed(value, type)` and `DeserializeBoxed(data, type)` write exactly what `Serialize<T>` writes, for types known only as a `Type`. Types with a common `[NinoType]` base are faster through `Serialize<TBase>`. See [Runtime Types](/en/docs/v4/basic#runtime-types).
- **`NinoSerializer.IsSupported(Type)`** (*rc.6*) tells whether Nino can serialize and deserialize a type, for code that has only a `Type`, such as the ASP.NET Core formatters. See [The Boxed API](/en/docs/v4/basic#the-boxed-api).
- **No initialization**: generated registries register themselves and are found lazily; `NinoSettings`, `NinoPolymorphic.Register<T>()` and `NinoRegistry.EnsureInitialized` are optional. See [At Startup](/en/docs/v4/start#at-startup).

## Web and ASP.NET Core [#web-and-aspnet-core]

- **ASP.NET Core** (*rc.6*): the `Nino.AspNetCore` package adds MVC input and output formatters (`AddNinoFormatters()`) and Minimal API bodies (`NinoBody<T>`) and results (`NinoResults`) for `application/x-nino`, read and written straight from the request and response pipes. See [ASP.NET Core](/en/docs/v4/advanced/aspnetcore).
- **TypeScript clients** (*rc.6*): the `Nino.TypeScript` package generates TypeScript classes, enums and codecs for your `[NinoType]`s after each build, with the `nino.ts` runtime, so browsers and Node read and write exactly the bytes .NET writes. See [TypeScript](/en/docs/v4/advanced/codegen#typescript); since rc.8 the package is Nino.Codegen.
- **Go, Rust and nino-gen** (*rc.8*): Go and Rust runtimes in Nino's repository read and write the same bytes, and Nino.Codegen (after each build) or the `nino-gen` tool (Nino.Codegen.Tool, from a built assembly) writes your `[NinoType]`s as TypeScript, Go or Rust. See [TypeScript, Go and Rust](/en/docs/v4/advanced/codegen), [Go](/en/docs/v4/advanced/codegen#go) and [Rust](/en/docs/v4/advanced/codegen#rust).
- **.NET in the browser**: your types themselves can also run on .NET WebAssembly. See [Browser and JavaScript Clients](/en/docs/v4/advanced/browser).

## Platforms [#platforms]

- **One format everywhere**: `netstandard2.0`, `netstandard2.1`, `net8.0` and `net10.0` write identical bytes, portable between CoreCLR, Mono and IL2CPP, 64-bit and 32-bit, x64 and Arm64. Nino defines its bytes instead of copying memory where runtimes disagree (`Nullable<T>`, tuples, `decimal`, 32-bit alignment) and zeroes padding, so equal values serialize to equal bytes. See [Platforms and Binary Format](/en/docs/v4/platforms).
- **Trimming and Native AOT**: Nino.Core is annotated for both, so `PublishTrimmed` and `PublishAot` give no warnings from Nino. See [Trimming and Native AOT](/en/docs/v4/platforms#trimming-and-native-aot).
- **Unity 2022.3+** from OpenUPM, with the generator and `Nino.UnityTypes.dll` in the package. See [Unity and HybridCLR](/en/docs/v4/advanced/unity).
- **Code fixes in Unity** (*rc.7*): the Unity package includes the analyzer's code fixes, so Rider and Visual Studio offer the same quick fixes as in a .NET project. See [Analyzer Diagnostics](/en/docs/v4/analyzers).
- **HybridCLR hot update** without an initialization call, and **Godot 4** as a regular NuGet package. See [HybridCLR and Hot Update](/en/docs/v4/platforms#hybridclr-and-hot-update) and [Godot](/en/docs/v4/platforms#godot).
- **Unloadable assemblies**: an assembly in a collectible `AssemblyLoadContext` unloads with it; Nino clears what it cached for it, on its own on .NET 8 and later, through `NinoRegistry.Remove` on .NET Core 3.0 to .NET 7. See [Unloading Assemblies](/en/docs/v4/platforms#unloading-assemblies).

## Tooling [#tooling]

- **Truly incremental source generator**: one file per `[NinoType]`, equatable models, no whole-compilation scans. Editing a type re-generates only that type, and an edit that changes no model (a comment, a method body) re-generates nothing.
- **Much less generated code**: collections, strings, nullables, tuples and the other built-in types are implemented once in `Nino.Core` as generic formatters; the generator only emits code for your `[NinoType]`s.
- **27 analyzer rules** (NINO001–NINO027) report mistakes while you type, such as an unsupported member type, a missing `partial` or two `[NinoFormerName]`s on one type, many with a one-click code fix. See [Analyzer Diagnostics](/en/docs/v4/analyzers).

## Removed [#removed]

- `[NinoExplicitOrder]`: use `[NinoType(false)]` with `[NinoMember(index)]`.
- The betas' `Serialize(object)`: now `SerializeBoxed`.
- Run-time formatter registration with `NinoFormatterCache<T>.Register<TFormatter>()`: declare formatters with `[assembly: NinoFormatter]` or `[NinoMemberFormatter]`.

See [Migrating from v3](/en/docs/v4/migration) and [Upgrading from a v4 Beta](/en/docs/v4/migration#upgrading-from-a-v4-beta).

## Quick Example [#quick-example]

```csharp
[NinoType, NinoPooled]
public sealed partial class Packet
{
    public int Id;
    public List<int> Values;

    // Required (the analyzer offers a fix that adds both).
    private static partial IEnumerable<Packet> OnNinoPoolWarmup() => Enumerable.Range(0, 16).Select(_ => new Packet());
    private partial void OnNinoPoolReturn() { /* clear state Nino does not deserialize */ }
}

var buffer = new NinoArrayBufferWriter(); // keep it and reuse it: serializing into it allocates nothing
NinoSerializer.Serialize(new Packet { Id = 1, Values = new List<int> { 1, 2, 3 } }, buffer);

var packet = NinoDeserializer.Deserialize<Packet>(buffer.WrittenSpan); // reuses a pooled instance (and its list) if there is one
// ... use it ...
packet.ReturnToPool();                                                 // returning it twice throws
```
