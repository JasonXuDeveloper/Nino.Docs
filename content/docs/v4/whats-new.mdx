Nino v4 rewrites the runtime and the source generator. It runs faster than v3 **and** MemoryPack, builds dramatically faster, and adds the features long-lived projects need.

<Callout type="warn">

The v4 binary format is **not compatible** with v3 or the earlier v4 betas/previews, and the API changed. See [Migrating from v3](/en/docs/v4/migration).

</Callout>

## Serializes Faster than v3 [#faster-than-v3]

The baseline is v3 **3.3.13**, the last v3 release, run back to back with v4 on the same machine.

<BenchmarkChart chart={['v3-serialize', 'v3-deserialize']} lang="en" />

Serializing classes is clearly faster; deserializing is on par with v3. Why, and the one case where v4 is a few nanoseconds slower: [v3 vs v4](/en/docs/v4/v3-vs-v4#runtime).

## Faster to Build

The v3 generator inlined the body of every subtype into each polymorphic base and re-emitted every type on every keystroke. v4 emits one file per type, once, and re-generates only what you edit.

<BenchmarkChart chart="compile" lang="en" />

The larger the project, the bigger the gap. The numbers for 330 and 1,100 types, and how they were measured: [Build Time and Generated Code](/en/docs/v4/perf#build-time-and-generated-code).

Measured against MemoryPack in the same run. ### Deserialize into Existing Objects

New in v4: deserialize by `ref` into the objects you already have, with any new instances taken from [`[NinoPooled]`](/en/docs/v4/pooling) pools. Against MemoryPack's overwrite mode, Nino is up to **<BenchValue k="reuse.max" /> faster**, and on the pooled paths it allocates **0 B** per call, while MemoryPack allocates on every call ([pooling results](/en/docs/v4/perf#pooling)).

Neither library allocates when serializing, and payloads are about the same size (`SimpleClass`: <BenchValue k="payload.v4" /> bytes in Nino, <BenchValue k="payload.memorypack" /> in MemoryPack). Read the [full comparison with MemoryPack](/en/docs/v4/vs-memorypack), including [where MemoryPack is still ahead](/en/docs/v4/vs-memorypack#where-memorypack-is-ahead), and every measurement on [Benchmarks](/en/docs/v4/perf).

## Highlights

### Faster to build
- **Truly incremental source generator**: one file per `[NinoType]`, equatable models, no whole-compilation scans. Editing a type re-generates only that type, and an edit that changes no model (a comment, a method body) re-generates nothing.
- **Much less generated code**: collections, strings, nullables, tuples and other built-in types are implemented once in `Nino.Core` as generic formatters; the generator only emits code for your `[NinoType]`s.
- **Analyzers and code fixes**: mistakes are reported while you type (NINO001–NINO024), many with a one-click fix. See the [diagnostics list](https://github.com/JasonXuDeveloper/Nino/blob/main/docs/diagnostics.md).

### Faster to run
- **Struct formatters that the JIT/AOT compiler inlines**, raw memory copies for unmanaged `[NinoType]` structs and their arrays and lists, and no allocations beyond the result objects. [Fixed-size types](/en/docs/v4/performance#fixed-size-types) are written straight into a `byte[]` of their exact size.
- **Interceptors on modern compilers**: on Roslyn 4.8+ (the .NET 8 SDK and later), `NinoSerializer`/`NinoDeserializer` calls with a known type are redirected at compile time to the generated formatter (no virtual call). Always on, nothing to configure; older compilers use the regular path, with the same bytes. See [Interceptors](/en/docs/v4/performance#interceptors).
- **Thread safe and cache friendly**: lock-free, copy-on-write registries; no shared mutable state on hot paths.

### Reuse instead of allocate
- **Reuse deserialization**: `NinoDeserializer.Deserialize(data, ref value)` populates existing objects, lists, arrays and dictionaries in place.
- **Pooled deserialization**: mark a class `[NinoPooled]` and Nino deserializes into instances you hand back with `ReturnToPool()`, reusing their lists, arrays and dictionaries. Dropped instances (the payload is `null`, a list shrinks, the type changes) go back to their pool or to a handler registered with `NinoSettings.SetRecycler<T>`.
- **`[NinoFactory]` factories** let Nino take new instances from your own pools.

See [Reuse Deserialization and Pooling](/en/docs/v4/pooling).

### Evolve your data
- **Opt-in version tolerance**: `[NinoType(versionTolerant: true)]` lets you append members to the most derived type, at any nesting depth, and old code skips the members it does not know.
- **Keyed members**: `[NinoType(keyed: true)]` writes members by name hash, so they can be reordered, removed and inserted.
- **Reference tracking**: `[NinoType(trackReferences: true)]` keeps shared references and cycles.
- **Deep object graphs**: objects nested more than 128 levels deep are deferred, then written and read from a shallower level, so recursive types of any depth, and hostile data, cannot overflow the stack. See [Deep Object Graphs](/en/docs/v4/basic#deep-object-graphs).

### More types, your way
- **User collections**: types derived from `List<T>`, `HashSet<T>`, `Dictionary<TKey, TValue>` and friends, without attributes.
- **More built-in types**: `PriorityQueue<TElement, TPriority>` on .NET 6+, and `ImmutableArray<T>` / `ImmutableList<T>` with the `Nino.Immutable` package.
- **Pluggable formatters**: `[assembly: NinoFormatter(typeof(MyFormatter<,>))]` teaches Nino a new type (yours or a third-party one). Type arguments and element formatters are inferred, generated code calls it directly, and the runtime uses the same registration. Nino's own BCL formatters are declared the same way. See [Custom Formatters](/en/docs/v4/custom-formatters).
- **Subtypes inherit `[NinoType]`** from their base class or interface.

### Runs everywhere
- **One format everywhere**: `netstandard2.0`, `netstandard2.1`, `net8.0` and `net10.0` produce identical bytes, and data is portable between CoreCLR, Mono and IL2CPP, 64-bit and 32-bit.
- **No init calls**: generated registries are found lazily, so hot-update assemblies (HybridCLR) just work.
- **Unity**: the generator ships in the package; there is nothing else to install.

## Quick Example

```csharp
[NinoType, NinoPooled]
public sealed partial class Packet
{
    public int Id;
    public List<int> Values;

    // Required (the analyzer offers a fix that adds both).
    private static partial IEnumerable<Packet> OnNinoPoolWarmup() => Enumerable.Range(0, 16).Select(_ => new Packet());
    private partial void OnNinoPoolReturn() { /* clear state Nino does not deserialize */ }
}

byte[] bytes = NinoSerializer.Serialize(new Packet { Id = 1, Values = new List<int> { 1, 2, 3 } });

var packet = NinoDeserializer.Deserialize<Packet>(bytes); // reuses a pooled instance (and its list) if there is one
// ... use it ...
packet.ReturnToPool();                                    // returning it twice throws
```
