Nino v4 rewrites the runtime and the source generator. It runs faster than v3 **and** MemoryPack, builds dramatically faster, and adds the features long-lived projects need.

<Callout type="warn">

The v4 binary format is **not compatible** with v3 or the earlier v4 betas/previews, and the API changed. See [Migrating from v3](/en/docs/v4/migration).

</Callout>

## Serializes Faster than v3 [#faster-than-v3]

The baseline is v3 **3.3.13**, the last release of the v3 API (the 3.9.x releases were test builds of v4 features), run back to back with v4 on the same machine.

<BenchmarkChart chart={['v3-serialize', 'v3-deserialize']} lang="en" />

Serializing classes is clearly faster, deserializing is as fast as v3 or a little faster, and arrays of unmanaged structs are on par. Why: [v3 vs v4](/en/docs/v4/v3-vs-v4#runtime).

## Faster to Build

The v3 generator inlined the body of every subtype into each polymorphic base and re-emitted every type on every keystroke. v4 emits one file per type, once, and re-generates only what you edit.

<BenchmarkChart chart="compile" lang="en" />

The larger the project, the bigger the gap. The numbers for 330 and 1,100 types, and how they were measured: [Build Time and Generated Code](/en/docs/v4/perf#build-time-and-generated-code).

## Faster than MemoryPack

Measured against MemoryPack in the same run. Nino wins clearly when serializing (up to <BenchValue k="serialize.max" />), leads on classes and polymorphic graphs when deserializing (up to <BenchValue k="deserialize.max" />), and is close on arrays of unmanaged values, where both do a single `memcpy`.

### Deserialize into Existing Objects

New in v4: deserialize by `ref` into the objects you already have, with any new instances taken from [`[NinoPooled]`](/en/docs/v4/pooling) pools. Against MemoryPack's overwrite mode, Nino is up to **<BenchValue k="reuse.max" /> faster**, and on the pooled paths it allocates **0 B** per call, while MemoryPack allocates on every call ([pooling results](/en/docs/v4/perf#pooling)).

Neither library allocates when serializing, and payloads are about the same size (`SimpleClass`: <BenchValue k="payload.v4" /> bytes in Nino, <BenchValue k="payload.memorypack" /> in MemoryPack). Read the [full comparison with MemoryPack](/en/docs/v4/vs-memorypack), including [where MemoryPack is still ahead](/en/docs/v4/vs-memorypack#where-memorypack-is-ahead), and every measurement on [Benchmarks](/en/docs/v4/perf).

## Highlights

The details behind each card, followed by the smaller changes.

<Accordions type="multiple">
<Accordion title="Interceptors" id="interceptors">

On Roslyn 4.8+ (the .NET 8 SDK and later), `NinoSerializer`/`NinoDeserializer` calls with a known type are redirected at compile time to the generated formatter (no virtual call). Always on, nothing to configure; older compilers use the regular path, with the same bytes. See [Interceptors](/en/docs/v4/performance#interceptors).

</Accordion>
<Accordion title="Keyed members and versioning" id="evolve-your-data">

- **Opt-in version tolerance**: `[NinoType(format: NinoFormat.VersionTolerant)]` lets you append members to the most derived type, at any nesting depth, and old code skips the members it does not know.
- **Keyed members**: `[NinoType(format: NinoFormat.Keyed)]` writes members by name hash, so they can be reordered, removed and inserted.

See [Evolving Your Data](/en/docs/v4/evolving-data).

</Accordion>
<Accordion title="Reference tracking" id="reference-tracking">

`[NinoType(trackReferences: true)]` keeps shared references and cycles: an object reached twice is written once and read back as one instance, at 4 bytes per tracked object. See [Reference Tracking](/en/docs/v4/reference-tracking).

</Accordion>
<Accordion title="Analyzers NINO001–NINO025" id="analyzers">

Mistakes are reported while you type (NINO001–NINO025), many with a one-click fix. See the [diagnostics list](https://github.com/JasonXuDeveloper/Nino/blob/main/docs/diagnostics.md).

</Accordion>
<Accordion title="Low GC and pooling" id="reuse-instead-of-allocate">

- **Reuse deserialization**: `NinoDeserializer.Deserialize(data, ref value)` populates existing objects, lists, arrays and dictionaries in place.
- **Pooled deserialization**: mark a class `[NinoPooled]` and Nino deserializes into instances you hand back with `ReturnToPool()`, reusing their lists, arrays and dictionaries. Dropped instances (the payload is `null`, a list shrinks, the type changes) go to a handler registered with `NinoSettings.SetRecycler<T>`, or else back to their pool.
- **`[NinoFactory]` factories** let Nino take new instances from your own pools.

See [Reuse Deserialization and Pooling](/en/docs/v4/pooling).

</Accordion>
<Accordion title="Thread safe" id="thread-safe">

Every `NinoSerializer` and `NinoDeserializer` method can be called concurrently without locks. Registries are lock-free and copy-on-write, scratch buffers are per thread, and no hot path writes shared memory, so threads never contend for a cache line. See [Thread Safety](/en/docs/v4/performance#thread-safety).

</Accordion>
<Accordion title="Identical bytes everywhere" id="runs-everywhere">

- **One format everywhere**: `netstandard2.0`, `netstandard2.1`, `net8.0` and `net10.0` produce identical bytes, and data is portable between CoreCLR, Mono and IL2CPP, 64-bit and 32-bit.
- **No init calls**: generated registries are found lazily, so hot-update assemblies (HybridCLR) just work.
- **Unloadable assemblies**: an assembly in a collectible `AssemblyLoadContext` unloads with it; Nino clears what it cached for it (on its own on .NET 8 and later; on .NET Core 3.0 to .NET 7, call `NinoRegistry.Remove`). See [Unloading Assemblies](/en/docs/v4/platforms#unloading-assemblies).
- **Unity**: the generator ships in the package; there is nothing else to install.

</Accordion>
<Accordion title="Truly incremental generator" id="incremental-generator">

- **Truly incremental source generator**: one file per `[NinoType]`, equatable models, no whole-compilation scans. Editing a type re-generates only that type, and an edit that changes no model (a comment, a method body) re-generates nothing.
- **Much less generated code**: collections, strings, nullables, tuples and other built-in types are implemented once in `Nino.Core` as generic formatters; the generator only emits code for your `[NinoType]`s.

</Accordion>
<Accordion title="Faster runtime code" id="faster-to-run">

- **Struct formatters that the JIT/AOT compiler inlines**, raw memory copies for unmanaged `[NinoType]` structs and their arrays and lists, and no allocations beyond the result objects. [Fixed-size types](/en/docs/v4/performance#fixed-size-types) are written straight into a `byte[]` of their exact size.
- **Deep object graphs**: objects nested more than 128 levels deep are deferred, then written and read from a shallower level, so recursive types of any depth, and hostile data, cannot overflow the stack. See [Deep Object Graphs](/en/docs/v4/basic#deep-object-graphs).

</Accordion>
<Accordion title="More types, your way" id="more-types-your-way">

- **User collections**: types derived from `List<T>`, `HashSet<T>`, `Dictionary<TKey, TValue>` and friends, without attributes.
- **More built-in types**: `PriorityQueue<TElement, TPriority>` on .NET 6+, and `ImmutableArray<T>` / `ImmutableList<T>` with the `Nino.Immutable` package.
- **Pluggable formatters**: `[assembly: NinoFormatter(typeof(MyFormatter<,>))]` teaches Nino a new type (yours or a third-party one). Type arguments and element formatters are inferred, generated code calls it directly, and the runtime uses the same registration. Nino's own BCL formatters are declared the same way. See [Custom Formatters](/en/docs/v4/custom-formatters).
- **Subtypes inherit `[NinoType]`** from their base class or interface.

</Accordion>
<Accordion title="A small, explicit API" id="a-small-explicit-api">

- **One option for the format**: `[NinoType(format: ...)]` takes a `NinoFormat` (`Positional`, the default, `VersionTolerant` or `Keyed`). Defining `WEAK_VERSION_TOLERANCE` in a project turns its `Positional` types into `VersionTolerant` ones. See [Evolving Your Data](/en/docs/v4/evolving-data).
- **Fixed-size types**: `NinoSerializer.Serialize(value)` of a type whose values always take the same number of bytes allocates the result at its final size, and `NinoSerializer.GetFixedSize<T>()` returns that size. See [Fixed-Size Types](/en/docs/v4/performance#fixed-size-types).
- **Layout metadata**: how each `[NinoType]` is written is recorded in the assembly's metadata (`[assembly: NinoTypeLayout]`), for compatibility checks and diffs between builds. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata).
- **Your own buffers**: `new NinoArrayBufferWriter(initialCapacity, pool)` rents from your `ArrayPool<byte>`. See [Reusing a Buffer](/en/docs/v4/basic#reusing-a-buffer).
- **A boxed API for runtime types**: `SerializeBoxed(value, type)` and `DeserializeBoxed(data, type)` serialize a type known only as a `Type` when the types share no common `[NinoType]` base, writing exactly what `Serialize<T>` writes. For message dispatch, plugins and tools, give the types a common `[NinoType]` base and call `Serialize<TBase>`/`Deserialize<TBase>`, which is faster and allocation-free; see [Runtime Types](/en/docs/v4/basic#runtime-types).
- **Removed**: `[NinoExplicitOrder]` (use `[NinoType(false)]` with `[NinoMember(index)]`), the betas' `Serialize(object)` (now `SerializeBoxed`) and run-time formatter registration with `NinoFormatterCache<T>.Register<TFormatter>()` (declare formatters with `[assembly: NinoFormatter]` or `[NinoCustomFormatter]`). See [Migrating from v3](/en/docs/v4/migration).

</Accordion>
</Accordions>

## Quick Example

```csharp
[NinoType, NinoPooled]
public sealed partial class Packet
{
    public int Id;
    public List<int> Values;

    // Required (the analyzer offers a fix that adds both).
    private static partial IEnumerable<Packet> OnNinoPoolWarmup() => Enumerable.Range(0, 16).Select(_ => new Packet());
    private partial void OnNinoPoolReturn() { /* clear state Nino does not deserialize */ }
}

var buffer = new NinoArrayBufferWriter(); // keep it and reuse it: serializing into it allocates nothing
NinoSerializer.Serialize(new Packet { Id = 1, Values = new List<int> { 1, 2, 3 } }, buffer);

var packet = NinoDeserializer.Deserialize<Packet>(buffer.WrittenSpan); // reuses a pooled instance (and its list) if there is one
// ... use it ...
packet.ReturnToPool();                                                 // returning it twice throws
```
