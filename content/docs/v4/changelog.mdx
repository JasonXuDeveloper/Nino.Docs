## 4.0.0-rc.8

### Wire Format [#wire-format-3]

- **String headers of 1, 3 or 5 bytes**: every string (members, elements and keys of collections, `StringBuilder`, the text of `Uri`, `CultureInfo` and `TimeZoneInfo`, and `[NinoUtf8]` strings) is written with a header whose first byte gives its size, as MessagePack's string markers do, instead of a 4-byte `int32`: the value itself up to `7F`, else `80` and a `uint16`, else `81` and a `uint32`, always the shortest form. The value is `0` for null, `2n + 1` for `n` Latin-1 chars (`1` is the empty string) and `2n` for `n` UTF-16 code units, so a string of up to 63 chars has a one-byte header: null is `00`, `""` is `01`, `"abc"` is `07 61 62 63`. A `[NinoUtf8]` string writes its char count plus one and its byte count as headers. A `StringBuilder` keeps the UTF-16 form (an empty one is `01`). Readers reject a header that is not in its shortest form or starts with `82` or above. The Go, Rust and TypeScript runtimes write and read the same bytes. This is version 4.1 of the wire format specification; data written by earlier 4.0 prereleases is not readable ([Upgrading from an Earlier Release Candidate](/en/docs/v4/migration#upgrading-from-an-earlier-release-candidate)). See [Strings](/en/docs/v4/wire-format#strings).
- **Tuples of eight items or more**: a member (or element) whose type is a `ValueTuple` of eight items or more is now written, every item in order as for shorter tuples, where it was skipped with warning NINO007 and wrote nothing. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types).
- **Nullable raw `[NinoType]` structs bound at run time**: `T?[]` and other `T?` sequences of a raw `[NinoType]` struct whose formatter the runtime builds (types no generated code names, serialized by `Type` or boxed) are written at the fixed stride generated code uses, so either side reads the other's bytes. Payloads such a formatter wrote before must be rewritten.
- **32-bit x86**: a member whose type is a struct (not a `[NinoType]`) holding a `TimeOnly`, `Complex`, `Int128` or `UInt128` after a smaller field is written in the canonical layout, as on 64-bit runtimes, instead of its x86 memory. See [Portable by Design](/en/docs/v4/platforms#portable-by-design).
- **`Int128` and `UInt128` in raw structs**: unmanaged structs that are not `[NinoType]`s and hold an `Int128` or `UInt128` write their padding as zeros on .NET 8 and later, as the canonical layout requires; it was copied from memory, so it held whatever was there. See [Raw Values](/en/docs/v4/wire-format#raw-values).
- **Closed generic `[NinoType]` structs**: a closed generic `[NinoType]` struct (`Pad<int>` of `struct Pad<T> { byte A; T B; }`) held as a member or collection element is written member by member, as its formatter writes it everywhere else; generated code copied it there as raw memory, padding included. The two encodings could not read each other: a value written by a top-level call or through a generic type could not be read as a member, nor the other way round. A field of a type parameter makes every closed type of a definition member by member; payloads holding such members must be rewritten. See [Generic Types](/en/docs/v4/defining-types#generic-types).

### New [#new-6]

- **Renamed before 4.0** (no aliases; the bytes do not change): `[NinoType(containNonPublicMembers)]` is `includeNonPublicMembers`, the member attribute `[NinoCustomFormatter]` is `[NinoMemberFormatter]` (apart from the type-level `[assembly: NinoFormatter]`), `NinoTypeId.GetName`/`GetIdName` are `GetRuntimeName`/`GetHashedName`, and `NinoSettings.DefaultPoolMaxRetained` is `PoolMaxRetained`. The subtype registry generated code calls, `Nino.Core.NinoPolymorphic<TBase>`, is `Nino.Core.CompilerServices.NinoSubtypes<TBase>` (the user API `NinoPolymorphic.Register` keeps its name). For formatters written by hand, `INinoBlockFormatter<T>` now extends `INinoFixedSizeFormatter<T>` (`FixedSize` and `WriteFixed(in value, ref destination)` replace `BlockSize` and `WriteBlock`, and `ReadBlock` takes the value first), and the `TryRegister` methods generated code calls return whether they registered. In the TypeScript runtime, the `NinoReader` and `NinoWriter` method generated code calls to start a version-tolerant or keyed region is `beginRegion` (was `region`, as .NET's `BeginRegion`), the presence byte is read by `present` (was `notNull`, as .NET's `ReadPresent`) and `presentAt`, and the registry of subtypes behind a type id is `NinoSubtypes` (was `NinoRegistry`, which in .NET names the per-assembly registrations): regenerate code that Nino.TypeScript or an earlier nino-gen wrote. See [Upgrading from an Earlier Release Candidate](/en/docs/v4/migration#upgrading-from-an-earlier-release-candidate).
- **Reading into an existing value in TypeScript, Go and Rust**: `deserializeInto(codec, bytes, value)`, `nino.DeserializeInto(data, &v, ReadXInto)` and `nino::deserialize_into(&bytes, &mut v)` read as `NinoDeserializer.Deserialize(data, ref value)` does: nested objects in place, arrays, slices and `Vec`s keeping their storage and elements, maps and sets cleared and refilled, polymorphic values reused only for the same type. nino-gen writes one read body per type for both forms. See [API](/en/docs/v4/advanced/codegen#api).
- **`serializeInto` in TypeScript**: `serializeInto(codec, value, target)` writes into a reused `NinoWriter` (emptied with the new `reset()`; no allocation once it is large enough, so no `ArrayBuffer`s pile up toward Node's full garbage collections) or into a `Uint8Array`, and returns the value's size, as `NinoSerializer.Serialize(value, bufferWriter)` does in .NET. See [API](/en/docs/v4/advanced/codegen#api).
- **Typed arrays in TypeScript**: nino-gen's `NumericArrays="typed"` (`--numeric-arrays typed`) writes arrays and lists of fixed-size numbers as typed arrays (`Int32Array`, `Float64Array`, `BigInt64Array`...), copied in one block. Serialize is faster in Node and Chromium and deserialize faster in Node; Chromium deserializes them 2 to 3.3 times slower and lists of small objects read 5 to 25% slower in both engines, so the default, `NumericArrays="plain"`, keeps `number[]`. See [Typed Arrays](/en/docs/v4/advanced/codegen#typed-arrays).
- **NINO028**: a warning for `[NinoMember]` on a member Nino never serializes (a static field or property, a constant, an indexer, a property without a setter that no constructor takes, or a backing field through `[field: NinoMember]`), which wrote nothing while NINO010 said the member was collected already; a code fix removes the attribute. NINO008 now names the member and its type. See [Diagnostics](/en/docs/v4/analyzers#diagnostics).
- **NINO027**: a warning for `[NinoFormerName]` on a generic type that is written with a type id (through a base class, an interface or `object`): every instantiation would take the same id and collide. See [Diagnostics](/en/docs/v4/analyzers#diagnostics).
- **Code fixes for NINO024 and NINO025**: the IDE removes a member's `[NinoFormerName]`s in a type that is not keyed, and a `[NinoFactory]` that a `[NinoConstructor]` makes unused; neither changes what is written or read. NINO003, NINO005, NINO007, NINO010, NINO011, NINO012 and NINO017 now say what happens and what to change (NINO003: writing the subtype throws). See [Diagnostics](/en/docs/v4/analyzers#diagnostics).
- **`NinoDataException`** (namespace `Nino.Core`, derived from `InvalidOperationException`) is thrown for every invalid input Nino rejects while deserializing, so untrusted data can be caught with one specific type; `catch (InvalidOperationException)` still catches it. See [NinoDataException](/en/docs/v4/security#ninodataexception).
- **`NinoSettings.MaxDepth`** (default 512, at least 128) and **`NinoSettings.MaxCollectionLength`** (default `int.MaxValue`) bound nesting and the element count a collection in the data may claim. Set them before the first serialization or deserialization; later they throw. See [Limits](/en/docs/v4/security#limits).
- **`NinoSettings.MaxHashCollisions`** (default 100): a key read from the data that finds more keys than this in its hash bucket throws `NinoDataException`, so data built to make keys collide (hash flooding) can no longer make reading a `Dictionary`, `HashSet`, lookup, `ImmutableDictionary`, `ImmutableHashSet` or `ConcurrentDictionary` quadratic. See [Hash Flooding](/en/docs/v4/security#hash-flooding).
- **`NinoSettings.Untrusted`** (off by default): for data from someone who could craft it, the dictionaries and sets Nino creates hash integer, `char`, `Guid` and `string` keys with a per-process secret, raw structs are checked as their constructors would check them (`bool`, `DateTime`, `decimal`, `DateOnly`, `TimeOnly`), and bytes left after the value throw `NinoDataException`. Off, it costs nothing. See [Untrusted Mode](/en/docs/v4/security#untrusted-mode).
- **`<NinoPrefetchLargeCollections>true</NinoPrefetchLargeCollections>`**, an MSBuild property (unset by default): in a project that sets it, top-level writes of a `T[]` or `List<T>` of a non-generic `[NinoType]` class that is not fixed-size, and reads into an existing one of as many elements, prefetch the objects ahead when the collection takes more than a quarter of the CPU's last-level cache and its objects are not in allocation order (replaced, shuffled or sorted after they were created), on .NET 8 and later on x64 and Arm64, through the interceptors (so not in Unity). The bytes are the same; without it, the generated code is that of before. See [Large Collections of Scattered Objects](/en/docs/v4/advanced/high-performance#large-collections).
- **Nino.Codegen** replaces Nino.TypeScript and writes your `[NinoType]`s as TypeScript, Go or Rust types and codecs after each build, from the layouts the generator publishes: one run per `<NinoCodegen Include="typescript|go|rust" Out="..." />` item, whose metadata are the generator's options (`Name`; `Names`, `ImportExtension`, `Runtime`; `Package`, `Tags`, `TagNames`; `Serde`, `SerdeNames`, `Strings`, `Maps`), with `NinoCodegenTargetFramework` and `NinoCodegenEnabled` for the project. The same generator is the **Nino.Codegen.Tool** .NET tool for a built assembly (`nino-gen --assembly <dll> --lang ts|go|rust --out <dir>`). Go structs carry `nino` tags and `json`/`yaml` tags (camelCase by default); Rust types can derive serde. An unknown option, one given twice or of another language, or a value an option does not take is error NINOGEN001, on the command line and in the build; the files a run writes are listed in a `.nino-gen` manifest in the output directory, and the next run deletes those it no longer writes. A project that references Nino.Codegen without an item gets warning NINOGEN004. See [TypeScript, Go and Rust](/en/docs/v4/advanced/codegen).
- **From Nino.TypeScript** (up to rc.7): reference Nino.Codegen instead and declare `<NinoCodegen Include="typescript" ... />`; `NinoTypeScriptOutput`, `NinoTypeScriptImportExtension` and `NinoTypeScriptNames` become its `Out`, `ImportExtension` and `Names`, and `NinoTypeScriptTargetFramework` and `NinoTypeScriptEnabled` become `NinoCodegenTargetFramework` and `NinoCodegenEnabled`. Until then the `NinoTypeScript*` properties still work, with warning NINOGEN003. The output is the same but for its header comment, the first run takes over the `.nino-ts` manifest, and `NINOTS001` and `NINOTS002` are now `NINOGEN001` and `NINOGEN002`. See [Migrating from Nino.TypeScript](/en/docs/v4/advanced/codegen#from-ninotypescript).
- **Go and Rust runtimes**, published with every release under Nino's version (`go get github.com/JasonXuDeveloper/Nino/runtimes/go/v4`, `cargo add nino-serialization`), read and write Nino's binary format, deep nesting, version-tolerant and keyed types included, and are tested against the same conformance corpus as .NET. Go (module `github.com/JasonXuDeveloper/Nino/runtimes/go/v4`) maps tagged structs (`nino:"0"`, `nino:"Name"`) with `nino.Marshal` and `nino.Unmarshal`, checked against the layout a type declares with `NinoLayout()`; Rust (crate `nino-serialization`, library `nino`) has `#[derive(NinoRead, NinoWrite)]` with `#[nino(...)]` attributes, checked against a published layout at compile time, an optional `serde` feature, and a reader whose bounds checks are safe code. Both take whether a type is deferrable from its published layout. The TypeScript runtime is published to npm as `nino-serialization` too, for generated code that imports it (`Runtime="nino-serialization"`) instead of a copy of `nino.ts`. See [Go](/en/docs/v4/advanced/codegen#go) and [Rust](/en/docs/v4/advanced/codegen#rust). Both are written for speed: strings are converted by SIMD kernels on x64 (AVX-512, AVX2, SSSE3) and Arm64 (NEON) ([SIMD on Every Platform](/en/docs/v4/simd#go)), arrays, slices and maps of fixed-size values are read and written as one block, Go checks sets for repeated elements in a seeded table of the reader's own, generated code calls each element's and each class body's code directly, and Rust prefetches the elements of lists larger than the CPU's cache when they hold strings, vectors or boxes. Every release times them against Protocol Buffers, MessagePack and each language's usual serializers: [Benchmarks in Other Languages](/en/docs/v4/benchmarks-runtimes).
- **Go: `EnterBody`, `ExitBody`, `CheckUniqueKeys`, `CheckUniqueValues` and `CheckUniqueStrings`**: `Reader.EnterBody`/`ExitBody` and `Writer.EnterBody`/`ExitBody` open a class body in place for code that calls the body directly, with `ReadClassInto`/`WriteClass` from 128 open bodies on (where .NET defers them); `nino.CheckUniqueKeys` checks pairs your own loop read for a repeated key, `nino.CheckUniqueValues` the elements of a set and `nino.CheckUniqueStrings` a set of nullable strings, comparing numbers as .NET does (any two NaNs are equal). Generated code uses them all, so it reads class bodies, dictionaries and sets without a call through a function value. See the runtime's [README](https://github.com/JasonXuDeveloper/Nino/tree/main/runtimes/go).
- **Go and Rust code written against `main` before this release** (both runtimes are new in rc.8): in Go, keyed members are read and written with `BeginMember`, `EndMember`, `SkipMember` and `KeyedMember` (were `BeginEntry`, `EndEntry`, `SkipEntry` and `KeyedEntry`; "entry" stays a dictionary's pair, `nino.Entry`), and the helpers that took each element's code as a function value (`ReadSlice`, `WriteSlice`, `ReadMap`, `WriteMap`, `ReadEntries`, `WriteEntries`, `ReadSet`, `WriteSet`, `ReadUnique`, `ReadUniqueEntries`, `ReadFixed`, `WriteFixed`, `WritePrimitivesRaw`, `ReadPrimitivesInto`, `ReadSealedInto`) are gone: loop with a direct call per element. Go's `Writer.Null` is `NullLength` (as .NET's `WriteNullLength`), and the old method names `Utf8`, `Utf8Ptr`, `NullableUtf8`, `Int128` and `UInt128` are gone (use `UTF8`, `UTF8Ptr`, `NullableUTF8`, `I128` and `U128`). In Rust, `NinoWrite::PREFETCH` is `PREFETCH_BYTES`, the helpers generated and derived code calls are `sum_fixed_sizes`, `decode_member` and `encode_member` (were `fixed_size`, `decode_next` and `encode_next`), `Reader::read_member`, `read_member_into`, `defer_mark` and `defer_trail` (were `read_in`, `read_into_in`, `mark` and `trail`), `Reader::utf16` and `Writer::utf16` (were `wide_string`, as Go's `UTF16`), the depth constants `DEPTH_INLINE` and `DEPTH_MAX` are `INLINE_DEPTH` and `MAX_DEPTH` (as Go's `InlineDepth` and `MaxDepth`), `nino::sealed_read!()` and `nino::sealed_write!()` write a sealed class's `NinoRead` and `NinoWrite` methods in a hand-written impl, and the derive's `format` is `"positional"`, `"version_tolerant"` or `"keyed"` (`"plain"` and `"tolerant"` are no longer accepted). Regenerate code an earlier nino-gen wrote. See [Go](/en/docs/v4/advanced/codegen#go) and [Rust](/en/docs/v4/advanced/codegen#rust).
- **Generic types in TypeScript, Go and Rust**: nino-gen generates generic `[NinoType]`s as generic types (`Box<T>`, `Box[T any]`, `BoxType<T>`), with codecs built from those of their type arguments (`BoxCodec(...)`), and closed uses such as `Box<int>` (closed generic structs included) as members of that generic type. Generic types written behind a type id (a class that is not sealed, an abstract class or an interface) are generated too, each closed type a slot of its own with the closed types it needs, as are `Nullable` and `KeyValuePair` type arguments inside collections (`Wrap<int?[]>`); a generic type that holds itself with other type arguments (`Nest<T>` holding `Nest<List<T>>`) is generated for TypeScript, and left out of Go and Rust with NINOGEN002. See [Generic Types](/en/docs/v4/advanced/codegen#generics) and [Generic Types Behind a Type Id](/en/docs/v4/advanced/codegen#generic-types-behind-a-type-id).
- **Closed generic types in polymorphic and `object` slots** (a generic subtype such as `Box<int> : Animal`) for TypeScript, Go and Rust: the closed types the assembly's code names are read from its metadata, each a case of the slots it is assignable to, behind the id of its closed .NET name: a TypeScript subclass (`BoxInt32 extends Box<number>`, and generic `XCodec`s take the class to build as an optional last argument), a Go case, a Rust variant. The targets accept every closed type the assembly names, where .NET in a fresh process accepts only those it has registered or written. See [Closed Generic Types in Slots](/en/docs/v4/advanced/codegen#closed-generic-types-in-slots).
- **Reference tracking in TypeScript, Go and Rust**: types declared with `trackReferences: true` are generated by nino-gen and read and written by the three runtimes, shared references and cycles included: TypeScript and Go return the same object for every reference to it, Rust holds tracked objects as `nino::Shared<T>`, and the objects one read creates are freed together when the last `Shared` outside them is dropped (or the read fails), cycles included; a `Shared` you clone keeps them alive. A header that names no object read so far, or an object of a type the slot does not allow, is rejected. See [Reference Tracking](/en/docs/v4/advanced/codegen#reference-tracking).
- **`[NinoType]` collections in TypeScript, Go and Rust**: a `[NinoType]` class deriving from a collection (`class Bag : List<int>` with members of its own) is generated with its elements in a field before its members (`$elements` in TypeScript, `Elements` in Go, `elements` in Rust). See [`[NinoType]` Collections](/en/docs/v4/advanced/codegen#ninotype-collections).
- **`useWasm()`** in the TypeScript runtime: in browsers and Deno, longer strings are read and written through a small WebAssembly module embedded in `nino.ts`, with the JavaScript paths kept where WebAssembly SIMD, GC or the JS String Builtins are unavailable or blocked (a Content Security Policy without `'wasm-unsafe-eval'`); `useWasm(false)` turns it off. The bytes are the same either way, and Node keeps its `Buffer` paths. See [Text in Browsers](/en/docs/v4/advanced/codegen#text-in-browsers).
- **`Maps`** (`--maps indexmap|std`) for Rust: `std` writes `std::collections::HashMap` and `HashSet` instead of `indexmap`'s, with no dependency but the crate; they are written in `HashMap`'s iteration order. `indexmap` stays the default. See [Options](/en/docs/v4/advanced/codegen#options).
- **`NinoTypeLayoutAttribute.Deferrable`** says whether a type's bodies nested past 128 class bodies are deferred, and the layout's text form carries it as `deferrable=true|false`, so code generators for other languages read it instead of re-deriving .NET's rules. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata).
- **Generic `[NinoType]`s with non-public members no longer need to be `partial`** when the project targets .NET 9 or later (the compilation defines `NET9_0_OR_GREATER`): generated code reaches the members through `[UnsafeAccessor]` declared in the generic formatter, as it does for non-generic types since .NET 8. A member inherited from a generic base still needs `partial` unless the base's type arguments are the type's own first type parameters in order (`class D<T, U> : Base<T>`, not `Base<List<T>>` or `Base<int>`), or the base is not generic; NINO002 and NINO022 say when. A non-public base member hidden by `new` in a generic type is now serialized too on .NET 9+, where it was skipped with NINO022. See [Private Members](/en/docs/v4/defining-types#private-members) and [Diagnostics](/en/docs/v4/analyzers#the-type).
- **Block formatters**: arrays, lists and spans of `[NinoType]` structs of fixed size that are not raw (a value tuple or `KeyValuePair` member, `LayoutKind.Auto`, auto-properties) are read and written as blocks: the generator gives such a struct's formatter `INinoBlockFormatter<T>`, so a collection of it takes one bounds check and the vector shuffles of tuples on .NET 8+, instead of one value at a time. The bytes are unchanged. See [Raw Memory for Unmanaged Data](/en/docs/v4/performance#raw-memory-for-unmanaged-data).
- **Burst kernels in Unity** (`Nino.Burst`, in the Unity package): with `com.unity.burst` 1.8 or later installed, arrays and lists of tuples and structs, raw structs with padding, Latin-1 strings and the ASCII text of `[NinoUtf8]` strings are moved with AVX2 or SSSE3 (x86 and x64) or Arm64 Neon instead of Nino's scalar netstandard paths, with the same bytes and no code change; invalid UTF-8 is rejected exactly as without Burst. In x64 players, Burst's AVX2 target moves blocks of 256 values or more (of up to 16 bytes each) with AVX2, and a CPU without AVX2 needs the SSE4 target for the SSSE3 kernels. Armv7 and IL2CPP or Mono players without Burst keep the scalar paths: install Burst for speed. Kernels of your own can be registered through `NinoKernels`, a table of native function pointers (`delegate* unmanaged[Cdecl]`) that Nino calls directly. See [Burst-Accelerated Kernels](/en/docs/v4/advanced/unity#burst-kernels) and the [Unity Benchmark](/en/docs/v4/benchmarks-unity).
- **WebAssembly SIMD kernels for Unity WebGL** (`Nino.WebGL`, in the Unity package): WebGL players built with WebAssembly SIMD (Unity 6's Target WebAssembly 2023; on Unity 2022.3, `--compiler-flags=-msimd128` in Additional IL2CPP Arguments, which needs Safari 16.4 or later) register the same kernels written in C, for Latin-1 strings and the ASCII text of `[NinoUtf8]` strings of 16 chars or more and arrays of tuples and of raw structs with padding of 32 values or more, with the same bytes. Players without SIMD keep the scalar paths. See [WebGL](/en/docs/v4/advanced/unity#webgl-kernels).
- **`deserializeExact`** in the TypeScript runtime: `deserialize` that also throws a `NinoError` when bytes follow the value, as Go's `DeserializeExact` and Rust's `deserialize_exact` do. See [Untrusted Data](/en/docs/v4/advanced/codegen#untrusted-data).
- The types only generated code uses (`NinoObject`, `NinoDirect`, `NinoUnsafe`, the formatter interfaces such as `INinoBodyFormatter<T>` and `INinoBlockFormatter<T>`, the subtype registry, ...) moved to the namespace `Nino.Core.CompilerServices`. Generated code needs nothing; code that named one of them by hand needs `using Nino.Core.CompilerServices;`. The constants of `INinoBodyFormatter<T>.Traits` are now `NinoBodyTraits` (they were `NinoBody`, the name of Nino.AspNetCore's `NinoBody<T>`).
- **A skill for AI coding assistants**: `npx skills add JasonXuDeveloper/Nino` installs the `nino-serialization` skill, which teaches Claude Code, Codex, Cursor and other coding agents Nino's recommended and fast forms, formats, pitfalls and diagnostics. See [AI Coding Assistants](/en/docs/v4/start#ai-coding-assistants).

### Performance [#performance-3]

- **Classes with string members**: deserializing a new instance no longer keeps the reader in memory, and one-character Latin-1 strings are shared instead of allocated: SimpleClass and new instances of a pooled type read 13-18% faster, version-tolerant classes 2.3-4.6% (GitHub's AMD EPYC 7763 and Neoverse-N2 runners).
- **Unchanged UTF-8 text in existing instances**: deserializing into an existing object (a pooled or `ref` target) keeps its long [`[NinoUtf8]`](/en/docs/v4/defining-types#string-encoding) text when the bytes have not changed: 17-22% faster in the pooled benchmark on the same runners. See [Deserializing into Existing Instances](/en/docs/v4/pooling#deserializing-into-existing-instances).
- **Sorted, immutable and string-keyed collections**: `SortedList<int, int>` deserializes 21% faster on Arm64 (Neoverse-N2), `SortedDictionary` 3% faster and `ImmutableDictionary`, `ImmutableHashSet` and `SortedSet` up to 3% faster on x64 and Arm64; `Dictionary<string, string>` deserializes 9% faster on x64 (AMD EPYC 7763) and 3% on Arm64.
- **`ConcurrentDictionary` on x64**: the read path finds each key's bucket and lock by fast modulo instead of two divisions: `ConcurrentDictionary<int, int>` deserializes 18-23% faster on GitHub's AMD EPYC 7763 runners; EPYC 9V45 and 9V74 (which divide fast) and Arm64 are on par, and Arm64 keeps the divisions.
- **Generic types and types from other assemblies**: members of generic `[NinoType]`s, of `[NinoType]`s generated in another assembly and of types that hold themselves are called directly in optimized .NET code instead of through a virtual call: a generic type holding an unmanaged tuple deserializes in 0.86-0.94 times the time on GitHub's AMD EPYC 7763, 9V45 and 9V74 and Neoverse-N2 runners and serializes 2-4% faster on the 7763, 9V74 and Neoverse-N2. See [Generic Types](/en/docs/v4/defining-types#generic-types).
- **No allocation per value in Unity players**: in IL2CPP builds, arrays and lists of tuples and of fixed-size structs no longer allocate for each element when no Burst kernel handles them, and `NinoSerializer.Serialize` no longer allocates for each call before writing: the netstandard builds create each formatter object once. See [Unity](/en/docs/v4/advanced/unity).
- **Generic types on Unity, Mono and Native AOT**: the formatter of a generic `[NinoType]` takes the formatters of its type arguments, so a member of type `T` is a direct call on every runtime, where IL2CPP, Mono and Native AOT made a virtual call per value. In .NET, arrays of generic polymorphic types read and write on par or faster on GitHub's x64 and Arm64 runners (serialize up to 11% faster on AMD EPYC 9V74). See [Generic Types](/en/docs/v4/defining-types#generic-types).
- **Padded structs and tuples in arrays**: arrays and lists of fixed-size values with padding that hold a `bool` (such as a `Waypoint` of a `Vector3`, a `float` and a `bool`) check their bools eight at a time instead of one by one, and deserialize in 0.80-0.92 times the time on GitHub's AMD EPYC 7763, 9V45 and 9V74, Intel Xeon Platinum and Neoverse-N2 runners (1,000 `Waypoint`s on EPYC 9V74: 1,522 to 1,210 ns). On Arm64 such values over 8 bytes are written in vector lane groups instead of one at a time: 1,000 `Waypoint`s serialize 3.4 times as fast on Neoverse-N2 (1,438 to 427 ns), and with the groups' loads on 16-byte boundaries in 0.76 times that again (430 to 325 ns, ahead of MemoryPack's copy of their memory). On AVX-512 VBMI CPUs that move them faster that way (AMD Zen 4 and 5, Intel Sapphire Rapids and later; Ice Lake keeps the lane groups), values over 16 bytes are written four or more at a time by one permute of two vectors: 0.65 times the time on Xeon Platinum 8573C (386 to 252 ns) and 0.76 on EPYC 9V45 (210 to 159 ns). The bytes are unchanged. See [Raw Memory for Unmanaged Data](/en/docs/v4/performance#raw-memory-for-unmanaged-data).
- **Large arrays of raw values**: between 32 KB and 1 MB, Nino copies with 32-byte vectors where they beat `memmove` on that vendor: 10,000 `Vector4`s serialize 9.5% faster on Intel Xeon Platinum 8370C (3.51 to 3.18 µs) and deserialize 4.5-7.7% faster on AMD EPYC 9V45 and 9V74 (96.6 to 92.2 µs, 111.0 to 102.4 µs).
- **Reading padded structs and tuples into new arrays**: a read of fixed-size values with padding now writes every byte of each value, padding as zero, so new arrays of them from 6 KB are allocated without being zeroed first, and values over 16 bytes are read eight at a time into whole vectors with their bools checked in the same pass (AVX-512): 1,000 `Waypoint`s deserialize in 0.77 to 0.85 times the time on GitHub's AMD EPYC 7763 and 9V74, Intel Xeon Platinum 8370C and Neoverse-N2 runners (EPYC 9V74: 1,203 to 922 ns), and a list of 1,000 `(int, long)` in 0.97 to 0.99. On x64 without AVX-512 the bools are checked in the same pass as the vector lane groups read the values: 1,000 `Waypoint`s deserialize in 0.92 times the time on GitHub's AMD EPYC 7763 (1,360 to 1,240 ns). In Untrusted mode, where such values are read a field at a time, arrays are zeroed as before. See [Raw Memory for Unmanaged Data](/en/docs/v4/performance#raw-memory-for-unmanaged-data).
- **Padded raw structs on Intel Ice Lake**: arrays of unmanaged structs with padding are masked with 32-byte vectors instead of 64-byte ones on Ice Lake, where the 64-byte ones were slower: 1,000 8-byte structs with a padding byte serialize in 83 ns instead of 116 on GitHub's Xeon Platinum 8370C (MemoryPack 88). Ice Lake is recognized by its CPU model, so every other Intel CPU keeps the 64-byte kernels, including Xeon Platinum 8573C, whose cloud VMs do not report AVX512-FP16.
- **Tuples and dictionaries on Intel Ice Lake**: on Ice Lake, lists and arrays of fixed-size values with padding whose blocks move whole 4-byte words (such as `(int, long)`, and the entries of a `Dictionary<int, int>`) are written from vector loads that start on a cache line, since a 64-byte load across two lines costs about twice as much there: 1,000 `(int, long)` serialize in 0.92 times the time on GitHub's Xeon Platinum 8370C (235 to 221 ns) and a `Dictionary<int, int>` of 1,000 entries in 0.81 (250 to 200 ns). Other CPUs are unchanged, and so are the bytes.
- **Raw blocks on Intel Ice Lake under Linux**: raw blocks of 2 to 32 KB (unpadded structs, `KeyValuePair<int, int>`, primitives) are copied with the C library's `rep movsb` on Ice Lake, whose split 64-byte loads made Nino's own vector copy slower there: 1,000 `KeyValuePair<int, int>` serialize in 0.85 times the time on GitHub's Xeon Platinum 8370C (151 to 128 ns) and a `Queue<int>` of 1,000 in 0.78 (94 to 74 ns). Other CPUs and operating systems are unchanged.
- **`HashSet` and `Dictionary` of unmanaged values**: the keys and values are moved out of the collection's own entries several at a time with SIMD shuffles instead of one entry at a time: a `HashSet<int>` of 1,000 serializes in 0.34-0.49 times the time on GitHub's AMD EPYC 7763, 9V45 and 9V74, Intel Xeon and Neoverse-N2 runners (327 to 141 ns on EPYC 7763, 372 to 126 ns on Neoverse-N2), a `Dictionary<int, int>` of 1,000 in 0.29-0.56 times (430 to 212 ns on EPYC 7763, 369 to 107 ns on Xeon Platinum 8573C), and classes that hold such collections faster accordingly (the polymorphic class array benchmark 0.69-0.84 times). The bytes are unchanged. See [Raw Memory for Unmanaged Data](/en/docs/v4/performance#raw-memory-for-unmanaged-data).
- **Untrusted mode**: the values that [`NinoSettings.Untrusted`](/en/docs/v4/security#untrusted-mode) checks in arrays and lists of raw structs (`bool`, `DateTime`, `decimal`, `DateOnly`, `TimeOnly`) are checked without a branch per value, and on .NET 8+ with SIMD: a list of 1,000 structs with a `DateTime` and a `bool` deserializes in 0.47-0.69 times the time on the same runners (5.55 to 2.76 µs on EPYC 7763, 6.13 to 2.86 µs on Neoverse-N2).
- **Strings in existing instances on Unity and .NET Framework**: the netstandard builds compare a Latin-1 or ASCII string with the one already in the instance eight bytes at a time instead of one char at a time, to keep it when the text is unchanged. No GitHub runner covers these platforms, so there are no numbers. See [Deserializing into Existing Instances](/en/docs/v4/pooling#deserializing-into-existing-instances).
- **32-bit .NET, .NET Framework and Mono**: on 32-bit .NET (x86, WebAssembly and Arm32) and 32-bit .NET Framework, values of 8 bytes or more (`long`, `double`, `Guid`, `decimal`, raw structs) are read and written with single unaligned loads and stores, and blocks of up to 64 bytes (most strings) are copied with the same overlapping moves as on 64-bit runtimes, instead of byte-by-byte copies and a `memmove` call; Mono and IL2CPP keep the byte copies on 32-bit Arm, where such loads can fault. On .NET Framework (and .NET Core 3.0 to 7), long Latin-1 strings are narrowed and widened with `Vector<T>` where the JIT accelerates it. Raw structs with padding are masked with `Vector<byte>` (SSE) on Mono with the System.Numerics.Vectors package, loaded and stored so that Mono compiles them to vector moves instead of `memcpy` calls; Unity, whose `Vector<T>` Mono never accelerates even where it reports itself accelerated, keeps the 8-byte path. Strings are never narrowed or widened with `Vector<T>` on Mono, where `Vector.Narrow` and `Vector.Widen` run in software. The bytes are unchanged; no GitHub runner covers these platforms, so there are no numbers. See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Unity kernels from shorter runs**: the Burst kernels are called through C# function pointers instead of delegates, and from 2 values instead of 16 for arrays and lists of tuples and structs and from 16 chars instead of 32 for Latin-1 strings, where they became faster in IL2CPP players; raw structs with padding still from 16, where their copy, made cheaper per call, now gains 1.06 to 1.09 times. Writing 2 to 12 small tuples into a buffer takes 1.2 to 3.4 times less time, strings of 16 to 31 chars are written 1.2 to 1.7 and read 1.2 to 1.6 times as fast (IL2CPP, Linux x64 GitHub runner, Unity 2022.3 and 6000.3). WebGL players with SIMD write and read 1000-char Latin-1 strings 2.1 to 6 times and write padded arrays of 1000 values 2.3 to 4.2 times as fast (headless Chrome). See [Burst-Accelerated Kernels](/en/docs/v4/advanced/unity#burst-kernels).
- **`[NinoUtf8]` strings in Unity**: with Burst, the ASCII text of `[NinoUtf8]` strings is narrowed and widened 16 chars at a time. Writing one into a buffer is 1.5 to 1.6 times as fast from 16 chars and 1.9 to 2.1 times at 1000; reading it 1.06 to 1.24 times from 16 chars and 1.2 to 1.25 times from 1000; ASCII text with a few accented letters gains 1.08 to 1.25 times, and CJK text is on par (IL2CPP, Linux x64 GitHub runners, Unity 2022.3 and 6000.3). WebGL players with SIMD write it 1.2 times as fast at 16 chars and 1.8 to 1.9 times at 1000, and read it 1.2 to 1.4 and 1.4 to 1.7 times as fast (headless Chrome). See [Burst-Accelerated Kernels](/en/docs/v4/advanced/unity#burst-kernels).
- **Unity on AVX2 CPUs**: x64 players read arrays of small tuples and structs (up to 16 bytes, 256 values or more) up to 3.5 times and write them up to 1.3 times as fast as with the SSSE3 kernels (IL2CPP, Burst AVX2 target). See [Burst-Accelerated Kernels](/en/docs/v4/advanced/unity#burst-kernels).
- **TypeScript in browsers**: with the WebAssembly text module, a text-heavy article reads 27-31% faster in Chromium on GitHub's x64 and Arm64 runners, and a list of mixed ASCII, Latin-1 and other strings writes about 12% faster on x64; Node is unchanged. See [Text in Browsers](/en/docs/v4/advanced/codegen#text-in-browsers).
- **TypeScript in Node**: strings of up to 48 chars are written without a regular expression or a native call: 1,000 ASCII strings serialize in 0.025-0.028 ms instead of 0.060-0.065 (GitHub's x64 and Arm64 runners), 1,000 mixed strings in 0.056-0.059 ms instead of 0.090, and the Lookup, OrderBook and Player cases take 0.39, 0.43 and 0.26 ms instead of 0.74-0.78, 0.76-0.79 and 0.31-0.34. Browsers are unchanged. See [TypeScript](/en/docs/v4/advanced/codegen#typescript).
- **TypeScript in Node, short CJK and Cyrillic text**: 1,000 strings of 4 to 16 such chars serialize in 69-73% less time (0.018 ms instead of 0.066 on x64, 0.034 instead of 0.108 on Arm64) and deserialize 46-47% faster; CJK strings of 24 to 40 chars read and write 5-7% faster (GitHub's runners). See [TypeScript](/en/docs/v4/advanced/codegen#typescript).
- **TypeScript string reads**: the TypeScript runtime reads strings 16-25% faster in Node and mixed text 13-18% faster in Chromium, writes them 3-15% faster, and generated code writes maps 8-12% faster in Node (GitHub's AMD EPYC 7763, 9V45 and 9V74 and Neoverse-N2 runners). See [TypeScript](/en/docs/v4/advanced/codegen#typescript).

### Fixes [#fixes-5]

- **NINO007 for type arguments without a formatter**: a member whose type closes a generic `[NinoType]` over a type Nino cannot write (`Box<Action>`, also inside `List<Box<Action>>`, `Box<Action>[]` or another generic) is now reported: such a member is written, but writing any value of it throws. A type parameter no member uses is not reported, and the bytes do not change. See [Diagnostics](/en/docs/v4/analyzers#diagnostics).
- **Untrusted data**: reading invalid data into an existing value (`Deserialize(data, ref value)`, or a member of a reused object) no longer leaves it holding a new array of uninitialized memory when the data was rejected after the array was allocated: raw `T?` arrays and lists, `bool` lists, collections of structs read as blocks with a `bool` such as `(int, bool)[]`, and values `NinoSettings.Untrusted` checks. What the read did not reach is left as it was or default. See [Invalid Data](/en/docs/v4/basic#invalid-data).
- **Untrusted data**: reading data Nino never writes throws `NinoDataException` in every mode: a `bool` or presence byte other than 0 or 1, a keyed member whose entry holds more bytes than its value, and a version-tolerant deferred section whose offset or entries do not match its region. Bool fields inside raw structs are still copied as they are, unless `NinoSettings.Untrusted` is set. See [What Is Rejected](/en/docs/v4/security#what-is-rejected).
- **Untrusted data**: arrays and lists of value tuples and `KeyValuePair`s with a `bool` item reject a bool byte other than 0 or 1 wherever it is, on every CPU; the vector read paths of .NET 8+ (AVX-512, AVX2, SSSE3, Arm64, WebAssembly) accepted some of them, depending on the instruction set and the position. See [What Is Rejected](/en/docs/v4/security#what-is-rejected).
- **Untrusted data**: data that nests a collection type holding itself (`class Tree : List<Tree>`) deeper than the depth limit throws `NinoDataException` instead of overflowing the stack, and the runtime-built formatter of such a type no longer overflows the stack while it is created. See [Invalid Data](/en/docs/v4/basic#invalid-data).
- **Untrusted data**: reading the same unknown type id again (corrupt, hostile or stale data) no longer searches every registry and loaded assembly each time; the id is found as soon as an assembly declaring it is loaded or registered. See [Subtypes in Other Assemblies](/en/docs/v4/polymorphism#subtypes-in-other-assemblies).
- **Untrusted data**: on .NET 8 and later, a `CultureInfo` read from the data can no longer grow the process's memory without bound (.NET keeps every culture it creates for the life of the process, and accepted any well-formed name): only cultures the runtime ships read back, aliases such as `zh-CN` included. Custom cultures and names with `-u-` or `-x-` extensions are now invalid data (`NinoDataException`), and in invariant globalization mode only the invariant culture reads back; .NET Framework, Mono and Unity are unchanged. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types).

See [Deep Object Graphs](/en/docs/v4/basic#deep-object-graphs).
- A value tuple of eight items or more can be the type argument of a generic `[NinoType]` that generated code never sees closed; Nino.Core threw "no formatter" for it. The bytes are those generated code writes for such a tuple. See [Serializable Types](/en/docs/v4/types#serializable-types).

- An assembly removed with `NinoRegistry.Remove` (or by its collectible `AssemblyLoadContext` unloading) is no longer registered again by a later read of an unknown type id, which kept it from unloading; an assembly loaded right after another one unloaded is found by reads by type id. See [Unloading Assemblies](/en/docs/v4/platforms#unloading-assemblies).
- With Nino.AspNetCore, a collectible `AssemblyLoadContext` whose types went through the MVC formatters can unload again. See [ASP.NET Core](/en/docs/v4/advanced/aspnetcore).
- With Nino.AspNetCore, only request bodies that are not valid Nino data (`NinoDataException`) are answered with 400 Bad Request; a failure on the server's side while reading one, such as a `[NinoFactory]` that returns null, propagates as the server error it is instead of being reported as the client's fault. See [ASP.NET Core](/en/docs/v4/advanced/aspnetcore#mvc).
- Under NativeAOT, generic unmanaged structs that are not `[NinoType]`s serialize as raw values, as with the JIT and in generated code, instead of failing for lack of a formatter.

See [Trimming and Native AOT](/en/docs/v4/platforms#trimming-and-native-aot).

See [SIMD on Every Platform](/en/docs/v4/simd#unity).

See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata).
- **TypeScript**: values nested deeper than 128 class bodies (linked lists, trees) are read and written byte for byte as .NET does, and deeply nested or forged data throws a `NinoError` instead of overflowing the stack; a `[NinoUtf8]` string whose bytes are not UTF-8 throws a `NinoError` instead of a `TypeError`. See [TypeScript](/en/docs/v4/advanced/codegen#typescript).
- **TypeScript**: the runtime rejects data .NET rejects: a repeated key or element in a map or set (of numbers, strings, `bigint`s, booleans or null), a keyed member whose value leaves bytes in its entry, and a malformed section of deferred bodies, each with a `NinoError`. See [Untrusted Data](/en/docs/v4/advanced/codegen#untrusted-data).

A map or set of more than 128 such keys now throws a `NinoError` when a key would find more than 100 keys in its bucket of V8's table, as .NET's [`MaxHashCollisions`](/en/docs/v4/security#hash-flooding) does. The guard is exact for V8 (Node, Chromium, Deno); Safari, Bun and Firefox hash numbers their own way. ### Performance [#performance-2]

- **Subtypes through generic bases**: values read or written through a generic base (`abstract class Box<T>`, `IRepository<T>`, a generic class) take the same generated dispatch as through a non-generic base, for the subtypes of each closed base declared in its assembly, whatever the type argument (a primitive, a tuple, a sealed or an open class), instead of a registry lookup and a virtual call for each value. See [Dispatch](/en/docs/v4/polymorphism#dispatch).
- **Small tuples on Arm64**: arrays and lists of small padded tuples read and write faster: 1,000 `(byte, int)` deserialize in 805 ns instead of 1,123 ns and serialize in 122 ns instead of 422 ns, 1,000 `(short, int)` in 801 ns instead of 1,103 ns and 124 ns instead of 200 ns, and the benchmark's `TupleList` case in 1,415 ns instead of 1,815 ns and 219 ns instead of 375 ns (GitHub's Arm64 runners). See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Collections written straight into their array**: `NinoSerializer.Serialize(value)` of an array or list of fixed-size elements (unmanaged values, `DateTimeOffset`s, tuples and raw structs) allocates an array of exactly its bytes and writes into it, without the pooled scratch buffer and the copy out of it. See [Allocation](/en/docs/v4/performance#allocation).
- **Tuples and pairs with padding faster without AVX-512**: arrays and lists of value tuples, `KeyValuePair`s and other padded raw values are written and read a group at a time, each 16-byte lane of a vector shuffled from at most two 16-byte windows (AVX2, SSSE3, Arm64 `TBL`, WebAssembly SIMD on .NET 10). A list of 1,000 `(int, long)` serializes in 194 ns instead of 380 ns on GitHub's x64 runners (EPYC 7763, AVX2). See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Padded tuples serialize at the same speed at every buffer alignment**: arrays and lists of tuples, `KeyValuePair`s and other padded structs are written by vectors aligned to the output, and the values before the first aligned vector and after the last were written one at a time, so the time depended on where the buffer started. Each end is now one more whole group of values, so the time no longer depends on it. See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **New arrays of tuples and `DateTimeOffset`s read faster on Intel CPUs**: on Intel x64 CPUs, arrays and lists that a read fills by vector shuffles or one value at a time are allocated zeroed, so each store no longer first reads its cache line from memory. Arrays filled by one block copy, and on Arm64 and AMD CPUs all arrays of 6 KB or more, stay uninitialized, which is as fast or faster there.
- **5-byte values without AVX-512**: arrays and lists of `(byte, int)` and other 5-byte values are moved several values at a time with AVX2 (six per 32-byte vector) and SSSE3 (twelve per four 16-byte vectors), instead of one at a time. See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Padded structs on Arm64**: arrays and lists of padded structs (tuples, `KeyValuePair`s) are copied 32 bytes a step with load and store pairs (`ldp`/`stp`), as the C library's `memcpy` does, instead of one 16-byte vector at a time.
- **`HashSet<T>` and `Dictionary<TKey, TValue>`** of raw values are written from their entries in one loop when no entry has been removed, without the enumerator's checks on every element. A new one that a read creates (default comparer) is filled by writing its entries and buckets directly, as `Add` would, without `Add`'s checks of the comparer, the free list and the capacity on every element; data that holds the same key twice still throws. A `HashSet<int>` of 1,000 serializes in 0.33 µs instead of 1.06 µs and deserializes in 2.6 µs instead of 6.1 µs on GitHub's x64 runners (EPYC 7763), and in 0.37 µs instead of 1.28 µs and 2.8 µs instead of 5.3 µs on the Arm64 runners (Neoverse-N2). The layouts and hashing of .NET (64-bit and 32-bit), .NET Framework, Mono and Unity are checked at startup against a filled collection through the public API; any other runtime keeps the enumerator and `Add` (the netstandard2.0 build, for .NET Framework, fills only dictionaries this way). See [Collection Types](/en/docs/v4/types#collection-types).
- **Copies without `memmove`**: block copies of 8 to 32 KB take Nino's vector loop instead of `memmove`, which is several times slower on some AMD EPYC CPUs. On x64 CPUs with AVX2 but without AVX-512 (AMD Zen 2 and 3, most Intel desktop CPUs) the loop of aligned 32-byte stores is used up to 1 MB, where it is faster than the C library's copy; beyond that, and on SSE-only and 32-bit CPUs from 16 KB, `memmove`.
- **New arrays on AMD CPUs**: a read that fills a new array of raw values by one block copy uses Nino's vector loop on AMD x64 CPUs from 6 KB too, where `memmove` (rep movsb) is slower than vector stores even into memory just allocated; Intel CPUs keep `memmove` there, which writes whole cache lines without reading them first. 1,000 `KeyValuePair<int, int>` deserialize in 418 ns instead of 465 ns on GitHub's EPYC 7763 runners.
- **Block copies on Arm64**: blocks of 65 bytes to 64 KB (arrays and lists of raw values, strings, byte arrays) are copied 64 bytes a step with load and store pairs (`ldp`/`stp`) from an aligned source address, instead of through `memmove`, which is slower at these sizes on GitHub's Arm64 runners (Neoverse-N2); padded structs align their loads the same way. See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Polymorphic arrays**: with the dispatch and collection changes above, an array of 100 polymorphic classes serializes in 34 µs instead of 46 µs and deserializes in 172 µs instead of 224 µs on GitHub's x64 runners (Xeon 6973P-C), and in 58 µs instead of 76 µs and 193 µs instead of 221 µs on the Arm64 runners (Neoverse-N2). See [Dispatch](/en/docs/v4/polymorphism#dispatch).
- **Faster copies of 33 to 128 bytes**: blocks of 33 to 64 bytes are copied inline as overlapping vectors on every 64-bit CPU, and 65 to 128 bytes as four 32-byte vectors with AVX2, instead of through `memmove`; arrays, lists and strings of raw values are read with the same copies below 6 KB (reads of 6 KB or more use `memmove`). See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Multi-dimensional arrays of fixed-size elements as blocks**: `T[,]`, `T[,,]` and `T[,,,]` of tuples, `DateTimeOffset`s and other fixed-size elements are written and read as blocks, as flat arrays are, instead of one value at a time. Lists and arrays no longer clear or copy over slots that the read overwrites.
- **Concurrent stacks and bags, and priority queues**: `ConcurrentStack<T>` and `ConcurrentBag<T>` of fixed-size elements are written as one block, and `PriorityQueue<TElement, TPriority>` reads and writes loop on a reader or writer held in registers.
- **Nullable members read with one bounds check**: `int?`, `long?`, `double?`, `DateTime?` and other nullable raw values read their presence byte and value under one bounds check instead of two.
- **Collections without a path of their own**: `Collection<T>`, `ObservableCollection<T>` and custom `ICollection<T>` types are written through a writer held in registers across the enumerator's calls, instead of storing and reloading it around every element.
- **Immutable dictionaries and sets read several times faster** (Nino.Immutable): `ImmutableDictionary<TKey, TValue>`, `ImmutableHashSet<T>`, `ImmutableSortedDictionary<TKey, TValue>` and `ImmutableSortedSet<T>` are built directly as their tree in one pass, instead of one builder `Add` (a walk down the tree and a rebalance) per item, or, for the sorted ones, a sort or a `SortedDictionary` in between. With 1,000 ints on GitHub's x64 runners (EPYC 7763), an `ImmutableDictionary` deserializes in 20.6 µs instead of 109.4 µs, an `ImmutableHashSet` in 19.7 µs instead of 92.1 µs, an `ImmutableSortedDictionary` in 13.3 µs instead of 55.6 µs and an `ImmutableSortedSet` in 13.2 µs instead of 18.5 µs; on the Arm64 runners (Neoverse-N2) in 21.3, 20.4, 14.6 and 13.8 µs instead of 81.7, 78.8, 62.5 and 19.1 µs. This holds on .NET, .NET Framework, Mono and Unity: the internal layout of System.Collections.Immutable is checked at startup, and the builder is used where it does not match, as well as for data the tree cannot take as it is (keys with equal hashes, out of order or null). See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Immutable dictionaries and sets written from their tree** (Nino.Immutable): the same four collections are copied out by walking their tree, instead of with their enumerator (which keeps a stack of nodes and checks it on every element), and written as an array: raw elements as one block. The bytes are the same as before. With 1,000 ints on GitHub's x64 runners (EPYC 7763), an `ImmutableDictionary` serializes in 3.1 µs instead of 14.7 µs, an `ImmutableHashSet` in 2.8 µs instead of 11.5 µs, an `ImmutableSortedDictionary` in 3.1 µs instead of 6.2 µs and an `ImmutableSortedSet` in 2.8 µs instead of 6.5 µs; on the Arm64 runners (Neoverse-N2) in 3.4, 3.1, 3.1 and 2.6 µs instead of 16.8, 13.4, 6.9 and 6.7 µs. See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **`LinkedList<T>` and `SortedDictionary<TKey, TValue>` read as their nodes**: a `LinkedList<T>` read into a new list links its nodes directly, without `AddLast`'s checks per item, and a `SortedDictionary<TKey, TValue>` whose data is in order builds its balanced red-black tree in one pass, instead of one `Add` (a walk down the tree and a rebalance) per item. With 1,000 ints, a `LinkedList` deserializes in 11.5 µs instead of 14.1 µs on GitHub's x64 runners (EPYC 7763) and in 12.3 µs instead of 14.5 µs on the Arm64 runners (Neoverse-N2), a `SortedDictionary` in 17.4 µs instead of 23.9 µs and in 16.7 µs instead of 27.1 µs. The layouts of .NET (64-bit and 32-bit), .NET Framework, Mono and Unity are checked at startup; any other runtime, and data out of order, keep the public API. See [Collection Types](/en/docs/v4/types#collection-types).
- **`SortedSet<T>` read as its tree**: a `SortedSet<T>` whose data is in order builds its red-black tree in one pass, as a `SortedDictionary<TKey, TValue>` does, instead of the constructor that copies the items, sorts the copy and drops duplicates. Other runtimes, and data out of order, keep the public API. See [Collection Types](/en/docs/v4/types#collection-types).
- **`KeyValuePair<TKey, TValue>` of raw keys and values** is written and read as one block, with one check per pair instead of one for the key and one for the value: dictionaries written pair by pair (`SortedDictionary<TKey, TValue>`, custom `IDictionary<TKey, TValue>` types) gain the most. The bytes are unchanged.
- **Keyed members and `Version`**: a keyed member's key and its region length are reserved together (with the raw members just before it), and a `Version` writes its four parts in one reservation and reads them under one bounds check. The bytes are unchanged. See [Keyed Members](/en/docs/v4/evolving-data#keyed-members).
- **`SortedSet<T>` and `SortedDictionary<TKey, TValue>` written from their tree**: copied out by an in-order walk of their nodes, instead of their own `CopyTo`, which keeps a stack of nodes and calls a delegate per node. The bytes are the same. With 1,000 ints, a `SortedSet` serializes in 2.8 µs instead of 5.5 µs on GitHub's x64 runners (EPYC 7763) and 2.8 µs instead of 5.0 µs on the Arm64 runners (Neoverse-N2), a `SortedDictionary` in 3.2 µs instead of 5.8 µs and 3.0 µs instead of 5.6 µs. A view of a set (`GetViewBetween`) and runtimes whose layout is not recognized keep `CopyTo`. See [Collection Types](/en/docs/v4/types#collection-types).
- **Empty collections**: an empty array, list, set, dictionary, priority queue or immutable collection no longer goes through the element loop (a call, and the reader or writer copied in and out); empty immutable sets and dictionaries are read as their shared `Empty` instance. Trees and other data with many empty leaf collections gain most.
- **`[NinoPooled]` types read before anything was returned to the pool**: a take from a pool that was never filled answers from one field read, without the thread-local access (and the call) that found the thread's stack empty. Programs that pool only some reads, and Unity and IL2CPP, where thread-local fields cost the most, gain most. The benchmark's pooled node deserializes in 156 ns instead of 205 ns on GitHub's x64 runners (EPYC 7763) and 145 ns instead of 193 ns on the Arm64 runners (Neoverse-N2). See [Built-in Pools](/en/docs/v4/pooling#ninopooled).
- **`ImmutableStack<T>`** (Nino.Immutable) serializes without a list to grow and reverse, allocating nothing: 1,000 ints in 2.7 µs instead of 4.5 µs on GitHub's Arm64 runners (Neoverse-N2) and 2.9 µs instead of 3.1 µs on the x64 runners (EPYC 7763). See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Version-tolerant types**: a run of raw members next to each other is read as one block under one check when the data has all of it (older data takes the member-by-member path): the benchmark's array of version-tolerant classes deserializes in 49.8 µs instead of 57.3 µs on GitHub's x64 runners (EPYC 7763). Keyed types reserve each member's key and region length together. See [Version Tolerance](/en/docs/v4/evolving-data#version-tolerance).
- **Unity's `AnimationCurve` and `Gradient`** (Nino.UnityTypes) reserve their bytes at once and read each run of keys under one bounds check, instead of one check per value. See [Unity Classes](/en/docs/v4/advanced/unity#unity-classes).
- **`Memory<T>` and `ReadOnlyMemory<T>`** of raw elements allocate their arrays as arrays are: from 6 KB without zeroing.
- **New arrays of 2 to 6 KB allocated zeroed**: an array a read fills by one block copy is allocated uninitialized only from 6 KB, where that is cheaper than zeroing it; below, the runtime's uninitialized allocation costs more than it saves. 1,000 ints deserialize into a `ReadOnlyCollection<T>` or `ReadOnlySequence<T>` in 257 and 264 ns instead of 348 ns on GitHub's x64 runners (EPYC 7763) and in 364 and 363 ns instead of 416 and 423 ns on the Arm64 runners (Neoverse-N2), and into a `Memory<T>` in 262 ns instead of 312 ns on x64.

### Fixes [#fixes-4]

- Generic abstract classes and generic interfaces with subtypes (`abstract class Box<T>`, `IRepository<T>`), and abstract classes nested in a generic type, no longer break the build: the generated formatter failed to compile in every format. Their subtypes are written and read as a non-generic base's are (see [Dispatch](/en/docs/v4/polymorphism#dispatch)), and data of a type that is not one of them throws ([#203](https://github.com/JasonXuDeveloper/Nino/pull/203)). See [Interfaces and Abstract Classes](/en/docs/v4/polymorphism#interfaces-and-abstract-classes).
- A class nested in a generic class (`Holder<long>.Base`) with subtypes in another assembly no longer overflows the stack the first time it is serialized. See [Subtypes in Other Assemblies](/en/docs/v4/polymorphism#subtypes-in-other-assemblies).
- When the generator cannot emit a type's formatter, the build fails with one error that names the type and the cause, instead of errors inside generated code.
- Serializing a span of unmanaged values past 4 GB, a `StringBuilder` past 1 G chars or UTF-8 text past 2 GB throws `OverflowException` instead of writing past the end of the buffer.
- Code fixes (implementing the `[NinoPooled]` hooks, adding or removing an attribute) keep the line breaks of the file they edit: on Windows they inserted CRLF lines into files with LF line breaks. See [Diagnostics](/en/docs/v4/analyzers#diagnostics).
- **Untrusted data**: data crafted against a reader can no longer crash the process: a struct that holds itself through a list, a nullable or an interface member, nested thousands deep, overflowed the stack; it now throws like any object nested more than 512 deep. See [Invalid Data](/en/docs/v4/basic#invalid-data).
- A failed read into an existing value (`Deserialize(data, ref value)`) of an array, list or `Memory<T>` of raw elements no longer leaves an array of uninitialized memory in it, and a `StringBuilder` length or a multi-dimensional array's dimensions are checked against the data before allocating (a 4-byte `StringBuilder` payload allocated 2 GB).
- Data that claims more elements than it holds can no longer make a read allocate hundreds of times its size (a 1 MB payload claiming large structs allocated 520 MB): a collection allocates ahead of its elements at most 16 times the bytes left in the input, and grows as elements are actually read. See [Invalid Data](/en/docs/v4/basic#invalid-data).
- Invalid `Version`, `Uri`, `CultureInfo`, `TimeZoneInfo` and `DateTimeOffset` values and null dictionary keys throw Nino's `InvalidOperationException` (the original exception as its `InnerException`) instead of the BCL's exceptions, so every invalid input is caught the same way and [Nino.AspNetCore](/en/docs/v4/advanced/aspnetcore) answers it with 400 instead of 500.

## 4.0.0-rc.6

### Wire Format [#wire-format-2]

- **Strings in one byte a char**: the default `string` encoding writes text whose chars are all at most U+00FF (ASCII, Latin-1) in one byte a char, behind a negative length header (`~length`); other text stays UTF-16, and `[NinoUtf8]` is unchanged. This covers every string in the default encoding: members, elements and keys of collections, and the text of `Uri`, `CultureInfo` and `TimeZoneInfo` values. This release still reads the UTF-16 strings earlier v4 releases wrote, but earlier releases cannot read the one-byte strings it writes, so upgrade the readers of your data before or together with its writers ([Upgrading from an Earlier Release Candidate](/en/docs/v4/migration#upgrading-from-an-earlier-release-candidate)). A `StringBuilder` keeps writing UTF-16 and reads both forms. See [Strings](/en/docs/v4/wire-format#strings) and [String Encoding](/en/docs/v4/defining-types#string-encoding).

### New [#new-4]

- **Nino.AspNetCore**: MVC input and output formatters (`AddNinoFormatters()`, `application/x-nino`, `?format=nino`) and Minimal API support (`NinoBody<T>` parameters, `NinoResults.Ok` and `NinoResults.Status`, `ReadFromNinoAsync` and `WriteAsNinoAsync`), reading and writing bodies straight from the request and response pipes, with no allocations of their own. See [ASP.NET Core](/en/docs/v4/advanced/aspnetcore).
- **Nino.TypeScript**: a build package that writes TypeScript classes, enums and codecs for the project's `[NinoType]`s after each build (`NinoTypeScriptOutput`, `NinoTypeScriptImportExtension`, `NinoTypeScriptNames`), with the `nino.ts` runtime, so browsers and Node read and write exactly the bytes Nino writes in .NET. Types it cannot express are left out with warning `NINOTS002`. See [TypeScript](/en/docs/v4/advanced/codegen#typescript).
- **Layout metadata by bytes**: `[assembly: NinoTypeLayout]` now describes each member by the bytes it is written as (`seq(string)`, `map(string,seq(raw(4)))`, `nullable(raw(4))`, `type(MyType)`...) instead of the formatter class, and keyed members carry their key (`:key=0x…`). Layouts recorded with an earlier release differ as text for every member that is not raw, though the bytes are unchanged apart from strings; record them again. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata).
- **`NinoSerializer.IsSupported(Type)`** tells whether Nino can serialize and deserialize a type, for integrations that only have a `Type`. See [The Boxed API](/en/docs/v4/basic#the-boxed-api).

### Performance [#performance-1]

- **Smaller payloads with Latin-1 strings**, with the same serialize and deserialize times as before: in the benchmark, `Orders` shrinks from 30,848 to 26,126 bytes, `Players` from 45,124 to 39,164 and `Tree` from 40,676 to 31,258, now smaller than MemoryPack's (27,990, 43,364 and 32,623). See [Benchmarks](/en/docs/v4/benchmarks).
- **Tuples and pairs with padding serialize faster**: arrays and lists of value tuples, `KeyValuePair`s and other raw values whose memory has padding are written as whole vectors of their bytes from an aligned destination, by one two-source permute a vector (AVX-512, of 4-byte words where each is a whole word of memory, otherwise of bytes with VBMI; AVX2; Arm64; WebAssembly on .NET 10): on an AVX-512 Xeon, 1,000 `(int, long)` serialize in 106 to 109 ns, against 228 ns in rc.5 and 136 to 141 ns for MemoryPack. See [SIMD on Every Platform](/en/docs/v4/simd#dotnet).
- **Tuples and pairs with padding read faster**: with AVX-512, padded raw values are read like they are written, each 64-byte vector of memory one two-source permute of the vectors of their bytes, stored at an aligned address: deserializing 1,000 `(int, long)` into an existing list or array takes 105 to 140 ns instead of 255 ns in rc.5, on par with MemoryPack (111 to 130 ns), which copies its 16-byte values as they are. Converting non-Latin-1 text also stores at aligned addresses: 1,000-char non-Latin-1 strings read about 8% faster (AVX-512 Xeon).
- **Mid-sized arrays read without zeroing**: arrays, lists and read-only collections of unmanaged values of 2 to 6 KB are now allocated uninitialized when read, as larger ones already were: a `ReadOnlyCollection<int>` of 1,000 deserializes in 450 to 510 ns instead of 570 to 590 ns (AVX-512 Xeon).
- **Faster TypeScript codecs**: generated code reads and writes runs of fixed-size members at offsets in one buffer, and `nino.ts` reads and writes text with Node's (Bun's, Deno's) native methods or `TextDecoder` and `TextEncoder` in browsers. In Node, 1,000 player records serialize in 1.15 ms instead of 2.07 ms and deserialize in 1.17 ms instead of 1.92 ms, text-heavy records 6.8 and 11 times faster, and arrays of numbers 2 to 5 times faster. Short text is read faster still: in Node, strings of up to 12 chars are sliced from one Latin-1 decode of up to 4 KB of the data, and text of up to 16 chars is read with one `String.fromCharCode` call, so lists of small records with short strings deserialize in 0.46 ms instead of 0.81 ms (0.42 ms instead of 0.65 ms in Chromium) and maps of short strings 1.5 times faster in Node. `serialize` no longer copies its result: it writes each result after the previous one in a shared 64 KB buffer and returns a view of it, which is never overwritten, and in Chromium arrays of numbers and structs serialize 1.3 to 1.5 times faster. See [API](/en/docs/v4/advanced/codegen#api) and [Compared with JSON](/en/docs/v4/advanced/codegen#performance).

### Fixes [#fixes-3]

- **Unity: libraries with an internal `ModuleInitializerAttribute`**, such as ZLinq's netstandard build, no longer break the build: the generator named that polyfill in its registry (error CS0122 "'ModuleInitializerAttribute' is inaccessible due to its protection level"). It now uses an initializer attribute only when the assembly can access it, and Unity registers through `[RuntimeInitializeOnLoadMethod]` as before. See [Unity](/en/docs/v4/advanced/unity).
- **TypeScript: `[NinoUtf8]` strings starting with U+FEFF** no longer fail to deserialize: `TextDecoder` dropped the char as a byte order mark. See [TypeScript](/en/docs/v4/advanced/codegen#typescript).

### Performance [#performance]

- **`Stack<T>`, `Queue<T>` and collections declared as interfaces** (`IList<T>`, `IEnumerable<T>`, `IReadOnlyCollection<T>`...) whose elements are unmanaged values or raw `[NinoType]` structs are written and read as one block, like a `List<T>` or an array of them. With 1,000 `int`s, they serialize 17× to 75× faster and deserialize 2.5× to 6× faster. A `Stack<T>` or `Queue<T>` of other elements is read and written through its backing array too. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **`DateTimeOffset`** is read and written through its two fields (their positions are checked once at startup, since .NET 10 stores them in another order than .NET 8, .NET Framework and Mono), and arrays and lists of it as one block. With 1,000 values, they serialize 2.9× faster and deserialize 2× faster. Invalid data still throws the constructor's exception. See [Primitive and Unmanaged Types](/en/docs/v4/types#primitive-and-unmanaged-types).
- **Arrays and lists of `[NinoType]` structs** keep the generated formatter after the struct has been serialized on its own; before, every element then went through a virtual call and raw structs lost their block copy. With 1,000 small structs (`int`, `short`, `bool`), they serialize 15× faster and deserialize 3.6× faster. Short strings and other blocks of up to 32 bytes are copied inline: a `List<KeyValuePair<int, string>>` serializes 1.3× faster. See [Collection Types](/en/docs/v4/types#collection-types).
- **Small classes in collections**: the body of a class with at most eight members, of which at most two need a formatter call (strings, collections, other types), is inlined into the collection's loop, also when the class is not sealed. Subtypes and nulls are handled as before. A list of such a non-sealed class serializes about 2× faster and deserializes about 1.3× faster. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **Blocks of 64 bytes to 8 KB** (arrays of unmanaged values and raw structs, strings) are written with 64-byte vectors on CPUs with AVX-512, up to 1.5× faster, and arrays of structs with padding with a 64-byte masked copy: 1,000 structs of `int`, `short` and `bool` serialize 1.6× faster. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **Structs with a string or another non-raw member** are passed to their generated body by reference instead of by value, so each element is no longer copied to the stack first. A list of 1,000 structs of four `long`s, a `string` and an `int` serializes 2× faster. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **Strings** are allocated directly by the runtime on .NET 8 and later and filled inline, without the checks and the copy call of `new string`: a string of 3 to 12 chars is read in 12 to 14 ns instead of 16 to 19, and types with many short strings deserialize 3% to 7% faster. Other runtimes read strings as before. See [Strings](/en/docs/v4/types#strings).
- **Classes and structs with nested members** keep the reader's and writer's position in registers without a stall: copying the reader or writer into a local and back now goes a field at a time, which the CPU forwards from its earlier stores instead of waiting for them. A list of player objects serializes 19% faster and deserializes 8% faster; lists of small classes, orders and trees gain 5% to 10%. The bytes are unchanged.
- **New `List<T>`s of unmanaged values or raw structs** of 6 KB or more get a backing array that is not cleared before the elements are copied into it, as arrays already did: a list of 10,000 `int`s deserializes about 15% faster. See [Collection Types](/en/docs/v4/types#collection-types).
- **`ImmutableArray<T>` and `ImmutableList<T>`** (`Nino.Immutable`) are written and read through arrays: an `ImmutableArray` is wrapped around the array it is read into without a copy, and an `ImmutableList` is built from one in a single pass. An `ImmutableArray<int>` of 1,000 serializes 13× faster and deserializes 8× faster, and an `ImmutableList<int>` of 1,000 deserializes 3.6× faster. The bytes are unchanged. See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Value tuples and `KeyValuePair`s of unmanaged values**, such as `(int, long)`: a tuple is written with one capacity check, and arrays and lists of them, such as `(int, int)[]` or `List<(int, long)>`, are written and read as one block: copied as memory when a value's memory matches its bytes, otherwise rearranged 16 or 64 bytes at a time with SIMD byte shuffles (SSSE3, Arm64, AVX-512 VBMI). 1,000 `(int, int)` or `KeyValuePair<int, int>` serialize 16× to 19× faster and deserialize 2.5× to 3× faster. A `List<(int, long)>` of 1,000 first became 1.25× faster to serialize and 2.3× faster to deserialize (one capacity check per tuple, and element loops that keep the reader's position in registers), then 5.4× and 2× faster again as one block. The bytes are unchanged. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types).
- **`SortedSet<T>`, `SortedDictionary<TKey, TValue>`, `SortedList<TKey, TValue>`, `LinkedList<T>` and `ConcurrentDictionary<TKey, TValue>`**, and types derived from them, are read and written through their own fields and methods instead of the general collection loop: a sorted set or dictionary is read as an array from which its balanced tree is built in one pass, a sorted list straight into its key and value arrays when the keys come in order, and a `ConcurrentDictionary` that Nino creates (no existing instance, and not a derived type) is built by its constructor from the pairs read, which sizes its table once and adds them without its locks. With 1,000 `int`s or `int` pairs, a `ConcurrentDictionary` deserializes in 15 µs instead of 1.88 ms (28× faster through direct calls, then about 4× faster again through the constructor) and serializes 1.3× faster; a `SortedDictionary` deserializes 1.8× and then 1.5× faster again and serializes 1.9× faster; a `SortedList` deserializes 5.5× faster and serializes 1.4× faster; a `SortedSet` serializes and deserializes 2× faster. The bytes are unchanged, and a repeated or null key still throws the same exception. See [Collection Types](/en/docs/v4/types#collection-types).
- **`ConcurrentStack<T>`**: a new one is filled with a single `PushRange` instead of a push per element, about 1.9× faster (1,000 `int`s in 9.3 µs instead of 17.9), and a new `ConcurrentQueue<T>` is built by its constructor, which sizes its first segment for the elements. An existing instance or a derived type is filled as before. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **SIMD on more CPUs**: on x64 CPUs without AVX-512 (AVX2, most desktops), blocks of 256 bytes to 4 KB are copied with 32-byte vectors: 256 bytes in 3.9 ns instead of 6.3, 2,500 bytes in 24.6 ns instead of 36.3. On Arm64, arrays and lists of value tuples, `KeyValuePair`s and raw structs of up to 8 bytes are rearranged 64 bytes at a time by table lookups, as AVX-512 VBMI does on x64, and on .NET 10 the 16-byte shuffle also runs with WebAssembly SIMD. The bytes are unchanged.

## 4.0.0-rc.3

### Wire Format [#wire-format-1]

Only the type described below writes different bytes than with rc.2.

- **A `[NinoType]` struct with `[StructLayout(LayoutKind.Explicit)]` from another assembly** is now written member by member in every build, as it already was when the IDE or a project reference saw it as source. From a package or a command-line build, rc.2 copied it as raw memory ([#202](https://github.com/JasonXuDeveloper/Nino/issues/202)).

### New [#new-1]

- **Raw bytes in the layout metadata**: `[assembly: NinoTypeLayout]` now shows the size and field offsets of every value copied as raw memory, including structs that are not `[NinoType]`s, so changing a field, `Pack`, `Size` or `[FieldOffset]` changes the layout. Raw members read `raw(n){name:type@offset:encoding,...}` instead of `raw(n)` or `raw`, and a raw struct's members are its raw layout. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata) ([#202](https://github.com/JasonXuDeveloper/Nino/issues/202)).
- **`NinoSerializer.Serialize<T>(in T value)`** takes the value by reference, as MemoryPack does, so serializing a struct copied as raw memory, read from a field, is an allocation and one copy straight into the array; rc.2 first copied it to the stack. Existing calls compile unchanged; a method group converted to `Func<T, byte[]>` needs a lambda. See [Serializing](/en/docs/v4/basic#serializing).

### Fixes [#fixes-1]

- **`[StructLayout]` and `[FieldOffset]` of structs from another assembly are read.** Roslyn does not show them as attributes on types from a package, so the generator took every such struct as sequential. A struct with explicit field offsets could then be copied as raw memory, whose size differs between 64-bit and 32-bit runtimes ([#202](https://github.com/JasonXuDeveloper/Nino/issues/202)).

## 4.0.0-rc.2

### Wire Format [#wire-format]

Only the types described below write different bytes than with rc.1.

- **A `[NinoType]` struct from another assembly whose members are auto-properties** (a positional `record struct`, for example) is now copied as raw memory in every build. rc.1 did so when the IDE or a project reference saw the struct as source, but not when it came from a package or a command-line build, which wrote it member by member. A struct, array or list that contains such a struct can therefore write different bytes than an rc.1 package or command-line build: where the struct has padding, the raw copy includes it, zeroed ([#200](https://github.com/JasonXuDeveloper/Nino/issues/200)).
- **`nint` and `nuint` members are serialized on netstandard** (Unity included). rc.1 skipped them there with NINO007; they are now written as 8 bytes, as on .NET 7 and later.

### New [#new]

- **Layout metadata**: the generator records how each `[NinoType]` is written as an `[assembly: NinoTypeLayout]`, so tools can compare layouts between builds. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata) ([#197](https://github.com/JasonXuDeveloper/Nino/issues/197)).
- **Unloading assemblies**: `NinoRegistry.Remove(assembly)` clears everything Nino cached for an assembly, so a collectible `AssemblyLoadContext` can unload it. On .NET 8 and later this happens on its own when the context unloads. See [Unloading Assemblies](/en/docs/v4/platforms#unloading-assemblies) ([#199](https://github.com/JasonXuDeveloper/Nino/issues/199)).
- **Your own buffer pool**: `new NinoArrayBufferWriter(initialCapacity, pool)` rents its arrays from the `ArrayPool<byte>` you pass in. See [Reusing a Buffer](/en/docs/v4/basic#reusing-a-buffer) ([#198](https://github.com/JasonXuDeveloper/Nino/issues/198)).

### Fixes [#fixes]

- **Two `[NinoFormerName]` on one type are reported** as error NINO026. The generator took the first one, and `NinoTypeId.Of` threw `AmbiguousMatchException`. See [Diagnostics](/en/docs/v4/analyzers) ([#201](https://github.com/JasonXuDeveloper/Nino/issues/201)).
