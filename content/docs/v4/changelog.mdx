What changed from one v4 release to the next, newest first. For everything v4 changed since v3, see [What's New in v4](/en/docs/v4/whats-new). Each GitHub release also lists every commit it contains.

## 4.0.0-rc.7

### Performance [#performance-2]

- **Collections written straight into their array**: `NinoSerializer.Serialize(value)` of an array or list of fixed-size elements (unmanaged values, `DateTimeOffset`s, tuples and raw structs) allocates an array of exactly its bytes and writes into it, without the pooled scratch buffer and the copy out of it: 1,000 `(int, long)` in about 1.7 µs instead of 1.85 µs on an AVX-512 Xeon, and 1.9 µs instead of 2.6 µs on CPUs without AVX2. See [Allocation](/en/docs/v4/performance#allocation).
- **Tuples and pairs with padding faster without AVX-512**: arrays and lists of value tuples, `KeyValuePair`s and other padded raw values are written and read a group at a time, each 16-byte lane of a vector shuffled from at most two 16-byte windows (AVX2, SSSE3, Arm64 `TBL`, WebAssembly SIMD on .NET 10). On a Xeon with AVX-512 turned off, 1,000 `(int, long)` deserialize into an existing list in 460 to 550 ns instead of 850 ns and serialize in 310 to 360 ns instead of 330 to 370 ns; with SSSE3 only they serialize in 415 to 500 ns instead of 790 to 890 ns. See [SIMD by Platform](/en/docs/v4/platforms#simd).
- **New arrays of tuples and `DateTimeOffset`s read faster**: arrays and lists that a read fills by vector shuffles or one value at a time are allocated zeroed again, so each store no longer first reads its cache line from memory; only arrays filled by one block copy stay uninitialized. With workstation GC on an AVX-512 Xeon, 1,000 `(int, long)` deserialize into a new list in 1.5 to 1.7 µs instead of 2.7 to 2.9 µs, and a `DateTimeOffset[1000]` in 3.7 to 3.8 µs instead of 5.0 to 5.6 µs.
- **Faster copies of 33 to 128 bytes**: blocks of 33 to 64 bytes are copied inline as overlapping vectors on every 64-bit CPU, and 65 to 128 bytes as four 32-byte vectors with AVX2, instead of through `memmove`; arrays, lists and strings of raw values are read with the same copies below 2 KB (reads of 2 KB or more keep `memmove`). See [SIMD by Platform](/en/docs/v4/platforms#simd).
- **Multi-dimensional arrays of fixed-size elements as blocks**: `T[,]`, `T[,,]` and `T[,,,]` of tuples, `DateTimeOffset`s and other fixed-size elements are written and read as flat arrays are: a `(int, long)[50, 20]` deserializes into an existing array in 140 ns instead of 1.3 µs and serializes in 1.5 to 1.7 µs instead of 3 µs, and a `DateTimeOffset[50, 20]` serializes in 1.7 µs instead of 2.5 µs. Lists and arrays no longer clear or copy over slots that the read overwrites.
- **Concurrent stacks and bags, and priority queues**: `ConcurrentStack<T>` and `ConcurrentBag<T>` of fixed-size elements are written as one block (1,000 ints in 4.4 to 4.5 µs instead of 5.4 to 5.7 µs), a `PriorityQueue<int, int>` of 1,000 deserializes in 3.5 µs instead of 4.7 µs.
- **Nullable members read with one bounds check**: `int?`, `long?`, `double?`, `DateTime?` and other nullable raw values read their has-value byte and value together: an array of 100 structs with four such members deserializes in 590 to 615 ns instead of 1,050 to 1,100 ns.
- **Collections without a path of their own**: `Collection<T>`, `ObservableCollection<T>` and custom `ICollection<T>` types are written through a writer held in registers across the enumerator's calls: an `ObservableCollection<int>` of 1,000 serializes in 2.7 to 2.9 µs instead of 4.3 to 5.1 µs.
- **`ImmutableStack<T>`** (Nino.Immutable) serializes without a list to grow and reverse: about twice as fast (1,000 ints in 4.3 to 4.8 µs instead of 8.2 to 9.5 µs), allocating nothing. See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Version-tolerant types**: a run of raw members next to each other is read as one block under one check when the data has all of it (older data takes the member-by-member path): about 20% faster for 100 objects with six adjacent raw members. Keyed types reserve each member's key and region length together (about 3% faster to serialize). See [Version Tolerance](/en/docs/v4/evolving-data#version-tolerance).
- **Unity's `AnimationCurve` and `Gradient`** (Nino.UnityTypes) are written and read as whole blocks: an `AnimationCurve` of 8 keys serializes about 3.5× faster (about 490 ns down to 140 ns) and deserializes about 1.3× faster; a `Gradient` is about 8% faster both ways. See [Unity Classes](/en/docs/v4/advanced/unity#unity-classes).
- **`Memory<T>` and `ReadOnlyMemory<T>`** of raw elements deserialize 5 to 10% faster, their arrays allocated without zeroing as arrays are.

### Fixes [#fixes-4]

- Serializing a span of unmanaged values past 4 GB, a `StringBuilder` past 1 G chars or UTF-8 text past 2 GB throws `OverflowException` instead of writing past the end of the buffer.

## 4.0.0-rc.6

### Wire Format [#wire-format-2]

- **Strings in one byte a char**: the default `string` encoding writes text whose chars are all at most U+00FF (ASCII, Latin-1) in one byte a char, behind a negative length header (`~length`); other text stays UTF-16, and `[NinoUtf8]` is unchanged. This covers every string in the default encoding: members, elements and keys of collections, and the text of `Uri`, `CultureInfo` and `TimeZoneInfo` values. This release still reads the UTF-16 strings earlier v4 releases wrote, but earlier releases cannot read the one-byte strings it writes, so upgrade the readers of your data before or together with its writers ([Upgrading from an Earlier Release Candidate](/en/docs/v4/migration#upgrading-from-an-earlier-release-candidate)). A `StringBuilder` keeps writing UTF-16 and reads both forms. See [Binary Format](/en/docs/v4/platforms#binary-format) and [String Encoding](/en/docs/v4/defining-types#string-encoding).

### New [#new-4]

- **Nino.AspNetCore**: MVC input and output formatters (`AddNinoFormatters()`, `application/x-nino`, `?format=nino`) and Minimal API support (`NinoBody<T>` parameters, `NinoResults.Ok` and `NinoResults.Status`, `ReadFromNinoAsync` and `WriteAsNinoAsync`), reading and writing bodies straight from the request and response pipes, with no allocations of their own. See [ASP.NET Core](/en/docs/v4/advanced/aspnetcore).
- **Nino.TypeScript**: a build package that writes TypeScript classes, enums and codecs for the project's `[NinoType]`s after each build (`NinoTypeScriptOutput`, `NinoTypeScriptImportExtension`, `NinoTypeScriptNames`), with the `nino.ts` runtime, so browsers and Node read and write exactly the bytes Nino writes in .NET. Types it cannot express are left out with warning `NINOTS002`. See [TypeScript Clients](/en/docs/v4/advanced/typescript).
- **Layout metadata by bytes**: `[assembly: NinoTypeLayout]` now describes each member by the bytes it is written as (`seq(string)`, `map(string,seq(raw(4)))`, `nullable(raw(4))`, `type(MyType)`...) instead of the formatter class, and keyed members carry their key (`:key=0x…`). Layouts recorded with an earlier release differ as text for every member that is not raw, though the bytes are unchanged apart from strings; record them again. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata).
- **`NinoSerializer.IsSupported(Type)`** tells whether Nino can serialize and deserialize a type, for integrations that only have a `Type`. See [The Boxed API](/en/docs/v4/basic#the-boxed-api).

### Performance [#performance-1]

- **Smaller payloads with Latin-1 strings**, with the same serialize and deserialize times as before: in the benchmark, `Orders` shrinks from 30,848 to 26,126 bytes, `Players` from 45,124 to 39,164 and `Tree` from 40,676 to 31,258, now smaller than MemoryPack's (27,990, 43,364 and 32,623). See [Benchmarks](/en/docs/v4/perf).
- **Tuples and pairs with padding serialize faster**: arrays and lists of value tuples, `KeyValuePair`s and other raw values whose memory has padding are written as whole vectors of their bytes from an aligned destination, by one two-source permute a vector (AVX-512, of 4-byte words where each is a whole word of memory, otherwise of bytes with VBMI; AVX2; Arm64; WebAssembly on .NET 10): on an AVX-512 Xeon, 1,000 `(int, long)` serialize in 106 to 109 ns, against 228 ns in rc.5 and 136 to 141 ns for MemoryPack. See [SIMD by Platform](/en/docs/v4/platforms#simd).
- **Tuples and pairs with padding read faster**: with AVX-512, padded raw values are read like they are written, each 64-byte vector of memory one two-source permute of the vectors of their bytes, stored at an aligned address: deserializing 1,000 `(int, long)` into an existing list or array takes 105 to 140 ns instead of 255 ns in rc.5, on par with MemoryPack (111 to 130 ns), which copies its 16-byte values as they are. Converting non-Latin-1 text also stores at aligned addresses: 1,000-char non-Latin-1 strings read about 8% faster (AVX-512 Xeon).
- **Mid-sized arrays read without zeroing**: arrays, lists and read-only collections of unmanaged values of 2 to 6 KB are now allocated uninitialized when read, as larger ones already were: a `ReadOnlyCollection<int>` of 1,000 deserializes in 450 to 510 ns instead of 570 to 590 ns (AVX-512 Xeon).
- **Faster TypeScript codecs**: generated code reads and writes runs of fixed-size members at offsets in one buffer, and `nino.ts` reads and writes text with Node's (Bun's, Deno's) native methods or `TextDecoder` and `TextEncoder` in browsers. In Node, 1,000 player records serialize in 1.15 ms instead of 2.07 ms and deserialize in 1.17 ms instead of 1.92 ms, text-heavy records 6.8 and 11 times faster, and arrays of numbers 2 to 5 times faster. Short text is read faster still: in Node, strings of up to 12 chars are sliced from one Latin-1 decode of up to 4 KB of the data, and text of up to 16 chars is read with one `String.fromCharCode` call, so lists of small records with short strings deserialize in 0.46 ms instead of 0.81 ms (0.42 ms instead of 0.65 ms in Chromium) and maps of short strings 1.5 times faster in Node. `serialize` no longer copies its result: it writes each result after the previous one in a shared 64 KB buffer and returns a view of it, which is never overwritten, and in Chromium arrays of numbers and structs serialize 1.3 to 1.5 times faster. See [API](/en/docs/v4/advanced/typescript#api) and [Compared with JSON](/en/docs/v4/advanced/typescript#compared-with-json).

### Fixes [#fixes-3]

- **Unity: libraries with an internal `ModuleInitializerAttribute`**, such as ZLinq's netstandard build, no longer break the build: the generator named that polyfill in its registry (error CS0122 "'ModuleInitializerAttribute' is inaccessible due to its protection level"). It now uses an initializer attribute only when the assembly can access it, and Unity registers through `[RuntimeInitializeOnLoadMethod]` as before. See [Unity](/en/docs/v4/advanced/unity).
- **TypeScript: `[NinoUtf8]` strings starting with U+FEFF** no longer fail to deserialize: `TextDecoder` dropped the char as a byte order mark. See [TypeScript Clients](/en/docs/v4/advanced/typescript).

## 4.0.0-rc.5

### New [#new-3]

- **More built-in types**: `BigInteger`, `Uri`, `Version`, `StringBuilder`, `BitArray`, `CultureInfo`, `TimeZoneInfo`, `Lazy<T>`, `Memory<T>`, `ReadOnlyMemory<T>`, `ReadOnlySequence<T>`, `ReadOnlyCollection<T>`, `ReadOnlyObservableCollection<T>`, `ILookup<TKey, TElement>`, `IGrouping<TKey, TElement>` and `BlockingCollection<T>` need no custom formatter any more. Where Nino already had a type of the same shape, the bytes are its bytes: `Memory<T>` and `ReadOnlySequence<T>` are written as a `T[]`, a `ReadOnlyCollection<T>` as a `List<T>`, a `StringBuilder` as a `string`. `System.Type` stays unsupported on purpose. See [Supported Types](/en/docs/v4/types#other-built-in-types).
- **Every immutable collection** in `Nino.Immutable`: `ImmutableHashSet<T>`, `ImmutableSortedSet<T>`, `ImmutableQueue<T>`, `ImmutableStack<T>`, `ImmutableDictionary<TKey, TValue>` and `ImmutableSortedDictionary<TKey, TValue>` join `ImmutableArray<T>` and `ImmutableList<T>`, each with the bytes of its mutable counterpart. See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Unity's `AnimationCurve`, `Gradient` and `RectOffset`**: the Unity package ships `Nino.UnityTypes.dll` with formatters for them, so they work as members, elements and top-level values, `null` and `ref` reuse included. See [Unity Classes](/en/docs/v4/advanced/unity#unity-classes).

### Performance [#performance]

- **`Stack<T>`, `Queue<T>` and collections declared as interfaces** (`IList<T>`, `IEnumerable<T>`, `IReadOnlyCollection<T>`...) whose elements are unmanaged values or raw `[NinoType]` structs are written and read as one block, like a `List<T>` or an array of them. With 1,000 `int`s, they serialize 17× to 75× faster and deserialize 2.5× to 6× faster. A `Stack<T>` or `Queue<T>` of other elements is read and written through its backing array too. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **`DateTimeOffset`** is read and written through its two fields (their positions are checked once at startup, since .NET 10 stores them in another order than .NET 8, .NET Framework and Mono), and arrays and lists of it as one block. With 1,000 values, they serialize 2.9× faster and deserialize 2× faster. Invalid data still throws the constructor's exception. See [Primitive and Unmanaged Types](/en/docs/v4/types#primitive-and-unmanaged-types).
- **Arrays and lists of `[NinoType]` structs** keep the generated formatter after the struct has been serialized on its own; before, every element then went through a virtual call and raw structs lost their block copy. With 1,000 small structs (`int`, `short`, `bool`), they serialize 15× faster and deserialize 3.6× faster. Short strings and other blocks of up to 32 bytes are copied inline: a `List<KeyValuePair<int, string>>` serializes 1.3× faster. See [Collection Types](/en/docs/v4/types#collection-types).
- **Small classes in collections**: the body of a class with at most eight members, of which at most two need a formatter call (strings, collections, other types), is inlined into the collection's loop, also when the class is not sealed. Subtypes and nulls are handled as before. A list of such a non-sealed class serializes about 2× faster and deserializes about 1.3× faster. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **Blocks of 64 bytes to 8 KB** (arrays of unmanaged values and raw structs, strings) are written with 64-byte vectors on CPUs with AVX-512, up to 1.5× faster, and arrays of structs with padding with a 64-byte masked copy: 1,000 structs of `int`, `short` and `bool` serialize 1.6× faster. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **Structs with a string or another non-raw member** are passed to their generated body by reference instead of by value, so each element is no longer copied to the stack first. A list of 1,000 structs of four `long`s, a `string` and an `int` serializes 2× faster. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **Strings** are allocated directly by the runtime on .NET 8 and later and filled inline, without the checks and the copy call of `new string`: a string of 3 to 12 chars is read in 12 to 14 ns instead of 16 to 19, and types with many short strings deserialize 3% to 7% faster. Other runtimes read strings as before. See [Strings](/en/docs/v4/types#strings).
- **Classes and structs with nested members** keep the reader's and writer's position in registers without a stall: copying the reader or writer into a local and back now goes a field at a time, which the CPU forwards from its earlier stores instead of waiting for them. A list of player objects serializes 19% faster and deserializes 8% faster; lists of small classes, orders and trees gain 5% to 10%. The bytes are unchanged.
- **New `List<T>`s of unmanaged values or raw structs** of 6 KB or more get a backing array that is not cleared before the elements are copied into it, as arrays already did: a list of 10,000 `int`s deserializes about 15% faster. See [Collection Types](/en/docs/v4/types#collection-types).
- **`ImmutableArray<T>` and `ImmutableList<T>`** (`Nino.Immutable`) are written and read through arrays: an `ImmutableArray` is wrapped around the array it is read into without a copy, and an `ImmutableList` is built from one in a single pass. An `ImmutableArray<int>` of 1,000 serializes 13× faster and deserializes 8× faster, and an `ImmutableList<int>` of 1,000 deserializes 3.6× faster. The bytes are unchanged. See [Immutable Collections](/en/docs/v4/types#immutable-collections).
- **Value tuples and `KeyValuePair`s of unmanaged values**, such as `(int, long)`: a tuple is written with one capacity check, and arrays and lists of them, such as `(int, int)[]` or `List<(int, long)>`, are written and read as one block: copied as memory when a value's memory matches its bytes, otherwise rearranged 16 or 64 bytes at a time with SIMD byte shuffles (SSSE3, Arm64, AVX-512 VBMI). 1,000 `(int, int)` or `KeyValuePair<int, int>` serialize 16× to 19× faster and deserialize 2.5× to 3× faster. A `List<(int, long)>` of 1,000 first became 1.25× faster to serialize and 2.3× faster to deserialize (one capacity check per tuple, and element loops that keep the reader's position in registers), then 5.4× and 2× faster again as one block. The bytes are unchanged. See [Other Built-in Types](/en/docs/v4/types#other-built-in-types).
- **`SortedSet<T>`, `SortedDictionary<TKey, TValue>`, `SortedList<TKey, TValue>`, `LinkedList<T>` and `ConcurrentDictionary<TKey, TValue>`**, and types derived from them, are read and written through their own fields and methods instead of the general collection loop: a sorted set or dictionary is read as an array from which its balanced tree is built in one pass, a sorted list straight into its key and value arrays when the keys come in order, and a `ConcurrentDictionary` that Nino creates (no existing instance, and not a derived type) is built by its constructor from the pairs read, which sizes its table once and adds them without its locks. With 1,000 `int`s or `int` pairs, a `ConcurrentDictionary` deserializes in 15 µs instead of 1.88 ms (28× faster through direct calls, then about 4× faster again through the constructor) and serializes 1.3× faster; a `SortedDictionary` deserializes 1.8× and then 1.5× faster again and serializes 1.9× faster; a `SortedList` deserializes 5.5× faster and serializes 1.4× faster; a `SortedSet` serializes and deserializes 2× faster. The bytes are unchanged, and a repeated or null key still throws the same exception. See [Collection Types](/en/docs/v4/types#collection-types).
- **`ConcurrentStack<T>`**: a new one is filled with a single `PushRange` instead of a push per element, about 1.9× faster (1,000 `int`s in 9.3 µs instead of 17.9), and a new `ConcurrentQueue<T>` is built by its constructor, which sizes its first segment for the elements. An existing instance or a derived type is filled as before. The bytes are unchanged. See [Collection Types](/en/docs/v4/types#collection-types).
- **SIMD on more CPUs**: on x64 CPUs without AVX-512 (AVX2, most desktops), blocks of 256 bytes to 4 KB are copied with 32-byte vectors: 256 bytes in 3.9 ns instead of 6.3, 2,500 bytes in 24.6 ns instead of 36.3. On Arm64, arrays and lists of value tuples, `KeyValuePair`s and raw structs of up to 8 bytes are rearranged 64 bytes at a time by table lookups, as AVX-512 VBMI does on x64, and on .NET 10 the 16-byte shuffle also runs with WebAssembly SIMD. The bytes are unchanged.

### Fixes [#fixes-2]

- **`List<T>` on .NET Framework and Mono**: the netstandard build of Nino.Core read and wrote a `List<T>`'s fields where .NET keeps them, but the `List<T>` of .NET Framework and Mono has one more field, so lists were written empty and a list read into was left broken. Each collection whose fields Nino uses (`List<T>`, `Stack<T>`, `Queue<T>`, `SortedList<TKey, TValue>`, `SortedSet<T>`, `SortedDictionary<TKey, TValue>`) now has its layout checked once at startup against an instance with known contents, and is read and written through its public methods on a runtime whose layout does not match. The fast paths now work on .NET Framework and Mono too. See [Collection Types](/en/docs/v4/types#collection-types).

## 4.0.0-rc.4

### New [#new-2]

- **Every `NinoSerializer.Serialize` overload takes `in T`**: `Serialize<T>(in T value, IBufferWriter<byte>)` and `Serialize<T>(in T value, ref Writer)` now take the value by reference, as `Serialize<T>(in T value)` does since rc.3, and so do `Writer.Write<T>(in T)` and `Writer.WriteValue<T>(in T)` (see [Writer and Reader](/en/docs/v4/custom-formatters#writer-and-reader)). A struct read from a field is written straight into the buffer; rc.3 first copied it to the stack. Existing calls compile unchanged. See [Serializing](/en/docs/v4/basic#serializing).

## 4.0.0-rc.3

### Wire Format [#wire-format-1]

Only the type described below writes different bytes than with rc.2.

- **A `[NinoType]` struct with `[StructLayout(LayoutKind.Explicit)]` from another assembly** is now written member by member in every build, as it already was when the IDE or a project reference saw it as source. From a package or a command-line build, rc.2 copied it as raw memory ([#202](https://github.com/JasonXuDeveloper/Nino/issues/202)).

### New [#new-1]

- **Raw bytes in the layout metadata**: `[assembly: NinoTypeLayout]` now shows the size and field offsets of every value copied as raw memory, including structs that are not `[NinoType]`s, so changing a field, `Pack`, `Size` or `[FieldOffset]` changes the layout. Raw members read `raw(n){name:type@offset:encoding,...}` instead of `raw(n)` or `raw`, and a raw struct's members are its raw layout. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata) ([#202](https://github.com/JasonXuDeveloper/Nino/issues/202)).
- **`NinoSerializer.Serialize<T>(in T value)`** takes the value by reference, as MemoryPack does, so serializing a struct copied as raw memory, read from a field, is an allocation and one copy straight into the array; rc.2 first copied it to the stack. Existing calls compile unchanged; a method group converted to `Func<T, byte[]>` needs a lambda. See [Serializing](/en/docs/v4/basic#serializing).

### Fixes [#fixes-1]

- **`[StructLayout]` and `[FieldOffset]` of structs from another assembly are read.** Roslyn does not show them as attributes on types from a package, so the generator took every such struct as sequential. A struct with explicit field offsets could then be copied as raw memory, whose size differs between 64-bit and 32-bit runtimes ([#202](https://github.com/JasonXuDeveloper/Nino/issues/202)).

## 4.0.0-rc.2

### Wire Format [#wire-format]

Only the types described below write different bytes than with rc.1.

- **A `[NinoType]` struct from another assembly whose members are auto-properties** (a positional `record struct`, for example) is now copied as raw memory in every build. rc.1 did so when the IDE or a project reference saw the struct as source, but not when it came from a package or a command-line build, which wrote it member by member. A struct, array or list that contains such a struct can therefore write different bytes than an rc.1 package or command-line build: where the struct has padding, the raw copy includes it, zeroed ([#200](https://github.com/JasonXuDeveloper/Nino/issues/200)).
- **`nint` and `nuint` members are serialized on netstandard** (Unity included). rc.1 skipped them there with NINO007; they are now written as 8 bytes, as on .NET 7 and later.

### New [#new]

- **Layout metadata**: the generator records how each `[NinoType]` is written as an `[assembly: NinoTypeLayout]`, so tools can compare layouts between builds. See [Layout Metadata](/en/docs/v4/evolving-data#layout-metadata) ([#197](https://github.com/JasonXuDeveloper/Nino/issues/197)).
- **Unloading assemblies**: `NinoRegistry.Remove(assembly)` clears everything Nino cached for an assembly, so a collectible `AssemblyLoadContext` can unload it. On .NET 8 and later this happens on its own when the context unloads. See [Unloading Assemblies](/en/docs/v4/platforms#unloading-assemblies) ([#199](https://github.com/JasonXuDeveloper/Nino/issues/199)).
- **Your own buffer pool**: `new NinoArrayBufferWriter(initialCapacity, pool)` rents its arrays from the `ArrayPool<byte>` you pass in. See [Reusing a Buffer](/en/docs/v4/basic#reusing-a-buffer) ([#198](https://github.com/JasonXuDeveloper/Nino/issues/198)).

### Fixes [#fixes]

- **Two `[NinoFormerName]` on one type are reported** as error NINO026. The generator took the first one, and `NinoTypeId.Of` threw `AmbiguousMatchException`. See [Diagnostics](/en/docs/v4/analyzers) ([#201](https://github.com/JasonXuDeveloper/Nino/issues/201)).

## 4.0.0-rc.1

The first release candidate. Data written by the v4 betas and previews cannot be read by it; see [Behavior Changes since the v4 Betas](/en/docs/v4/migration#behavior-changes-since-the-v4-betas) for everything that changed since them.
