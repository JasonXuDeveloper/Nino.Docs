This page compares Nino v3 with Nino v4: features, build time and generated code, and runtime performance. For upgrading, see [Migrating from v3](/en/docs/v4/migration).

## Features

| | v3 | v4 |
| --- | --- | --- |
| API | generated `Serializer` / `Deserializer` per assembly, extension methods | `NinoSerializer` / `NinoDeserializer` in `Nino.Core` |
| Binary format | positional | positional by default, identical bytes on every target framework; padding zeroed (deterministic output) |
| Version tolerance | `WEAK_VERSION_TOLERANCE` for the whole project, append at the end | `versionTolerant` per type; append to the most derived type, at any depth; old code skips new members |
| Keyed members (reorder / remove / insert) | no | `[NinoType(keyed: true)]` |
| Shared references and cycles | no | `[NinoType(trackReferences: true)]` |
| Deserialize into existing instances | no | `Deserialize(data, ref value)`, with recycling of dropped instances |
| Object pooling | no | `[NinoPooled]`, `[NinoFactory]` factories, `NinoSettings.SetRecycler<T>` |
| Subtypes of a `[NinoType]` | need their own `[NinoType]` | inherit it |
| User collections (subclasses of `List<T>`, `Dictionary<,>`, ...) | dictionary subclasses need a public indexer | supported without attributes |
| `PriorityQueue<,>`, immutable collections | no | `PriorityQueue<,>` on .NET 6+; `ImmutableArray<T>` and `ImmutableList<T>` with `Nino.Immutable` |
| Custom formatters | no | `[NinoCustomFormatter]` per member, `[assembly: NinoFormatter]` per type |
| Boxed / runtime-typed API | no | `Serialize(object)`, `Deserialize(data, Type)` |
| Diagnostics | compile errors in generated code | 24 analyzer diagnostics (NINO001–NINO024), many with code fixes |
| Incremental generator | no: whole-compilation scans, all types re-generated on every edit | one file per type, only edited types re-generated |
| Interceptors | no | always on with Roslyn 4.8+ (the .NET 8 SDK and later) |
| Hot update (HybridCLR) | supported | supported, no initialization call |
| Unity | 2022.3+, `Microsoft.CodeAnalysis` installed manually | 2022.3+, generator included in the package |
| Thread safety | inline caches could race under contention | lock-free, copy-on-write registries |

## Build Time and Generated Code

v4 against v3 **3.3.13**, the last v3 release. Measured on a synthetic assembly of `N` abstract root classes, each with a chain of 8 derived classes, a sealed leaf and a struct (`N × 11` types), with primitives, strings, `List<T>`, `Dictionary<int, string>`, references to other `[NinoType]`s and private fields. Intel Xeon 2.80 GHz, 4 cores, Ubuntu 24.04, .NET SDK 10.0.402; the ratios are what to look at.

|---|---:|---:|---:|

| Re-generating after editing a member | 1.31 s | 0.19 s | **6.9× faster** |
| Re-generating after editing a comment | 1.11 s | 0.19 s | **5.8× faster** |
| IL of the generated code | 2.2 MB | 0.37 MB | **6.0× smaller** |

</Tab>
<Tab value="1,100 types (N = 100)">

| | v3 (3.3.13) | v4 | v4 vs v3 |
|---|---:|---:|---:|
| Generated source | 62.0 MB (1,204,143 lines) | 3.9 MB (72,429 lines) | **16× smaller** |
| Compiling the generated code (emit) | 636 s | 2.2 s | **289× faster** |
| Running the generator | 5.5 s | 0.68 s | **8.1× faster** |
| Re-generating after editing a member | 4.1 s | 0.57 s | **7.2× faster** |
| Re-generating after editing a comment | 4.1 s | 0.45 s | **9.0× faster** |
| IL of the generated code | 7.3 MB | 1.3 MB | **5.6× smaller** |

v3's compile time grows much faster than the number of types: 3.3× the types took 11× the compile time (56 s → 636 s).

</Tab>
</Tabs>

v3 inlined the bodies of every subtype into each polymorphic base and re-generated every type on every edit. v4 emits each body once and grows linearly: about 3.5 KB of source and 2 ms of compile time per type. Editing a type in the IDE re-generates that type only.

## Runtime

Nino v4 against v3 3.3.13 from NuGet, measured back to back on the same machine. See [Benchmarks](/en/docs/v4/perf) for absolute times and the comparison with MemoryPack.

<BenchmarkChart chart={['v3-serialize', 'v3-deserialize']} lang="en" />

Serializing classes is clearly faster. Deserializing is on par with v3, which is bound by allocating the result objects, while v4 also does reference tracking, reuse deserialization and payload validation. Arrays of structs with padding serialize a few nanoseconds slower, because v4 zeroes the padding so the output is deterministic; a struct without padding (see [Struct Layout](/en/docs/v4/performance#struct-layout)) copies as fast as in v3. v4 adds what v3 could not do: deserializing into existing and pooled instances, which allocates **0 B** per call. See [What's New in v4](/en/docs/v4/whats-new).
