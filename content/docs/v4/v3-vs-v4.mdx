This page compares Nino v3 with Nino v4 in three areas: features, build time and generated code, and runtime performance. For the upgrade steps, see [Migrating from v3](/en/docs/v4/migration).

## Features

| | v3 | v4 |
| --- | --- | --- |
| API | generated `Serializer` / `Deserializer` per assembly, extension methods | `NinoSerializer` / `NinoDeserializer` in `Nino.Core` |
| Binary format | positional | positional by default, identical bytes on every target framework; padding zeroed (deterministic output) |
| Version tolerance | `WEAK_VERSION_TOLERANCE` for the whole project, append at the end | `versionTolerant` per type; append to the most derived type, at any nesting depth; old code skips new members |
| Keyed members (reorder / remove / insert) | no | `[NinoType(keyed: true)]` |
| Shared references and cycles | no | `[NinoType(trackReferences: true)]` |
| Deserialize into existing instances | no | `Deserialize(data, ref value)`, with recycling of dropped instances |
| Object pooling | no | `[NinoPooled]`, `[NinoFactory]` factories, `NinoSettings.SetRecycler<T>` |
| Subtypes of a `[NinoType]` | need their own `[NinoType]` | inherit it |
| User collections (subclasses of `List<T>`, `Dictionary<,>`, ...) | dictionary subclasses need a public indexer | supported without attributes |
| `PriorityQueue<,>`, immutable collections | no | `PriorityQueue<,>` on .NET 6+; `ImmutableArray<T>` and `ImmutableList<T>` with `Nino.Immutable` |
| Custom formatters | no | `[NinoCustomFormatter]` per member, `[assembly: NinoFormatter]` per type |
| Boxed / runtime-typed API | no | `Serialize(object)`, `Deserialize(data, Type)` |
| Diagnostics | compile errors in generated code | 24 analyzer diagnostics (NINO001–NINO024), many with code fixes |
| Incremental generator | no: scans the whole compilation and re-generates every type on every edit | one file per type, only edited types re-generated |
| Interceptors | no | always on with Roslyn 4.8+ (the .NET 8 SDK and later) |
| Hot update (HybridCLR) | supported | supported, no initialization call |
| Unity | 2022.3+, `Microsoft.CodeAnalysis` installed manually | 2022.3+, generator included in the package |
| Thread safety | inline caches could race under contention | lock-free, copy-on-write registries |

## Build Time and Generated Code

The baseline is v3 **3.3.13**, the last v3 release, on a synthetic project of 330 and 1,100 polymorphic types. Look at the ratios rather than the absolute times.

<BenchmarkChart chart="compile" lang="en" table={false} />

v3 inlined the body of every subtype into each polymorphic base and re-generated every type on every edit. v4 emits each body once and grows linearly: about 3.5 KB of source and 2 ms of compile time per type. Editing a type in the IDE re-generates that type only.

Each stage, for 330 and 1,100 types, with the harness and how the times were taken: [Build Time and Generated Code](/en/docs/v4/perf#build-time-and-generated-code).

## Runtime

Nino v4 is measured against v3 3.3.13 from NuGet, back to back on the same machine. See [Benchmarks](/en/docs/v4/perf) for absolute times and the comparison with MemoryPack.

<BenchmarkChart chart={['v3-serialize', 'v3-deserialize']} lang="en" />

Serializing classes is clearly faster. Deserializing is on par with v3. Its cost is dominated by allocating the result objects, and v4 also handles reference tracking, reuse deserialization and payload validation on top of that. Arrays of structs with padding serialize a few nanoseconds slower, because v4 zeroes the padding to keep the output deterministic; a struct without padding (see [Struct Layout](/en/docs/v4/performance#struct-layout)) copies as fast as in v3. v4 also does something v3 could not: it deserializes into existing and pooled instances, allocating **0 B** per call. See [What's New in v4](/en/docs/v4/whats-new).
