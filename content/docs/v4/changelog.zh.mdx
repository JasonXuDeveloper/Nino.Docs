## 4.0.0-rc.11

### 新功能 [#new-9]

- **`NinoNullable<T>`**：给高频写入的集合用的可空值。Nino 写出的字节和 `T?` 完全一样（两边能互相读对方的数据），但它的内存里没有填充、也没有残留字节，所以 `T` 是基元类型、枚举、`DateTime` 或 `TimeSpan` 时，它的数组和 `List<>` 整块拷贝读写，而 `T?[]` 要边拷边逐个元素清零。它能从 `T`、`T?` 隐式转换过来，也能隐式转成 `T?`。见[高频集合里的可空值](/zh/docs/v4/performance#nino-nullable)（[#275](https://github.com/JasonXuDeveloper/Nino/issues/275)）。

### 性能 [#performance-6]

- **可空值**：非托管 `T` 的 `T?`（`int?`、`long?`、`DateTime?`、原始结构体）一次预留就完成读写，不再把值拆开；带可空原始成员的类型体把写入器留在寄存器里；顶层为 null 的类读写时不再创建读取器和写入器。在 GitHub 的 runner 上（AMD EPYC 7763 和 9V74、Intel Xeon 8370C、Neoverse-N2），有 8 个可空成员的类序列化比 rc.10 快 1.7-3.3 倍，反序列化快 1.04-1.25 倍，100 个这样的对象反序列化快 1.13-1.30 倍，`SimpleStruct?` 序列化快 1.14-4.3 倍，null 类引用快 1.3-1.7 倍（[#275](https://github.com/JasonXuDeveloper/Nino/issues/275)）。

## 4.0.0-rc.10

### 新功能 [#new-8]

- **直接读取 `ReadOnlySequence<byte>`**：新增 `NinoDeserializer.Deserialize<T>(in ReadOnlySequence<byte>)` 和 `Deserialize<T>(in ReadOnlySequence<byte>, ref T)`，`PipeReader` 或 gRPC 交给你的数据可以直接读。只有一段时原地读取，跨多段时拷贝一次：1,024 字节以内拷到栈上，更大的拷进池化数组。被拦截的调用和 span 一样直接调用生成的格式化器。参见[多段输入](/zh/docs/v4/advanced/streams#readonlysequence-input)。
- **布局基线与兼容性检查**：用 IDE 重构或 `nino-gen layouts` 生成一个 `NinoLayouts.cs`（内容是 `[assembly: NinoLayouts(...)]`），记下要存储或传输的类型的布局。之后你一边写代码，分析器一边比对：改动会让旧数据或旧版本读不了时报 [NINO034](/zh/docs/v4/analyzers#nino034)，会悄无声息丢数据时报 [NINO035](/zh/docs/v4/analyzers#nino035)，兼容但有前提时报 [NINO036](/zh/docs/v4/analyzers#nino036)；基线本身读不了时报 [NINO037](/zh/docs/v4/analyzers#nino037)。代码修复可以撤销改动（加上旧名、把 `sealed` 加回或去掉、把成员挪到末尾），也可以把改动接受进基线；`nino-gen layouts --check` 在 CI 里跑同一套规则。这个特性带 `[Conditional]`，不会编译进你的程序集。参见[布局基线](/zh/docs/v4/evolving-data#layout-baseline)。
- **`Stream` 与异步读写**：新增 `NinoSerializer.Serialize(value, stream)`、`SerializeAsync(value, stream)`，以及 `NinoDeserializer.Deserialize<T>(stream)`（也可以用 `ref` 读入已有实例）、`DeserializeAsync<T>(stream)`，还有接收 `Type` 的装箱版本，以前流与压缩页要你复制的辅助方法用不着了。写入时，流里的字节和 `Serialize(value)` 完全相同，从 Nino 的池化缓冲区写出，不分帧。读取时，先把流从当前位置读到结尾，再开始解码；字节读进池化数组（公开了缓冲区的 `MemoryStream`，以及类型恰好是 `UnmanagedMemoryStream` 或 `MemoryMappedViewStream` 的流，直接在原内存上读），数组只随读到的字节增长，之后和读 span 一样检查数据。被拦截的调用直接调用生成的格式化器。异步调用返回 `ValueTask`，需要 .NET Standard 2.1 及以上；.NET Standard 2.0 版本（.NET Framework 用的就是它）只有同步调用。一个流上传多条消息仍然要[分帧](/zh/docs/v4/advanced/streams#frames)。参见[流](/zh/docs/v4/advanced/streams#streams)。
- **序列化回调**：给 `[NinoType]` 类或结构体的方法标上 `[NinoOnSerializing]`、`[NinoOnSerialized]`、`[NinoOnDeserializing]` 或 `[NinoOnDeserialized]`，Nino 每次写、读这个类型的值时都会在前后调用它们，不管值在哪里：顶层、成员和集合里，以及基类或接口槽位里的子类型，基类的回调先执行。生成的代码直接调用这些方法，IL2CPP 和 Native AOT 不用额外配置，字节也不变。新规则 [NINO038](/zh/docs/v4/analyzers#nino038) 到 [NINO044](/zh/docs/v4/analyzers#nino044) 报告 Nino 调用不到的回调（签名不对、是 `private`、类型不是 `[NinoType]`、同一种回调标了两个方法、需要在值上执行却是 `static`、由成员创建的类型用了实例方法的 `[NinoOnDeserializing]`、标在按原始内存拷贝的结构体上），NINO039 和 NINO040 带代码修复。参见[回调](/zh/docs/v4/defining-types#callbacks)。
- **netstandard 版本多了两个原生内核**：`NinoKernels.Interleave32` 把键和值都是四字节原始值的 `SortedList` 按二进制格式写成键值对，`NinoKernels.NormalizeBoolSlots` 在读写 `bool?` 的数组和列表时检查并规整槽位；注册的内核必须和参照实现 `Interleave32Scalar`、`NormalizeBoolSlotsScalar` 逐字节一致。Unity 包注册了这两个内核的 Burst 版本（AVX2、SSE2 和 Neon）。参见[注册自己的内核](/zh/docs/v4/simd#registering-kernels)和 [Burst 加速内核](/zh/docs/v4/advanced/unity#burst-kernels)。
- **`nino-gen inspect`**：按程序集的布局读一条消息，列出每个成员的偏移、长度、编码和值：类型 ID 解析成类型名，键控条目带上键（不认识的键显示为跳过的字节），还有引用头和推迟的主体。`--json` 输出给工具用的结果树，`--hex` 和 `--offset` 可以读十六进制转储或大缓冲区里的一帧。数据有问题时，先显示已经读到的部分，再给出出错的偏移和没通过的检查。参见[查看一条消息](/zh/docs/v4/advanced/codegen#inspect)。
- **Unity 包带签名**：每次发布都会用 Unity 的包签名给 Unity 包签名，把签好的 `.tgz` 附到这个包版本的 GitHub Release 上，OpenUPM 原样发布这个文件。所以 Unity 6.3 及以上会显示包已签名，不再提示未签名；用 Git URL 添加的包仍然没有签名（[#266](https://github.com/JasonXuDeveloper/Nino/issues/266)）。见 [Unity 安装](/zh/docs/v4/advanced/unity#setup)。
- **.NET 11**：单元测试在 .NET 11 运行时上跑。目标框架为 `net11.0` 的项目用的是 `Nino.Core` 的 `net10.0` 版本，所有快路径都照常生效。见[支持的平台](/zh/docs/v4/platforms#supported-platforms)。

### 性能 [#performance-5]

- **直接写进任意 `IBufferWriter<byte>`**：以前只有原始值能直接写进外部的写入器，别的都要先写进 Nino 的暂存缓冲区再拷过去。现在原始值的数组、列表和[固定大小的类型](/zh/docs/v4/performance#fixed-size-types)也是按大小调一次 `GetSpan`，直接写进 `PipeWriter`、`ArrayBufferWriter<byte>` 这类写入器。.NET Standard 2.1 及以上还包括原始值的 `ArraySegment<T>`、底层是数组的 `Memory<T>` 和只有一段的 `ReadOnlySequence<T>`，.NET 8 及以上再加上原始值的多维数组。其余的值照旧拷贝一次。详见[序列化到任意 IBufferWriter](/zh/docs/v4/advanced/high-performance#serialize-into-any-ibufferwriter)。
- **数据拷贝统一走 Nino 的块拷贝**：之前还有几处拷贝用的是 .NET 的 `Memmove`（AMD CPU 上 glibc 用 `rep movsb` 实现），现在都换成 Nino 自己的块拷贝：原地写进外部 `IBufferWriter<byte>` 的原始值（见上一条）；从暂存缓冲区拷进外部写入器的数据（现在按数据大小调一次 `GetSpan`，不再有多少空间用多少，长数据不会再分好几次拷）；多段 `ReadOnlySequence<byte>` 的每一段；池化缓冲区和读流时的扩容；以及 .NET 10 上新建的、超过 64 字节的 `BitArray`。拿 Nino 的拷贝换掉 `Memmove` 后，把 1,000 个 `int` 写进 `ArrayBufferWriter<byte>`，x64 上快 1.07-1.41 倍，Arm64 上快 1.27 倍；1,000 个值的 `Memory<int>` 分别快 1.09-1.45 倍和 1.23 倍；其余用例持平（GitHub 的 x64 runner：AMD EPYC 7763、9V74，Intel Xeon 8573C；Arm64：Neoverse-N2）（[#261](https://github.com/JasonXuDeveloper/Nino/issues/261)）。
- **原始键值的 `SortedList`**：键值对一次向量遍历写完（netstandard 版本用 `Interleave32` 内核）：1,000 对 `int` 序列化在 x64 上快 15.7-17.1 倍、Arm64 上快 12.3 倍，反序列化分别快 2.0-2.8 倍和 1.9 倍（GitHub 的 x64 runner：Intel Xeon 8370C、8573C，AMD EPYC 7763、9V45、9V74；Arm64：Neoverse-N2）。和 MemoryPack 的对比见[基准测试](/zh/docs/v4/benchmarks)。
- **接口类型的集合**：声明成 `IEnumerable<T>`、`ICollection<T>`、`IList<T>`、各种 `IReadOnly*` 接口或 `ReadOnlyCollection<T>` 的成员，以前都是一个个枚举着写。现在只要集合本身实现了 `ICollection<T>`：元素大小固定的，先拷进池化数组再整块写出；其他类型的元素有 16 个及以上时，也先一次性拷出来再写。`ILookup<TKey, TElement>` 的分组同样处理。1,000 个值的 `ReadOnlyCollection<int>` 序列化在 x64 上快 16-23 倍、Arm64 上快 18.9 倍；1,000 个元素的 `ILookup<int, int>` 分别快 5.0-6.6 倍和 4.8 倍；经 `IReadOnlyList<string>` 写 1,000 个字符串，分别快 1.16-1.32 倍和 1.17 倍（GitHub 的 x64 runner：Intel Xeon 8370C、8573C，AMD EPYC 7763、9V45、9V74；Arm64：Neoverse-N2）。写出的字节不变。
- **`BitArray`**：位数据直接写进输出，1,000 位的序列化在 x64 上快 2.0-2.2 倍、Arm64 上快 2.5 倍（GitHub 的 x64 runner：Intel Xeon 8370C、8573C，AMD EPYC 7763、9V45、9V74；Arm64：Neoverse-N2）。
- **多态集合**：基类或接口的数组、列表在循环里直接写各个子类型，嵌套深度每个元素只查一次，不再每个子类型查一次：8 种类型、1,000 个子类型实例的数组，无论经非泛型基类还是封闭泛型基类，序列化在 x64 上快 1.13-1.49 倍、Arm64 上快 1.40-1.46 倍（GitHub 的 x64 runner：Intel Xeon 8370C、8573C，AMD EPYC 7763、9V45、9V74；Arm64：Neoverse-N2）。
- **.NET 9 和 11 上的 `ConcurrentStack<T>`**：原始元素的免分配写入以前只在 .NET 8 和 10 上生效，现在 .NET 8 及以上都直接读它的节点。

### 修复 [#fixes-7]

- **.NET 8 及以上复用 Latin-1 字符串**：复用反序列化时，内容没变的非 ASCII Latin-1 字符串（`"café"`）会保留下来，不再分配新字符串；成员、集合里都一样，不走 SIMD 的路径也一样。参见[哪些调用会分配内存](/zh/docs/v4/advanced/zero-allocation#what-allocates)。
- **元素很大的空多维数组**：读取空的 `T[,]`（及更高维）时，即使元素类型在内存里比写出的字节大得多，也不再抛 `IndexOutOfRangeException`。
- **预取不再执行你的 getter**：开启 [`NinoPrefetchLargeCollections`](/zh/docs/v4/advanced/type-design#large-collections) 后，预取集合里的对象只读字段，以及不会被重写替换掉的自动属性；以前虚自动属性被子类用自己的 getter 重写时，每个对象会多调用一次这个 getter。
- **没有值的 `Nullable` 写成 0**：raw 值的 `T?[]` 和 `List<T?>`，以及带 `Nullable` 字段的 raw 结构体，原先每遇到一个 null，值的那几个字节都照内存原样拷贝。某个 `T?` 所在的内存要是从没赋过值（未初始化或租来的数组、用 `Unsafe` 构造的结构体），里面的旧字节就会写进输出，相等的值也可能序列化出不同的字节。现在这部分一律写 0，和[二进制格式](/zh/docs/v4/wire-format#raw-values)的规定一致。正常赋值的值，写出的字节和以前一样。写 0 要花时间：在 GitHub 的 x64 runner 上（AMD EPYC 7763、9V45、9V74，Intel Xeon 8573C、6973P-C），序列化 `int?` 或 `long?` 的集合耗时是 rc.9 的 1.2 到 1.9 倍，`decimal?` 最多 1.2 倍；Arm64（Neoverse-N2）上是 2.3 到 2.9 倍。反序列化不受影响（剩下的开销在 [#270](https://github.com/JasonXuDeveloper/Nino/issues/270) 里跟进）。清零是在集合那一遍向量拷贝里顺带完成的，向量宽度和 Nino 的掩码拷贝一样（有 AVX-512 时 64 字节，AVX2 时 32 字节，Arm64 上用结构化加载），不再单独扫一遍。
- **检查过支持情况之后才注册的格式化器**：`NinoSerializer.IsSupported` 和 Nino.AspNetCore 的 MVC 格式化器对某个类型答过“不支持”之后，再为它注册格式化器，现在也能认出来；MVC 只在 Native AOT 下缓存“不支持”，因为那里之后不会再有新的注册。参见 [ASP.NET Core](/zh/docs/v4/advanced/aspnetcore)。
- **注册失败的程序集可以卸载了**：查找某个程序集生成的注册表失败（读取它的特性时抛了异常），而这个程序集恰好正在[卸载](/zh/docs/v4/platforms#unloading-assemblies)、从 Nino 的注册表里移除，Nino 事后仍会留着对它的强引用，它所在的可回收 `AssemblyLoadContext` 就回收不掉。现在移除了的程序集不会再被留住。
- **Burst 2.0（Unity 6000.6）**：注册了 Burst 内核时，序列化 16 个字符及以上的字符串会从 `NinoBurst.Narrow` 抛出 `InvalidOperationException`（“This Exception was thrown from a function compiled with Burst”）。原因是有个分支在一个条件里同时判断 Neon 和 SSE2，Burst 2.0 把它编译成了中止，而 Burst 1.8.29 编译同样的代码没有问题。现在每个内核的每个分支只判断一种指令集，Burst 1.8 和 2.0 都能编译对；Nino 的 CI 也分别在 Burst 1.8（Unity 2022.3）和 2.0（Unity 6000.6）上跑这些内核。另外，启动时会经函数指针把每个内核都调一遍，输入覆盖所有分支，结果和 Nino 的标量代码逐字节比对：抛异常或写出的字节不一样的内核不用（这部分工作走 Nino 自己的路径），同时输出一条警告，写明是哪个内核、Burst 和 Unity 的版本、CPU 型号，并请你到 issue 页反馈。Player 里内核一抛异常，进程就直接结束了，什么检查都来不及，所以在 Player 里自检只能查出写错的字节（[#265](https://github.com/JasonXuDeveloper/Nino/issues/265)）。参见 [Burst 加速内核](/zh/docs/v4/advanced/unity#self-test)。
- **Go 和 TypeScript 限制一次读取预先分配的内存**：以前集合长度只和剩余字节数比，嵌套的集合可以一层层重复声称这些字节，1 MB 的恶意数据在 Go 里能分配约 1 GB（直接内存耗尽崩溃，不是返回错误），在 Node 里也会让进程中止。现在一次读取里所有集合共用一份预分配额度：每字节数据 16 字节，再加 16 KB，和 Rust 的读取一样，超出部分边读边扩容；nino-gen 生成的 TypeScript 读取代码也用它（需要重新生成）。Go 的 `ReadShape` 还会把多维数组的每个元素至少算作一个字节。参见 [Go](/zh/docs/v4/advanced/go#untrusted-data) 和 [TypeScript](/zh/docs/v4/advanced/typescript#untrusted-data)。
- **Rust 能读某一维为 0 的多维数组**：.NET 写出的 `new int[1000, 0]` 这类多维数组，Rust 不再读失败；另一维为 0 时，超过 .NET 数组上限的维度也会被拒绝。

</Release>

## 4.0.0-rc.9

### 新功能 [#new-7]

- **4.0 之前改名和调整参数顺序**（没有保留旧名；字节不变）：`[NinoType(allowInheritance)]` 改为 `inheritedBySubtypes`（`NinoTypeAttribute.InheritedBySubtypes`），代码修复会改写这个参数，现在也会把 v3 的 `containNonPublicMembers` 改成 `includeNonPublicMembers`；`NinoPolymorphic.Register<T>()` 和 `Register(Type)` 改为 `TryRegister<T>()` 和 `TryRegister(Type)`，类型注册不了时返回 `false`；`NinoHeader.NullFlag` 改为 `NinoHeader.Presence`，.NET、Go 和 Rust 发布的布局写成 `header=Presence` 和 `id=0x...`（原来是 `typeId=`，`NinoTypeLayoutAttribute` 的构造函数参数也一样）。所有读取 API 都把读取器放在第一个参数：`NinoDeserializer.Deserialize(ref reader, ref value)`、`DeserializeBoxed(ref reader, ref value, type)`，以及 `INinoFormatter<T>.Deserialize(ref Reader reader, ref T value)`，自己写的格式化器要把这两个参数对调。Rust 中，nino-gen 在每个生成类型上声明的 ID 改为 `NINO_TYPE_ID`（原来是 `TYPE_ID`），和 `NINO_TYPE_NAME`、`NINO_LAYOUT` 命名一致：请重新生成，并把代码中的 `Cat::TYPE_ID` 改成 `Cat::NINO_TYPE_ID`（`<Cat as NinoReadBody>::TYPE_ID` 不变）。生成的注册表用一次 `Nino.Core.CompilerServices.NinoTypes` 调用注册每个 `[NinoType]`；只有生成代码才调用的 `NinoPolymorphic.Register<TSub, TFormatter>(id)`、`RegisterTracked`、`NinoFormatterCache<T>.TryRegisterFixed` 和 `TryRegisterTop` 已移除，所以由更早版本生成过代码的程序集都要重新编译。参见[从更早的候选版本升级](/zh/docs/v4/migration#upgrading-from-an-earlier-release-candidate)。
- **移除 `WEAK_VERSION_TOLERANCE`。** 项目还定义着它时，错误 NINO032（“`WEAK_VERSION_TOLERANCE` 不会让类型版本容错”）会标出每个原本靠它变成版本容错的按位置格式类型，代码修复给类型加上 `format: NinoFormat.VersionTolerant`，字节不变（可以一次修复整个解决方案）；然后删掉这个符号。参见[版本容错](/zh/docs/v4/evolving-data#version-tolerance)。
- **UTF-8 只有一种写法**：字符串成员上的 `[NinoMemberFormatter(typeof(Utf8StringFormatter))]` 按 `[NinoUtf8]` 处理（字节相同，发布的布局中为 `utf8`）；提示 NINO031 及其代码修复会把它改写成 `[NinoUtf8]`。警告 NINO030 报告不起作用的 `[NinoUtf8]`：成员类型里没有内置格式化器会写的字符串，成员由 `[NinoMemberFormatter]` 写出，或者成员根本不参与序列化（`[NinoIgnore]`、非公共、只读、静态、显式接口实现，或 `autoCollect: false` 时没有 `[NinoMember]`）；代码修复会去掉它。参见[字符串编码](/zh/docs/v4/defining-types#string-encoding)。
- **NINO033**：接口成员上的 `[NinoUtf8]`、`[NinoMemberFormatter]` 或 `[NinoIgnore]` 不起作用，报警告：实现类型写的是自己的成员，用自己的特性，接口成员上只有 `[NinoMember(index)]` 算数。编译里有类型显式实现这个成员或用了它的默认实现时（这时写的是接口成员，这些特性会生效），不报。代码修复把特性移到实现成员上；没有实现成员时直接删掉。参见[接口与抽象类](/zh/docs/v4/polymorphism#interfaces-and-abstract-classes)。
- **手写 impl 用的 Rust 宏**：`nino::raw_read!()` 和 `nino::raw_write!()` 根据原始结构体的 `nino::Raw` impl 写出它的 `NinoRead` 和 `NinoWrite` impl，和 nino-gen 生成的代码、derive 一样；`nino::type_consts!(id, name, layout)` 声明 nino-gen 为每个类型生成的 `NINO_TYPE_ID`、`NINO_TYPE_NAME` 和 `NINO_LAYOUT` 常量，文档只在 crate 里写一次。参见[手写 impl](/zh/docs/v4/advanced/rust#hand-written)。

### 性能 [#performance-4]

- **不可信模式下带 `bool` 的普通结构体列表**：开启 [`NinoSettings.Untrusted`](/zh/docs/v4/security#untrusted-mode) 时，`bool` 字段和相邻字段在同一轮 SIMD 检查里完成：x64 上快 11-20%，已算上本版本的越界读取修复（1,000 个值：GitHub 的 AMD EPYC 7763 runner 上 2.70 → 2.40 µs，EPYC 9V45 上 1.40 → 1.11 µs），Arm64 上持平。
- **IDE 里的源生成器**：没改任何声明的编辑，不再让生成器把每一处顶层 `Serialize`/`Deserialize` 调用重新绑定一遍；这类调用很多的项目，打字时生成器的开销小得多。

### 修复 [#fixes-6]

- **不可信模式读取值为普通结构体的字典**：开启 [`NinoSettings.Untrusted`](/zh/docs/v4/security#untrusted-mode) 时，读取值为普通结构体的 `Dictionary`（如 `Dictionary<long, DateTime>`）不再越过输入末尾多读最多一个键的长度；输入恰好结束在内存页边界时，这可能让进程崩溃。从未因此误收过错误的值。
- **一个成员错误只报一次**：基类成员的 NINO007 和 NINO029 只由声明它的类型报一次，不再在同一位置为每个子类型各报一次。参见[分析器](/zh/docs/v4/analyzers)。
- **`[NinoType]` 接口成员的显式实现**：显式实现 `[NinoType]` 接口属性的类型（`int IFoo.X { get; set; }`）不再因 CS1061 编译失败。接口的成员通过接口写出（结构体不装箱），用的是接口成员上的 `[NinoUtf8]`、`[NinoMemberFormatter]` 和 `[NinoIgnore]`，布局和隐式实现相同。参见[接口与抽象类](/zh/docs/v4/polymorphism#interfaces-and-abstract-classes)。
- **生成的 Rust 代码中的类型 ID**：nino-gen 写出的 Rust 代码把 `NinoReadBody::TYPE_ID` 和 `NinoWriteBody::TYPE_ID` 设为类型的 ID，和 `#[derive]` 一样；之前它们是 0，泛型代码通过 `<T as NinoReadBody>::TYPE_ID` 取到的每个生成类型的 ID 都是 0。参见 [Rust：生成的代码](/zh/docs/v4/advanced/rust#generated-code)。
- **含 null 的 Rust 字符串 Set**：nino-gen 写出的 Rust 代码能读 .NET 写出的、含 null 的 `HashSet<string>`（任何字符串 Set，包括 `[NinoUtf8]` 的）；之前会报 `UnexpectedNull` 失败。它的元素现在是 `Option<String>`、`Option<WideString>` 或 `Option<Utf8>`，所以构造或读取这类 Set 的 Rust 代码要相应修改（`IndexSet<String>` 变为 `IndexSet<Option<String>>`）。Go 和 TypeScript 原本就能读取。参见 [Rust：类型](/zh/docs/v4/advanced/rust#types)。

## 4.0.0-rc.8

### 二进制格式 [#wire-format-3]

- **1、3 或 5 字节的字符串头**：每个字符串（成员、集合的元素和键、`StringBuilder`，`Uri`、`CultureInfo` 和 `TimeZoneInfo` 的文本，以及 `[NinoUtf8]` 字符串）不再以 4 字节的 `int32` 作头，而是像 MessagePack 的字符串标记一样，头的大小由它的第一个字节决定：不超过 `7F` 时就是值本身，否则是 `80` 加一个 `uint16`，再大就是 `81` 加一个 `uint32`，总是取最短形式。头的值为 `0` 表示 null，`2n + 1` 表示 `n` 个 Latin-1 字符（`1` 即空字符串），`2n` 表示 `n` 个 UTF-16 码元，所以 63 个字符以内的字符串，头只占 1 字节：null 是 `00`，`""` 是 `01`，`"abc"` 是 `07 61 62 63`。`[NinoUtf8]` 字符串用头写出字符数加一和字节数。`StringBuilder` 仍用 UTF-16 形式（为空时是 `01`）。不是最短形式、或以 `82` 及以上字节开头的头，读取方一律拒绝。Go、Rust 和 TypeScript 运行时读写的字节完全一致。这是二进制格式规范的 4.1 版；更早的 4.0 预发行版写出的数据读不了（[从更早的候选版本升级](/zh/docs/v4/migration#upgrading-from-an-earlier-release-candidate)）。参见[字符串](/zh/docs/v4/wire-format#strings)。
- **8 项及以上的元组**：类型为 8 项及以上 `ValueTuple` 的成员（或元素）现在会写出，各项按顺序写，和较短的元组一样；之前直接跳过，报 NINO007 警告，什么都不写。参见[其他内置类型](/zh/docs/v4/types#other-built-in-types)。
- **运行时绑定的可空原始 `[NinoType]` 结构体**：由运行时构建格式化器的原始 `[NinoType]` 结构体（没有生成代码引用、按 `Type` 或装箱序列化的类型），它的 `T?[]` 和其他 `T?` 序列现在按生成代码用的固定步长写，两边能互相读对方的字节。这类格式化器以前写出的数据需要重新写一遍。
- **32 位 x86**：类型为结构体（不是 `[NinoType]`）、且在较小字段之后含有 `TimeOnly`、`Complex`、`Int128` 或 `UInt128` 的成员，现在和 64 位运行时一样按规范布局写，不再照搬 x86 上的内存。参见[可移植的设计](/zh/docs/v4/platforms#portable-by-design)。
- **32 位 x86 .NET 和 .NET Framework 上原始结构体中的 `DateTime`**：按原始字节写入的结构体（不是 `[NinoType]` 的结构体，或布局在不同运行时上不同的 `[NinoType]` 结构体）如果在较小字段之后含有 `DateTime`，现在和 64 位 .NET 一样按规范布局写。Windows x86 .NET 把 `DateTime` 字段按 4 字节对齐，`struct { int A; DateTime B; }` 原先照搬 12 字节的内存，而不是 16 字节；.NET Framework（64 位和 32 位）会重排含 `DateTime` 的结构体的字段，`struct { byte A; DateTime B; int C; }` 原先照搬 16 字节的内存（`int` 在前），而不是 24 字节。这两种字节其他运行时都读不了。参见[可移植的设计](/zh/docs/v4/platforms#portable-by-design)。
- **原始结构体中的值元组、`KeyValuePair`、`DateTimeOffset` 和 `nint`**：不是 `[NinoType]`、且含有这些类型的非托管结构体，在每个运行时上都按同一种规范布局写出，即 64 位 CoreCLR 的布局（二进制格式规范 4.2 版）。值元组的各项放在 64 位 CoreCLR 自动布局放置的位置（较大的基元项在前：在 `struct { int A; (int, long) B; }` 中 `long` 位于 `int` 之前），`KeyValuePair` 先键后值，`DateTimeOffset` 按 .NET 10 的方式存放（以分钟为单位的偏移为 `int`，UTC 时间位于第 8 字节），`nint`/`nuint`/指针占 8 字节。这样的结构体以前照搬内存，而 Mono 和 IL2CPP（元组按声明顺序）、.NET Framework、32 位运行时和 .NET 8（`DateTimeOffset` 里是 `short`）的布局各不相同，一个运行时写的数据，另一个运行时读不了。字节在 Mono、IL2CPP、.NET Framework 和 32 位运行时上有变化，在 .NET 8 上对偏移为负的 `DateTimeOffset` 有变化；64 位 .NET 8 和 10 对元组和键值对、.NET 10 对 `DateTimeOffset` 写出的字节与之前相同，只是填充现在写为零；这类结构体的 `T?` 数组或列表现在与任何原始结构体一样，把存在字节填充到结构体的对齐（此前在每个运行时上都只占一个字节）。nino-gen 生成的 Go、Rust 和 TypeScript 代码对原始结构体中的元组和键值对读写同样的字节（此前它按声明顺序发布元组，键值对则完全没有发布），含 `nint`、`nuint`、指针、`Int128` 或 `DateTimeOffset` 的原始结构体也会生成（[代码生成](/zh/docs/v4/advanced/codegen#raw-struct-fields)）；原始结构体里的 `DateTimeOffset` 在 TypeScript 中仍报 NINOGEN002。每个 BCL 结构体在各运行时上的布局（CI 实测）见[结构体布局](/zh/docs/v4/struct-layouts)。
- **`Vector<T>` 不能再序列化**：`Vector<T>` 无论单独出现还是在别的类型里（数组、集合及继承集合的类、元组、`T?`、原始结构体），都会被拒绝：写代码时报错误 NINO029，第一次需要它的格式化器时抛 `NotSupportedException`，不会写出或读入任何字节（二进制格式规范 4.4 版）。它是 16、32 或 64 字节，由 CPU 决定，所以没有哪种编码能在所有平台上读回。rc.7 及以前它在所有平台上都写成 16 字节，在 AVX2 机器上高半部分会悄悄丢失；含它的数据这个版本读不了。请改存固定数量的通道，再通过标了 `[NinoIgnore]` 的成员提供向量（见 [`Vector<T>` 不能序列化](/zh/docs/v4/struct-layouts#vector-t)）。`Vector64<T>` 到 `Vector512<T>` 仍然能序列化，在原始结构体里按自身大小对齐，和 x64 上的 64 位 .NET 一致（以前按 8 对齐，在那里要转换）。
- **原始结构体中的 `Int128` 和 `UInt128`**：不是 `[NinoType]`、且含有 `Int128` 或 `UInt128` 的非托管结构体，在 .NET 8 及更高版本上按规范布局的要求把填充写成零；之前填充是从内存拷贝的，内容不确定。参见[原始值](/zh/docs/v4/wire-format#raw-values)。
- **封闭的泛型 `[NinoType]` 结构体**：作为成员或集合元素的封闭泛型 `[NinoType]` 结构体（`struct Pad<T> { byte A; T B; }` 的 `Pad<int>`）现在逐成员写出，和它的格式化器在别处的写法一致；生成的代码以前在那里把它连同填充字节按原始内存拷贝。两种编码互相读不了：顶层调用或通过泛型类型写出的值，不能当作成员读出，反过来也一样。只要定义里有字段的类型是类型参数，它的每个封闭类型都逐成员写；含有这类成员的数据需要重新写一遍。参见[泛型类型](/zh/docs/v4/defining-types#generic-types)。

### 新功能 [#new-6]

- **4.0 正式版前的改名**（不保留旧名；字节不变）：`[NinoType(containNonPublicMembers)]` 改为 `includeNonPublicMembers`，成员级特性 `[NinoCustomFormatter]` 改为 `[NinoMemberFormatter]`（与类型级的 `[assembly: NinoFormatter]` 区分开），`NinoTypeId.GetName`/`GetIdName` 改为 `GetRuntimeName`/`GetHashedName`，`NinoSettings.DefaultPoolMaxRetained` 改为 `PoolMaxRetained`，生成代码调用的子类型注册表 `Nino.Core.NinoPolymorphic<TBase>` 改为 `Nino.Core.CompilerServices.NinoSubtypes<TBase>`（用户 API `NinoPolymorphic.Register` 名称不变）。对于手写的格式化器，`INinoBlockFormatter<T>` 现在派生自 `INinoFixedSizeFormatter<T>`（用 `FixedSize` 和 `WriteFixed(in value, ref destination)` 取代 `BlockSize` 和 `WriteBlock`，`ReadBlock` 的值参数放在前面），生成代码调用的各个 `TryRegister` 方法会返回这次是否完成了注册。TypeScript 运行时中，生成代码用来开始版本容错或键控区域的 `NinoReader` 和 `NinoWriter` 方法改为 `beginRegion`（原为 `region`，与 .NET 的 `BeginRegion` 一致），读取存在字节的方法改为 `present`（原为 `notNull`，与 .NET 的 `ReadPresent` 一致）和 `presentAt`，类型 ID 背后的子类型注册表改为 `NinoSubtypes`（原为 `NinoRegistry`，该名称在 .NET 中指每个程序集的注册）：Nino.TypeScript 或旧版 nino-gen 生成的代码请重新生成。参见[从更早的候选版本升级](/zh/docs/v4/migration#upgrading-from-an-earlier-release-candidate)。
- **TypeScript、Go 和 Rust 可以读进已有的值**：`deserializeInto(codec, bytes, value)`、`nino.DeserializeInto(data, &v, ReadXInto)` 和 `nino::deserialize_into(&bytes, &mut v)` 和 `NinoDeserializer.Deserialize(data, ref value)` 的读法一样：嵌套对象原地读取，数组、切片和 `Vec` 保留存储和元素，映射和 Set 先清空再填充，多态值只在类型相同时复用。nino-gen 为每个类型只生成一份读取代码，两种读法共用。参见 [API](/zh/docs/v4/advanced/typescript#api)。
- **TypeScript 的 `serializeInto`**：`serializeInto(codec, value, target)` 写进复用的 `NinoWriter`（用新增的 `reset()` 清空；长到足够大后不再分配内存，不会堆积 `ArrayBuffer` 而触发 Node 的完整垃圾回收）或一个 `Uint8Array`，返回值的字节数，相当于 .NET 里的 `NinoSerializer.Serialize(value, bufferWriter)`。参见 [API](/zh/docs/v4/advanced/typescript#api)。
- **TypeScript 中的类型化数组**：nino-gen 的 `NumericArrays="typed"`（`--numeric-arrays typed`）把固定大小数字的数组和列表生成为类型化数组（`Int32Array`、`Float64Array`、`BigInt64Array`……），整块拷贝。在 Node 和 Chromium 里序列化更快，在 Node 里反序列化更快；但 Chromium 反序列化它们要慢 2 到 3.3 倍，小对象列表在两种引擎里读取都慢 5% 到 25%，所以默认仍是 `NumericArrays="plain"`，即 `number[]`。参见[类型化数组](/zh/docs/v4/advanced/typescript#typed-arrays)。
- **NINO028**：`[NinoMember]` 标在 Nino 从不序列化的成员上（静态字段或属性、常量、索引器、没有 setter 且没有构造函数接收的属性，或通过 `[field: NinoMember]` 标在幕后字段上）时报这个警告：这样的成员什么都不写，而 NINO010 过去却说它已经自动收集了；代码修复会删掉这个特性。NINO008 现在会给出成员和类型的名字。参见[诊断](/zh/docs/v4/analyzers#diagnostics)。
- **NINO029**：成员是 `Vector<T>`、成员类型含有它（作为元素、类型参数、基类型或它实现的 `IEnumerable<T>`，或任意深度的普通结构体字段；`class Lanes : List<Vector<int>>` 报 NINO029，而不是 NINO007；格式化器会写出该类型参数的泛型 `[NinoType]` 以它封闭时，如 `Box<Vector<int>>`，也包括泛型子类型经由基类型参数写出它的情况，如 `TagShelf<U> : Shelf<Tag<U>>` 下的 `Shelf<Tag<Vector<int>>>`；而 `Outer<T> { [NinoIgnore] T X; Tag<T> Y; }` 在 `Tag<T>` 不写出 `T` 时，`Outer<Vector<int>>` 不报），`NinoSerializer`/`NinoDeserializer` 调用需要它，或手写使用 Nino.Core 的格式化器和 `Writer`/`Reader` 方法处理它，无论是创建出来还是只放在字段、属性或局部变量里（`new UnmanagedFormatter<Vector<int>>()`、`static UnmanagedFormatter<Vector<int>> F;`、`writer.Write(vector)`、`reader.Read(out Vector<int> v)`，运行时同样抛 `NotSupportedException`）时报错误；自己写的格式化器、标了 `[NinoIgnore]` 的成员、只读属性和 ref struct 不报，消息会指向固定通道的写法。参见[诊断](/zh/docs/v4/analyzers#diagnostics)。
- **NINO027**：泛型类型会连同类型 ID 写出（通过基类、接口或 `object`）时，它上面的 `[NinoFormerName]` 报这个警告：每个实例化都得到同一个 ID，会冲突。参见[诊断](/zh/docs/v4/analyzers#diagnostics)。
- **NINO024 和 NINO025 的代码修复**：IDE 可以删掉非键控类型成员上的 `[NinoFormerName]`，以及因为有 `[NinoConstructor]` 而永远不会调用的 `[NinoFactory]`；两者都不改变读写的内容。NINO003、NINO005、NINO007、NINO010、NINO011、NINO012 和 NINO017 的消息现在会说明后果和改法（NINO003：写这个子类型会抛异常）。参见[诊断](/zh/docs/v4/analyzers#diagnostics)。
- **`NinoDataException`**（命名空间 `Nino.Core`，派生自 `InvalidOperationException`）：反序列化时，Nino 拒绝的每一种无效输入都抛它，读不可信数据时捕获这一个具体类型就够了；`catch (InvalidOperationException)` 照样能捕获。参见 [NinoDataException](/zh/docs/v4/security#ninodataexception)。
- **`NinoSettings.MaxDepth`**（默认 512，至少 128）和 **`NinoSettings.MaxCollectionLength`**（默认 `int.MaxValue`）限制嵌套深度，以及数据里一个集合能声称的元素个数。请在第一次序列化或反序列化之前设置；之后再设会抛异常。参见[限制](/zh/docs/v4/security#limits)。
- **`NinoSettings.MaxHashCollisions`**（默认 100）：从数据里读到的键，如果在它的哈希桶里碰到的键超过这个数，就抛出 `NinoDataException`，所以故意构造冲突键的数据（哈希洪泛）没法再让读取 `Dictionary`、`HashSet`、查找表、`ImmutableDictionary`、`ImmutableHashSet` 或 `ConcurrentDictionary` 变成平方级。参见[哈希洪泛](/zh/docs/v4/security#hash-flooding)。
- **`NinoSettings.Untrusted`**（默认关闭）：用于可能被人蓄意构造的数据。Nino 创建的字典和 Set 用每个进程独有的密钥对整数、`char`、`Guid` 和 `string` 键求哈希，原始结构体按它的构造函数的方式检查（`bool`、`DateTime`、`decimal`、`DateOnly`、`TimeOnly`），值后面还有剩余字节就抛 `NinoDataException`。关闭时没有任何开销。参见[不可信模式](/zh/docs/v4/security#untrusted-mode)。
- **`<NinoPrefetchLargeCollections>true</NinoPrefetchLargeCollections>`**（MSBuild 属性，默认不设置）：在设置了它的项目里，顶层写出非泛型、非固定大小的 `[NinoType]` 类的 `T[]` 或 `List<T>`，或者读入元素个数相同的已有集合时，如果集合超过 CPU 末级缓存的四分之一，并且对象不按分配顺序排列（创建后被替换、打乱或排过序），就会提前预取后面的对象；适用于 .NET 8 及更高版本的 x64 和 Arm64，通过拦截器生效（所以 Unity 里没有）。写出的字节不变；不设置时生成的代码和以前一样。见[散落在内存中的大型集合](/zh/docs/v4/advanced/type-design#large-collections)。
- **Nino.Codegen** 取代 Nino.TypeScript，在每次构建后根据生成器发布的布局，把你的 `[NinoType]` 写成 TypeScript、Go 或 Rust 类型和编解码器：每个 `<NinoCodegen Include="typescript|go|rust" Out="..." />` 项运行一次，项的元数据就是生成器的选项（`Name`；`Names`、`ImportExtension`、`Runtime`；`Package`、`Tags`、`TagNames`；`Serde`、`SerdeNames`、`Strings`、`Maps`），项目级属性为 `NinoCodegenTargetFramework` 和 `NinoCodegenEnabled`。同一个生成器也以 .NET 工具 **Nino.Codegen.Tool** 提供，用于已构建的程序集（`nino-gen --assembly <dll> --lang ts|go|rust --out <dir>`）。Go 结构体带 `nino` 标签以及 `json`/`yaml` 标签（默认 camelCase）；Rust 类型可以派生 serde。未知的选项、重复给出或属于别的语言的选项、选项不接受的值，都是错误 NINOGEN001，命令行和构建里都一样；一次运行写出的文件记在输出目录的 `.nino-gen` 清单里，下次运行会删掉不再写出的文件。引用了 Nino.Codegen 却没声明项的项目会收到警告 NINOGEN004。参见 [TypeScript、Go 与 Rust](/zh/docs/v4/advanced/codegen)。
- **从 Nino.TypeScript 迁移**（直到 rc.7）：改为引用 Nino.Codegen，并声明 `<NinoCodegen Include="typescript" ... />`；`NinoTypeScriptOutput`、`NinoTypeScriptImportExtension` 和 `NinoTypeScriptNames` 变成该项的 `Out`、`ImportExtension` 和 `Names`，`NinoTypeScriptTargetFramework` 和 `NinoTypeScriptEnabled` 变成 `NinoCodegenTargetFramework` 和 `NinoCodegenEnabled`。改之前，`NinoTypeScript*` 属性仍然有效，但会报警告 NINOGEN003。输出除了文件头注释都不变，第一次运行会接管 `.nino-ts` 清单，`NINOTS001` 和 `NINOTS002` 改名为 `NINOGEN001` 和 `NINOGEN002`。参见[从 Nino.TypeScript 迁移](/zh/docs/v4/advanced/typescript#from-ninotypescript)。
- **Go 和 Rust 运行时**：随每次发布以 Nino 的版本号发布（`go get github.com/JasonXuDeveloper/Nino/runtimes/go/v4`、`cargo add nino-serialization`），读写 Nino 的二进制格式，包括深层嵌套、版本容错和键控类型，并用和 .NET 相同的一致性语料测试。Go（模块 `github.com/JasonXuDeveloper/Nino/runtimes/go/v4`）通过 `nino.Marshal` 和 `nino.Unmarshal` 映射带标签的结构体（`nino:"0"`、`nino:"Name"`），并对照类型用 `NinoLayout()` 声明的布局检查；Rust（crate `nino-serialization`，库名 `nino`）提供 `#[derive(NinoRead, NinoWrite)]` 和 `#[nino(...)]` 属性，在编译时对照发布的布局检查，另有可选的 `serde` 功能，读取时的边界检查全是安全代码。两者都从发布的布局里读取类型是否可推迟。TypeScript 运行时也以 `nino-serialization` 发布到 npm：生成代码可以改为从这个包导入运行时（`Runtime="nino-serialization"`），不必再复制 `nino.ts`。参见 [Go](/zh/docs/v4/advanced/go) 和 [Rust](/zh/docs/v4/advanced/rust)。两者都为速度而写：字符串由 x64（AVX-512、AVX2、SSSE3）和 Arm64（NEON）上的 SIMD 内核转换（[SIMD](/zh/docs/v4/simd#go)），向量化不划算的非 ASCII 短字符串，走按字符类别分路径的标量循环（Arm64 上的 Rust）；固定大小值的数组、切片和映射整块读写；Go 用读取器自带的带种子哈希表检查 Set 里的重复元素；生成的代码直接调用每个元素和每个类成员体的代码；Rust 写超出 CPU 缓存、元素含字符串、向量或 box 的列表时，提前预取元素。每次发布都会把它们和 Protocol Buffers、MessagePack 以及各语言常用的序列化库对比计时：见[基准测试：Go、Rust 与 TypeScript](/zh/docs/v4/benchmarks-runtimes)。
- **Go：`EnterBody`、`ExitBody`、`CheckUniqueKeys`、`CheckUniqueValues` 和 `CheckUniqueStrings`**：`Reader.EnterBody`/`ExitBody` 和 `Writer.EnterBody`/`ExitBody` 供直接调用成员体代码的代码原地打开类的成员体，打开的成员体达到 128 层起改用 `ReadClassInto`/`WriteClass`（.NET 在这里推迟）；`nino.CheckUniqueKeys` 检查你自己的循环读出的键值对有没有重复键，`nino.CheckUniqueValues` 对 Set 的元素、`nino.CheckUniqueStrings` 对可为 null 的字符串 Set 做同样的检查，数值按 .NET 的方式比较（任意两个 NaN 相等）。生成的代码都用了它们，所以读类的成员体、字典和 Set 时不再经过函数值调用。见运行时的 [README](https://github.com/JasonXuDeveloper/Nino/tree/main/runtimes/go)。
- **对照本版之前的 `main` 写的 Go 和 Rust 代码**（两个运行时都是 rc.8 新增的）：Go 的键控成员改用 `BeginMember`、`EndMember`、`SkipMember` 和 `KeyedMember` 读写（原为 `BeginEntry`、`EndEntry`、`SkipEntry` 和 `KeyedEntry`；“entry” 仍指字典的键值对 `nino.Entry`），接受函数值作为每个元素读写代码的辅助函数（`ReadSlice`、`WriteSlice`、`ReadMap`、`WriteMap`、`ReadEntries`、`WriteEntries`、`ReadSet`、`WriteSet`、`ReadUnique`、`ReadUniqueEntries`、`ReadFixed`、`WriteFixed`、`WritePrimitivesRaw`、`ReadPrimitivesInto`、`ReadSealedInto`）已删除：改为对每个元素直接调用的循环。Go 的 `Writer.Null` 改名为 `NullLength`（与 .NET 的 `WriteNullLength` 一致），旧方法名 `Utf8`、`Utf8Ptr`、`NullableUtf8`、`Int128` 和 `UInt128` 已删除（改用 `UTF8`、`UTF8Ptr`、`NullableUTF8`、`I128` 和 `U128`）。Rust 的 `NinoWrite::PREFETCH` 改名为 `PREFETCH_BYTES`，生成代码与 derive 调用的辅助函数改为 `sum_fixed_sizes`、`decode_member` 和 `encode_member`（原为 `fixed_size`、`decode_next` 和 `encode_next`），`Reader::read_member`、`read_member_into`、`defer_mark` 和 `defer_trail`（原为 `read_in`、`read_into_in`、`mark` 和 `trail`），`Reader::utf16` 与 `Writer::utf16`（原为 `wide_string`，与 Go 的 `UTF16` 一致），深度常量 `DEPTH_INLINE` 和 `DEPTH_MAX` 改名为 `INLINE_DEPTH` 和 `MAX_DEPTH`（与 Go 的 `InlineDepth`、`MaxDepth` 一致），`nino::sealed_read!()` 和 `nino::sealed_write!()` 在手写的 impl 中写出密封类的 `NinoRead` 与 `NinoWrite` 方法，derive 的 `format` 取 `"positional"`、`"version_tolerant"` 或 `"keyed"`（不再接受 `"plain"` 和 `"tolerant"`）。旧版 nino-gen 生成的代码请重新生成。见 [Go](/zh/docs/v4/advanced/go) 和 [Rust](/zh/docs/v4/advanced/rust)。
- **TypeScript、Go 和 Rust 中的泛型类型**：nino-gen 把泛型 `[NinoType]` 生成为泛型类型（`Box<T>`、`Box[T any]`、`BoxType<T>`），其编解码器由类型参数的编解码器组合而成（`BoxCodec(...)`），`Box<int>` 这样的封闭用法（包括封闭的泛型结构体）作为成员时就是带类型参数的泛型类型。按类型 ID 写出的泛型类型（非密封类、抽象类或接口）现在也会生成，每个封闭类型是一个单独的槽位，并带上它需要的封闭类型；集合中的 `Nullable` 和 `KeyValuePair` 类型实参（`Wrap<int?[]>`）也一样；以其他类型参数包含自身的泛型类型（`Nest<T>` 包含 `Nest<List<T>>`）为 TypeScript 生成，在 Go 和 Rust 中跳过并给出 NINOGEN002。参见[泛型类型](/zh/docs/v4/advanced/codegen#generics)和[按类型 ID 写出的泛型类型](/zh/docs/v4/advanced/codegen#generic-types-behind-a-type-id)。
- **多态槽位和 `object` 槽位中的封闭泛型类型**（例如泛型子类型 `Box<int> : Animal`），适用于 TypeScript、Go 和 Rust：从程序集的元数据里读出它的代码提到的封闭类型，每个都成为它能赋值到的槽位的一个分支，按封闭 .NET 名称的 ID 写出：TypeScript 里是一个子类（`BoxInt32 extends Box<number>`，泛型 `XCodec` 的最后一个可选参数是要构建的类），Go 里是一个分支，Rust 里是一个变体。目标语言接受程序集提到的每个封闭类型，而刚启动的 .NET 进程只接受它注册过或写出过的类型。参见[槽位中的封闭泛型类型](/zh/docs/v4/advanced/codegen#closed-generic-types-in-slots)。
- **TypeScript、Go 和 Rust 中的引用追踪**：声明了 `trackReferences: true` 的类型现在由 nino-gen 生成，并由这三个运行时读写，包括共享引用和循环：TypeScript 和 Go 对同一个对象的每个引用都返回同一个对象；Rust 用 `nino::Shared<T>` 持有追踪的对象，一次读取创建的对象（包括循环）在它们之外的最后一个 `Shared` 被 drop 时（或读取失败时）一起释放，克隆的 `Shared` 会让它们继续存活。引用头指向还没读到的对象，或指向槽位不允许的类型的对象，一律拒绝。参见[引用追踪](/zh/docs/v4/advanced/codegen#reference-tracking)。
- **TypeScript、Go 和 Rust 中的 `[NinoType]` 集合**：派生自集合的 `[NinoType]` 类（带自己成员的 `class Bag : List<int>`）现在也会生成，元素放在成员之前的一个字段里（TypeScript 中是 `$elements`，Go 中是 `Elements`，Rust 中是 `elements`）。参见 [`[NinoType]` 集合](/zh/docs/v4/advanced/codegen#ninotype-collections)。
- TypeScript 运行时的 **`useWasm()`**：在浏览器和 Deno 里，较长的字符串通过嵌在 `nino.ts` 里的一个小型 WebAssembly 模块读写；WebAssembly SIMD、GC 或 JS String Builtins 不可用或被拦截（内容安全策略不含 `'wasm-unsafe-eval'`）时，仍走 JavaScript 路径；`useWasm(false)` 可以关掉它。两种方式写出的字节一致，Node 仍走 `Buffer` 路径。参见[浏览器中的文本](/zh/docs/v4/advanced/typescript#text-in-browsers)。
- Rust 的 **`Maps`**（`--maps indexmap|std`）：`std` 用 `std::collections::HashMap` 和 `HashSet` 代替 `indexmap` 的类型，除了这个 crate 不再有其他依赖；它们按 `HashMap` 的迭代顺序写出。默认仍是 `indexmap`。参见[选项](/zh/docs/v4/advanced/codegen#options)。
- **`NinoTypeLayoutAttribute.Deferrable`** 说明类型的主体嵌套超过 128 层类主体时是否推迟；布局的文本形式用 `deferrable=true|false` 记录它，其他语言的代码生成器直接读取，不必重新推导 .NET 的规则。参见[布局元数据](/zh/docs/v4/evolving-data#layout-metadata)。
- **带非公开成员的泛型 `[NinoType]` 不再需要 `partial`**，只要项目面向 .NET 9 或更高版本（编译定义了 `NET9_0_OR_GREATER`）：生成代码通过泛型格式化器里声明的 `[UnsafeAccessor]` 访问这些成员，和 .NET 8 起非泛型类型的做法一样。从泛型基类继承的成员仍需 `partial`，除非基类的类型实参正好是这个类型自己按顺序排列的前几个类型参数（`class D<T, U> : Base<T>` 可以，`Base<List<T>>` 或 `Base<int>` 不行），或者基类不是泛型；NINO002 和 NINO022 会说明什么时候需要。泛型类型里被 `new` 隐藏的非公开基类成员，在 .NET 9+ 上现在也会序列化，以前会跳过并报 NINO022。参见[私有成员](/zh/docs/v4/defining-types#private-members)和[诊断](/zh/docs/v4/analyzers#the-type)。
- **块格式化器**：大小固定但不满足原始内存条件的 `[NinoType]` 结构体（含值元组或 `KeyValuePair` 成员、`LayoutKind.Auto`、自动属性）的数组、列表和 span 按块读写：生成器让这种结构体的格式化器实现 `INinoBlockFormatter<T>`，它的集合就只做一次边界检查，在 .NET 8+ 上还能用元组的向量重排，不再逐个值处理。字节不变。参见[非托管数据按原始内存拷贝](/zh/docs/v4/performance#raw-memory-for-unmanaged-data)。
- **Unity 中的 Burst 内核**（Unity 包中的 `Nino.Burst`）：安装 `com.unity.burst` 1.8 或更高版本后，元组和结构体的数组与列表、带填充的原始结构体、Latin-1 字符串以及 `[NinoUtf8]` 字符串中的 ASCII 文本改用 AVX2 或 SSSE3（x86 和 x64）或 Arm64 Neon 搬运，不再走 Nino 的 netstandard 标量路径；写出的字节一致，代码不用改；无效 UTF-8 的拒绝方式和没有 Burst 时完全一样。在 x64 Player 中，Burst 的 AVX2 目标用 AVX2 搬运 256 个值及以上的块（每个值最多 16 字节），不支持 AVX2 的 CPU 需要 SSE4 目标才能使用 SSSE3 内核。Armv7 以及没装 Burst 的 IL2CPP 和 Mono Player 仍走标量路径：想要速度就装 Burst。自己的内核可以注册到 `NinoKernels`：一张原生函数指针（`delegate* unmanaged[Cdecl]`）表，Nino 直接调用这些指针。见 [Burst 加速内核](/zh/docs/v4/advanced/unity#burst-kernels)和 [基准测试：Unity 与 Burst](/zh/docs/v4/benchmarks-unity)。
- **Unity WebGL 的 WebAssembly SIMD 内核**（Unity 包中的 `Nino.WebGL`）：用 WebAssembly SIMD 构建的 WebGL Player（Unity 6 的 Target WebAssembly 2023；Unity 2022.3 上在 Additional IL2CPP Arguments 中加入 `--compiler-flags=-msimd128`，需要 Safari 16.4 或更高版本）会注册用 C 写的同一套内核，处理 16 个字符及以上的 Latin-1 字符串和 `[NinoUtf8]` 字符串里的 ASCII 文本，以及 32 个值及以上的元组数组和带填充的原始结构体数组，字节一致。没有 SIMD 的 Player 仍走标量路径。见 [WebGL](/zh/docs/v4/advanced/unity#webgl-kernels)。
- TypeScript 运行时新增 **`deserializeExact`**：和 `deserialize` 一样，但值后面还有字节时抛出 `NinoError`，和 Go 的 `DeserializeExact` 和 Rust 的 `deserialize_exact` 一致。参见[不可信数据](/zh/docs/v4/advanced/codegen#untrusted-data)。
- 只有生成代码使用的类型（`NinoObject`、`NinoDirect`、`NinoUnsafe`、`INinoBodyFormatter<T>` 和 `INinoBlockFormatter<T>` 等格式化器接口、子类型注册表……）移到了命名空间 `Nino.Core.CompilerServices`。生成代码不用改；手写代码直接用到它们时，要加上 `using Nino.Core.CompilerServices;`。`INinoBodyFormatter<T>.Traits` 的常量类改名为 `NinoBodyTraits`（原名 `NinoBody`，与 Nino.AspNetCore 的 `NinoBody<T>` 同名）。

### 性能 [#performance-3]

- **含字符串成员的类**：反序列化新实例时，读取器不再留在内存里；单个字符的 Latin-1 字符串改为共享，不再分配：SimpleClass 和池化类型的新实例读取快 13-18%，版本容错类快 2.3-4.6%（GitHub 的 AMD EPYC 7763 和 Neoverse-N2 runner）。
- **已有实例中未变的 UTF-8 文本**：读入已有对象（池化或 `ref` 目标）时，如果字节没变，就保留对象里原有的较长 [`[NinoUtf8]`](/zh/docs/v4/defining-types#string-encoding) 文本：在同样的 runner 上，池化基准快 17-22%。参见[反序列化到已有实例](/zh/docs/v4/pooling#deserializing-into-existing-instances)。
- **`CultureInfo` 和 `TimeZoneInfo`**：在 .NET 8 及以上，读过的区域性名称直接查表，不再每次问 ICU 运行时是否自带这个区域性（只保存接受过的名称，不区分大小写，最多 4,096 个），所以 `CultureInfo` 的反序列化耗时是 rc.7 的 0.43-0.57 倍（GitHub 的 x64 和 Arm64 runner）；系统 `TimeZoneInfo` 内联检查它为空的调整规则，反序列化耗时是 rc.7 的 0.89-0.99 倍。参见[其他内置类型](/zh/docs/v4/types#other-built-in-types)。
- **已有实例中未变的字符串**：在 .NET 8 及以上，读入已有对象的 63 个字符以内的 Latin-1 字符串，在读它的同一次调用里就和对象原有的字符串比较，原始类型键的 `Dictionary` 里没变的字符串也不再重新存入：把 1,000,000 个打乱的条目读入已有对象，耗时是 rc.7 的 0.56-0.95 倍；没变的字符串成员也不再写回对象（带方法体的 setter 仍会调用）：池化基准的反序列化耗时是 rc.7 的 0.86-0.97 倍（GitHub 的 Neoverse-N2、Xeon 6975P 和 8573C runner）。参见[反序列化到已有实例](/zh/docs/v4/pooling#deserializing-into-existing-instances)。
- **有序、不可变和字符串键的集合**：`SortedList<int, int>` 在 Arm64（Neoverse-N2）上反序列化快 21%，`SortedDictionary` 快 3%，`ImmutableDictionary`、`ImmutableHashSet` 和 `SortedSet` 在 x64 和 Arm64 上最多快 3%；`Dictionary<string, string>` 在 x64（AMD EPYC 7763）上反序列化快 9%，Arm64 上快 3%。
- **x64 上的 `ConcurrentDictionary`**：读取时用快速取模代替两次除法，确定每个键的桶和锁：`ConcurrentDictionary<int, int>` 在 GitHub 的 AMD EPYC 7763 runner 上反序列化快 18-23%；EPYC 9V45 和 9V74（除法本来就快）以及 Arm64 持平，Arm64 仍用除法。
- **泛型类型和其他程序集的类型**：泛型 `[NinoType]` 和在其他程序集里生成的 `[NinoType]`，它们的成员在优化后的 .NET 代码里直接调用，不再经过虚调用：持有非托管元组的泛型类型在 GitHub 的 AMD EPYC 7763、9V45、9V74 和 Neoverse-N2 runner 上反序列化耗时为原来的 0.86-0.94 倍，在 7763、9V74 和 Neoverse-N2 上序列化快 2-4%。参见[泛型类型](/zh/docs/v4/defining-types#generic-types)。
- **持有自身的集合**：通过集合持有自身、层与层之间没有 `[NinoType]` 的类（`class Tree : List<Tree>`、`class Map : Dictionary<string, Map>`），改由生成器为它写的一个结构体读写：这个结构体负责计入本层深度并直接调用下一层，不再每层都经过运行时格式化器做一次虚调用：由 5,461 个这种列表组成的树在 GitHub 的 AMD EPYC 7763、9V45、9V74、Intel Xeon Platinum 8573C 和 Neoverse-N2 runner 上序列化耗时为原来的 0.35-0.42 倍，反序列化为 0.52-0.58 倍。深度限制和字节都不变。参见[深层对象图](/zh/docs/v4/reference-tracking#deep-object-graphs)。
- **Unity Player 中不再按值分配**：在 IL2CPP 构建里，没有 Burst 内核处理时，元组和固定大小结构体的数组与列表不再为每个元素分配内存，`NinoSerializer.Serialize` 也不再在每次调用写之前分配：netstandard 版本里每个格式化器对象只创建一次。参见 [Unity](/zh/docs/v4/advanced/unity)。
- **Unity、Mono 和 Native AOT 上的泛型类型**：泛型 `[NinoType]` 的格式化器把类型实参的格式化器作为自己的类型参数，类型为 `T` 的成员在所有运行时上都直接调用；IL2CPP、Mono 和 Native AOT 以前对每个值都要做一次虚调用。在 .NET 上，泛型多态类型的数组在 GitHub 的 x64 和 Arm64 runner 上读写持平或更快（在 AMD EPYC 9V74 上序列化最多快 11%）。参见[泛型类型](/zh/docs/v4/defining-types#generic-types)。
- **数组中带填充的结构体和元组**：含 `bool` 且带填充的固定大小值（例如由 `Vector3`、`float` 和 `bool` 组成的 `Waypoint`）组成的数组和列表，改为一次检查八个 bool，不再逐个检查，在 GitHub 的 AMD EPYC 7763、9V45、9V74、Intel Xeon Platinum 和 Neoverse-N2 runner 上反序列化用时为原来的 0.80-0.92 倍（EPYC 9V74 上 1,000 个 `Waypoint`：1,522 降到 1,210 ns）。在 Arm64 上，超过 8 字节的这类值改为按向量通道组写出，不再逐个写：1,000 个 `Waypoint` 在 Neoverse-N2 上序列化快 3.4 倍（1,438 降到 427 ns）；通道组的加载再改成按 16 字节边界对齐后，用时又降到原来的 0.76 倍（430 降到 325 ns，比 MemoryPack 直接拷贝内存还快）。在这种写法更快的 AVX-512 VBMI CPU 上（AMD Zen 4 和 5、Intel Sapphire Rapids 及之后；Ice Lake 仍用通道组），超过 16 字节的值改为用一条双向量置换一次写出四个或更多：Xeon Platinum 8573C 上用时为原来的 0.65 倍（386 降到 252 ns），EPYC 9V45 上为 0.76 倍（210 降到 159 ns）。写出的字节不变。参见[非托管数据按原始内存拷贝](/zh/docs/v4/performance#raw-memory-for-unmanaged-data)。
- **原始值的大数组**：在 32 KB 到 1 MB 之间，如果某个厂商的 CPU 上 32 字节向量比 `memmove` 快，Nino 就改用向量拷贝：10,000 个 `Vector4` 在 Intel Xeon Platinum 8370C 上序列化快 9.5%（3.51 降到 3.18 µs），在 AMD EPYC 9V45 和 9V74 上反序列化快 4.5-7.7%（96.6 降到 92.2 µs，111.0 降到 102.4 µs）。
- **把带填充的结构体和元组读入新数组**：读带填充的固定大小值时，现在会写满每个值的每个字节（填充写 0），所以 6 KB 起的新数组分配时不用先清零；超过 16 字节的值改为一次读八个、写满整个向量，同一遍里顺带检查其中的 bool（AVX-512）：1,000 个 `Waypoint` 在 GitHub 的 AMD EPYC 7763、9V74、Intel Xeon Platinum 8370C 和 Neoverse-N2 runner 上反序列化用时为原来的 0.77 到 0.85 倍（EPYC 9V74：1,203 降到 922 ns），1,000 个 `(int, long)` 的列表为 0.97 到 0.99 倍。在不支持 AVX-512 的 x64 上，向量通道组读这些值的同一遍里检查 bool：在 GitHub 的 AMD EPYC 7763 上，1,000 个 `Waypoint` 反序列化用时为原来的 0.92 倍（1,360 降到 1,240 ns）。不可信模式下，这类值逐字段读取，数组仍和以前一样先清零。参见[非托管数据按原始内存拷贝](/zh/docs/v4/performance#raw-memory-for-unmanaged-data)。
- **Intel Ice Lake 上带填充的原始结构体**：在 Ice Lake 上，带填充的非托管结构体数组改用 32 字节向量（而不是 64 字节向量）屏蔽填充，因为 64 字节向量在那里更慢：在 GitHub 的 Xeon Platinum 8370C 上，1,000 个带一个填充字节的 8 字节结构体序列化从 116 ns 降到 83 ns（MemoryPack 为 88 ns）。Ice Lake 按 CPU 型号识别，所以其他 Intel CPU 都保留 64 字节内核，包括在云虚拟机里不报告 AVX512-FP16 的 Xeon Platinum 8573C。
- **Intel Ice Lake 上的元组和字典**：在 Ice Lake 上，带填充、按整 4 字节字搬运的固定大小值（例如 `(int, long)`、`Dictionary<int, int>` 的条目）组成的列表和数组，改为从缓存行边界开始做向量加载再写出，因为在那里跨两条缓存行的 64 字节加载代价约为两倍：在 GitHub 的 Xeon Platinum 8370C 上，1,000 个 `(int, long)` 序列化用时为原来的 0.92 倍（235 降到 221 ns），1,000 个条目的 `Dictionary<int, int>` 为 0.81 倍（250 降到 200 ns）。其他 CPU 不受影响，写出的字节也不变。
- **Linux 上 Intel Ice Lake 的原始内存块**：在 Ice Lake 上，2 到 32 KB 的原始内存块（无填充的结构体、`KeyValuePair<int, int>`、基元类型）改用 C 库的 `rep movsb` 拷贝，因为跨缓存行的 64 字节加载让 Nino 自己的向量拷贝在那里反而更慢：在 GitHub 的 Xeon Platinum 8370C 上，1,000 个 `KeyValuePair<int, int>` 序列化用时为原来的 0.85 倍（151 降到 128 ns），1,000 个元素的 `Queue<int>` 为 0.78 倍（94 降到 74 ns）。其他 CPU 和操作系统不受影响。
- **非托管值的 `HashSet` 和 `Dictionary`**：用 SIMD 重排指令从集合自己的 entries 里一次取出多个键和值，不再逐个 entry 写出：1,000 个元素的 `HashSet<int>` 在 GitHub 的 AMD EPYC 7763、9V45、9V74、Intel Xeon 和 Neoverse-N2 runner 上序列化耗时降到原来的 0.34-0.49 倍（EPYC 7763 上 327 降到 141 ns，Neoverse-N2 上 372 降到 126 ns），1,000 对的 `Dictionary<int, int>` 降到 0.29-0.56 倍（EPYC 7763 上 430 降到 212 ns，Xeon Platinum 8573C 上 369 降到 107 ns），含有这类集合的类也跟着变快（多态类数组基准降到 0.69-0.84 倍）。字节不变。参见[非托管数据按原始内存拷贝](/zh/docs/v4/performance#raw-memory-for-unmanaged-data)。
- **不可信模式**：[`NinoSettings.Untrusted`](/zh/docs/v4/security#untrusted-mode) 检查原始结构体数组和列表里的值（`bool`、`DateTime`、`decimal`、`DateOnly`、`TimeOnly`）时，不再每个值一次分支，在 .NET 8+ 上还用 SIMD 检查：由 1,000 个含一个 `DateTime` 和一个 `bool` 的结构体组成的列表，在同样的 runner 上反序列化耗时降到原来的 0.47-0.69 倍（EPYC 7763 上 5.55 降到 2.76 µs，Neoverse-N2 上 6.13 降到 2.86 µs）。
- **Unity 和 .NET Framework 上已有实例中的字符串**：netstandard 版本拿 Latin-1 或 ASCII 字符串和实例里已有的字符串比较时（文本没变就保留原字符串），一次比八个字节，不再逐个字符比较。GitHub runner 不覆盖这些平台，所以没有数字。参见[反序列化到已有实例](/zh/docs/v4/pooling#deserializing-into-existing-instances)。
- **32 位 .NET、.NET Framework 和 Mono**：在 32 位 .NET（x86、WebAssembly 和 Arm32）和 32 位 .NET Framework 上，8 字节及以上的值（`long`、`double`、`Guid`、`decimal`、原始结构体）改用一次非对齐加载和存储读写，不超过 64 字节的块（大多数字符串）用和 64 位运行时相同的重叠搬运拷贝，不再逐字节拷贝或调用 `memmove`；32 位 Arm 上的 Mono 和 IL2CPP 仍逐字节拷贝，因为那里这种加载可能出错。在 .NET Framework（以及 .NET Core 3.0 到 7）上，JIT 能加速 `Vector<T>` 时，较长的 Latin-1 字符串就用它收窄和展宽。在装了 System.Numerics.Vectors 包的 Mono 上，带填充的原始结构体用 `Vector<byte>`（SSE）清零填充，加载和存储的写法让 Mono 编译成向量搬运，而不是 `memcpy` 调用；Unity 的 `Vector<T>` 即使报告已加速，Mono 也从不加速它，所以保留每次 8 字节的路径。Mono 上的 `Vector.Narrow` 和 `Vector.Widen` 是软件实现，所以在 Mono 上字符串从不用 `Vector<T>` 收窄或展宽。字节不变；GitHub 的 runner 不覆盖这些平台，所以没有数字。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **更短的数据也走 Unity 内核**：Burst 内核改用 C# 函数指针调用，不再用委托；元组和结构体的数组与列表从 2 个值起（原来是 16 个）、Latin-1 字符串从 16 个字符起（原来是 32 个）就用内核，这正是 IL2CPP Player 里内核开始变快的长度；带填充的原始结构体仍从 16 个起，每次调用的开销降下来后，那里快了 1.06 到 1.09 倍。把 2 到 12 个小元组写入缓冲区的耗时减少到 1/1.2 到 1/3.4，16 到 31 个字符的字符串写入快 1.2 到 1.7 倍、读取快 1.2 到 1.6 倍（IL2CPP，GitHub 的 Linux x64 runner，Unity 2022.3 和 6000.3）。带 SIMD 的 WebGL Player 读写 1000 个字符的 Latin-1 字符串快 2.1 到 6 倍，写入 1000 个值的带填充数组快 2.3 到 4.2 倍（无头 Chrome）。见 [Burst 加速内核](/zh/docs/v4/advanced/unity#burst-kernels)。
- **Unity 中的 `[NinoUtf8]` 字符串**：装了 Burst 后，`[NinoUtf8]` 字符串里的 ASCII 文本一次收窄、展宽 16 个字符。写入缓冲区时，16 个字符起快 1.5 到 1.6 倍，1000 个字符时快 1.9 到 2.1 倍；读取时 16 个字符起快 1.06 到 1.24 倍，1000 个字符起快 1.2 到 1.25 倍；夹带少量重音字母的 ASCII 文本快 1.08 到 1.25 倍，CJK 文本持平（IL2CPP，GitHub 的 Linux x64 runner，Unity 2022.3 和 6000.3）。启用 SIMD 的 WebGL Player 写入 16 个字符快 1.2 倍、1000 个字符快 1.8 到 1.9 倍，读取分别快 1.2 到 1.4 倍和 1.4 到 1.7 倍（无头 Chrome）。参见 [Burst 加速内核](/zh/docs/v4/advanced/unity#burst-kernels)。
- **AVX2 CPU 上的 Unity**：x64 Player 读小元组和结构体（每个最多 16 字节、256 个值及以上）的数组，最高比 SSSE3 内核快 3.5 倍，写最高快 1.3 倍（IL2CPP，Burst AVX2 目标）。参见 [Burst 加速内核](/zh/docs/v4/advanced/unity#burst-kernels)。
- **浏览器中的 TypeScript**：有了 WebAssembly 文本模块，在 GitHub 的 x64 和 Arm64 runner 上的 Chromium 里，以文本为主的文章读取快 27-31%，ASCII、Latin-1 和其他字符混合的字符串列表在 x64 上写入快约 12%；Node 不受影响。参见[浏览器中的文本](/zh/docs/v4/advanced/typescript#text-in-browsers)。
- **Node 中的 TypeScript**：48 个字符及以下的字符串，写入时不再经过正则表达式和原生调用：序列化 1,000 个 ASCII 字符串从 0.060-0.065 ms 降到 0.025-0.028 ms（GitHub 的 x64 和 Arm64 runner），1,000 个混合字符串从 0.090 ms 降到 0.056-0.059 ms，Lookup、OrderBook 和 Player 用例分别从 0.74-0.78、0.76-0.79 和 0.31-0.34 ms 降到 0.39、0.43 和 0.26 ms。浏览器不受影响。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。
- **Node 中的 TypeScript，短中文和俄文文本**：1,000 个 4 到 16 个字符的这类字符串，序列化耗时减少 69-73%（x64 上从 0.066 ms 降到 0.018 ms，Arm64 上从 0.108 ms 降到 0.034 ms），反序列化快 46-47%；24 到 40 个字符的中文字符串读写快 5-7%（GitHub runner）。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。
- **TypeScript 的字符串读取**：TypeScript 运行时在 Node 中读取字符串快 16-25%，在 Chromium 中读取混合文本快 13-18%，写入字符串快 3-15%，生成的代码在 Node 中写入映射快 8-12%（GitHub 的 AMD EPYC 7763、9V45 和 9V74 以及 Neoverse-N2 runner）。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。

### 修复 [#fixes-5]

- **IL2CPP 上的值元组列表**：格式化器在运行时构建的值元组或 `KeyValuePair` 的 `List<T>`，在 Unity 的 IL2CPP Player 里和其他运行时一样逐项写出。IL2CPP 不保留泛型参数上的特性，所以这种列表以前照搬了 IL2CPP 里各项的内存，其他运行时都读不了。参见[可移植的设计](/zh/docs/v4/platforms#portable-by-design)。
- **IL2CPP 上你自己的格式化器**：用 `[assembly: NinoFormatter]` 注册、类型参数标了 `[NinoRaw]`、`[NinoCreated]` 或 `unmanaged` 的格式化器，在 Unity 的 IL2CPP Player 里运行时只绑定满足条件的类型，和其他运行时一致。IL2CPP 不保留泛型参数上的特性，以前 `[NinoRaw]` 格式化器会绑定到值元组，写出 IL2CPP 的内存；现在你的程序集生成的注册表会在启动时登记这些标记。参见[自定义格式化器](/zh/docs/v4/custom-formatters)。
- **类型参数没有格式化器时报 NINO007**：成员类型用 Nino 写不了的类型封闭了泛型 `[NinoType]` 时（`Box<Action>`，也包括套在 `List<Box<Action>>`、`Box<Action>[]` 或其他泛型里），现在会报告：这样的成员仍会写出，但写它的任何值都会抛异常。没有成员用到的类型参数不报，字节不变。参见[诊断](/zh/docs/v4/analyzers#diagnostics)。
- **不可信数据**：把无效数据读入已有值（`Deserialize(data, ref value)`，或被复用对象的成员）时，如果数据在数组分配之后才被拒绝，这个值不会再留着一个装满未初始化内存的新数组：原始 `T?` 的数组和列表、`bool` 列表、按块读取且带 `bool` 的结构体集合（如 `(int, bool)[]`），以及 `NinoSettings.Untrusted` 检查的值。读取没走到的部分保持原样或为默认值。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- **不可信数据**：读到 Nino 从不会写出的数据时，任何模式下都抛出 `NinoDataException`：不是 0 或 1 的 `bool` 或存在字节、条目里的字节比值多的键控成员，以及偏移或条目和所在区域对不上的版本容错推迟段。原始结构体里的 bool 字段仍原样拷贝，除非设置了 `NinoSettings.Untrusted`。参见[会被拒绝的数据](/zh/docs/v4/security#what-is-rejected)。
- **不可信数据**：带 `bool` 项的值元组和 `KeyValuePair` 的数组和列表，不管不是 0 或 1 的 bool 字节在哪个位置、在什么 CPU 上，一律拒绝；.NET 8+ 的向量读取路径（AVX-512、AVX2、SSSE3、Arm64、WebAssembly）以前会因指令集和位置不同而放过其中一部分。参见[会被拒绝的数据](/zh/docs/v4/security#what-is-rejected)。
- **不可信数据**：包含自身的集合类型（`class Tree : List<Tree>`）嵌套超过深度限制的数据，现在抛出 `NinoDataException`，不再栈溢出；运行时为这类类型构建格式化器时也不再栈溢出。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- **不可信数据**：再次读到同一个未知类型 ID（损坏、恶意或过期的数据）时，不再每次都搜一遍所有注册表和已加载的程序集；声明这个 ID 的程序集一加载或注册，就能找到它。参见[其他程序集里的子类型](/zh/docs/v4/polymorphism#subtypes-in-other-assemblies)。
- **不可信数据**：在 .NET 8 及更高版本上，从数据里读出的 `CultureInfo` 不会再让进程内存无限增长（.NET 在进程整个生命周期里保留它创建的每个区域性，而 Nino 以前接受任何格式正确的名称）：只有运行时自带的区域性才能读回，包括 `zh-CN` 这样的别名。自定义区域性和带 `-u-`、`-x-` 扩展的名称现在算无效数据（`NinoDataException`），固定（invariant）全球化模式下只有固定区域性能读回；.NET Framework、Mono 和 Unity 不变。参见[其他内置类型](/zh/docs/v4/types#other-built-in-types)。
- 序列化通过包含自身的结构体或集合（或包含自己的集合）嵌套超过 `NinoSettings.MaxDepth` 的对象图时，抛出 `InvalidOperationException`，不再栈溢出。参见[深层对象图](/zh/docs/v4/reference-tracking#deep-object-graphs)。
- 写出的对象图如果在记录（或其他 Nino 不能推迟的类）外面套着包含自身的结构体，两者合计超过 `NinoSettings.MaxDepth` 时抛出 `InvalidOperationException`，不再写出连自己的读取方都会拒绝的数据。参见[深层对象图](/zh/docs/v4/reference-tracking#deep-object-graphs)。
- 八项及以上的值元组，现在可以作为泛型 `[NinoType]` 的类型实参，即使生成代码从没见过这个封闭形式；Nino.Core 以前会抛出“no formatter”。写出的字节和生成代码为这种元组写的一致。参见[可序列化的类型](/zh/docs/v4/types#serializable-types)。
- 读入已有的、带自定义比较器的 `Dictionary<TKey, TValue>` 时，原始键现在用这个比较器求哈希；之前查找可能找不到这些键。参见[集合类型](/zh/docs/v4/types#collection-types)。
- 用 `NinoRegistry.Remove` 移除的程序集（或其可回收 `AssemblyLoadContext` 卸载时移除的程序集），不会再因为之后读到未知类型 ID 而重新注册、导致卸载不掉；另一个程序集卸载后紧接着加载的程序集，按类型 ID 读取时能找到。参见[卸载程序集](/zh/docs/v4/platforms#unloading-assemblies)。
- 用 Nino.AspNetCore 时，可回收 `AssemblyLoadContext` 里的类型经过 MVC 格式化器后，上下文仍能卸载。参见 [ASP.NET Core](/zh/docs/v4/advanced/aspnetcore)。
- 用 Nino.AspNetCore 时，只有请求体不是有效 Nino 数据（`NinoDataException`）才返回 400 Bad Request；服务器端读取时出的错（比如 `[NinoFactory]` 返回 null）按服务器错误抛出，不再算成客户端的错。参见 [ASP.NET Core](/zh/docs/v4/advanced/aspnetcore#mvc)。
- 在 NativeAOT 下，不是 `[NinoType]` 的泛型非托管结构体按原始值序列化，和 JIT、生成代码一致，不再因为找不到格式化器而失败。
- 在 x64 的 NativeAOT 下，内存里的字节排布和写出时不同的值元组、`KeyValuePair` 和固定大小结构体（例如 `(int, long)`），它们的数组和列表在支持 SSSE3 的 CPU 上用 SSSE3 重排指令（`pshufb`）搬运；之前走的是重排的软件实现，比 JIT 下慢很多倍。参见[裁剪与 Native AOT](/zh/docs/v4/platforms#trimming-and-native-aot)。
- 对值类型调用 `NinoSerializer.SerializeBoxed(null, type)` 抛出 `ArgumentNullException`，不再是 `NullReferenceException`。
- 在大端主机上，通过顶层调用序列化原始值、原始值数组和固定大小类型时，和其他类型一样直接拒绝，不再按主机字节序写出。
- Nino.Core 之外不能再继承 `NinoSubtypeHandler`，也不能调用 `NinoPolymorphic<TBase>.Register(NinoSubtypeHandler)`：只有生成的注册代码会添加多态子类型。
- 从 alpha 键数量为 -1 的数据反序列化 Unity `Gradient` 时，抛出 `NinoDataException`，不再是 `OverflowException`。参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)。
- 从颜色键或 alpha 键超过 8 个（Unity 的上限）的数据反序列化 Unity `Gradient` 时，在分配之前抛出 `NinoDataException`，不再是 Unity 的 setter 抛出的异常。参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)。
- Unity 的 `RectOffset` 遇到不是 0 或 1 的存在字节时抛出 `NinoDataException`，与其他所有可空值一致，不再当作存在读取。参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)。
- 项目里两个 `[NinoType]` 的名称只有大小写不同（`RawS` 和 `Raws`）时，又能正常生成代码了；之前生成器报 CS8785 失败，什么都不生成。
- 通过 `using` 别名或 `using static` 写的顶层 `NinoSerializer`/`NinoDeserializer` 调用也会被拦截，格式化器也会为 AOT 注册，和写明类名的调用一样。
- 在 Native AOT 下，如果程序只在 `NinoSerializer.GetFixedSize<T>()` 里、或作为 `SerializeBoxed`、`DeserializeBoxed`、`IsSupported` 的 `typeof` 参数提到某个封闭泛型 `[NinoType]`，它现在和 JIT 下一样能用：生成器也会注册这些类型；以前只注册 `Serialize` 和 `Deserialize` 的类型参数，这些调用会抛出“no formatter”。参见[裁剪与 Native AOT](/zh/docs/v4/platforms#trimming-and-native-aot)。
- 在 IDE 里修改 `[assembly: NinoFormatter(...)]` 注册后，用到它的生成格式化器会跟着更新，不再一直保持旧版本直到下次重新构建。参见[自定义格式化器](/zh/docs/v4/custom-formatters)。
- 封闭泛型类型的槽位里放的封闭泛型子类型（`Shelf<string>` 成员里的 `ListShelf<string>`），现在在从没写出或提到它的进程里也能读，不再报子类型未注册。参见[泛型类型](/zh/docs/v4/defining-types#generic-types)。
- 读到元素个数标为 null 的 `[NinoType]` 集合时，抛出 `NinoDataException`，不再是 `NullReferenceException`。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- 针对 Nino.Core 的 netstandard 构建编译、并向 `NinoKernels` 注册内核的库（比如 Unity 包的 Burst 内核），现在在 .NET 8 及更高版本上也能加载，以前那里缺这个类型；.NET 8 及更高版本的构建仍用自己的向量路径，从不调用这些内核。参见[SIMD](/zh/docs/v4/simd#unity)。
- 源生成器不再在内存里留着已关闭项目的缓存模型和语法树，这曾让 IDE（和构建服务器）用久了内存不断上涨。
- `Half`、`Rune`、`DateOnly`、`TimeOnly`、`Index`、`Range`、`Complex`、`Int128`、`UInt128` 以及可空值数组的已发布布局（`NinoTypeLayoutAttribute`）现在反映 Nino 实际写出的字节，而不是引用程序集里的占位字段。参见[布局元数据](/zh/docs/v4/evolving-data#layout-metadata)。
- **TypeScript**：嵌套超过 128 层类主体的值（链表、树），读写和 .NET 逐字节一致；嵌套过深或伪造的数据抛出 `NinoError`，不再栈溢出；字节不是合法 UTF-8 的 `[NinoUtf8]` 字符串抛出 `NinoError`，不再是 `TypeError`。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。
- **TypeScript**：运行时拒绝 .NET 拒绝的数据：映射或 Set 里重复的键或元素（数字、字符串、`bigint`、布尔值或 null）、值读完后条目里还剩字节的键控成员，以及格式错误的推迟主体段，都抛出 `NinoError`。参见[不可信数据](/zh/docs/v4/advanced/typescript#untrusted-data)。
- **TypeScript**：没有成员的 `[NinoType]` 的生成代码在开启 `noUnusedParameters` 时也能编译（空的读写主体把参数命名为 `_r`、`_w` 和 `_v`）。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。
- **TypeScript 里的哈希洪泛**：V8 给 `Map` 和 `Set` 的 number 和 `bigint` 键求哈希时不加种子，所以数据可以专挑落进同一个桶的 `HashSet<int>` 元素或 `Dictionary<long, T>` 键，让读取变成平方级（在 Node 里，8,000 个这样的整数要多花 40 倍时间）。现在键超过 128 个的这类 map 或 set，只要某个键在 V8 哈希表里所在的桶已有超过 100 个键，就抛出 `NinoError`，和 .NET 的 [`MaxHashCollisions`](/zh/docs/v4/security#hash-flooding) 一致。这个检查对 V8（Node、Chromium、Deno）是精确的；Safari、Bun 和 Firefox 各有自己的数值哈希。字符串键也要过这道检查：V8 把数组索引形式的字符串（`"0"` 到 `"4294967294"`）按数值求哈希，所以 `"0"`、`"2048"`、`"4096"` 这样的 4,000 个键，比其他数字字符串多花 117 倍时间。重新生成 TypeScript 代码即可启用。
- **TypeScript**：运行时拒绝 tick 数超过 `DateTime.MaxValue` 的 `DateTime`，以及小数位数超过 28 或标志位有其他位被置位的 `decimal`，抛出 `NinoError`，和 Go、Rust 运行时一致，不再读出一个写不回去的值。参见[不可信数据](/zh/docs/v4/advanced/codegen#untrusted-data)。
- **Go 和 Rust**：夏令时切换时有一小时会重复，.NET 为这一小时里的本地时间写出的 `DateTime`（kind 3）现在能读出来并原样写回，不再报无效数据（Go 以前还拒绝写出它）；Rust 的 `kind()` 和 .NET 一样返回 `Local`，新增的 `is_ambiguous_local()` 能把它区分出来。参见 [Go](/zh/docs/v4/advanced/go#values) 和 [Rust](/zh/docs/v4/advanced/rust#values)。
- **Rust**：derive 不再把带 `#[nino(utf8)]` 成员、且字符串短于 4 字节的结构体列表当成长度无效而拒绝；以前这种成员按至少 4 字节算，实际应是 1 字节。参见 [Rust](/zh/docs/v4/advanced/rust)。
- **Go**：在支持 AVX-512 的 Intel Mac（macOS 12.2 及更高版本）上，字符串读写现在用 AVX-512 内核；之前用的是 AVX2 内核，因为 macOS 要等线程第一次用到 AVX-512 寄存器时才启用它们。参见[SIMD](/zh/docs/v4/simd#go)。
- **Go 里浮点数的 Set 元素和字典键**：两个 NaN 元素（或键）现在算重复，和 .NET 一致；以前 Go 运行时把它们当成不同的值，接受了 .NET 会拒绝的数据。`-0` 和 `0` 本来就相等。见 [Go](/zh/docs/v4/advanced/go)。

## 4.0.0-rc.7

### 新功能 [#new-5]

- **Unity 中的代码修复**：Unity 包现在带有 `Nino.Generator.CodeFixes.dll`，Rider 和 Visual Studio 里，Nino 分析器的警告有和 NuGet 项目一样的快速修复（加上 `partial`、无参构造函数、对象池钩子等）。参见[分析器](/zh/docs/v4/analyzers)。

### 性能 [#performance-2]

- **经泛型基类型读写的子类型**：通过泛型基类型（`abstract class Box<T>`、`IRepository<T>`、泛型类）读写的值，和通过非泛型基类型一样用生成的分派，覆盖每个封闭基类型在它所在程序集里声明的子类型，类型实参可以是任何类型（基元类型、元组、密封类或非密封类），不再每个值都做一次注册表查找和一次虚调用。参见[分派](/zh/docs/v4/polymorphism#dispatch)。
- **Arm64 上的小元组**：小的带填充元组组成的数组和列表读写更快：1,000 个 `(byte, int)` 反序列化从 1,123 ns 降到 805 ns，序列化从 422 ns 降到 122 ns；1,000 个 `(short, int)` 分别从 1,103 ns 降到 801 ns、从 200 ns 降到 124 ns；基准测试的 `TupleList` 用例分别从 1,815 ns 降到 1,415 ns、从 375 ns 降到 219 ns（GitHub 的 Arm64 机器）。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **集合直接写入大小正好的数组**：对元素固定大小的数组和列表（非托管值、`DateTimeOffset`、元组和原始结构体）调用 `NinoSerializer.Serialize(value)` 时，直接分配大小正好的数组写进去，不再先写进池化的临时缓冲区再拷出来。参见[内存分配](/zh/docs/v4/performance#allocation)。
- **不支持 AVX-512 时，带填充的元组和键值对更快**：值元组、`KeyValuePair` 以及其他带填充的原始值组成的数组和列表，写入和读取都按组处理，向量的每个 16 字节通道由最多两个 16 字节窗口经通道内重排拼成（AVX2、SSSE3、Arm64 `TBL`、.NET 10 上的 WebAssembly SIMD）。在 GitHub 的 x64 runner（EPYC 7763，AVX2）上，1,000 个 `(int, long)` 的列表序列化从 380 ns 降到 194 ns。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **带填充的元组在任何缓冲区对齐下序列化速度一致**：元组、`KeyValuePair` 以及其他带填充的结构体组成的数组和列表，按对齐到输出的向量写；第一个对齐向量之前和最后一个之后的值原本逐个写，所以耗时取决于缓冲区的起始位置。现在两端各多写一整组值，耗时就和起始位置无关了。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **Intel CPU 上新建的元组和 `DateTimeOffset` 数组读取更快**：在 Intel x64 CPU 上，读取时靠向量重排或逐个写值填满的数组和列表，改为分配已清零的内存，这样每次写入不用先把所在的缓存行从内存读进来。靠一次块拷贝填满的数组，以及 Arm64 和 AMD CPU 上 6 KB 及以上的所有数组，仍不清零分配，在那里这样一样快或更快。
- **不支持 AVX-512 时的 5 字节值**：`(byte, int)` 等 5 字节值组成的数组和列表，在 AVX2（每个 32 字节向量 6 个值）和 SSSE3（每 4 个 16 字节向量 12 个值）上按组搬运，不再逐个处理。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **Arm64 上带填充的结构体**：带填充的结构体（元组、`KeyValuePair`）组成的数组和列表，用成对的加载和存储（`ldp`/`stp`）每步拷贝 32 字节，和 C 库的 `memcpy` 一样，不再每次只处理一个 16 字节向量。
- **`HashSet<T>` 和 `Dictionary<TKey, TValue>`**：原始值的这两种集合没删过条目时，用一个循环直接从内部条目数组写出，不再经过枚举器对每个元素的检查。读取时新建的集合（默认比较器）直接写入条目和桶，结果和 `Add` 一样，但不再对每个元素检查比较器、空闲链表和容量；数据里同一个键出现两次仍会抛异常。在 GitHub 的 x64 runner（EPYC 7763）上，1,000 个元素的 `HashSet<int>` 序列化从 1.06 µs 降到 0.33 µs，反序列化从 6.1 µs 降到 2.6 µs；在 Arm64 runner（Neoverse-N2）上分别从 1.28 µs 降到 0.37 µs、从 5.3 µs 降到 2.8 µs。启动时会用公开 API 校验一个这样填充的集合，覆盖 .NET（64 位和 32 位）、.NET Framework、Mono 和 Unity 的内部布局和哈希方式；其他运行时仍用枚举器和 `Add`（供 .NET Framework 使用的 netstandard2.0 构建只对字典这样填充）。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **拷贝不再调用 `memmove`**：8 到 32 KB 的块拷贝改用 Nino 的向量循环，不再调用 `memmove`，后者在部分 AMD EPYC CPU 上慢好几倍。在支持 AVX2 但不用 AVX-512 的 x64 CPU（AMD Zen 2 和 3、大多数 Intel 桌面 CPU）上，对齐的 32 字节存储循环一直用到 1 MB，在这个范围内比 C 库的拷贝快；更大的块，以及只有 SSE 和 32 位 CPU 上 16 KB 起的块，仍用 `memmove`。
- **AMD CPU 上的新数组**：读取时用一次块拷贝填充原始值新数组，在 AMD x64 CPU 上 6 KB 及以上也改用 Nino 的向量循环：即使是刚分配的内存，`memmove`（rep movsb）在这些 CPU 上也比向量存储慢；Intel CPU 在这个范围仍用 `memmove`，它整行写入缓存行，不必先读入。在 GitHub 的 EPYC 7763 runner 上，1,000 个 `KeyValuePair<int, int>` 的反序列化从 465 ns 降到 418 ns。
- **Arm64 上的块拷贝**：65 字节到 64 KB 的块（原始值组成的数组和列表、字符串、字节数组）从对齐的源地址开始，每次 64 字节，用成对的加载和存储（`ldp`/`stp`）拷贝，不再调用 `memmove`；在 GitHub 的 Arm64 runner（Neoverse-N2）上，这个范围内 `memmove` 更慢。带填充的结构体也同样对齐加载。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **多态数组**：加上上面的分派和集合改进，100 个多态类组成的数组在 GitHub 的 x64 runner（Xeon 6973P-C）上序列化从 46 µs 降到 34 µs、反序列化从 224 µs 降到 172 µs，在 Arm64 runner（Neoverse-N2）上分别从 76 µs 降到 58 µs、从 221 µs 降到 193 µs。参见[分派](/zh/docs/v4/polymorphism#dispatch)。
- **33 到 128 字节的拷贝更快**：33 到 64 字节的块在所有 64 位 CPU 上用相互重叠的向量内联拷贝，65 到 128 字节在支持 AVX2 时用四个 32 字节向量内联拷贝，不再调用 `memmove`；原始值组成的数组、列表和字符串在 6 KB 以下的读取也用同样的拷贝（6 KB 及以上用 `memmove`）。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **元素固定大小的多维数组按块处理**：元组、`DateTimeOffset` 及其他固定大小元素组成的 `T[,]`、`T[,,]`、`T[,,,]`，与一维数组一样按块写入和读取，不再逐个处理值。列表和数组也不再清零或搬运读取时会被覆盖的槽位。
- **并发栈和包、优先队列**：元素固定大小的 `ConcurrentStack<T>` 和 `ConcurrentBag<T>` 整块写入；`PriorityQueue<TElement, TPriority>` 的读写循环使用保留在寄存器中的读取器或写入器。
- **可空成员只做一次边界检查**：`int?`、`long?`、`double?`、`DateTime?` 等原始值的可空类型，读取时标志字节和值只做一次边界检查，而不是两次。
- **没有专门路径的集合**：`Collection<T>`、`ObservableCollection<T>` 和自定义的 `ICollection<T>` 类型写入时，写入器在枚举器的调用之间保留在寄存器中，不再在每个元素前后存取一次。
- **不可变字典和 Set 的反序列化快数倍**（Nino.Immutable）：`ImmutableDictionary<TKey, TValue>`、`ImmutableHashSet<T>`、`ImmutableSortedDictionary<TKey, TValue>` 和 `ImmutableSortedSet<T>` 一次性直接构建成内部的树，不再对每个元素调用一次 builder 的 `Add`（每次都要沿树下行并重新平衡）；有序的两种也不再先排序或先建一个 `SortedDictionary`。在 GitHub 的 x64 runner（EPYC 7763）上，1,000 个 int 的 `ImmutableDictionary` 反序列化从 109.4 µs 降到 20.6 µs，`ImmutableHashSet` 从 92.1 µs 降到 19.7 µs，`ImmutableSortedDictionary` 从 55.6 µs 降到 13.3 µs，`ImmutableSortedSet` 从 18.5 µs 降到 13.2 µs；在 Arm64 runner（Neoverse-N2）上分别从 81.7、78.8、62.5、19.1 µs 降到 21.3、20.4、14.6、13.8 µs。这在 .NET、.NET Framework、Mono 和 Unity 上都成立：启动时会校验 System.Collections.Immutable 的内部布局，对不上时用 builder；树没法直接容纳的数据（哈希值相同、顺序不对或为 null 的键）也交给 builder。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **不可变字典和 Set 直接从树写出**（Nino.Immutable）：上面这四种集合改为直接遍历内部的树取出元素，不再用枚举器（它维护一个节点栈，每个元素都要检查），再按数组写出：原始元素整块写一次。写出的字节不变。在 GitHub 的 x64 runner（EPYC 7763）上，1,000 个 int 的 `ImmutableDictionary` 序列化从 14.7 µs 降到 3.1 µs，`ImmutableHashSet` 从 11.5 µs 降到 2.8 µs，`ImmutableSortedDictionary` 从 6.2 µs 降到 3.1 µs，`ImmutableSortedSet` 从 6.5 µs 降到 2.8 µs；在 Arm64 runner（Neoverse-N2）上分别从 16.8、13.4、6.9、6.7 µs 降到 3.4、3.1、3.1、2.6 µs。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **`LinkedList<T>` 和 `SortedDictionary<TKey, TValue>` 直接按节点读入**：读入新的 `LinkedList<T>` 时直接把节点串起来，不再对每个元素做 `AddLast` 的检查；数据有序时，`SortedDictionary<TKey, TValue>` 一次建成平衡的红黑树，不再每个元素调一次 `Add`（每次都要沿树往下走并重新平衡）。1,000 个 int 的 `LinkedList` 反序列化在 GitHub 的 x64 runner（EPYC 7763）上从 14.1 µs 降到 11.5 µs，在 Arm64 runner（Neoverse-N2）上从 14.5 µs 降到 12.3 µs；`SortedDictionary` 分别从 23.9 µs 降到 17.4 µs、从 27.1 µs 降到 16.7 µs。启动时会校验 .NET（64 位和 32 位）、.NET Framework、Mono 和 Unity 的布局；其他运行时以及顺序不对的数据仍走公开 API。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`SortedSet<T>` 直接按树读入**：数据有序时，`SortedSet<T>` 和 `SortedDictionary<TKey, TValue>` 一样一次建成红黑树，不再走那个先复制元素、给副本排序、再去重的构造函数。其他运行时以及顺序不对的数据仍走公开 API。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **原始类型键值的 `KeyValuePair<TKey, TValue>`** 整块读写，每对只检查一次，不再键和值各查一次：逐对写出的字典（`SortedDictionary<TKey, TValue>`、自定义的 `IDictionary<TKey, TValue>` 类型）受益最多。字节不变。
- **键控成员和 `Version`**：键控成员的键和区段长度（连同紧挨在前面的原始成员）一次预留；`Version` 的四个部分一次预留后写入，读取时只做一次边界检查。字节不变。参见[键控成员](/zh/docs/v4/evolving-data#keyed-members)。
- **`SortedSet<T>` 和 `SortedDictionary<TKey, TValue>` 直接从树写出**：按中序遍历节点拷出，不再调用它们自己的 `CopyTo`（它维护一个节点栈，每个节点调一次委托）。写出的字节不变。1,000 个 int 的 `SortedSet` 序列化在 GitHub 的 x64 runner（EPYC 7763）上从 5.5 µs 降到 2.8 µs，在 Arm64 runner（Neoverse-N2）上从 5.0 µs 降到 2.8 µs；`SortedDictionary` 分别从 5.8 µs 降到 3.2 µs、从 5.6 µs 降到 3.0 µs。集合的视图（`GetViewBetween`）以及认不出布局的运行时仍用 `CopyTo`。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **空集合**：空的数组、列表、Set、字典、优先队列和不可变集合不再进入逐元素循环（省掉一次调用，以及读取器或写入器的拷入拷出）；空的不可变 Set 和字典读成共享的 `Empty` 实例。树这类含大量空叶子集合的数据受益最多。
- **池里还没有归还过实例时读取 `[NinoPooled]` 类型**：从没放进过实例的池，取实例时只读一个字段就返回，不再为了发现本线程的栈是空的去访问线程局部字段（还要调一次方法）。只在部分读取里用池的程序，以及线程局部字段开销最大的 Unity 和 IL2CPP，受益最多。基准测试中池化节点的反序列化在 GitHub 的 x64 runner（EPYC 7763）上从 205 ns 降到 156 ns，在 Arm64 runner（Neoverse-N2）上从 193 ns 降到 145 ns。参见[内置对象池](/zh/docs/v4/pooling#ninopooled)。
- **`ImmutableStack<T>`**（Nino.Immutable）序列化不再先填充并反转一个列表，且不分配内存：1,000 个 int 在 GitHub 的 Arm64 runner（Neoverse-N2）上从 4.5 µs 降到 2.7 µs，在 x64 runner（EPYC 7763）上从 3.1 µs 降到 2.9 µs。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **版本容错类型**：数据完整时，相邻的一组原始成员整块读取，只检查一次（旧版本写的数据走逐个成员的路径）：基准测试中版本容错类组成的数组，在 GitHub 的 x64 runner（EPYC 7763）上反序列化从 57.3 µs 降到 49.8 µs。键控类型把每个成员的键和区域长度一起预留。参见[版本容错](/zh/docs/v4/evolving-data#version-tolerance)。
- **Unity 的 `AnimationCurve` 和 `Gradient`**（Nino.UnityTypes）一次预留所需字节，读取时每段关键帧只做一次边界检查，而不是每个值一次。参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)。
- **原始元素组成的 `Memory<T>` 和 `ReadOnlyMemory<T>`** 的数组和普通数组一样分配：从 6 KB 起不清零。
- **2 到 6 KB 的新数组改为清零分配**：读取时靠一次块拷贝填满的数组，只在 6 KB 及以上才不清零分配，这时省下的清零才比代价大；更小的数组用运行时的不清零分配反而更慢。1,000 个 int 反序列化为 `ReadOnlyCollection<T>` 或 `ReadOnlySequence<T>`，在 GitHub 的 x64 runner（EPYC 7763）上从 348 ns 降到 257 和 264 ns，在 Arm64 runner（Neoverse-N2）上从 416 和 423 ns 降到 364 和 363 ns；反序列化为 `Memory<T>` 在 x64 上从 312 ns 降到 262 ns。

### 修复 [#fixes-4]

- 带子类型的泛型抽象类和泛型接口（`abstract class Box<T>`、`IRepository<T>`），以及嵌套在泛型类型里的抽象类，不再导致编译失败：之前不管用哪种格式，生成的格式化器都编译不过。现在它们的子类型和非泛型基类型的子类型一样读写（见[分派](/zh/docs/v4/polymorphism#dispatch)），数据里的类型不是它的子类型时抛异常（[#203](https://github.com/JasonXuDeveloper/Nino/pull/203)）。参见[接口与抽象类](/zh/docs/v4/polymorphism#interfaces-and-abstract-classes)。
- 嵌套在泛型类里的类（`Holder<long>.Base`）在其他程序集里有子类型时，第一次序列化不再栈溢出。参见[其他程序集里的子类型](/zh/docs/v4/polymorphism#subtypes-in-other-assemblies)。
- 生成器没法为某个类型生成格式化器时，构建报一个指明类型和原因的错误，而不是在生成代码里报一堆错误。
- 序列化超过 4 GB 的非托管值 span、超过 1 G 字符的 `StringBuilder` 或超过 2 GB 的 UTF-8 文本时，抛出 `OverflowException`，不再越过缓冲区末尾写入。
- 代码修复（实现 `[NinoPooled]` 钩子、添加或移除特性）沿用所编辑文件的换行符：之前在 Windows 上会往使用 LF 换行的文件里插入 CRLF 行。参见[诊断列表](/zh/docs/v4/analyzers#diagnostics)。
- **不可信数据**：专门针对读取器伪造的数据不会再让进程崩溃：以前，通过列表、可空类型或接口成员包含自身的结构体，嵌套几千层就会栈溢出；现在和嵌套超过 512 层的对象一样抛出异常。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- 读入已有值（`Deserialize(data, ref value)`）失败时，原始类型元素的数组、列表或 `Memory<T>` 不会再留下一个装着未初始化内存的数组；`StringBuilder` 的长度和多维数组的各维度会先和数据比对再分配（之前 4 字节的 `StringBuilder` 数据会分配 2 GB）。
- 声称的元素个数比实际内容多的数据，没法再让一次读取分配几百倍于自身大小的内存（以前 1 MB 自称装着大结构体的数据会分配 520 MB）：集合在读到元素之前，最多预先分配输入剩余字节数的 16 倍，之后随实际读到的元素扩容。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- 无效的 `Version`、`Uri`、`CultureInfo`、`TimeZoneInfo`、`DateTimeOffset` 值和字典的 null 键，抛出 Nino 的 `InvalidOperationException`（原异常放在 `InnerException` 里），不再抛 BCL 的异常；所有无效输入都能用同一种方式捕获，[Nino.AspNetCore](/zh/docs/v4/advanced/aspnetcore) 也会返回 400 而不是 500。

</Release>

## 4.0.0-rc.6

### 二进制格式 [#wire-format-2]

- **每个字符一个字节的字符串**：默认的 `string` 编码在所有字符都不超过 U+00FF（ASCII、Latin-1）时，每个字符写一个字节，头部为负数长度（`~长度`）；其他文本仍是 UTF-16，`[NinoUtf8]` 不变。这适用于所有默认编码的字符串：成员、集合的元素和键，以及 `Uri`、`CultureInfo` 和 `TimeZoneInfo` 值的文本。本版本仍能读取此前 v4 版本写出的 UTF-16 字符串，但此前的版本读不了本版本写出的单字节字符串，所以读取数据的一方要先于写入数据的一方升级，或者同时升级（[从更早的候选版本升级](/zh/docs/v4/migration#upgrading-from-an-earlier-release-candidate)）。`StringBuilder` 仍以 UTF-16 写出，两种形式都能读取。参见[字符串](/zh/docs/v4/wire-format#strings)和[字符串编码](/zh/docs/v4/defining-types#string-encoding)。

### 新功能 [#new-4]

- **Nino.AspNetCore**：MVC 输入和输出格式化器（`AddNinoFormatters()`、`application/x-nino`、`?format=nino`）以及 Minimal API 支持（`NinoBody<T>` 参数、`NinoResults.Ok` 和 `NinoResults.Status`、`ReadFromNinoAsync` 和 `WriteAsNinoAsync`），直接基于请求和响应管道读写请求体与响应，自身不做任何分配。参见 [ASP.NET Core](/zh/docs/v4/advanced/aspnetcore)。
- **Nino.TypeScript**：一个构建包，每次构建后为项目的 `[NinoType]` 写出 TypeScript 类、枚举和编解码器（`NinoTypeScriptOutput`、`NinoTypeScriptImportExtension`、`NinoTypeScriptNames`），并附带 `nino.ts` 运行时，浏览器和 Node 与 .NET 互通，字节一致。表达不了的类型直接跳过，并报警告 `NINOTS002`。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。
- **按字节描述的布局元数据**：`[assembly: NinoTypeLayout]` 现在按每个成员写出的字节来描述它（`seq(string)`、`map(string,seq(raw(4)))`、`nullable(raw(4))`、`type(MyType)` 等），不再写格式化器类名；键控成员带上了它的键（`:key=0x…`）。和之前版本记录的布局相比，每个非原始内存成员的文本都不一样了，但除了字符串，字节并没有变；请重新记录。参见[布局元数据](/zh/docs/v4/evolving-data#layout-metadata)。
- **`NinoSerializer.IsSupported(Type)`** 判断 Nino 能否序列化和反序列化某个类型，供只有 `Type` 的集成代码使用。参见[装箱 API](/zh/docs/v4/basic#the-boxed-api)。

### 性能 [#performance-1]

- **含 Latin-1 字符串的数据更小**，序列化和反序列化时间与之前相同：基准测试中，`Orders` 从 30,848 字节降到 26,126 字节，`Players` 从 45,124 降到 39,164，`Tree` 从 40,676 降到 31,258，现在都比 MemoryPack 的更小（27,990、43,364 和 32,623）。参见[基准测试：.NET 运行速度](/zh/docs/v4/benchmarks)。
- **带填充的元组和键值对序列化更快**：值元组、`KeyValuePair` 以及其他内存中有填充的原始值组成的数组和列表，先对齐目标地址，再每个向量用一次双源置换按整向量写出它们的字节（AVX-512：每个 4 字节字都是内存中完整的一个字时按字置换，否则用 VBMI 按字节置换；AVX2；Arm64；.NET 10 上的 WebAssembly）：在一台 AVX-512 Xeon 上，1,000 个 `(int, long)` 序列化用时 106 到 109 ns，rc.5 为 228 ns，MemoryPack 为 136 到 141 ns。参见[SIMD](/zh/docs/v4/simd#dotnet)。
- **带填充的元组和键值对读取更快**：在 AVX-512 上，带填充的原始值按写入的方式读取，内存中每个 64 字节向量由其字节向量经一次双源置换得到，并存储到对齐地址：把 1,000 个 `(int, long)` 反序列化到已有的列表或数组需要 105 到 140 ns，rc.5 为 255 ns，与 MemoryPack（111 到 130 ns，按原样复制其 16 字节的值）持平。转换非 Latin-1 文本时同样按对齐地址存储：1,000 字符的非 Latin-1 字符串读取快约 8%（AVX-512 Xeon）。
- **中等大小的数组读取时不再清零**：2 到 6 KB 的非托管值数组、列表和只读集合，读取时和更大的数组一样以未初始化方式分配：1,000 个 `int` 的 `ReadOnlyCollection<int>` 反序列化从 570 到 590 ns 降到 450 到 510 ns（AVX-512 Xeon）。
- **TypeScript 编解码更快**：生成的代码在同一块缓冲区里按偏移读写连续的固定大小成员，`nino.ts` 用 Node（以及 Bun、Deno）的原生方法读写文本，浏览器中用 `TextDecoder` 和 `TextEncoder`。在 Node 中，1,000 条玩家记录序列化从 2.07 ms 降到 1.15 ms，反序列化从 1.92 ms 降到 1.17 ms；文本为主的记录快 6.8 倍和 11 倍，数值数组快 2 到 5 倍。短文本读得更快：在 Node 中，不超过 12 个字符的字符串从对最多 4 KB 数据的一次 Latin-1 解码中切出，不超过 16 个字符的文本用一次 `String.fromCharCode` 调用读取，因此含短字符串的小记录列表反序列化从 0.81 ms 降到 0.46 ms（Chromium 中从 0.65 ms 降到 0.42 ms），短字符串映射在 Node 中快 1.5 倍。`serialize` 不再复制结果：每个结果都紧接在上一个之后写进共享的 64 KB 缓冲区，返回它上面的视图，且永远不会被覆盖；在 Chromium 中，数值和结构体数组的序列化快 1.3 到 1.5 倍。参见 [API](/zh/docs/v4/advanced/typescript#api) 和[与 JSON 对比](/zh/docs/v4/advanced/typescript#performance)。

### 修复 [#fixes-3]

- **Unity：引用了带 internal `ModuleInitializerAttribute` 的库**（如 ZLinq 的 netstandard 版本）时不再编译失败：生成器曾在注册表中引用这个 polyfill（错误 CS0122 "'ModuleInitializerAttribute' is inaccessible due to its protection level"）。现在只有程序集能访问某个初始化特性时才会使用它，Unity 照旧通过 `[RuntimeInitializeOnLoadMethod]` 注册。参见 [Unity](/zh/docs/v4/advanced/unity)。
- **TypeScript：以 U+FEFF 开头的 `[NinoUtf8]` 字符串**不再反序列化失败：`TextDecoder` 把这个字符当作字节序标记丢掉了。参见 [TypeScript](/zh/docs/v4/advanced/typescript)。

## 4.0.0-rc.5

### 新功能 [#new-3]

- **更多内置类型**：`BigInteger`、`Uri`、`Version`、`StringBuilder`、`BitArray`、`CultureInfo`、`TimeZoneInfo`、`Lazy<T>`、`Memory<T>`、`ReadOnlyMemory<T>`、`ReadOnlySequence<T>`、`ReadOnlyCollection<T>`、`ReadOnlyObservableCollection<T>`、`ILookup<TKey, TElement>`、`IGrouping<TKey, TElement>` 和 `BlockingCollection<T>` 不再需要自定义格式化器。如果 Nino 已经支持形状相同的类型，就沿用它的字节：`Memory<T>` 和 `ReadOnlySequence<T>` 按 `T[]` 写入，`ReadOnlyCollection<T>` 按 `List<T>` 写入，`StringBuilder` 按 `string` 写入。`System.Type` 有意继续不支持。参见[支持的类型](/zh/docs/v4/types#other-built-in-types)。
- **所有不可变集合**：`Nino.Immutable` 在 `ImmutableArray<T>` 和 `ImmutableList<T>` 之外，新增 `ImmutableHashSet<T>`、`ImmutableSortedSet<T>`、`ImmutableQueue<T>`、`ImmutableStack<T>`、`ImmutableDictionary<TKey, TValue>` 和 `ImmutableSortedDictionary<TKey, TValue>`，每种都与对应的可变集合字节相同。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **Unity 的 `AnimationCurve`、`Gradient` 和 `RectOffset`**：Unity 包附带 `Nino.UnityTypes.dll`，提供它们的格式化器，因此它们可以作为成员、元素和顶层值使用，支持 `null` 和 `ref` 复用。参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)。

### 性能 [#performance]

- **`Stack<T>`、`Queue<T>` 和以接口声明的集合**（`IList<T>`、`IEnumerable<T>`、`IReadOnlyCollection<T>` 等），元素是非托管值或按原始内存复制的 `[NinoType]` 结构体时，会像 `List<T>` 和数组一样整块读写。以 1,000 个 `int` 为例，序列化快 17 到 75 倍，反序列化快 2.5 到 6 倍。其他元素类型的 `Stack<T>` 和 `Queue<T>` 也改为直接读写其内部数组。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`DateTimeOffset`** 改为直接读写它的两个字段（字段位置在启动时检查一次，因为 .NET 10 的字段顺序和 .NET 8、.NET Framework、Mono 不同），它的数组和列表整块读写。以 1,000 个值为例，序列化快 2.9 倍，反序列化快 2 倍。非法数据仍抛出与构造函数相同的异常。参见[基元类型与非托管类型](/zh/docs/v4/types#primitive-and-unmanaged-types)。
- **`[NinoType]` 结构体的数组和列表**在该结构体被单独序列化之后，仍使用生成的格式化器；以前此后每个元素都要经过一次虚调用，按原始内存复制的结构体也不再整块复制。以 1,000 个小结构体（`int`、`short`、`bool`）为例，序列化快 15 倍，反序列化快 3.6 倍。短字符串和其他不超过 32 字节的块改为内联复制：`List<KeyValuePair<int, string>>` 序列化快 1.3 倍。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **集合中的小类**：最多有八个成员、其中最多两个需要调用格式化器（字符串、集合或其他类型）的类，其主体会内联到集合的循环中，未密封的类也是如此。子类型和 null 的处理不变。这类未密封类的列表序列化约快 2 倍，反序列化约快 1.3 倍。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **64 字节到 8 KB 的块**（非托管值和原始结构体的数组、字符串）在支持 AVX-512 的 CPU 上用 64 字节向量写出，最多快 1.5 倍；带填充的结构体数组改用 64 字节掩码复制：1,000 个由 `int`、`short` 和 `bool` 组成的结构体序列化快 1.6 倍。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **含字符串或其他非原始成员的结构体**改为按引用传给生成的主体，不再按值传递，因此每个元素不再先复制到栈上。由 1,000 个结构体（四个 `long`、一个 `string` 和一个 `int`）组成的列表序列化快 2 倍。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **字符串**在 .NET 8 及以上由运行时直接分配并在内联代码中填充，省去了 `new string` 的参数检查和复制调用：读取 3 到 12 个字符的字符串从 16 到 19 ns 降到 12 到 14 ns，含大量短字符串的类型反序列化快 3% 到 7%。其他运行时的读取方式不变。参见[字符串](/zh/docs/v4/types#strings)。
- **含嵌套成员的类和结构体**：把读取器或写入器复制到局部变量再复制回去时，改为逐个字段复制，CPU 可以直接从之前的写入转发数据，不必等它们写入缓存，读写位置得以一直留在寄存器中。玩家对象列表序列化快 19%，反序列化快 8%；小类列表、订单和树快 5% 到 10%。写出的字节不变。
- **新建的非托管值或原始结构体 `List<T>`**，大小在 6 KB 及以上时，其底层数组不再先清零再复制元素，和数组的做法一致：10,000 个 `int` 的列表反序列化快约 15%。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`ImmutableArray<T>` 和 `ImmutableList<T>`**（`Nino.Immutable`）改为通过数组读写：`ImmutableArray` 直接包装读入的数组，不再复制；`ImmutableList` 从数组一次建好。1,000 个元素的 `ImmutableArray<int>` 序列化快 13 倍、反序列化快 8 倍，1,000 个元素的 `ImmutableList<int>` 反序列化快 3.6 倍。写出的字节不变。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **由非托管值组成的值元组和 `KeyValuePair`**（如 `(int, long)`）：每个元组只做一次容量检查；它们的数组与列表（如 `(int, int)[]`、`List<(int, long)>`）改为整块读写：值的内存与写出的字节一致时直接按内存复制，否则用 SIMD 字节重排（SSSE3、Arm64、AVX-512 VBMI）每次处理 16 或 64 字节。1,000 个 `(int, int)` 或 `KeyValuePair<int, int>` 序列化快 16 到 19 倍，反序列化快 2.5 到 3 倍。1,000 个元素的 `List<(int, long)>` 先是序列化快 1.25 倍、反序列化快 2.3 倍（每个元组一次容量检查，元素循环把读取位置保留在寄存器里），整块读写后又分别快 5.4 倍和 2 倍。写出的字节不变。参见[其他内置类型](/zh/docs/v4/types#other-built-in-types)。
- **`SortedSet<T>`、`SortedDictionary<TKey, TValue>`、`SortedList<TKey, TValue>`、`LinkedList<T>` 和 `ConcurrentDictionary<TKey, TValue>`**（及其派生类型）改为通过它们自己的字段和方法读写，不再走通用的集合循环：有序 Set 和有序字典先读成数组，再一次建好平衡树；有序列表在键按其比较器有序时直接读进键数组和值数组；由 Nino 创建的 `ConcurrentDictionary`（没有已有实例，且不是派生类型）用读到的键值对调用其构造函数创建，表一次分配到位，插入时不加锁。1,000 个 `int` 或 `int` 键值对时，`ConcurrentDictionary` 反序列化从 1.88 ms 降到 15 µs（改为直接调用后快 28 倍，改用构造函数后又快约 4 倍），序列化快 1.3 倍；`SortedDictionary` 反序列化先快 1.8 倍、再快 1.5 倍，序列化快 1.9 倍；`SortedList` 反序列化快 5.5 倍、序列化快 1.4 倍；`SortedSet` 序列化和反序列化都快 2 倍。写出的字节不变，重复键和 null 键仍抛出同样的异常。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`ConcurrentStack<T>`**：新建的实例改为一次 `PushRange` 填入，不再逐个 Push，快约 1.9 倍（1,000 个 `int` 从 17.9 µs 降到 9.3 µs）；新建的 `ConcurrentQueue<T>` 改用构造函数创建，首个分段一次按元素个数分配。已有实例和派生类型照旧填充。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **更多 CPU 用上 SIMD**：在没有 AVX-512 的 x64 CPU 上（AVX2，大多数台式机），256 字节到 4 KB 的块改用 32 字节向量复制：256 字节从 6.3 ns 降到 3.9 ns，2,500 字节从 36.3 ns 降到 24.6 ns。在 Arm64 上，8 字节以内的值元组、`KeyValuePair` 和原始结构体的数组与列表改用查表指令每次重排 64 字节，与 x64 上的 AVX-512 VBMI 相同；在 .NET 10 上，16 字节的字节重排也支持 WebAssembly SIMD。写出的字节不变。

### 修复 [#fixes-2]

- **.NET Framework 和 Mono 上的 `List<T>`**：Nino.Core 的 netstandard 版本按 .NET 的字段位置读写 `List<T>`，但 .NET Framework 和 Mono 的 `List<T>` 多一个字段，导致列表被写成空列表，读入的列表也会损坏。现在 Nino 直接读写字段的每种集合（`List<T>`、`Stack<T>`、`Queue<T>`、`SortedList<TKey, TValue>`、`SortedSet<T>`、`SortedDictionary<TKey, TValue>`）都会在启动时用一个内容已知的实例核对一次布局；布局不符的运行时改用公开方法读写。这些快速路径现在在 .NET Framework 和 Mono 上同样生效。参见[集合类型](/zh/docs/v4/types#collection-types)。

</Release>

## 4.0.0-rc.3

### 二进制格式 [#wire-format-1]

只有下面这种类型写出的字节和 rc.2 不同。

- **另一个程序集里带 `[StructLayout(LayoutKind.Explicit)]` 的 `[NinoType]` 结构体**，现在无论怎么构建都逐个成员写出。IDE 或项目引用把它当作源码时本来就是这样；通过 NuGet 包引用或在命令行构建时，rc.2 会把它按原始内存整体拷贝（[#202](https://github.com/JasonXuDeveloper/Nino/issues/202)）。

### 新功能 [#new-1]

- **布局元数据里写出原始字节**：`[assembly: NinoTypeLayout]` 现在会写出每个按原始内存拷贝的值的大小和字段偏移，不是 `[NinoType]` 的结构体也一样，所以改了字段、`Pack`、`Size` 或 `[FieldOffset]`，布局都会跟着变。原始成员原来写作 `raw(n)` 或 `raw`，现在写作 `raw(n){name:type@offset:encoding,...}`；原始内存结构体的成员部分就是它的原始布局。参见[布局元数据](/zh/docs/v4/evolving-data#layout-metadata)（[#202](https://github.com/JasonXuDeveloper/Nino/issues/202)）。
- **`NinoSerializer.Serialize<T>(in T value)`** 改为按引用接收值，和 MemoryPack 一样。序列化一个从字段读出、按原始内存拷贝的结构体，现在只有一次分配和一次直接拷进数组的拷贝；rc.2 会先把它拷到栈上。已有的调用无需改动就能编译；把方法组转换成 `Func<T, byte[]>` 的地方需要改用 lambda。参见[序列化](/zh/docs/v4/basic#serializing)。

### 修复 [#fixes-1]

- **会读取另一个程序集里结构体的 `[StructLayout]` 和 `[FieldOffset]`。** 对于来自 NuGet 包的类型，Roslyn 不会把它们当作特性给出，所以生成器以前把这类结构体都当成顺序布局。带显式字段偏移的结构体因此可能被按原始内存拷贝，而它的大小在 64 位和 32 位运行时上不一样（[#202](https://github.com/JasonXuDeveloper/Nino/issues/202)）。

## 4.0.0-rc.2

### 二进制格式 [#wire-format]

只有下面这些类型写出的字节和 rc.1 不同。

- **另一个程序集里、成员是自动属性的 `[NinoType]` 结构体**（比如位置式的 `record struct`），现在无论怎么构建都按原始内存整体拷贝。rc.1 只有在 IDE 或项目引用把它当作源码时才这样做；通过 NuGet 包引用或在命令行构建时，它会被逐个成员写出。因此，包含这种结构体的结构体、数组或列表，写出的字节可能和 rc.1 的包引用或命令行构建不同：结构体中有填充时，整体拷贝会把填充（清零后）一并写出（[#200](https://github.com/JasonXuDeveloper/Nino/issues/200)）。
- **netstandard（包括 Unity）下的 `nint`、`nuint` 成员现在会被序列化。** rc.1 在这些平台上会跳过它们并报 NINO007；现在和 .NET 7 及以上一样，按 8 字节写出。

### 新功能 [#new]

- **布局元数据**：生成器为每个 `[NinoType]` 记录一条 `[assembly: NinoTypeLayout]`，说明它是怎么写出的，方便工具对比两次构建的布局。参见[布局元数据](/zh/docs/v4/evolving-data#layout-metadata)（[#197](https://github.com/JasonXuDeveloper/Nino/issues/197)）。
- **卸载程序集**：`NinoRegistry.Remove(assembly)` 会清除 Nino 为某个程序集缓存的全部内容，让可回收的 `AssemblyLoadContext` 能够卸载它。在 .NET 8 及以上，上下文卸载时会自动完成这一步。参见[卸载程序集](/zh/docs/v4/platforms#unloading-assemblies)（[#199](https://github.com/JasonXuDeveloper/Nino/issues/199)）。
- **自定义缓冲池**：`new NinoArrayBufferWriter(initialCapacity, pool)` 从你传入的 `ArrayPool<byte>` 租用数组。参见[复用缓冲区](/zh/docs/v4/basic#reusing-a-buffer)（[#198](https://github.com/JasonXuDeveloper/Nino/issues/198)）。

### 修复 [#fixes]

- **一个类型上有两个 `[NinoFormerName]` 时会报错 NINO026。** 以前生成器会取第一个，而 `NinoTypeId.Of` 会抛出 `AmbiguousMatchException`。参见[分析器](/zh/docs/v4/analyzers)（[#201](https://github.com/JasonXuDeveloper/Nino/issues/201)）。

</Release>
