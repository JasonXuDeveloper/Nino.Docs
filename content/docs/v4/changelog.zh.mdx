这里按从新到旧的顺序，列出 v4 各版本之间的变化。v4 相对 v3 的全部变化见 [v4 新特性](/zh/docs/v4/whats-new)。每个 GitHub Release 也会列出它包含的全部提交。

## 4.0.0-rc.7

### 新功能 [#new-5]

- **Unity 中的代码修复**：Unity 包现在带有 `Nino.Generator.CodeFixes.dll`，Rider 和 Visual Studio 中对 Nino 分析器警告提供与 NuGet 项目相同的快速修复（加上 `partial`、无参构造函数、对象池钩子等）。参见[分析器诊断](/zh/docs/v4/analyzers)。

### 性能 [#performance-2]

- **经泛型基类型读写的子类型**：通过泛型基类型（`abstract class Box<T>`、`IRepository<T>`、泛型类）读写的值，与通过非泛型基类型一样使用生成的分派，覆盖每个封闭基类型在其程序集中声明的子类型，类型参数可以是任何类型（基元类型、元组、密封类或非密封类），不再为每个值做一次注册表查找和一次虚调用。参见[分派](/zh/docs/v4/polymorphism#dispatch)。
- **Arm64 上的小元组**：小的带填充元组组成的数组和列表读写更快：1,000 个 `(byte, int)` 反序列化从 1,123 ns 降到 805 ns，序列化从 422 ns 降到 122 ns；1,000 个 `(short, int)` 分别从 1,103 ns 降到 801 ns、从 200 ns 降到 124 ns；基准测试的 `TupleList` 用例分别从 1,815 ns 降到 1,415 ns、从 375 ns 降到 219 ns（GitHub 的 Arm64 机器）。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **集合直接写入大小正好的数组**：对元素定长的数组和列表（非托管值、`DateTimeOffset`、元组和原始结构体）调用 `NinoSerializer.Serialize(value)` 时，直接分配大小正好的数组并写入，不再经过池化的临时缓冲区再拷贝出来。参见[内存分配](/zh/docs/v4/performance#allocation)。
- **不支持 AVX-512 时，带填充的元组和键值对更快**：值元组、`KeyValuePair` 以及其他带填充的原始值组成的数组和列表，写入和读取都按组处理，向量的每个 16 字节通道由至多两个 16 字节窗口经通道内重排得到（AVX2、SSSE3、Arm64 `TBL`、.NET 10 上的 WebAssembly SIMD）。在 GitHub 的 x64 runner（EPYC 7763，AVX2）上，1,000 个 `(int, long)` 的列表序列化从 380 ns 降到 194 ns。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **带填充的元组在任何缓冲区对齐下序列化速度一致**：元组、`KeyValuePair` 以及其他带填充的结构体组成的数组和列表，按对齐到输出的向量写入；第一个对齐向量之前和最后一个之后的值原本逐个写入，所以耗时取决于缓冲区起始位置。现在两端各多写一整组值，耗时不再取决于起始位置。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **Intel CPU 上新建的元组和 `DateTimeOffset` 数组读取更快**：在 Intel x64 CPU 上，读取时靠向量重排或逐个写值填满的数组和列表改为分配已清零的内存，每次写入不再先从内存读入所在的缓存行。一次块拷贝填满的数组，以及 Arm64 和 AMD CPU 上 6 KB 及以上的所有数组，仍不清零分配，在那里同样快或更快。
- **不支持 AVX-512 时的 5 字节值**：`(byte, int)` 等 5 字节值组成的数组和列表，在 AVX2（每个 32 字节向量 6 个值）和 SSSE3（每 4 个 16 字节向量 12 个值）上按组搬运，不再逐个处理。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **Arm64 上带填充的结构体**：带填充的结构体（元组、`KeyValuePair`）组成的数组和列表，用成对的加载和存储（`ldp`/`stp`）每步拷贝 32 字节，和 C 库的 `memcpy` 一样，不再每次只处理一个 16 字节向量。
- **`HashSet<T>` 和 `Dictionary<TKey, TValue>`**：原始值组成的集合在没有删除过条目时，直接从内部条目数组用一个循环写出，不再经过枚举器对每个元素的检查。读取时新建的集合（默认比较器）直接写入条目和桶，与 `Add` 的结果相同，但不再对每个元素检查比较器、空闲链表和容量；数据里同一个键出现两次仍会抛出异常。在 GitHub 的 x64 runner（EPYC 7763）上，1,000 个元素的 `HashSet<int>` 序列化从 1.06 µs 降到 0.33 µs，反序列化从 6.1 µs 降到 2.6 µs；在 Arm64 runner（Neoverse-N2）上分别从 1.28 µs 降到 0.37 µs、从 5.3 µs 降到 2.8 µs。启动时会用公开 API 校验一个这样填充的集合，覆盖 .NET（64 位和 32 位）、.NET Framework、Mono 和 Unity 的内部布局和哈希方式；其他运行时继续使用枚举器和 `Add`（供 .NET Framework 使用的 netstandard2.0 构建只对字典这样填充）。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **拷贝不再调用 `memmove`**：8 到 32 KB 的块拷贝改用 Nino 的向量循环，不再调用 `memmove`，后者在部分 AMD EPYC CPU 上慢好几倍。在支持 AVX2 但不用 AVX-512 的 x64 CPU（AMD Zen 2 和 3、大多数 Intel 桌面 CPU）上，对齐的 32 字节存储循环一直用到 1 MB，在这个范围内比 C 库的拷贝快；更大的块，以及只有 SSE 和 32 位 CPU 上 16 KB 起的块，仍用 `memmove`。
- **AMD CPU 上的新数组**：读取时用一次块拷贝填充原始值新数组，在 AMD x64 CPU 上 6 KB 及以上也改用 Nino 的向量循环：即使是刚分配的内存，`memmove`（rep movsb）在这些 CPU 上也比向量存储慢；Intel CPU 在这个范围仍用 `memmove`，它整行写入缓存行，不必先读入。在 GitHub 的 EPYC 7763 runner 上，1,000 个 `KeyValuePair<int, int>` 的反序列化从 465 ns 降到 418 ns。
- **Arm64 上的块拷贝**：65 字节到 64 KB 的块（原始值组成的数组和列表、字符串、字节数组）从对齐的源地址开始，每次 64 字节，用成对的加载和存储（`ldp`/`stp`）拷贝，不再调用 `memmove`；在 GitHub 的 Arm64 runner（Neoverse-N2）上，这个范围内 `memmove` 更慢。带填充的结构体也同样对齐加载。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **多态数组**：加上上面的分派和集合改进，100 个多态类组成的数组在 GitHub 的 x64 runner（Xeon 6973P-C）上序列化从 46 µs 降到 34 µs、反序列化从 224 µs 降到 172 µs，在 Arm64 runner（Neoverse-N2）上分别从 76 µs 降到 58 µs、从 221 µs 降到 193 µs。参见[分派](/zh/docs/v4/polymorphism#dispatch)。
- **33 到 128 字节的拷贝更快**：33 到 64 字节的块在所有 64 位 CPU 上用相互重叠的向量内联拷贝，65 到 128 字节在支持 AVX2 时用四个 32 字节向量内联拷贝，不再调用 `memmove`；原始值组成的数组、列表和字符串在 6 KB 以下的读取也用同样的拷贝（6 KB 及以上用 `memmove`）。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **元素定长的多维数组按块处理**：元组、`DateTimeOffset` 及其他定长元素组成的 `T[,]`、`T[,,]`、`T[,,,]`，与一维数组一样按块写入和读取，不再逐个处理值。列表和数组也不再清零或搬运读取时会被覆盖的槽位。
- **并发栈和包、优先队列**：元素定长的 `ConcurrentStack<T>` 和 `ConcurrentBag<T>` 整块写入；`PriorityQueue<TElement, TPriority>` 的读写循环使用保留在寄存器中的读取器或写入器。
- **可空成员只做一次边界检查**：`int?`、`long?`、`double?`、`DateTime?` 等原始值的可空类型，读取时标志字节和值只做一次边界检查，而不是两次。
- **没有专门路径的集合**：`Collection<T>`、`ObservableCollection<T>` 和自定义的 `ICollection<T>` 类型写入时，写入器在枚举器的调用之间保留在寄存器中，不再在每个元素前后存取一次。
- **不可变字典和集合的反序列化快数倍**（Nino.Immutable）：`ImmutableDictionary<TKey, TValue>`、`ImmutableHashSet<T>`、`ImmutableSortedDictionary<TKey, TValue>` 和 `ImmutableSortedSet<T>` 一次性直接构建成内部的树，不再对每个元素调用一次 builder 的 `Add`（每次都要沿树下行并重新平衡）；有序的两种也不再先排序或先建一个 `SortedDictionary`。在 GitHub 的 x64 runner（EPYC 7763）上，1,000 个 int 的 `ImmutableDictionary` 反序列化从 109.4 µs 降到 20.6 µs，`ImmutableHashSet` 从 92.1 µs 降到 19.7 µs，`ImmutableSortedDictionary` 从 55.6 µs 降到 13.3 µs，`ImmutableSortedSet` 从 18.5 µs 降到 13.2 µs；在 Arm64 runner（Neoverse-N2）上分别从 81.7、78.8、62.5、19.1 µs 降到 21.3、20.4、14.6、13.8 µs。这在 .NET、.NET Framework、Mono 和 Unity 上都成立：启动时会校验 System.Collections.Immutable 的内部布局，布局不符时使用 builder；树无法直接容纳的数据（哈希值相同、顺序不对或为 null 的键）同样交给 builder。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **不可变字典和集合直接从树写出**（Nino.Immutable）：上述四种集合改为直接遍历内部的树取出元素，不再使用枚举器（它维护一个节点栈并在每个元素上做检查），再按数组写出：原始元素一次整块写入。写出的字节不变。在 GitHub 的 x64 runner（EPYC 7763）上，1,000 个 int 的 `ImmutableDictionary` 序列化从 14.7 µs 降到 3.1 µs，`ImmutableHashSet` 从 11.5 µs 降到 2.8 µs，`ImmutableSortedDictionary` 从 6.2 µs 降到 3.1 µs，`ImmutableSortedSet` 从 6.5 µs 降到 2.8 µs；在 Arm64 runner（Neoverse-N2）上分别从 16.8、13.4、6.9、6.7 µs 降到 3.4、3.1、3.1、2.6 µs。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **`LinkedList<T>` 和 `SortedDictionary<TKey, TValue>` 直接按节点读入**：读入新的 `LinkedList<T>` 时直接把节点连起来，不再对每个元素做 `AddLast` 的检查；数据有序时，`SortedDictionary<TKey, TValue>` 一次建成平衡的红黑树，不再对每个元素调用一次 `Add`（每次都要沿树下行并重新平衡）。1,000 个 int 的 `LinkedList` 反序列化在 GitHub 的 x64 runner（EPYC 7763）上从 14.1 µs 降到 11.5 µs，在 Arm64 runner（Neoverse-N2）上从 14.5 µs 降到 12.3 µs；`SortedDictionary` 分别从 23.9 µs 降到 17.4 µs、从 27.1 µs 降到 16.7 µs。启动时会校验 .NET（64 位和 32 位）、.NET Framework、Mono 和 Unity 的布局；其他运行时以及顺序不对的数据仍走公开 API。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`SortedSet<T>` 直接按树读入**：数据有序时，`SortedSet<T>` 与 `SortedDictionary<TKey, TValue>` 一样一次建成红黑树，不再经过先复制元素、排序副本、再去重的构造函数。其他运行时以及顺序不对的数据仍走公开 API。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **原始类型键值的 `KeyValuePair<TKey, TValue>`** 整块写入和读取，每对只做一次检查，不再键和值各检查一次：逐对写入的字典（`SortedDictionary<TKey, TValue>`、自定义的 `IDictionary<TKey, TValue>` 类型）受益最多。字节不变。
- **键控成员和 `Version`**：键控成员的键和区段长度（连同紧挨在它前面的原始成员）一次预留；`Version` 的四个部分一次预留写入，读取时只做一次边界检查。字节不变。参见[键控成员](/zh/docs/v4/evolving-data#keyed-members)。
- **`SortedSet<T>` 和 `SortedDictionary<TKey, TValue>` 直接从树写出**：按中序遍历节点拷出，不再调用它们自己的 `CopyTo`（后者维护一个节点栈，并对每个节点调用一次委托）。写出的字节不变。1,000 个 int 的 `SortedSet` 序列化在 GitHub 的 x64 runner（EPYC 7763）上从 5.5 µs 降到 2.8 µs，在 Arm64 runner（Neoverse-N2）上从 5.0 µs 降到 2.8 µs；`SortedDictionary` 分别从 5.8 µs 降到 3.2 µs、从 5.6 µs 降到 3.0 µs。集合的视图（`GetViewBetween`）以及布局无法识别的运行时仍用 `CopyTo`。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **空集合**：空的数组、列表、集合、字典、优先队列和不可变集合不再进入逐元素循环（一次调用，以及读取器或写入器的拷入拷出）；空的不可变集合和字典读成共享的 `Empty` 实例。树等含有大量空叶子集合的数据受益最多。
- **池里还没有归还过实例时读取 `[NinoPooled]` 类型**：从没放入过实例的池，取实例时只读一个字段就返回，不再为发现本线程的栈是空的而访问线程局部字段（并调用一次方法）。只对部分读取使用池的程序，以及线程局部字段开销最大的 Unity 和 IL2CPP，受益最多。基准测试中池化节点的反序列化在 GitHub 的 x64 runner（EPYC 7763）上从 205 ns 降到 156 ns，在 Arm64 runner（Neoverse-N2）上从 193 ns 降到 145 ns。参见[内置对象池](/zh/docs/v4/pooling#ninopooled)。
- **`ImmutableStack<T>`**（Nino.Immutable）序列化不再先填充并反转一个列表，且不分配内存：1,000 个 int 在 GitHub 的 Arm64 runner（Neoverse-N2）上从 4.5 µs 降到 2.7 µs，在 x64 runner（EPYC 7763）上从 3.1 µs 降到 2.9 µs。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **版本容错类型**：相邻的一组原始成员在数据完整时作为一个块读取，只做一次检查（旧版本写的数据走逐个成员的路径）：基准测试中版本容错类组成的数组，在 GitHub 的 x64 runner（EPYC 7763）上反序列化从 57.3 µs 降到 49.8 µs。键控类型把每个成员的键和区域长度一起预留。参见[版本容错](/zh/docs/v4/evolving-data#version-tolerance)。
- **Unity 的 `AnimationCurve` 和 `Gradient`**（Nino.UnityTypes）一次预留所需字节，读取时每段关键帧只做一次边界检查，而不是每个值一次。参见 [Unity 类](/zh/docs/v4/advanced/unity#unity-classes)。
- **原始元素组成的 `Memory<T>` 和 `ReadOnlyMemory<T>`** 的数组和普通数组一样分配：从 6 KB 起不清零。
- **2 到 6 KB 的新数组改为清零分配**：读取时一次块拷贝填满的数组，只在 6 KB 及以上才不清零分配，这时省下的清零开销才大于代价；更小的数组用运行时的不清零分配反而更慢。1,000 个 int 反序列化为 `ReadOnlyCollection<T>` 或 `ReadOnlySequence<T>`，在 GitHub 的 x64 runner（EPYC 7763）上从 348 ns 降到 257 和 264 ns，在 Arm64 runner（Neoverse-N2）上从 416 和 423 ns 降到 364 和 363 ns；反序列化为 `Memory<T>` 在 x64 上从 312 ns 降到 262 ns。

### 修复 [#fixes-4]

- 带子类型的泛型抽象类和泛型接口（`abstract class Box<T>`、`IRepository<T>`），以及嵌套在泛型类型里的抽象类，不再导致编译失败：之前在任何格式下生成的格式化器都编译不过。现在它们的子类型和非泛型基类型的子类型一样读写（见[分派](/zh/docs/v4/polymorphism#dispatch)），数据中的类型不是其子类型时会抛出异常（[#203](https://github.com/JasonXuDeveloper/Nino/pull/203)）。参见[接口与抽象类](/zh/docs/v4/polymorphism#interfaces-and-abstract-classes)。
- 嵌套在泛型类里的类（`Holder<long>.Base`）在其他程序集中有子类型时，第一次序列化不再栈溢出。参见[其他程序集中的子类型](/zh/docs/v4/polymorphism#subtypes-in-other-assemblies)。
- 生成器无法生成某个类型的格式化器时，构建会报一个指明类型和原因的错误，而不是在生成代码里报一堆错误。
- 序列化超过 4 GB 的非托管值 span、超过 1 G 字符的 `StringBuilder` 或超过 2 GB 的 UTF-8 文本时，抛出 `OverflowException`，不再越过缓冲区末尾写入。
- 代码修复（实现 `[NinoPooled]` 钩子、添加或移除特性）沿用所编辑文件的换行符：之前在 Windows 上会往使用 LF 换行的文件里插入 CRLF 行。参见[诊断列表](/zh/docs/v4/analyzers#diagnostics)。
- **不可信数据**：针对读取器伪造的数据不会再让进程崩溃：之前，一个通过列表、可空类型或接口成员包含自身的结构体，嵌套几千层就会栈溢出；现在和嵌套超过 512 层的对象一样抛出异常。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- 读入已有值（`Deserialize(data, ref value)`）失败时，原始类型元素的数组、列表或 `Memory<T>` 不会再留下一个装着未初始化内存的数组；`StringBuilder` 的长度和多维数组的各维度会先和数据比对再分配（之前 4 字节的 `StringBuilder` 数据会分配 2 GB）。
- 声称的元素数多于实际内容的数据，无法再让一次读取分配数百倍于自身大小的内存（之前 1 MB 声称装着大结构体的数据会分配 520 MB）：一个集合在读到元素之前最多预先分配输入剩余字节数的 16 倍，并随实际读到的元素扩容。参见[无效数据](/zh/docs/v4/basic#invalid-data)。
- 无效的 `Version`、`Uri`、`CultureInfo`、`TimeZoneInfo`、`DateTimeOffset` 值和字典的 null 键，抛出 Nino 的 `InvalidOperationException`（原异常放在 `InnerException` 里），不再抛出 BCL 的异常；所有无效输入都能用同一种方式捕获，[Nino.AspNetCore](/zh/docs/v4/advanced/aspnetcore) 也会返回 400 而不是 500。

## 4.0.0-rc.6

### 二进制格式 [#wire-format-2]

- **每个字符一个字节的字符串**：默认的 `string` 编码在所有字符都不超过 U+00FF（ASCII、Latin-1）时，每个字符写一个字节，头部为负数长度（`~长度`）；其他文本仍是 UTF-16，`[NinoUtf8]` 不变。这适用于所有默认编码的字符串：成员、集合的元素和键，以及 `Uri`、`CultureInfo` 和 `TimeZoneInfo` 值的文本。本版本仍能读取此前 v4 版本写出的 UTF-16 字符串，但此前的版本读不了本版本写出的单字节字符串，所以读取数据的一方要先于写入数据的一方升级，或者同时升级（[从更早的候选版本升级](/zh/docs/v4/migration#upgrading-from-an-earlier-release-candidate)）。`StringBuilder` 仍以 UTF-16 写出，两种形式都能读取。参见[二进制格式](/zh/docs/v4/platforms#binary-format)和[字符串编码](/zh/docs/v4/defining-types#string-encoding)。

### 新功能 [#new-4]

- **Nino.AspNetCore**：MVC 输入和输出格式化器（`AddNinoFormatters()`、`application/x-nino`、`?format=nino`）以及 Minimal API 支持（`NinoBody<T>` 参数、`NinoResults.Ok` 和 `NinoResults.Status`、`ReadFromNinoAsync` 和 `WriteAsNinoAsync`），直接基于请求和响应管道读写请求体与响应，自身不做任何分配。参见 [ASP.NET Core](/zh/docs/v4/advanced/aspnetcore)。
- **Nino.TypeScript**：一个构建包，每次构建后为项目的 `[NinoType]` 写出 TypeScript 类、枚举和编解码器（`NinoTypeScriptOutput`、`NinoTypeScriptImportExtension`、`NinoTypeScriptNames`），并附带 `nino.ts` 运行时，浏览器和 Node 读写的字节与 Nino 在 .NET 中写出的完全相同。无法表达的类型会被跳过，并给出警告 `NINOTS002`。参见 [TypeScript 客户端](/zh/docs/v4/advanced/typescript)。
- **按字节描述的布局元数据**：`[assembly: NinoTypeLayout]` 现在按每个成员写出的字节来描述它（`seq(string)`、`map(string,seq(raw(4)))`、`nullable(raw(4))`、`type(MyType)` 等），不再写格式化器类名；键控成员带上了它的键（`:key=0x…`）。用之前版本记录的布局，每个非原始内存成员的文本都会不同，但除字符串外字节并未改变；请重新记录。参见[布局元数据](/zh/docs/v4/evolving-data#layout-metadata)。
- **`NinoSerializer.IsSupported(Type)`** 判断 Nino 能否序列化和反序列化某个类型，供只有 `Type` 的集成代码使用。参见[装箱 API](/zh/docs/v4/basic#the-boxed-api)。

### 性能 [#performance-1]

- **含 Latin-1 字符串的数据更小**，序列化和反序列化时间与之前相同：基准测试中，`Orders` 从 30,848 字节降到 26,126 字节，`Players` 从 45,124 降到 39,164，`Tree` 从 40,676 降到 31,258，现在都比 MemoryPack 的更小（27,990、43,364 和 32,623）。参见[基准测试](/zh/docs/v4/perf)。
- **带填充的元组和键值对序列化更快**：值元组、`KeyValuePair` 以及其他内存中有填充的原始值组成的数组和列表，先对齐目标地址，再每个向量用一次双源置换按整向量写出它们的字节（AVX-512：每个 4 字节字都是内存中完整的一个字时按字置换，否则用 VBMI 按字节置换；AVX2；Arm64；.NET 10 上的 WebAssembly）：在一台 AVX-512 Xeon 上，1,000 个 `(int, long)` 序列化用时 106 到 109 ns，rc.5 为 228 ns，MemoryPack 为 136 到 141 ns。参见[各平台的 SIMD](/zh/docs/v4/platforms#simd)。
- **带填充的元组和键值对读取更快**：在 AVX-512 上，带填充的原始值按写入的方式读取，内存中每个 64 字节向量由其字节向量经一次双源置换得到，并存储到对齐地址：把 1,000 个 `(int, long)` 反序列化到已有的列表或数组需要 105 到 140 ns，rc.5 为 255 ns，与 MemoryPack（111 到 130 ns，按原样复制其 16 字节的值）持平。转换非 Latin-1 文本时同样按对齐地址存储：1,000 字符的非 Latin-1 字符串读取快约 8%（AVX-512 Xeon）。
- **中等大小的数组读取时不再清零**：2 到 6 KB 的非托管值数组、列表和只读集合，读取时和更大的数组一样以未初始化方式分配：1,000 个 `int` 的 `ReadOnlyCollection<int>` 反序列化从 570 到 590 ns 降到 450 到 510 ns（AVX-512 Xeon）。
- **TypeScript 编解码更快**：生成的代码在同一块缓冲区里按偏移读写连续的定长成员，`nino.ts` 用 Node（以及 Bun、Deno）的原生方法读写文本，浏览器中用 `TextDecoder` 和 `TextEncoder`。在 Node 中，1,000 条玩家记录序列化从 2.07 ms 降到 1.15 ms，反序列化从 1.92 ms 降到 1.17 ms；文本为主的记录快 6.8 倍和 11 倍，数值数组快 2 到 5 倍。短文本读得更快：在 Node 中，不超过 12 个字符的字符串从对最多 4 KB 数据的一次 Latin-1 解码中切出，不超过 16 个字符的文本用一次 `String.fromCharCode` 调用读取，因此含短字符串的小记录列表反序列化从 0.81 ms 降到 0.46 ms（Chromium 中从 0.65 ms 降到 0.42 ms），短字符串映射在 Node 中快 1.5 倍。`serialize` 不再复制结果：每个结果都紧接在上一个之后写进共享的 64 KB 缓冲区，返回它上面的视图，且永远不会被覆盖；在 Chromium 中，数值和结构体数组的序列化快 1.3 到 1.5 倍。参见 [API](/zh/docs/v4/advanced/typescript#api) 和[与 JSON 对比](/zh/docs/v4/advanced/typescript#compared-with-json)。

### 修复 [#fixes-3]

- **Unity：引用了带 internal `ModuleInitializerAttribute` 的库**（如 ZLinq 的 netstandard 版本）时不再编译失败：生成器曾在注册表中引用这个 polyfill（错误 CS0122 "'ModuleInitializerAttribute' is inaccessible due to its protection level"）。现在只有程序集能访问某个初始化特性时才会使用它，Unity 照旧通过 `[RuntimeInitializeOnLoadMethod]` 注册。参见 [Unity](/zh/docs/v4/advanced/unity)。
- **TypeScript：以 U+FEFF 开头的 `[NinoUtf8]` 字符串**不再反序列化失败：`TextDecoder` 把这个字符当作字节序标记丢掉了。参见 [TypeScript 客户端](/zh/docs/v4/advanced/typescript)。

## 4.0.0-rc.5

### 新功能 [#new-3]

- **更多内置类型**：`BigInteger`、`Uri`、`Version`、`StringBuilder`、`BitArray`、`CultureInfo`、`TimeZoneInfo`、`Lazy<T>`、`Memory<T>`、`ReadOnlyMemory<T>`、`ReadOnlySequence<T>`、`ReadOnlyCollection<T>`、`ReadOnlyObservableCollection<T>`、`ILookup<TKey, TElement>`、`IGrouping<TKey, TElement>` 和 `BlockingCollection<T>` 不再需要自定义格式化器。如果 Nino 已经支持形状相同的类型，就沿用它的字节：`Memory<T>` 和 `ReadOnlySequence<T>` 按 `T[]` 写入，`ReadOnlyCollection<T>` 按 `List<T>` 写入，`StringBuilder` 按 `string` 写入。`System.Type` 有意继续不支持。参见[支持的类型](/zh/docs/v4/types#other-built-in-types)。
- **所有不可变集合**：`Nino.Immutable` 在 `ImmutableArray<T>` 和 `ImmutableList<T>` 之外，新增 `ImmutableHashSet<T>`、`ImmutableSortedSet<T>`、`ImmutableQueue<T>`、`ImmutableStack<T>`、`ImmutableDictionary<TKey, TValue>` 和 `ImmutableSortedDictionary<TKey, TValue>`，每种都与对应的可变集合字节相同。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **Unity 的 `AnimationCurve`、`Gradient` 和 `RectOffset`**：Unity 包附带 `Nino.UnityTypes.dll`，提供它们的格式化器，因此它们可以作为成员、元素和顶层值使用，支持 `null` 和 `ref` 复用。参见 [Unity 的类](/zh/docs/v4/advanced/unity#unity-classes)。

### 性能 [#performance]

- **`Stack<T>`、`Queue<T>` 和以接口声明的集合**（`IList<T>`、`IEnumerable<T>`、`IReadOnlyCollection<T>` 等），元素是非托管值或按原始内存复制的 `[NinoType]` 结构体时，会像 `List<T>` 和数组一样整块读写。以 1,000 个 `int` 为例，序列化快 17 到 75 倍，反序列化快 2.5 到 6 倍。其他元素类型的 `Stack<T>` 和 `Queue<T>` 也改为直接读写其内部数组。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`DateTimeOffset`** 改为直接读写它的两个字段（字段位置在启动时检查一次，因为 .NET 10 的字段顺序和 .NET 8、.NET Framework、Mono 不同），它的数组和列表整块读写。以 1,000 个值为例，序列化快 2.9 倍，反序列化快 2 倍。非法数据仍抛出与构造函数相同的异常。参见[基元类型与非托管类型](/zh/docs/v4/types#primitive-and-unmanaged-types)。
- **`[NinoType]` 结构体的数组和列表**在该结构体被单独序列化之后，仍使用生成的格式化器；以前此后每个元素都要经过一次虚调用，按原始内存复制的结构体也不再整块复制。以 1,000 个小结构体（`int`、`short`、`bool`）为例，序列化快 15 倍，反序列化快 3.6 倍。短字符串和其他不超过 32 字节的块改为内联复制：`List<KeyValuePair<int, string>>` 序列化快 1.3 倍。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **集合中的小类**：最多有八个成员、其中最多两个需要调用格式化器（字符串、集合或其他类型）的类，其主体会内联到集合的循环中，未密封的类也是如此。子类型和 null 的处理不变。这类未密封类的列表序列化约快 2 倍，反序列化约快 1.3 倍。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **64 字节到 8 KB 的块**（非托管值和原始结构体的数组、字符串）在支持 AVX-512 的 CPU 上用 64 字节向量写出，最多快 1.5 倍；带填充的结构体数组改用 64 字节掩码复制：1,000 个由 `int`、`short` 和 `bool` 组成的结构体序列化快 1.6 倍。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **含字符串或其他非原始成员的结构体**改为按引用传给生成的主体，不再按值传递，因此每个元素不再先复制到栈上。由 1,000 个结构体（四个 `long`、一个 `string` 和一个 `int`）组成的列表序列化快 2 倍。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **字符串**在 .NET 8 及以上由运行时直接分配并在内联代码中填充，省去了 `new string` 的参数检查和复制调用：读取 3 到 12 个字符的字符串从 16 到 19 ns 降到 12 到 14 ns，含大量短字符串的类型反序列化快 3% 到 7%。其他运行时的读取方式不变。参见[字符串](/zh/docs/v4/types#strings)。
- **含嵌套成员的类和结构体**：把读取器或写入器复制到局部变量再复制回去时，改为逐个字段复制，CPU 可以直接从之前的写入转发数据，不必等它们写入缓存，读写位置得以一直留在寄存器中。玩家对象列表序列化快 19%，反序列化快 8%；小类列表、订单和树快 5% 到 10%。写出的字节不变。
- **新建的非托管值或原始结构体 `List<T>`**，大小在 6 KB 及以上时，其底层数组不再先清零再复制元素，和数组的做法一致：10,000 个 `int` 的列表反序列化快约 15%。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`ImmutableArray<T>` 和 `ImmutableList<T>`**（`Nino.Immutable`）改为通过数组读写：`ImmutableArray` 直接包装读入的数组，不再复制；`ImmutableList` 从数组一次建好。1,000 个元素的 `ImmutableArray<int>` 序列化快 13 倍、反序列化快 8 倍，1,000 个元素的 `ImmutableList<int>` 反序列化快 3.6 倍。写出的字节不变。参见[不可变集合](/zh/docs/v4/types#immutable-collections)。
- **由非托管值组成的值元组和 `KeyValuePair`**（如 `(int, long)`）：每个元组只做一次容量检查；它们的数组与列表（如 `(int, int)[]`、`List<(int, long)>`）改为整块读写：值的内存与写出的字节一致时直接按内存复制，否则用 SIMD 字节重排（SSSE3、Arm64、AVX-512 VBMI）每次处理 16 或 64 字节。1,000 个 `(int, int)` 或 `KeyValuePair<int, int>` 序列化快 16 到 19 倍，反序列化快 2.5 到 3 倍。1,000 个元素的 `List<(int, long)>` 先是序列化快 1.25 倍、反序列化快 2.3 倍（每个元组一次容量检查，元素循环把读取位置保留在寄存器里），整块读写后又分别快 5.4 倍和 2 倍。写出的字节不变。参见[其他内置类型](/zh/docs/v4/types#other-built-in-types)。
- **`SortedSet<T>`、`SortedDictionary<TKey, TValue>`、`SortedList<TKey, TValue>`、`LinkedList<T>` 和 `ConcurrentDictionary<TKey, TValue>`**（及其派生类型）改为通过它们自己的字段和方法读写，不再走通用的集合循环：有序集合和有序字典先读成数组，再一次建好平衡树；有序列表在键按其比较器有序时直接读进键数组和值数组；由 Nino 创建的 `ConcurrentDictionary`（没有已有实例，且不是派生类型）用读到的键值对调用其构造函数创建，表一次分配到位，插入时不加锁。1,000 个 `int` 或 `int` 键值对时，`ConcurrentDictionary` 反序列化从 1.88 ms 降到 15 µs（改为直接调用后快 28 倍，改用构造函数后又快约 4 倍），序列化快 1.3 倍；`SortedDictionary` 反序列化先快 1.8 倍、再快 1.5 倍，序列化快 1.9 倍；`SortedList` 反序列化快 5.5 倍、序列化快 1.4 倍；`SortedSet` 序列化和反序列化都快 2 倍。写出的字节不变，重复键和 null 键仍抛出同样的异常。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **`ConcurrentStack<T>`**：新建的实例改为一次 `PushRange` 填入，不再逐个 Push，快约 1.9 倍（1,000 个 `int` 从 17.9 µs 降到 9.3 µs）；新建的 `ConcurrentQueue<T>` 改用构造函数创建，首个分段一次按元素个数分配。已有实例和派生类型照旧填充。写出的字节不变。参见[集合类型](/zh/docs/v4/types#collection-types)。
- **更多 CPU 用上 SIMD**：在没有 AVX-512 的 x64 CPU 上（AVX2，大多数台式机），256 字节到 4 KB 的块改用 32 字节向量复制：256 字节从 6.3 ns 降到 3.9 ns，2,500 字节从 36.3 ns 降到 24.6 ns。在 Arm64 上，8 字节以内的值元组、`KeyValuePair` 和原始结构体的数组与列表改用查表指令每次重排 64 字节，与 x64 上的 AVX-512 VBMI 相同；在 .NET 10 上，16 字节的字节重排也支持 WebAssembly SIMD。写出的字节不变。

### 修复 [#fixes-2]

- **.NET Framework 和 Mono 上的 `List<T>`**：Nino.Core 的 netstandard 版本按 .NET 的字段位置读写 `List<T>`，但 .NET Framework 和 Mono 的 `List<T>` 多一个字段，导致列表被写成空列表，读入的列表也会损坏。现在 Nino 直接读写字段的每种集合（`List<T>`、`Stack<T>`、`Queue<T>`、`SortedList<TKey, TValue>`、`SortedSet<T>`、`SortedDictionary<TKey, TValue>`）都会在启动时用一个内容已知的实例核对一次布局；布局不符的运行时改用公开方法读写。这些快速路径现在在 .NET Framework 和 Mono 上同样生效。参见[集合类型](/zh/docs/v4/types#collection-types)。
