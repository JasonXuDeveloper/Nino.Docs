Nino 不用调优就很快。这一页讲它内部怎么做，好让你的类型和调用一直留在快速路径上。实测数据见 [.NET 基准测试](/zh/docs/v4/benchmarks)；在自己的代码里怎么用好这些路径，见[高性能序列化](/zh/docs/v4/advanced/high-performance)和[零分配模式](/zh/docs/v4/advanced/zero-allocation)里的做法。

## 拦截器 [#interceptors]

项目用 **Roslyn 4.8 及以上版本**编译时（.NET 8 SDK 及以上、Visual Studio 2022 17.8+、新版 Rider），只要调用处知道类型实参，生成器就会拦截这次 `NinoSerializer`/`NinoDeserializer` 调用，在编译期把它直接接到生成的格式化器上。这样调用就绕过了格式化器缓存（`NinoFormatterCache<T>`，常规调用在这里查 `T` 的格式化器）和其中的虚调用，字节完全一样。

```csharp
// 会拦截：这里知道具体类型
byte[] bytes = NinoSerializer.Serialize(order);
Order copy = NinoDeserializer.Deserialize<Order>(bytes);

// 不拦截：T 是类型参数，走普通调用
static byte[] Save<T>(T value) => NinoSerializer.Serialize(value);
```

每次调用省下几纳秒，在紧密循环里频繁序列化小数据时最有用。

- **一直开启，不用配置，也关不掉。** `Nino.Generator` 包里有面向 Roslyn 4.3、4.8 和 4.12 的三个生成器版本，NuGet 挑你的编译器能加载的最新那个。4.8 和 4.12 版本会拦截调用，包里的 build props 会自动把 `NinoGen` 加进 `InterceptorsNamespaces` / `InterceptorsPreviewNamespaces`。
- **看编译器，不看目标框架**：用 .NET 8+ SDK 编译的 `netstandard2.0` 库一样会拦截。
- **旧编译器直接走常规路径**，字节一样。Unity 包里是生成器的 Roslyn 4.3 版本，所以 Unity 项目从不拦截。
- 有些调用不拦截，因为拦截了也没好处：原始值和原始元素数组（常规路径本来就直接拷贝；只有原始值的 `Deserialize<T>(data)` 会拦截，变成一次读取）；在别的程序集里声明的 `[NinoType]`（调用方项目只能经格式化器缓存拿到它的格式化器，和常规调用一样）；以及泛型代码里的调用。
- [固定大小类型](#fixed-size-types)的 `Serialize(value)` 会改调专门的代码，直接写进大小正好的 `byte[]`。
- 项目里设了 `<NinoPrefetchLargeCollections>true</NinoPrefetchLargeCollections>` 后，类的大数组和大列表的拦截调用还会预取里面的对象；见[散落在内存中的大型集合](/zh/docs/v4/advanced/high-performance#large-collections)。
- 拦截的调用和常规调用用的总是同一个格式化器：格式化器都用特性声明，运行时换不掉，所以生成器知道运行时会找到哪一个。

<Callout type="warn">

如果项目自己设置了 `InterceptorsNamespaces` 或 `InterceptorsPreviewNamespaces`，要在原值后面**追加**（`$(InterceptorsNamespaces);MyNamespace`），别直接覆盖。不然 `NinoGen` 就丢了，Nino 不生成拦截器（常规调用照样能用）。

</Callout>

## 内联的结构体格式化器 [#struct-formatters-inlined]

所有格式化器都是结构体，元素的格式化器作为类型实参传进去（`ListFormatter<TList, T, TFormatter>`）。成员用 `default(TFormatter).Serialize(...)` 调用格式化器，这是 JIT 或 AOT 编译器能内联的直接调用。所以序列化一个 `List<Order>`，编译出来就是一个循环，循环体里直接写 Order 的各个成员。没有哪个元素要虚分派，哪里都没有反射。

剩下的唯一一次间接调用，是你自己发起的那次，比如 `NinoSerializer.Serialize(value)`：没被拦截时，它要经 `NinoFormatterCache<T>`（一个泛型静态字段，也就是格式化器缓存）找到 `T` 的格式化器。

## 精简的机器码 [#machine-code]

顶层调用会把整条格式化器链内联进一个方法，JIT 为这一整个方法只有一份内联预算。Nino 把预算留给你的数据真正要走的路径：

- **罕见路径是函数调用。** 大块拷贝的向量循环、逐元素循环、原始读取里的拷贝、不是 Latin-1 的字符串、回收，都是单独的方法，不内联，所以读一个 `SimpleClass` 不会带上一段它永远跑不到的 512 位拷贝循环。原本要调好几次辅助方法的检查，合并成一个 `static readonly` 字段，JIT 把它当常量读。这些路径上的小辅助方法都标了 `AggressiveInlining`：在很大的方法里，哪怕参数全是常量，JIT 也可能不内联。
- **不做永远不会失败的检查。** 元素循环（数组和列表的回退路径、原地读取、填充掩码、对象池、引用表、不可变集合）用指向元素的引用遍历，不用下标，所以每个元素都没有边界检查，往引用类型数组里存值也没有协变检查。块大小是 JIT 期常量，除以它只是一次移位。长度溢出检查保留：每次调用一次，用来防恶意输入。

Nino 仓库每次改动读写路径都会检查这一点：`benchmarks/asm.py compare` 列出和基准提交相比机器码变了的每个方法，所以一个改动不会悄悄拖慢它没碰过的类型。

## 非托管数据按原始内存拷贝 [#raw-memory-for-unmanaged-data]

非托管值按原始内存拷贝：

- 基元类型、枚举、`DateTime`、`Guid`、`Vector3` 和其他非托管结构体；
- `[NinoType]` 中连续的非托管成员，作为**一整块**写入，只做一次边界检查；
- 非托管元素的数组、`List<T>`、`Stack<T>`、`Queue<T>`、`ImmutableArray<T>`，以及声明为接口（`IList<T>`、`IEnumerable<T>` 等）的集合：整个集合**一次拷贝**；
- 非托管元素的 `HashSet<T>` 和 `Dictionary<TKey, TValue>`：只预留一次空间，直接从集合自己的 entries 数组里把键和值整块取出，CPU 支持时用 [SIMD](/zh/docs/v4/simd#dotnet) 一次处理多个 entry（见[可移植的设计](/zh/docs/v4/platforms#portable-by-design)里的“集合的内部字段”）；
- 非托管值组成的值元组和 `KeyValuePair` 的数组和列表：整块处理，CPU 支持时用 [SIMD](/zh/docs/v4/simd#dotnet) 重排成写出的顺序；
- 符合原始内存条件的 `[NinoType]` 结构体（见[结构体](/zh/docs/v4/defining-types#structs)），不管是单独出现还是在数组、列表里；
- 大小固定、但不符合原始内存条件的 `[NinoType]` 结构体（含值元组或 `KeyValuePair` 成员、`LayoutKind.Auto`、自动属性，或者里面套着这样的结构体）的数组、列表和 span：它的生成格式化器也按块读写，每个成员在固定偏移上，所以整个集合只做一次边界检查，在 .NET 8+ 上还能走元组的向量路径（没有 SIMD 时是一个循环），不用一个值一个值地处理。条件是每个成员都是原始值、原始值组成的元组或键值对，或者另一个这样的结构体，而且都能就地赋值（没有 `[NinoConstructor]`，也没有只能 `init` 的成员）；可空成员不算固定大小。字节不变。

写入时会把填充字节清零，所以相等的值总是写出相同的字节，哪怕结构体放在从没清零过的内存里（`ArrayPool` 租来的数组、`[SkipLocalsInit]` 下的 `stackalloc`）。Nino 在运行时第一次写某个类型时识别填充：字段偏移只读一次，结果成为 JIT 期常量，所以没有填充的结构体不为这项检查付任何代价。带填充的结构体数组在同一趟拷贝里用 SIMD 掩码处理，比普通 `memcpy` 稍贵一点。如果某个运行时在内存里排布结构体的方式和规范布局不同（Mono、IL2CPP、.NET Framework 和 32 位平台上的部分结构体），就改成逐字段转换（[结构体布局](/zh/docs/v4/struct-layouts#cost)）。

### 结构体布局 [#struct-layout]

热点结构体怎么声明，决定它走哪条路径：

| 声明方式 | 路径 |
| --- | --- |
| 调整字段顺序，让它不需要填充（`int, int, DateTime`） | 普通的整块拷贝 |
| 给 `int, DateTime` 加上 `[StructLayout(LayoutKind.Sequential, Pack = 4)]` | 结构体更小（12 字节而不是 16 字节），整块拷贝：最快，数据也最小 |
| 字段之间有空隙（`int, DateTime`：`int` 后面空 4 字节） | 整块拷贝，再用掩码清掉填充 |
| `[StructLayout(LayoutKind.Auto)]` | **不按原始内存写**：运行时可能重排字段，所以 Nino 逐个字段写，耗时是整块拷贝的好几倍；不过它的数组和列表仍然按块读写（见上文） |

```csharp title="Layouts.cs"
using System;
using System.Runtime.InteropServices;
using Nino.Core;

[NinoType]
public partial struct Sample // 16 字节，其中 4 字节是填充
{
    public int Id;
    public DateTime Time;
}

[NinoType]
[StructLayout(LayoutKind.Sequential, Pack = 4)] // [!code highlight]
public partial struct PackedSample // 12 字节，没有填充
{
    public int Id;
    public DateTime Time;
}
```

填充是怎么来的：默认（`LayoutKind.Sequential`）每个字段按自身大小对齐（最多 8 字节），结构体的大小再向上取整到最大的对齐值。`DateTime` 内部是一个 `ulong`，必须从 8 的倍数开始：在 4 字节的 `int` 后面，运行时会塞进 4 个空字节。调整字段顺序（大的在前）能去掉字段之间的填充，去不掉末尾的：`DateTime, int` 还是 16 字节。

`Pack = N` 把每个字段的对齐上限设成 `N`。要去掉全部填充，就把 `Pack` 设成**最小字段**的大小：这样每个字段都紧挨着前一个。`Pack` 设大了还可能留空隙：`short, long, short` 默认 24 字节，`Pack = 2` 是 12 字节（没有填充），`Pack = 4` 还是 16 字节。`Pack = 1` 总能去掉填充，但也让本来不必的字段失去了对齐。

`Pack` 也会改变结构体在内存里的布局：`Time` 不再按 8 字节对齐。这在 x64 和 ARM64 上没有开销，但会改变写出的字节，所以存数据之前就要定好布局。

怎样让你自己的类型一直走这条路径（用哪些集合、什么会关掉原始内存拷贝），见[批量数据保持原始内存格式](/zh/docs/v4/advanced/high-performance#keep-bulk-data-raw)。

<Callout type="info">

原始布局以 64 位平台的规范布局为准。在结构体布局不同的运行时上（32 位平台、旧版 Mono），Nino 逐个字段转换成同样的字节，数据照样可移植，只是慢一些。参见[平台](/zh/docs/v4/platforms)。

</Callout>

## 固定大小的类型 [#fixed-size-types]

有些类型不管值是什么，写出的字节数都一样。对这类类型，`NinoSerializer.Serialize(value)` 按最终大小分配 `byte[]`，把值直接写进去：不用暂存缓冲区，不用 writer，没有扩容检查，最后也不用拷贝。字节和通用路径一样。

```csharp title="SensorReading.cs"
using Nino.Core;

[NinoType]
public struct GeoPoint               // 原始值：8 字节
{
    public float Latitude;
    public float Longitude;
}

[NinoType]
public sealed class SensorReading    // 固定大小：1（存在字节）+ 4 + 8 + 8 + 1 = 22 字节
{
    public int SensorId;
    public long Timestamp;
    public GeoPoint Location;
    public bool Alarm;
}
```

```csharp
byte[] bytes = NinoSerializer.Serialize(reading);         // 一个新的 byte[22]，值直接写在里面
int size = NinoSerializer.GetFixedSize<SensorReading>();  // 22
```

满足下面几条的类型是固定大小的：

- 非泛型的 `[NinoType]` **结构体**或**密封类**；
- 格式是 `NinoFormat.Positional`（默认），没开 `trackReferences`，也不是集合类型；
- 所有成员都是在 32 位和 64 位运行时上布局相同的非托管值（基元类型、枚举、`DateTime`、`Guid`，以及由它们组成的原始结构体），或者其他固定大小的结构体，并且没有 `[NinoMemberFormatter]`。

有 `string`、数组或集合、类、`T?`、元组、`DateTimeOffset` 或 `nint` 成员，类型的大小就不固定。按原始内存写的结构体（见[原始内存](#raw-memory-for-unmanaged-data)）也是固定大小的，而且一直都是直接拷进大小正好的数组；这条路径把同样的待遇扩展到不能按原始内存写的结构体（有忽略的字段、套了别的结构体）和密封类。

- **自动生效。** 在 Roslyn 4.8+ 上，[拦截器](#interceptors)把固定大小类型的 `Serialize(value)` 接到这条路径；没有拦截器时（Unity、泛型代码、旧编译器），常规调用做一次检查后也走这条路径，优化后的代码会把这次检查折叠成常量。
- 只有返回 `byte[]` 的 `Serialize(value)` 走这条路径。序列化到 `IBufferWriter<byte>` 或 `Writer` 照旧。元素整块写入的数组和列表（非托管值、原始结构体、元组、`DateTimeOffset`）也直接写进大小正好的数组（见[内存分配](#allocation)）；其他固定大小类型的数组和列表走常规路径。
- 值为 `null` 的密封类只写一个存在字节；其他值都正好占 `GetFixedSize<T>()` 字节。
- `NinoSerializer.GetFixedSize<T>()` 对固定大小的类型和原始值返回大小，对其他类型返回 `-1`。可以用它定缓冲区大小，或者在启动时检查消息的大小。

## 内存分配 [#allocation]

- **序列化不分配内存**，只有你要的那个 `byte[]` 例外。序列化到复用的 `NinoArrayBufferWriter`（或任意 `IBufferWriter<byte>`），每次调用分配 0 B。
- **返回的 `byte[]` 大小正好**：写之前就知道大小的（固定大小的值，以及元素固定大小的数组和列表），Nino 按这个大小分配，直接写进去；其他值先写进池化的暂存缓冲区，再拷出来一次。
- **反序列化只分配结果对象**，这些对象也能复用：用 `ref` 读入已有实例，新实例从 `[NinoPooled]` 对象池里取。复用实例时分配 0 B，只有内容变了的字符串例外：内容没变的字符串原样保留，变了的文本才读成新实例（非 ASCII 的 `[NinoUtf8]` 文本一律读成新实例）。见[复用与对象池](/zh/docs/v4/pooling)。
- 默认情况下，字符都不超过 U+00FF 的字符串每个字符写一个字节，其他文本按 UTF-16 写，都只要一遍收窄、扩宽或复制。`[NinoUtf8]` 要转码，非空字符串在字符数后面还要多写一个字节数（UTF-8 不超过 127 字节时占 1 字节）；只有以 ASCII 为主、夹着少量更宽字符的文本，用它才更小（见[字符串](/zh/docs/v4/wire-format#strings)）。

每种写入目标是直接写，还是先写进当前线程的<Term id="scratch-buffer" lang="zh">暂存缓冲区</Term>再拷贝一次，以及每种调用分配什么，见[哪些调用会分配内存](/zh/docs/v4/advanced/zero-allocation#what-allocates)。读取这边，`NinoDeserializer` 接受 `ReadOnlySpan<byte>`：手里已有的内存（池化数组、管道分段、内存映射文件），切一段直接传进去就行，不用拷贝。

## 线程安全 [#thread-safety]

`NinoSerializer` 和 `NinoDeserializer` 的所有方法都**能并发调用**，不用加锁：

- 热路径不写共享内存，所以多个序列化线程不会争用缓存行；
- 暂存缓冲区和引用追踪表每个线程一份；同一线程上的嵌套调用（比如在自定义格式化器里再序列化一次）也有自己的一份，所以重入是安全的；
- 格式化器查找用的是只写一次的泛型静态字段；多态表是不可变快照，写时复制替换，读取无锁；
- `NinoPool<T>` 每个线程最多留 64 个实例，只有批量转移时才碰加锁的共享栈；它的热字段独占一条 64 字节的缓存行。

**不**线程安全的是你自己持有的状态：`NinoArrayBufferWriter`、`Writer` 或 `Reader`，以及反序列化的目标对象。每个线程或每个连接各用一个缓冲区。

<Callout type="warn">

`NinoSettings` 的值是普通字段，读的时候不做同步。在启动时、任何线程第一次序列化之前就设好。

</Callout>

## 多态 [#polymorphism]

多态值多花 4 字节的类型 ID。子类型和基类声明在同一个程序集里时，生成器为写入生成一串类型判断，为读取生成一个按 ID 的 `switch`，常见的情况直接调用子类型的格式化器；别的程序集里的子类型、泛型子类型和开了引用追踪的类型，经无锁注册表分派；泛型基类的每个封闭类型，其子类型也照这个方式分派。密封类只要一个存在字节，也不用分派；该怎么做见[密封类，以及通过基类分派](/zh/docs/v4/advanced/high-performance#sealed-and-polymorphic)。

## 测量 [#measuring]

- 用 BenchmarkDotNet 或其他长时间运行的方式测。分层编译下，短时间运行测到的是没优化的 Tier-0 代码，这时 Nino 里 `static readonly` 的布局检查还没折叠成常量。
- 反序列化大集合时，时间往往主要花在分配和清零结果上，不在 Nino 本身。用复用实例的方式测，才看得出序列化器自己占多少。
