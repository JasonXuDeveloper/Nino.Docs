Nino runs on .NET Standard 2.0 and later, Unity 2022.3+ (Mono and IL2CPP) and Godot 4, and writes the same bytes on every runtime, CPU and pointer size. This page lists the supported targets and describes the binary format.

## Supported Platforms

| Component | Targets |
| --- | --- |
| `Nino.Core` (runtime) | `netstandard2.0`, `netstandard2.1`, `net8.0`, `net10.0` |
| `Nino.Generator` (generator, analyzer) | Roslyn 4.3 and later; builds for Roslyn 4.3, 4.8 and 4.12 in one package |
| `Nino.Immutable` (immutable collections) | `netstandard2.0`, `net8.0` |
| `Nino.AspNetCore` ([ASP.NET Core](/en/docs/v4/advanced/aspnetcore)) | `net8.0`, `net10.0` |
| `Nino.Codegen`, `Nino.Codegen.Tool` ([TypeScript, Go and Rust](/en/docs/v4/advanced/codegen)) | a build tool for projects of any target framework, and a .NET tool, run on .NET 8 or later; the generated code needs TypeScript 5.7+ (ES2020 environments), Go 1.22+ or Rust 1.88+ |
| Generated code | C# 9 or later |
| Unity | 2022.3 and later, Mono and IL2CPP, every player platform |
| Godot | Godot 4 .NET projects (.NET 8 from Godot 4.4, .NET 6 before) |
| Hot update | HybridCLR, with no initialization call |
| Trimming and Native AOT | annotated in the `net8.0` and `net10.0` builds ([details](#trimming-and-native-aot)) |

**Every target writes identical bytes.** `netstandard2.0`, `netstandard2.1`, `net8.0` and `net10.0` each use the best primitives available to them ([SIMD](#simd), `[UnsafeAccessor]` on .NET 8+), and the test suite checks the same golden payloads against each build. Data written by a .NET 10 server can be read by a Unity IL2CPP client on a 32-bit Android phone, and the other way round.

## Binary Format

Every platform writes the format the [Wire Format](/en/docs/v4/wire-format) page describes, byte by byte in the specification it links to: little-endian values written unaligned, with no envelope, schema or field names, since the declared type decides how the bytes are read. A string has a header of 1, 3 or 5 bytes and is written in one byte a char when every char is at most U+00FF, otherwise as UTF-16 ([Strings](/en/docs/v4/wire-format#strings)); an unmanaged value is its bytes in one canonical layout ([Raw Values](/en/docs/v4/wire-format#raw-values)); an object has a header chosen by its declared type and a body in its type's format ([Objects](/en/docs/v4/wire-format#objects)). Every length is checked against the bytes left before anything is allocated ([Untrusted Data](/en/docs/v4/security)). How Nino keeps these bytes the same where runtimes lay out memory differently is the next section.

## Portable by Design

Nino defines its bytes instead of copying whatever a runtime has in memory. Runtimes do not always agree on memory layout, so these cases are handled explicitly:

<Accordions type="multiple">
<Accordion title={<><code>Nullable&lt;T&gt;</code></>} value="nullable">

CoreCLR and Unity 2021.3+ store `bool hasValue; T value;`, while old Mono (Unity 2019.4 and earlier) stores the value first. Copying a `T?` as raw memory produces different bytes on each. Nino writes a single `T?` as a presence byte followed by the value; arrays and lists of `T?` use the canonical layout and are converted element by element where the runtime differs.

</Accordion>
<Accordion title={<><code>ValueTuple</code> and <code>KeyValuePair</code></>} value="tuple">

`ValueTuple` is `LayoutKind.Auto` on .NET, so CoreCLR may reorder its fields, while Mono lays them out sequentially. Nino always writes a tuple or `KeyValuePair` as its items in declaration order, never as its memory. Arrays and lists of tuples and pairs whose items are all raw are still moved as one block: copied as memory where the runtime's layout matches the bytes (checked once at startup), otherwise rearranged with [SIMD shuffles](#simd) where the CPU has them, else item by item. The bytes are the same on every path.

</Accordion>
<Accordion title={<><code>decimal</code>, <code>DateTimeOffset</code>, <code>nint</code></>} value="bcl">

`decimal` is aligned to 8 bytes on CoreCLR and to 4 on Mono and IL2CPP, so a struct holding one can have a different layout; Nino converts it to the canonical layout. `DateTimeOffset` is written as UTC ticks plus the offset in minutes (10 bytes), never raw. `nint`/`nuint` are always 8 bytes.

</Accordion>
<Accordion title="32-bit platforms" value="32bit">

`struct { int a; long b; }` is 16 bytes on x64 and 12 bytes on x86 .NET and Mono. Nino's raw layout is the canonical 64-bit one; where a runtime differs, values are converted field by field into the same bytes (at some cost in speed) and bulk raw copies are skipped.

</Accordion>
<Accordion title="Padding" value="padding">

Code that builds structs in uninitialized memory (`SkipLocalsInit`, `stackalloc`, `GC.AllocateUninitializedArray`) can leave stale bytes in padding. Nino zeroes padding on write, so equal values always serialize to equal bytes and no stale memory leaks into a payload.

</Accordion>
<Accordion title="Big-endian hosts" value="endian">

Not supported. Constructing a `Writer` or `Reader` on a big-endian host throws `PlatformNotSupportedException`, so Nino never writes or reads bytes in the wrong order. Every platform .NET and Unity run on today is little-endian.

</Accordion>
<Accordion title="Collection internals" value="collection-layouts">

Nino reads and writes the fields of `List<T>`, `Stack<T>`, `Queue<T>`, `SortedList<TKey, TValue>`, `SortedSet<T>` and `SortedDictionary<TKey, TValue>` directly, and their layouts differ between runtimes (.NET Framework and Mono add a `_syncRoot` field). Each layout is checked once at startup against instances whose contents are known; a collection whose layout is not recognized goes through its public methods. Either way it writes the same bytes. (On .NET 8 and later, `List<T>` goes through `CollectionsMarshal`.)

`HashSet<T>` and `Dictionary<TKey, TValue>` of unmanaged elements are written straight from their entries array when no entry has been removed. Three layouts are recognized (.NET 5 and later, 64-bit and 32-bit; .NET Framework, Mono and Unity), each checked at startup against a collection with an entry removed and filled again. A set or dictionary with removed entries, or one on a runtime whose layout is not recognized (an IL2CPP build that differs, for one), goes through its enumerator and writes the same bytes. A new set or dictionary that a read creates (default comparer) is filled the same way in reverse: its entries and buckets are written as `Add` would write them. How a runtime hashes (whether hash codes are masked to 31 bits, what an empty bucket holds) is found at startup by filling a collection and checking it through the public API; where none passes, and in the netstandard2.0 build for sets (no `EnsureCapacity` to size one), each element goes through `Add`.

</Accordion>
</Accordions>

## SIMD by Platform [#simd]

The net8.0 and net10.0 builds of `Nino.Core` use hardware intrinsics where the CPU has them (AVX-512, AVX2 and SSSE3 on x64, AdvSimd on Arm64, SIMD on WebAssembly) and portable code where it does not. Unity, .NET Framework and .NET Core 3.0 to .NET 7 load the netstandard builds, which have none; in Unity, [Burst-compiled kernels](/en/docs/v4/advanced/unity#burst-kernels) take their place. Every path writes the same bytes: the tests run with AVX-512, without it, without AVX2, with all SIMD turned off, and on Arm64. What each instruction set does in .NET, Unity, Go, Rust and TypeScript is in [SIMD on Every Platform](/en/docs/v4/simd).

## Unity

- Install from [OpenUPM](/en/docs/v4/start#unity-project). The package ships `Nino.Core.dll` and the generator (`Nino.Generator.dll`, labelled `RoslynAnalyzer`), `Nino.UnityTypes.dll` (formatters for [`AnimationCurve`, `Gradient` and `RectOffset`](/en/docs/v4/advanced/unity#unity-classes)), plus `System.Buffers`, `System.Memory` and `System.Runtime.CompilerServices.Unsafe`.
- Unity compiles against .NET Standard: there is no `[UnsafeAccessor]`, so a type with serialized non-public members or `[NinoPooled]` must be `partial` (NINO002), which its code fix adds in Rider or Visual Studio.
- The package ships the generator's Roslyn 4.3 build, so calls are not intercepted. They use the regular path and write the same bytes.
- Generated registries carry `[RuntimeInitializeOnLoadMethod]` (and `[InitializeOnLoadMethod]` in the editor), which runs them at startup and keeps them from being stripped by IL2CPP.
- Unity types such as `Vector3`, `Quaternion` and `Matrix4x4` are unmanaged and are written as raw memory.

See [Unity and HybridCLR](/en/docs/v4/advanced/unity) for project setup and IL2CPP tips.

## Godot

- Godot 4 C# projects are regular .NET projects (`Godot.NET.Sdk`, targeting .NET 8 from Godot 4.4 and .NET 6 before): install Nino from NuGet. The generator, the analyzers and, with the .NET 8 SDK, the interceptors run as in any .NET project; on .NET 6, types with serialized non-public members must be `partial`.
- Godot's math structs (`Vector3`, `Transform3D`, `Color`, ...) are copied as raw memory. Their layout differs in double-precision builds, so data containing them cannot move between a double-precision and a single-precision build.
- Engine objects (`Node`, `Resource`) are not serialized: store ids, paths or values instead.

See [Godot](/en/docs/v4/advanced/godot) for setup, save games, networking and rebuilding in the editor.

## HybridCLR and Hot Update

Generated registries are discovered lazily: the first time Nino meets a type of an assembly, or an unknown type id while reading, it finds that assembly's registry. A hot-update assembly loaded with `Assembly.Load` therefore needs **no initialization call**, and its types (including subtypes of base classes in AOT assemblies) are found on first use.

Generated code avoids forwarding facades on purpose: interpreters such as HybridCLR's and Mono's do not inline, so every extra call layer would cost real time there.

## Trimming and Native AOT [#trimming-and-native-aot]

The `net8.0` and `net10.0` builds of `Nino.Core` are marked `IsTrimmable` and `IsAotCompatible`, and the trim and AOT analyzers check every build, so publishing with `PublishTrimmed` or `PublishAot` gives no warnings from Nino. A project targeting .NET 8 or later gets one of these builds.

- **Native AOT** (and any runtime that cannot compile code): Nino uses only the formatters the generator wrote. Every type you serialize must therefore appear in code the generator sees, as a member type or as the type argument of a `Serialize` or `Deserialize` call. A type that only exists at run time fails with an error that names it, never with wrong data.
- **Trimmed apps on a JIT** keep the run-time path that builds formatters for such types; what it needs from the trimmer is annotated.
- **CPU features under Native AOT**: on x64, Native AOT compiles for SSE2 and checks for a few later instruction sets at startup, among them SSSE3, so Nino takes its [SSSE3 paths](#simd) on CPUs that have it. Its AVX2 and AVX-512 paths need a higher baseline, which also makes the app require it: `<IlcInstructionSet>x86-64-v3</IlcInstructionSet>` for AVX2, `x86-64-v4` for AVX-512, or `native` for the CPU of the build machine. On Arm64, AdvSimd is part of Native AOT's baseline and every Arm64 path is taken.

The generator writes the same formatters for IL2CPP, which is why Nino needs no reflection there either. See [Unity and HybridCLR](/en/docs/v4/advanced/unity#il2cpp).

## Unloading Assemblies

A server that hot-reloads its logic loads it into a collectible `AssemblyLoadContext` and unloads the old context on each reload. On .NET 8 and later, when the context of an assembly with generated Nino code starts unloading, Nino clears everything it cached for that assembly: its registry, the formatters, type ids and raw memory layouts of its types, its polymorphic subtypes and its `[assembly: NinoFormatter]` registrations. The old context can then be collected, and the new version of the same types loads without type id collisions.

```csharp
var context = new AssemblyLoadContext("logic", isCollectible: true);
var logic = context.LoadFromAssemblyPath(path);
// ... serialize and deserialize the logic's [NinoType]s ...

context.Unload(); // Nino clears what it cached for the assembly here
```

The net8.0 and net10.0 builds of Nino.Core do this, and a project targeting .NET 8 or later gets one of them. A project on .NET Core 3.0 to .NET 7 gets the netstandard2.1 build, which cannot reach `AssemblyLoadContext`: there, call `NinoRegistry.Remove(assembly)` yourself before unloading, and the context is collected just the same.

```csharp
NinoRegistry.Remove(logic); // .NET Core 3.0 to .NET 7
context.Unload();
```

On .NET 8 and later, `Remove` does nothing more than the automatic cleanup; call it only to be sure the cleanup has happened before you unload. Unity (Mono and IL2CPP), HybridCLR and .NET Framework cannot unload a single assembly at all, so `Remove` does not make one unloadable there.

Call `Remove` only once nothing serializes or deserializes the assembly's types any more; Nino cannot handle them afterwards. A formatter that the unloaded assembly declares for a type of **another** assembly (an `[assembly: NinoFormatter]` for a type in a shared library) stays registered once Nino has used it, so put such formatters in the shared library.
