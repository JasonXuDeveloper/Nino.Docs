Nino runs on .NET Standard 2.0 and later, Unity 2022.3+ (Mono and IL2CPP) and Godot 4, and writes the same bytes on every runtime, CPU and pointer size. This page lists the supported targets and describes the binary format.

## Supported Platforms

| Component | Targets |
| --- | --- |
| `Nino.Core` (runtime) | `netstandard2.0`, `netstandard2.1`, `net8.0`, `net10.0` |
| `Nino.Generator` (generator, analyzer) | Roslyn 4.3 and later; builds for Roslyn 4.3, 4.8 and 4.12 in one package |
| `Nino.Immutable` (immutable collections) | `netstandard2.0`, `net8.0` |
| `Nino.AspNetCore` ([ASP.NET Core](/en/docs/v4/advanced/aspnetcore)) | `net8.0`, `net10.0` |
| `Nino.TypeScript` ([TypeScript Clients](/en/docs/v4/advanced/typescript)) | a build tool for projects of any target framework, run on the SDK's .NET 8 or later runtime; the generated code needs TypeScript 5.7+ and runs in ES2020 environments |
| Generated code | C# 9 or later |
| Unity | 2022.3 and later, Mono and IL2CPP, every player platform |
| Godot | Godot 4 .NET projects (.NET 8 from Godot 4.4, .NET 6 before) |
| Hot update | HybridCLR, with no initialization call |
| Trimming and Native AOT | annotated in the `net8.0` and `net10.0` builds ([details](#trimming-and-native-aot)) |

**Every target writes identical bytes.** `netstandard2.0`, `netstandard2.1`, `net8.0` and `net10.0` each use the best primitives available to them ([SIMD](#simd), `[UnsafeAccessor]` on .NET 8+), and the test suite checks the same golden payloads against each build. Data written by a .NET 10 server can be read by a Unity IL2CPP client on a 32-bit Android phone, and the other way round.

## Binary Format

All multi-byte values are **little-endian** and written unaligned. Positional types carry no schema and no field names: the generated code knows the layout.

| Value | Encoding |
| --- | --- |
| Unmanaged value (`int`, `Guid`, enums, raw structs) | its raw bytes, canonical layout, padding zeroed |
| `bool` | 1 byte |
| `T?` | 1 byte has-value flag, then the value if present |
| Length of an array or collection | `int32`; `-1` means `null` |
| `string` | `int32` header (`-1` = null, `0` = empty): `~length` then one byte per char when every char is at most U+00FF, otherwise the length then the UTF-16 code units |
| `string` with `[NinoUtf8]` | `int32` length in UTF-16 chars (`-1` = null, `0` = empty), then `int32` length in bytes, then the UTF-8 bytes |
| Array or list of unmanaged `T` | length, then one block of elements |
| Other collections | length, then each element |
| Dictionary | length, then key/value pairs |
| `T[,]` and higher ranks | each dimension's length, then elements in row-major order |

A default string picks its form per string. When every char is at most U+00FF (ASCII and Latin-1: English, digits, identifiers, keys, Western European text), it is written in one byte a char after the header `~length` (`-length - 1`): `"Ada"` is `FC FF FF FF` `41 64 61`. Any other text is written as UTF-16 after its length: `"名字"` is `02 00 00 00` `0D 54 57 5B`. Both forms carry the length in chars, so the reader allocates the string at its final length and widens or copies the chars into it in one pass. A `StringBuilder` is always written in the UTF-16 form, which the same reader reads.

A `[NinoUtf8]` string starts with the string's length in UTF-16 chars (`string.Length`): `-1` for `null`, `0` for an empty string, and nothing follows either. A non-empty `[NinoUtf8]` string then carries its length in bytes, followed by exactly that many UTF-8 bytes. An unpaired surrogate is written as U+FFFD, which is one char as well, so the char count always matches the string that is read back.

The reader allocates the string at its final length and transcodes exactly the given bytes into it in one pass; the next value starts right after them. It throws `InvalidOperationException` when:

- the byte count is larger than the bytes left;
- the char count does not match the decoded bytes;
- the bytes are not strict UTF-8 (overlong forms and encoded surrogates included) or end in the middle of a character.

For example, `"é😀"` is 3 chars (U+00E9 and a surrogate pair) and 6 UTF-8 bytes, so it is written as `03 00 00 00` `06 00 00 00` `C3 A9 F0 9F 98 80`; `null` is `FF FF FF FF` and `""` is `00 00 00 00`.

Objects get a header that depends on the **declared** type:

| Declared type | Header |
| --- | --- |
| `struct` | none |
| `sealed class` | 1 byte: `0` = null, `1` = instance |
| non-sealed class, abstract class, interface | `int32` type id: `0` = null, otherwise the runtime type's id |

The type id is the FNV-1a hash of the type's name in runtime form (`Namespace.Outer+Inner`). The same hash code is compiled into the generator and the runtime, so ids cannot diverge.

The body after the header depends on the type's format:

| Format | Body |
| --- | --- |
| positional (default) | the members, those of `[NinoType]` base classes first |
| `NinoFormat.VersionTolerant` | `int32` byte length, then the members of the whole hierarchy, root first: one length per object, whatever the depth |
| `NinoFormat.Keyed` | `int32` byte length, then `int32` key, `int32` length and value for each member |

A `trackReferences` type adds an `int32` reference header (`0` = null, `n > 0` = the n-th object already written, `-1` = a new object, followed by its usual encoding). See [Evolving Your Data](/en/docs/v4/evolving-data) and [Reference Tracking](/en/docs/v4/reference-tracking).

Every length read from a payload is validated against the bytes left before anything is allocated, so malformed or hostile input cannot trigger huge allocations, and truncated data throws instead of reading past the end.

## Portable by Design

Nino defines its bytes instead of copying whatever a runtime has in memory. Runtimes do not always agree on memory layout, so these cases are handled explicitly:

<Accordions type="multiple">
<Accordion title={<><code>Nullable&lt;T&gt;</code></>} value="nullable">

CoreCLR and Unity 2021.3+ store `bool hasValue; T value;`, while old Mono (Unity 2019.4 and earlier) stores the value first. Copying a `T?` as raw memory produces different bytes on each. Nino writes a single `T?` as a has-value byte followed by the value; arrays and lists of `T?` use the canonical layout and are converted element by element where the runtime differs.

</Accordion>
<Accordion title={<><code>ValueTuple</code> and <code>KeyValuePair</code></>} value="tuple">

`ValueTuple` is `LayoutKind.Auto` on .NET, so CoreCLR may reorder its fields, while Mono lays them out sequentially. Nino always writes a tuple or `KeyValuePair` as its items in declaration order, never as its memory. Arrays and lists of tuples and pairs whose items are all raw are still moved as one block: copied as memory where the runtime's layout matches the bytes (checked once at startup), otherwise rearranged with [SIMD shuffles](#simd) where the CPU has them, else item by item. The bytes are the same on every path.

</Accordion>
<Accordion title={<><code>decimal</code>, <code>DateTimeOffset</code>, <code>nint</code></>} value="bcl">

`decimal` is aligned to 8 bytes on CoreCLR and to 4 on Mono and IL2CPP, so a struct holding one can have a different layout; Nino converts it to the canonical layout. `DateTimeOffset` is written as UTC ticks plus the offset in minutes (10 bytes), never raw. `nint`/`nuint` are always 8 bytes.

</Accordion>
<Accordion title="32-bit platforms" value="32bit">

`struct { int a; long b; }` is 16 bytes on x64 and 12 bytes on x86 .NET and Mono. Nino's raw layout is the canonical 64-bit one; where a runtime differs, values are converted field by field into the same bytes (at some cost in speed) and bulk raw copies are skipped.

</Accordion>
<Accordion title="Padding" value="padding">

Code that builds structs in uninitialized memory (`SkipLocalsInit`, `stackalloc`, `GC.AllocateUninitializedArray`) can leave stale bytes in padding. Nino zeroes padding on write, so equal values always serialize to equal bytes and no stale memory leaks into a payload.

</Accordion>
<Accordion title="Big-endian hosts" value="endian">

Not supported. Constructing a `Writer` or `Reader` on a big-endian host throws `PlatformNotSupportedException`, so Nino never writes or reads bytes in the wrong order. Every platform .NET and Unity run on today is little-endian.

</Accordion>
<Accordion title="Collection internals" value="collection-layouts">

Nino reads and writes the fields of `List<T>`, `Stack<T>`, `Queue<T>`, `SortedList<TKey, TValue>`, `SortedSet<T>` and `SortedDictionary<TKey, TValue>` directly, and their layouts differ between runtimes (.NET Framework and Mono add a `_syncRoot` field). Each layout is checked once at startup against instances whose contents are known; a collection whose layout is not recognized goes through its public methods. Either way it writes the same bytes. (On .NET 8 and later, `List<T>` goes through `CollectionsMarshal`.)

</Accordion>
</Accordions>

## SIMD by Platform [#simd]

The net8.0 and net10.0 builds of `Nino.Core` use hardware intrinsics where the CPU has them, and fall back to portable code where it does not. Every path writes the same bytes: the tests run with AVX-512, without it, without AVX2 and with all SIMD turned off, and on Arm64.

| Platform | What Nino uses |
| --- | --- |
| x64 with AVX-512 | 64-byte vector copies for blocks of 64 bytes to 8 KB; byte permutes (AVX-512 VBMI) for tuples and `KeyValuePair`s of raw items, whose memory differs from their bytes: where their memory has padding, two-source permutes write them as whole 64-byte vectors from an aligned destination (16 `(int, long)` in three), of 4-byte words where each is a whole word of memory (AVX-512F, no VBMI needed), otherwise of bytes (VBMI), and read the same way, each 64-byte vector of memory stored at an aligned address; other such items 64 bytes at a time (VBMI); 512-bit masked copies that zero padding |
| x64 with AVX2 | 32-byte vector copies for blocks of 256 bytes to 4 KB (also on AVX-512 CPUs where .NET prefers 256-bit vectors); such tuples and pairs with padding moved a group at a time, written and read: each 16-byte lane of a 32-byte vector shuffled (`vpshufb`) from at most two 16-byte windows of the source, loads shared across a group's vectors and lanes far apart joined by one lane permute (`vperm2i128`), stores on 32-byte boundaries where the values allow; otherwise an SSSE3 16-byte shuffle per value for such tuples and pairs of up to 16 bytes |
| x64 with SSSE3 | such tuples and pairs with padding moved a group of 16-byte vectors at a time, each two shuffles (`pshufb`) ORed; otherwise the 16-byte shuffle per value; `memmove` for blocks |
| Arm64 | AdvSimd: two-register table lookups (`TBL`) that move such tuples and pairs with padding a group of 16-byte vectors at a time, written and read; otherwise the 16-byte shuffle per value (`TBL`), and four 4-register table lookups per 64 bytes for values of up to 8 bytes; strings of 33 to 64 bytes copied as two pairs of 16-byte vectors; `memmove` for blocks |
| WebAssembly with SIMD (.NET 10) | two swizzles per 16-byte vector for such tuples and pairs with padding, written and read a group at a time as on SSSE3; otherwise the 16-byte shuffle per value (`PackedSimd`, `i8x16.swizzle`) |
| Arm32; Unity (Mono, IL2CPP), .NET Framework and .NET Core 3.0 to .NET 7 | no hardware intrinsics: blocks through `memmove`, rearranged values one at a time |

Strings in the [one-byte form](#binary-format) are narrowed when written and widened when read with 16-byte vectors, and 32-byte ones where AVX2 is available, on every CPU that accelerates them, in the net8.0 and net10.0 builds; the netstandard builds convert four chars at a time.

Unity and .NET Framework, as well as .NET Core 3.0 to .NET 7, use the `netstandard2.0`/`netstandard2.1` builds, which contain no intrinsics. On every platform, blocks of up to 32 bytes (most strings) are copied inline on 64-bit runtimes, and padding is masked with 512-bit vectors on AVX-512, otherwise with `Vector<T>` where the runtime accelerates it, else 8 bytes at a time.

## Unity

- Install from [OpenUPM](/en/docs/v4/start#unity-project). The package ships `Nino.Core.dll` and the generator (`Nino.Generator.dll`, labelled `RoslynAnalyzer`), `Nino.UnityTypes.dll` (formatters for [`AnimationCurve`, `Gradient` and `RectOffset`](/en/docs/v4/advanced/unity#unity-classes)), plus `System.Buffers`, `System.Memory` and `System.Runtime.CompilerServices.Unsafe`.
- Unity compiles against .NET Standard: there is no `[UnsafeAccessor]`, so a type with serialized non-public members or `[NinoPooled]` must be `partial` (NINO002, with a code fix).
- The package ships the generator's Roslyn 4.3 build, so calls are not intercepted. They use the regular path and write the same bytes.
- Generated registries carry `[RuntimeInitializeOnLoadMethod]` (and `[InitializeOnLoadMethod]` in the editor), which runs them at startup and keeps them from being stripped by IL2CPP.
- Unity types such as `Vector3`, `Quaternion` and `Matrix4x4` are unmanaged and are written as raw memory.

See [Unity and HybridCLR](/en/docs/v4/advanced/unity) for project setup and IL2CPP tips.

## Godot

- Godot 4 C# projects are regular .NET projects (`Godot.NET.Sdk`, targeting .NET 8 from Godot 4.4 and .NET 6 before). Install with `dotnet add package Nino --prerelease`; see [Godot Project](/en/docs/v4/start#godot-project).
- Built with the .NET 8 SDK or later (required from Godot 4.4), the source generator, the analyzers and the interceptors all run. A project that targets .NET 8 also reaches private members through `[UnsafeAccessor]` without `partial` (except in generic types); on .NET 6 such types must be `partial` (NINO002).
- Godot's math structs (`Vector2`, `Vector3`, `Quaternion`, `Transform3D`, `Color`, ...) are unmanaged and are copied as raw memory.
- In a Godot build with double precision (`real_t` = `double`), these structs hold `double` fields, so their layout differs from the default single-precision build. Data containing Godot math types written by one build cannot be read by the other; use your own structs or primitive fields for data shared between the two.
- Serialize your own data types; Godot objects such as `Node` and `Resource` are engine objects and are not serialized.

## HybridCLR and Hot Update

Generated registries are discovered lazily: the first time Nino meets a type of an assembly, or an unknown type id while reading, it finds that assembly's registry. A hot-update assembly loaded with `Assembly.Load` therefore needs **no initialization call**, and its types (including subtypes of base classes in AOT assemblies) are found on first use.

Generated code avoids forwarding facades on purpose: interpreters such as HybridCLR's and Mono's do not inline, so every extra call layer would cost real time there.

## Trimming and Native AOT [#trimming-and-native-aot]

The `net8.0` and `net10.0` builds of `Nino.Core` are marked `IsTrimmable` and `IsAotCompatible`, and the trim and AOT analyzers check every build, so publishing with `PublishTrimmed` or `PublishAot` gives no warnings from Nino. A project targeting .NET 8 or later gets one of these builds.

- **Native AOT** (and any runtime that cannot compile code): Nino uses only the formatters the generator wrote. Every type you serialize must therefore appear in code the generator sees, as a member type or as the type argument of a `Serialize` or `Deserialize` call. A type that only exists at run time fails with an error that names it, never with wrong data.
- **Trimmed apps on a JIT** keep the run-time path that builds formatters for such types; what it needs from the trimmer is annotated.

The generator writes the same formatters for IL2CPP, which is why Nino needs no reflection there either. See [Unity and HybridCLR](/en/docs/v4/advanced/unity#il2cpp).

## Unloading Assemblies

A server that hot-reloads its logic loads it into a collectible `AssemblyLoadContext` and unloads the old context on each reload. On .NET 8 and later, when the context of an assembly with generated Nino code starts unloading, Nino clears everything it cached for that assembly: its registry, the formatters, type ids and raw memory layouts of its types, its polymorphic subtypes and its `[assembly: NinoFormatter]` registrations. The old context can then be collected, and the new version of the same types loads without type id collisions.

```csharp
var context = new AssemblyLoadContext("logic", isCollectible: true);
var logic = context.LoadFromAssemblyPath(path);
// ... serialize and deserialize the logic's [NinoType]s ...

context.Unload(); // Nino clears what it cached for the assembly here
```

The net8.0 and net10.0 builds of Nino.Core do this, and a project targeting .NET 8 or later gets one of them. A project on .NET Core 3.0 to .NET 7 gets the netstandard2.1 build, which cannot reach `AssemblyLoadContext`: there, call `NinoRegistry.Remove(assembly)` yourself before unloading, and the context is collected just the same.

```csharp
NinoRegistry.Remove(logic); // .NET Core 3.0 to .NET 7
context.Unload();
```

On .NET 8 and later, `Remove` does nothing more than the automatic cleanup; call it only to be sure the cleanup has happened before you unload. Unity (Mono and IL2CPP), HybridCLR and .NET Framework cannot unload a single assembly at all, so `Remove` does not make one unloadable there.

Call `Remove` only once nothing serializes or deserializes the assembly's types any more; Nino cannot handle them afterwards. A formatter that the unloaded assembly declares for a type of **another** assembly (an `[assembly: NinoFormatter]` for a type in a shared library) stays registered once Nino has used it, so put such formatters in the shared library.
