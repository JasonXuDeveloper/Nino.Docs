Nino v4 is a breaking release. This page lists every API, attribute and option that changed, with before/after code, and explains what to do with data written by v3.

<Callout type="warn">

The v4 binary format is **not compatible** with v3 or with the earlier v4 betas/previews. v4 cannot read data written by v3, and v3 cannot read data written by v4. If you have persisted v3 data (save games, caches, config files), read [Converting v3 data](#converting-v3-data) before upgrading.

</Callout>

## Checklist

<Steps>
<Step>

Update the `Nino` NuGet package (or the OpenUPM package in Unity) to v4.

</Step>
<Step>

Replace `Serializer`/`Deserializer` calls with `NinoSerializer`/`NinoDeserializer`, and remove `using <YourAssembly>.NinoGen;`.

</Step>
<Step>

Replace `WEAK_VERSION_TOLERANCE` with `[NinoType(versionTolerant: true)]` on the types that need it (optional, see below).

</Step>
<Step>

Update `[NinoFormerName]` arguments to the runtime type name form.

</Step>
<Step>

Build, and fix what the analyzer reports (`NINO001`–`NINO024`); most diagnostics have a code fix.

</Step>
<Step>

Convert or discard persisted v3 data.

</Step>
</Steps>

## Serialization API

In v3, the generator emitted static `Serializer` and `Deserializer` classes (and extension methods) into each assembly's `<AssemblyName>.NinoGen` namespace. In v4, there is one API in `Nino.Core`, the same for every assembly.

| v3 | v4 |
| --- | --- |
| `using MyGame.NinoGen;` | `using Nino.Core;` |
| `Serializer.Serialize(obj)` / `obj.Serialize()` | `NinoSerializer.Serialize(obj)` |
| `Serializer.Serialize(obj, bufferWriter)` / `obj.Serialize(bufferWriter)` | `NinoSerializer.Serialize(obj, bufferWriter)` |
| `obj.Serialize(ref writer)` | `NinoSerializer.Serialize(obj, ref writer)` |
| `Deserializer.Deserialize(data, out T value)` | `T value = NinoDeserializer.Deserialize<T>(data)` |
| `Deserializer.Deserialize(out T value, ref reader)` | `T value = NinoDeserializer.Deserialize<T>(ref reader)` |
| `Serializer.GetBufferWriter()` / `ReturnBufferWriter(...)` | a reused `NinoArrayBufferWriter` (see [Serialize and Deserialize](/en/docs/v4/basic#reusing-a-buffer)) |
| (none) | `NinoDeserializer.Deserialize(data, ref value)`: deserialize into an existing instance |
| (none) | `NinoSerializer.Serialize(object)`, `NinoDeserializer.Deserialize(data, Type)`: boxed / runtime types |

<Tabs items={["v3", "v4"]}>

<Tab value="v3">

```csharp
using MyGame.NinoGen;

byte[] bytes = obj.Serialize();

Deserializer.Deserialize(bytes, out ObjClass result);
```

</Tab>
<Tab value="v4">

```csharp
using Nino.Core;

byte[] bytes = NinoSerializer.Serialize(obj);

ObjClass result = NinoDeserializer.Deserialize<ObjClass>(bytes);
```

</Tab>
</Tabs>

Buffer reuse:

<Tabs items={["v3", "v4"]}>

<Tab value="v3">

```csharp
var bufferWriter = Serializer.GetBufferWriter();
obj.Serialize(bufferWriter);
Serializer.ReturnBufferWriter(bufferWriter);
```

</Tab>
<Tab value="v4">

```csharp
var buffer = new NinoArrayBufferWriter(); // keep and reuse it (one per thread)
buffer.ResetWrittenCount();
NinoSerializer.Serialize(obj, buffer);
```

</Tab>
</Tabs>

<Callout type="info">

`Span<T>` values could be passed to v3's generated `Serialize`. In v4, `T` is a generic type argument, which cannot be a `ref struct`: serialize an array, a `List<T>` or an `ArraySegment<T>` instead.

</Callout>

## Attributes and Options

| v3 | v4 |
| --- | --- |
| `[NinoType]`, `[NinoType(autoCollect, containNonPublicMembers)]` | unchanged; new optional parameters `allowInheritance`, `versionTolerant`, `keyed`, `trackReferences` |
| every subtype needs its own `[NinoType]` | subtypes **inherit** `[NinoType]` from their base class or interface (unless it sets `allowInheritance: false`) |
| `WEAK_VERSION_TOLERANCE` (whole project) | `[NinoType(versionTolerant: true)]` per type; the symbol still exists and turns it on for every type of the project |
| `[NinoFormerName("global::Old.Namespace.Type")]` (name copied from `NinoTypeConst.g.cs`) | `[NinoFormerName("Old.Namespace.Type")]`: runtime form, no `global::`, `+` for nested types |
| `[NinoMember(index)]`, `[NinoIgnore]`, `[NinoUtf8]`, `[NinoConstructor(...)]`, `[NinoExplicitOrder(...)]` | unchanged; `[NinoConstructor]` can also mark a static factory method |
| `[NinoPrivateProxy]` (emitted by the generator) | removed; private members are reached through `[UnsafeAccessor]` (.NET 8+) or a generated accessor in the `partial` type |
| (none) | `[NinoPooled]`, `[NinoFactory]`, `[NinoCustomFormatter]`, `[assembly: NinoFormatter]` |

### Names from the v4 betas

Code written against an early v4 beta uses names that changed before the release:

| v4 beta | v4 |
| --- | --- |
| `[NinoRefDeserialization]` | `[NinoFactory]` |
| `NinoFactory<T>` | `NinoActivator<T>` |
| `NinoDeserializer.DeserializeRef(ref value, data)` | `NinoDeserializer.Deserialize(data, ref value)` |
| `NinoDeserializer.DeserializeRef(ref value, ref reader)` | `NinoDeserializer.Deserialize(ref value, ref reader)` |
| "ref deserialization" | reuse deserialization |

### Behavior Changes since the v4 Betas [#behavior-changes-since-the-v4-betas]

4.0.0-rc.1 also changed three behaviors that code and data from the betas may depend on:

- **`[NinoUtf8]` strings are prefixed with their length in chars**, like UTF-16 strings, instead of their length in bytes. Data with `[NinoUtf8]` members written by a beta cannot be read; data without them is unaffected by this change. See [Binary Format](/en/docs/v4/platforms#binary-format).
- **`NinoFormatterCache<T>.Register<TFormatter>()` must run before `T` is first used.** The first serialization or deserialization of `T` fixes its formatter; registering one afterwards throws an `InvalidOperationException` instead of taking effect for some calls only. Move such calls to startup. See [Registering at Run Time](/en/docs/v4/custom-formatters#registering-at-run-time).
- **`Reader.Position` of a reader returned by `ReadSlice()` is an offset in the whole input**, not from the start of the slice. A custom formatter that compared it with the slice's length should record the position when the slice starts and subtract it. See [Positions in a Slice](/en/docs/v4/custom-formatters#positions-in-a-slice).

### Version tolerance

<Tabs items={["v3", "v4"]}>

<Tab value="v3">

```csharp
// v3: #define WEAK_VERSION_TOLERANCE in the project settings
[NinoType]
public class SaveData
{
    public int Id;
    public string Name;
    public bool Extra; // appended later
}
```

</Tab>
<Tab value="v4">

```csharp
[NinoType(versionTolerant: true)]
public class SaveData
{
    public int Id;
    public string Name;
    public bool Extra; // appended later
}
```

</Tab>
</Tabs>

v4's version tolerance is more capable than v3's: members can be appended to the type **or any of its base classes**, at any nesting depth. For reordering, removing or inserting members, use `[NinoType(keyed: true)]`. See [Version Tolerance](/en/docs/v4/evolving-data#version-tolerance) and [Keyed Members](/en/docs/v4/evolving-data#keyed-members).

<Callout type="warn">

In v3, `WEAK_VERSION_TOLERANCE` also allowed changing a member to an unmanaged type of the same size (`int` → `float`). Do not rely on that in v4: changing a member's type is not a tolerated change.

</Callout>

### Former names

<Tabs items={["v3", "v4"]}>

<Tab value="v3">

```csharp
[NinoType]
[NinoFormerName("global::MyGame.Items.Sword")]
public class Weapon { ... }
```

</Tab>
<Tab value="v4">

```csharp
[NinoType]
[NinoFormerName("MyGame.Items.Sword")]
public class Weapon { ... }
```

</Tab>
</Tabs>

Former names only matter for data written by v4 itself (v3 data cannot be read anyway), so you only need them for types renamed after you adopted v4.

### Polymorphism

<Tabs items={["v3", "v4"]}>

<Tab value="v3">

```csharp
[NinoType]
public abstract class Shape { public int Id; }

[NinoType] // no longer required: inherited from Shape
public class Circle : Shape { public float Radius; }
```

</Tab>
<Tab value="v4">

```csharp
[NinoType]
public abstract class Shape { public int Id; }

public class Circle : Shape { public float Radius; }
```

</Tab>
</Tabs>

Keeping `[NinoType]` on a subtype is harmless and lets it set its own options. Its options replace the inherited ones, so repeat any you want to keep, such as `versionTolerant: true`; only `trackReferences` stays on for every subtype of a tracked type.

## Generated Code
- Generated formatters live in the `<AssemblyName>.NinoGen` namespace but are not meant to be called directly. Remove any code that referenced the v3 generated classes (`Serializer`, `Deserializer`, `NinoTypeConst`, ...).
- There is one generated file per `[NinoType]`, and editing one type re-generates only that type.
- Problems that v3 reported as compile errors in generated code are now analyzer diagnostics on your code. A member whose type cannot be serialized is a warning (NINO007) and is skipped, instead of a compile error. See the [diagnostics list](https://github.com/JasonXuDeveloper/Nino/blob/main/docs/diagnostics.md).

## Unity
- Unity 2022.3 or later is still required.
- The OpenUPM package ships the source generator. You no longer need to install the `Microsoft.CodeAnalysis` NuGet packages into your Unity project manually; remove them if you only added them for Nino.
- Calls are not intercepted in Unity: the package ships the generator's Roslyn 4.3 build, and interceptors need Roslyn 4.8. Calls use the regular path and write the same bytes.
- `asmdef` files still need to reference `Nino.Core.dll` when `Override References` is used.

## HybridCLR
- Hot-update assemblies need **no initialization call**: Nino finds the generated registry of an assembly the first time one of its types is used, even when the assembly is loaded with `Assembly.Load`.
- v4's documentation and tests cover HybridCLR; ILRuntime is no longer listed as supported.

## Converting v3 Data
v4 cannot read v3 data, and the two versions cannot both be referenced by one project (both use the `Nino.Core` assembly and namespace). To keep persisted data:

<Steps>
<Step>

Build a small **converter** that still references Nino v3 and your v3 types. It reads the old data with v3's `Deserializer` and exports it in a neutral form (for example JSON), or hands the objects to a second assembly that references v4 (for example by loading it in a separate `AssemblyLoadContext`).

</Step>
<Step>

In the v4 application, import the neutral data and write it with `NinoSerializer`.

</Step>
<Step>

If you cannot convert offline (for example save games on players' devices), ship the converter logic with the game and mark new data with a **header** (a magic number or version byte). Data with the header is read with v4; data without it is converted once and saved again with v4.

</Step>
</Steps>

See also [Versioning](/en/docs/v4/versioning#reading-data-from-an-older-version).

<Callout type="idea">

Data that lives only in memory or on the wire between processes you deploy together (network messages, caches) does not need converting: deploy all ends with v4 at once.

</Callout>
