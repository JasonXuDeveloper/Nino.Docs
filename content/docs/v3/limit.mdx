What Nino v3 does not do, and the limitations of earlier releases that v3 removed.

## Current Limitations [#current-limitations]
- **Source generator required.** Nino has to be used with its source generator.
- **`WEAK_VERSION_TOLERANCE` is all or nothing.** A project that defines `WEAK_VERSION_TOLERANCE` cannot deserialize data serialized by a project that does not define it, and vice versa.
- **Unsupported types fail the build.** Serializing a type that is not supported (such as `Queue<T>`) causes a compilation error.
- **`ValueTuple` differs between .NET Core and Unity/Mono.** See below.

<Callout type="info" title="Why ValueTuple is not portable">

This is not Nino's fault. [Mono's implementation of `ValueTuple`](https://github.com/mono/mono/blob/0f53e9e151d92944cacab3e24ac359410c606df6/mcs/class/corlib/Mono/RuntimeStructs.cs#L83) does not specify a struct layout for value tuples, so Nino serializes and deserializes their fields in sequence. Unity uses Mono in the editor, and in players when IL2CPP is not selected. IL2CPP is believed to behave like Mono.

[.NET Core's implementation](https://github.com/dotnet/runtime/blob/37e4d45236e68946db9d264593aa31a9c00534bc/src/libraries/System.Private.CoreLib/src/System/ValueTuple.cs#L425) lays value tuples out with `LayoutKind.Auto`, which can produce a different layout from Mono's. So `ValueTuple` data is not compatible between .NET Core and Unity/Mono.

</Callout>

## Resolved Limitations [#resolved-limitations]

<Accordions type="multiple">
<Accordion value="former-name" title="Cannot rename a type or its namespace after serialization">

Resolved in v3.2.2: a renamed type can still deserialize data serialized under its old name or namespace. See [Former Name](/en/docs/v3/advanced#former-name).

</Accordion>
<Accordion value="collections" title="No version tolerance for collections">

Resolved in v3.2.0: you can change a type's members and still deserialize data serialized before the change, even inside a collection (list, dictionary, and so on) with polymorphic elements.

</Accordion>
<Accordion value="non-public" title="Cannot serialize or deserialize non-public fields and properties">

Resolved in v3.0.6, with some caveats:
- Before .NET 8.0, a type that contains private members must be `partial`, for example `partial class MyClass`.
- Before .NET 8.0, a serializable nested type cannot declare private members.
- On .NET 8.0 and later, **there are no restrictions**.

See [Choosing Members](/en/docs/v3/types#choosing-members).

</Accordion>
<Accordion value="unmanaged-polymorphism" title="Polymorphic unmanaged structs serialize differently with and without a cast to their interface">

Resolved in v3.0.3: every polymorphic unmanaged struct is serialized and deserialized the same way, whether or not it is cast to its interface.

</Accordion>
<Accordion value="big-endian" title="Big-endian platforms">

Nino assumes a little-endian platform (the C# default), so data may deserialize incorrectly on a big-endian one. To target a big-endian platform, add the define symbol `BIG_ENDIAN` to the `Nino.Core` project, compile it yourself and use the compiled DLL.

In practice every platform that runs .NET (Unity included) is little-endian, so you do not need to worry about this. Add `BIG_ENDIAN` only if you actually hit an endianness problem.

</Accordion>
</Accordions>
